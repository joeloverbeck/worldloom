# Writing the Updated Spec (Step 7)

After all findings are resolved and approved:

## Pre-Apply Verification

Run targeted checks to confirm each finding still holds (grep confirming symbol presence/absence, count validation, path-exists, file-read of the target line). Emit the verification table in chat before any Write/Edit call — a vague "I checked the findings" is not sufficient.

**Row-shape taxonomy**: five row shapes are valid in the pre-apply table, each with its own trigger:

- **Command-backed row** (default): `Finding | <grep / test / file-read command> | <result>`. Use whenever any symbol named in the finding can be grepped, any path can be `test -f`'d, or any line can be read.
- **Judgment-only row**: `Finding | Judgment — <restated rationale> | <result>`. Use for findings whose recommendation is purely analytical (arithmetic re-derivation, judgment-based refinement, no codebase symbol being referenced) OR when the user delegates resolution to the reassessor's reasoning ("you decide based on FOUNDATIONS"); in the latter case, append `; Q<N> delegated` to the rationale so the delegation is auditable. Use sparingly — prefer command-backed whenever a symbol is greppable. A bare `Judgment` without the restated rationale is treated as a skipped check, parallel to how a bare acknowledgment is treated as a skipped reference load.
- **User-answered row**: `Finding | User answer Q<N> = (<option>): <one-line paraphrase of the chosen option> | Apply as: <concise edit description>`. Use when the user explicitly answers a Step 6 Question with an option label. The Question + answer IS the check; do NOT prefix with `Judgment —` (the Judgment shape is reserved for analytical rationale or delegated resolution, not for user-selected options). See the SKILL.md pre-apply-table example (I4 row) for the canonical form. **Terse user replies**: when the user replies tersely (e.g., `go with (a)`, `recommended (a)`, `1) a 2) b`), expand the response into the canonical form by paraphrasing the option text from the Step 6 presentation — the audit trail in the table records what the option meant, not the user's verbatim wording. **No-op (confirms-existing-text) case**: when the answer validates content the spec already contains rather than directing a change (e.g., a question whose chosen option matches what the spec already specifies), the Result column reads `no edit — confirms existing §<section>` instead of `Apply as: <edit>`; the row still documents that the question was resolved and why no edit followed.
- **Hybrid user-answered + proactive-verification row**: when a user-answered option's phrasing names a codebase claim (file path, type existence, function signature, line number), spot-verify the claim via a command-backed check even when the user's approval was unconditional. Record the verification outcome in the Result column alongside the "Apply as: ..." notation (format: `<verification outcome>. Apply as: <edit description>`). This is a proactive instance of §Conditional approval (see `references/findings-and-questions.md`) — the premise verification is auditor-initiated rather than user-imposed, but the row shape is the same. Do NOT split into two rows; the row's Check column remains the user-answered form, and the hybrid is a refinement of the user-answered shape, not a fourth peer.
- **Subsumed-by-other-finding row**: `Finding | Subsumed by <other-finding-key>: <one-line reason naming why the absorbing finding's rewrite makes this finding's recommendation moot> | Apply as: <description of the absorbing finding's edit that handles this finding's recommendation>`. Use when one approved Step 6 finding's recommendation is naturally absorbed into another approved finding's rewrite at pre-apply-table build time — the absorbing finding's rewrite scope reshapes or eliminates the absorbed finding's target text, so the absorbed finding requires no independent edit. Distinct from the §Late-discovered findings absorption rule below (which covers findings *discovered late* during edit application or planning, absorbed into an existing finding's row): here both findings were approved at Step 6 and the subsumption is a property of the approved rewrite's scope rather than a discovery during writing. The subsumed row preserves audit-trail visibility (the approved finding still appears in the table) without duplicating the edit work; the absorbing finding's row carries the actual edit description. Common shapes the subsumed-by row covers: (a) `Subsumed by Q<N>=(<option>): <reason>` when a Step 6 Question's chosen option dictates a rewrite that mooted a separately-keyed finding (e.g., M6's source-report citation mooted when Q2=(a) removes the section the citation would have lived in); (b) `Subsumed by I<N>: <reason>` when one Issue's rewrite reshapes the target section enough that another Issue's narrower recommendation becomes redundant (e.g., I3's inventory-step expansion mooted when I2's branch_path rewrite collapses §4.1 entirely). The User-answered row shape (or other peer shape) covers the absorbing row; this row shape covers the absorbed one.

**Multi-section pre-edit grep**: when a finding's Result column names multiple sections of the spec to edit (e.g., `Approach + Deliverables`, `Approach + Verification`, `Deliverables + Risks`), run an exact-string grep for the changed terminology across the entire spec before opening the first Edit call AND before drafting the Result column for the affected row, and record the grep's **actual** count + line numbers in the Result column (e.g., `3 instances at lines L1, L2, L3 — apply at all`). Do NOT draft estimated values for the count or line numbers ahead of the grep; the grep IS the authoritative source. If a pre-grep estimate appeared in a draft row, replace it with the actuals before emitting the pre-apply table; if the grep ran after the table was first emitted and the actuals differ from any estimate, re-emit the affected row with the corrected count + line numbers so the audit trail records actual values, not estimates. Cross-section restatements drift silently because the deliverable's number is unchanged — only its content shifts; the verification table verifies the finding still holds, but it does not by itself verify the edits will be complete. This is the pre-edit instantiation of §Apply Changes' "When materially modifying a deliverable's mechanism, name, or surface area" rule — moved into the pre-apply phase so the count is in hand when edits begin, and the post-apply confirmation grep at Step 8 has a target row count to verify against. Inline-per-finding Result-column entries are sufficient on their own — do not duplicate the count + line numbers as prose outside the table.

**Cross-spec extension**: when the user-directed-authorization carve-out (`SKILL.md` §Guardrails §No scope creep) extends an edit to a sibling spec or to `specs/IMPLEMENTATION-ORDER.md` (typical case: the same stale claim restated in both the primary spec and the implementation-order row), the multi-section pre-edit grep also covers the authorized cross-spec target. Run the grep across all authorized files in one batch, and record cross-spec counts + line numbers either inline in the affected finding's Result column (when ≤2 files are involved and the result is short) or as a separate trailing summary row per the §Cross-finding pre-edit grep shape (b) below (when ≥3 file targets are involved). The cross-spec grep is bounded by the user's explicit authorization — only files the user authorized are in scope; speculative cross-spec greps remain forbidden per the §No scope creep guardrail. Worked precedent: SPEC-77 reassessment (2026-05-23) — Q1(a) authorized `specs/IMPLEMENTATION-ORDER.md` row 2 to mirror SPEC-77's I2 fold-claim removal; pre-edit grep ran across both files in one batch (`grep -in "fold\\|may be folded\\|Slice B implementation" specs/SPEC-77-...md specs/IMPLEMENTATION-ORDER.md`), surfacing 3 SPEC-77 sites + 1 IMPLEMENTATION-ORDER row before the first Edit call.

**Syntax-variant + `replace_all` discipline**: when the changed terminology is a token that may appear with different surrounding syntax at different sites (parens vs no parens, commas vs prose, capitalization variants, list-item markers, trailing punctuation), grep for the BARE token plus `-i` for case-insensitive — not the surrounding context — to catch all sites. `replace_all: true` is a syntactic-exact match: it catches every occurrence of the literal `old_string` but cannot catch sibling sites that use different surrounding syntax. The pre-edit grep is therefore still required when relying on `replace_all`, to confirm all sites use the same byte-exact `old_string` (or to enumerate the syntax variants that need separate Edit calls). Parallel to `skill-audit/references/cascade-and-summary-discipline.md` §Cascade-scan discipline §"search for semantic variants, not just exact strings" — both rules treat syntax-variant grep as cheaper-than-recovery prevention; this rule covers pre-apply phase in reassess-spec, the sibling covers cascade-scan phase in skill-audit. Worked precedent: SPEC-78 reassessment (2026-05-23) — Finding I1 targeted `SPEC-48 STEMO` at §5 row-4 (no inner parens) AND `SPEC-48 (STEMO)` at §10 References (with inner parens) for the same logical token rename. `replace_all: true` on the §10 variant's `old_string` caught only that site; the §5 row-4 variant was missed. Post-apply confirmation grep (Step 8) caught the residue and forced one follow-up Edit. A pre-edit `grep -in "STEMO"` would have surfaced both sites + their syntax variants at planning time, eliminating the recovery cycle. Second worked precedent: SPEC-84 reassessment (2026-05-25) — Issue I2 eliminated the framing tokens `global_slt_branch_local_dependency` and `branch-local` (as applied to STPLAN-99) across the spec. Audit-time site enumeration in I2's Suggestion named 3 sites (§2 case 2, §4.1 SLT-3, §4.2 prose); pre-edit Multi-section grep for the specific phrasings the finding expected to remove (`branch-local to BR-2`, `global_slt_branch_local_dependency`) caught those 3 sites but missed 2 additional sites at §6 ac 3 + §7 FOUNDATIONS row that used the compound variant `branch-local-ref`. Post-apply confirmation grep (Step 8) caught the residue as late-discovered finding LD-1 and forced one follow-up Edit. A pre-finalization `grep -in "branch-local"` (bare token, case-insensitive) would have surfaced all 5 sites at audit-time site enumeration per §Pre-finalization site-counting (`references/findings-and-questions.md` §Step 5), eliminating the recovery cycle.

The §Cross-finding pre-edit grep trailing summary row form (option (b) below) is the only canonical placement for grep-summary content outside individual Result columns; reserve it for the cross-finding case.

**Cross-finding pre-edit grep** (when N findings share the same cross-cutting grep): when ≥2 findings collectively touch overlapping spec sections (typical of reassessments with several interlocking findings affecting the same Approach + Deliverables + Verification + Risks + Outcome restatements), the multi-section pre-edit grep may be reported in either of two shapes:

- (a) **Inline per-finding**: restate the same grep result in each affected finding's Result column. Cleaner when only 2 findings overlap and the grep result is short.
- (b) **Trailing summary row**: a single row at the table foot covering the cross-cutting grep, labeled `Multi-section pre-edit grep` (literal label; no `I/M/A` finding-key letter), summarizing the count + line numbers and naming which findings the grep covers (e.g., `7 instances at lines L1, L2, L3, L4, L5, L6, L7 — covers I1, I2, M1, A1; per-finding application listed in respective Result columns above`). Cleaner for ≥3 affected findings, OR for 2 findings with a long grep result (~5+ instances) where inline restatement of the same N-line aggregate Result-column footprint would clutter the table.

Choose (a) for 2 overlapping findings with a short grep result (~≤4 instances); choose (b) for 3+ findings OR for 2 findings with a long grep result (~5+ instances) where inline restatement would clutter the table. The numeric thresholds are recommendations, not hard cuts — the underlying signal is whether inline restatement of the same N-line aggregate Result-column footprint clutters the table. The trailing summary row is procedural — it is not a finding row and does not consume an `I/M/A` key. Document which shape was used so a future reader can reconcile the verification table against the post-apply confirmation grep at Step 8.

Classify any mismatch between check and finding into one of three tiers:

- **Recommendation-changing mismatch**: the check invalidates the finding's *recommendation* — the approved fix no longer applies, the target text/symbol has moved, or a different fix is now warranted. Re-present the corrected finding to the user and wait for confirmation before applying any edit **for that finding**. Do not silently substitute different changes. If the correction is a pure retraction (no substitute fix is warranted — the finding itself is withdrawn), note the retraction transparently as `retracted: <reason>` in the table and proceed with the remaining approved findings; fresh re-approval is only required when a different fix is being substituted in place of the retracted one.
- **Evidence-refining mismatch**: the check refines the finding's *supporting evidence* but leaves the recommendation unchanged (e.g., a symbol the finding claimed was absent turns out to exist at a different location, and the recommendation already targets the actual location used by the consumer). Note the refinement inline in the Result column of the pre-apply table and proceed.
- **Scope-extending mismatch**: the approved recommendation still applies, but fulfilling it requires a new deliverable, migration, or package-boundary change not discussed at question time. Note the scope extension inline in the Result column and proceed. Additionally, surface the scope extension in the Step 8 summary under a dedicated line so the user sees it in both places. **Pre-declared variant**: when a Step 6 Question's option description explicitly named the scope-extending consequence (e.g., "requires follow-up edit to SPEC-X" or "extends SPEC-Y's public contract"), the user's approval of that option carries scope acknowledgement — the consequence was disclosed, not discovered. The Step 7 verification row should cite the question explicitly (e.g., `scope-extending: pre-declared in Q2`) rather than framing the extension as freshly discovered; the Step 8 dedicated line still lists the extension so the audit trail records both the pre-declaration and the confirmation. The pre-declared variant does not trigger fresh re-approval — it is a confirmation path, not a mismatch that changes the approved recommendation. If the scope extension constitutes a cross-package type migration, also apply the Pre-Process "Emergent migration at Step 7" guidance and run 3.6 cross-package consumer analysis before finalizing edits.

When in doubt, treat the mismatch as recommendation-changing and re-present — it is cheaper to ask than to apply the wrong fix.

## Apply Changes

- Incorporate corrections from the user's plan approval or question responses.
- Preserve existing structure and voice. Change only what was agreed upon.
- Prefer Edit for ≤3 localized changes; prefer full Write when insertions cause **cascading renumbering** or the change is a **diffuse rewrite** of contiguous prose. The decision keys on the *shape* of the change, not the count of sections touched: many independent surgical edits across many sections (no renumbering, each a self-contained string replacement) are well-served by targeted Edits even when they span >50% of the spec's sections — a full Write is acceptable there but not preferred. Worked precedent: SPEC-93 reassessment (2026-05-28) — 16 surgical Edits across §1–§9 with no renumbering applied cleanly as targeted Edits; the spanning-many-sections fact alone did not warrant a full Write.
- If inserting new deliverables, renumber all subsequent deliverables and update any intra-spec cross-references to deliverable numbers.
- When removing deliverables, grep the spec for all references to the removed deliverable number (e.g., "D4") and update or remove them. Check: Approach, Verification steps, FOUNDATIONS Alignment table, Out of Scope, Risks & Open Questions, and any cross-deliverable references.
- **External-spec references are not intra-spec cross-references**: when renumbering deliverables (insert) or grepping for deliverable-number references (remove), exclude citations to OTHER specs' phases/deliverables (e.g., `SPEC-56 Phase 6`, `SPEC-04 §C`) — these are external citations that must be preserved verbatim, not renumbered. A bare `Phase N` / `D N` grep over-matches them; anchor the renumber scan to the spec's own deliverable headers (`## Phase N`, `### Deliverable N`) or qualify the grep to exclude sibling-spec `SPEC-NN` prefixes. Distinguishing the spec's own deliverable numbers from external-spec phase/deliverable citations is the load-bearing judgment when an insertion cascades a renumber.
- When materially modifying a deliverable's mechanism, name, or surface area (without changing its number), grep the spec for the deliverable's old key concepts (function names, type names, CLI command names that the modification eliminates) AND scan these sections for restatements that need updating: Problem Statement, Approach, Dependencies, FOUNDATIONS Alignment, Verification, Risks. Cross-section restatements drift silently because the deliverable's number is unchanged — only its content shifted.
- **For material mechanism redirects** (one approach rejected in favor of another during reassessment — distinct from the wording-only mechanism modification above), consider adding a brief "Why X and not Y" rationale paragraph to the affected §Design / §Approach section, explaining the schema / semantic / FOUNDATIONS reason the rejected approach was insufficient. This authors the Rule 6 audit trail at the spec level — the rejected approach remains greppable with its rejection rationale attached, so future readers don't re-propose it without context. The §Post-Apply Confirmation §Audit-trail retention exception then recognizes these paragraphs as acceptable retention sites for eliminated terminology rather than as unfinished eliminations. Worked precedent: SPEC-83 reassessment (2026-05-25) — Issue I1 redirected the cooldown-filter selection-page key from `SE.parent_page_id` to `SE.created_at_page`; the Step 7 edit added a "Why `created_at_page` and not `parent_page_id`" rationale paragraph to §4.1 explaining the cross-branch leak the rejected key would have admitted under fork scenarios; post-apply grep at Step 8 found 2 retained `parent_page_id` mentions both inside that rationale paragraph and the §7 Rule 4 mechanism row — both cited as audit-trail retentions per §Audit-trail retention exception rather than as unfinished eliminations.
- **Risks & Open Questions resolution**: if a finding (typically an Improvement or Addition) resolves an entry in the spec's §Risks & Open Questions section (or whatever open-questions surface the spec uses), update or remove that entry alongside the primary edit. Either delete the entry outright or rewrite it as resolved with a one-line note pointing at the resolving deliverable. A spec with a "still open" risk that the reassessment actually closed produces a misleading audit trail — Rule 6 (No Silent Retcons) at the spec level: closing an open question is a change, and the change should be visible in the §Risks section, not implicit in the deliverable edits.
- **New deliverable vs. amendment**: When a finding introduces substantial new logic (new mechanism, new type, new event surface), consider a new numbered deliverable rather than expanding an existing one. Criteria: (a) distinct implementation site (new file, new module, new package), (b) independently implementable and testable, (c) would make existing deliverable unwieldy if inlined.
- **Cross-category deliverable additions**: when a finding adds a deliverable that doesn't fit the spec's existing section categories (e.g., a documentation edit when the spec only has Schema / Validator / Skill / Fixture sections, an MCP-tool edit when the spec only has Skill sections, a CLI-flag edit when the spec only has Schema sections), either (a) re-title the encompassing section to widen its scope (e.g., "Skill Changes" → "Skill and Doc Changes"), or (b) add the new sub-section under the closest-fit existing section with a one-line inline note naming the category mismatch (e.g., *"(Not a skill — included here under §5 for atomic-landing convenience; this is a documentation edit.)"*). Option (a) is preferred when ≥2 of the deliverables in the section share the new category (the rename amortizes across multiple sub-sections); option (b) is preferred for one-off additions to keep the spec's diff small. Worked precedent: SPEC-79 reassessment (2026-05-24) — Issue I7 added an edit to `docs/MACHINE-FACING-LAYER.md` to a spec whose §5 was titled "Skill Changes"; the operator chose option (b), adding §5.6 with the inline note *"(Not a skill — included here under §5 for atomic-landing convenience; this is a documentation edit.)"* to bridge the category mismatch without renaming the section header.
- **Spec-vs-implementation boundary**: when a finding adds a Deliverables-table row for a file outside the target spec's primary scope (e.g., template files in sibling skills, schema files referenced by the spec), the row is a spec-level commitment to the future implementer — the actual file edit happens at ticket-decomposition / ticket-implementation time, NOT during reassess-spec. The reassess-spec skill never edits files outside the primary spec target except when explicitly authorized by user direction (per the user-directed-authorization carve-out in `SKILL.md` §Guardrails §No scope creep). Without such authorization, the file edit lands in tickets, not in this reassessment. Worked precedent: a reassess-spec session adding a `storylet-pool-authoring/templates/storylet-record.yaml` row to a SPEC-20 Deliverables table — the row commits the future implementer to the template comment edit; reassess-spec itself does not run the Edit on the template file.
- **Late-discovered findings**: If writing reveals minor factual errors not covered by the plan (incorrect symbol names in prose, typos in cross-references, outdated package-version constraints), fix them and note in Step 8 as "Also fixed:" items. If the new finding would constitute a HIGH or CRITICAL Issue, re-present to the user before applying. **Canonical location by discovery phase**: if the late finding is discovered during edit **planning** (before any Write/Edit call — e.g., surfaced while building the Step 7 pre-apply verification table), add it to the pre-apply table keyed `LD-N` (late-discovered, 1-based within this reassessment), then reference that key from Step 8's "Also fixed:" rather than duplicating the content. If discovered during edit **application** or **post-apply verification**, Step 8 "Also fixed:" alone is sufficient — no pre-apply row is required for a finding that surfaced after the pre-apply table was emitted. **Absorption into an approved finding**: when a late finding discovered during edit planning naturally fits within an existing approved finding's recommendation (same edit target, same semantic change, same severity tier), absorb it into that finding's Pre-Apply Verification row(s) and note the absorption inline in the Result column (e.g., `Apply as: <original edit description>; also addresses late-discovered <N-word description>`) rather than keying a new `LD-N` row. Reserve `LD-N` keying for late findings that open an edit target NOT covered by any approved finding. The absorption form preserves audit-trail visibility (the absorbed content still surfaces in the verification table via the Result column annotation) while avoiding spurious row proliferation when a late finding is a natural extension of approved work. When in doubt — especially when the absorption would silently change the severity profile of the hosting finding — prefer explicit `LD-N` keying.
- If the user requests corrections after reviewing, apply them and re-present affected sections.

## Retroactive Branch (classification (d))

If Step 3 validation concluded all deliverables already landed, Step 7's output shape is **not** deliverable refinement. Instead:

1. Flip the spec's **Status** to `✅ COMPLETED`.
2. Populate the **Outcome** section with:
   - Completion date (absolute, not relative).
   - Landed changes (cite file paths + line numbers).
   - Delivering commit(s) or sibling spec(s) — git log or `specs/IMPLEMENTATION-ORDER.md` provides these.
   - Deviations from original plan (especially work absorbed by downstream work).
   - Verification commands **re-run at reassessment time**, with their pass/fail status. Do not copy verification from memory — rerun each command now to catch post-delivery regressions.
3. Mark historical **Motivating Evidence** / **Problem Statement** as such — add a short parenthetical noting the drift described was resolved by the landed implementation, so a future reader doesn't treat a stale condition as a live one.
4. Cross-reference any downstream specs or skills that extended or absorbed original-spec scope.
5. Do **not** apply structural refinements to deliverables that already shipped — the spec file is now a historical record, and editing deliverable sections to match current code would confuse the causal narrative.

After Step 7 completes for (d), Step 8 drives archival + `specs/IMPLEMENTATION-ORDER.md` reconciliation rather than suggesting ticket decomposition (see main SKILL.md Step 8 retroactive path).

## Post-Apply Confirmation

Grep the updated spec for:

1. Eliminated stale references — should return zero matches. (For phrase-elimination checks, use literal-string `grep` without `-E`; when regex anchoring is necessary, prefer `[^.;]*` over `.*` to avoid greedy cross-sentence matches that produce false positives by spanning the corrected line.)
2. Corrected references — should return expected matches.
3. File path references in newly added deliverables — should resolve to existing files.
4. If the spec carries re-runnable commands — a §Verification section's commands, OR an embedded completeness-sweep / gate command (e.g., a §5-style `grep` sweep) that a finding edited during this reassessment — ensure the command text resolves (e.g., `world-index build animalia` must reference a CLI entry that exists at `tools/world-index/src/cli.ts`); for an edited gate-command, additionally re-run it to confirm sane output (paralleling the audit-time embedded-gate coverage check at `references/codebase-validation.md` §3.6). This applies with equal force when a finding ADDED or edited the Verification section during this reassessment: run the resolve-check on the newly-authored commands, not only on pre-existing ones. A freshly-written command (e.g., a `world-validate` invocation added by an Addition) is the easiest to ship unverified, because the operator mentally files post-apply confirmation under "verify eliminations + corrected references" (checks 1-3) and overlooks newly-authored command text.

**Audit-trail retention exception**: when an eliminated reference appears in a deliberate "this was removed" rejection paragraph (Rule 6 audit-trail at the spec level — naming what was removed and why preserves the attribution chain per Default Reality), check 1's grep will show N≥1 for the eliminated term. Inspect each match's surrounding context: matches inside an explanatory rejection paragraph are acceptable retentions; matches inside an active config block, instruction, normative statement, or other operational surface indicate incomplete elimination. Cite the audit-trail-retention site explicitly in Step 8's summary so a future reader can distinguish acceptable retention from unfinished elimination — e.g., *"The 3 remaining occurrences of `<eliminated_term>` are all on line N in the deliberate '<rejection-paragraph-name>' rejection paragraph (audit-trail explanation, not active references); confirmed by inspection."*

For classification (d) retroactive, additionally:

5. Grep every concrete artifact named in the spec's Motivating Evidence / Problem Statement (symbols, file paths, thresholds, type names) and prove its absence or corrected form in the current codebase.

Record results for Step 8.
