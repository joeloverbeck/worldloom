# Findings Classification and Presentation (Steps 5-6)

## Step 5: Classify Findings

Organize findings from Steps 3 and 4 into:

- **Issues**: Factually wrong, stale, violates FOUNDATIONS, or proposes redundant deliverables when existing infrastructure suffices. Blocks ticket decomposition.
- **Improvements**: Not wrong, but a refinement would make implementation cleaner, safer, or more aligned.
- **Additions**: Beneficial features not in the spec that align with its goals. Apply YAGNI — only natural extensions of the spec's scope.

For each finding, record:

- What the spec says (or omits)
- What the codebase actually has (with file paths and line references)
- The recommended change

Tag severity: CRITICAL (blocks tickets), HIGH (fix before tickets), MEDIUM (improves quality), LOW (nice to fix).

**Severity-bump re-keying**: Severity-bumps that cross the must-fix threshold (HIGH and CRITICAL entail must-fix) cause re-keying from M-prefix (Improvement) to I-prefix (Issue) — a HIGH-severity finding belongs under "Issues (must fix)", not under "Improvements (should fix)", regardless of whether the initial classification placed it in Improvements. Severity-bumps within Improvement scope (LOW → MEDIUM) keep the M-prefix. Severity-drops follow the same rule in reverse: a finding initially keyed I-prefix that drops below HIGH severity moves to M-prefix. Re-key during draft, not during the user-facing presentation, so the final keys presented at Step 6 are stable and the user never sees a finding's key change between rounds.

**Pre-finalization site-counting for stale-claim corrections and finding-introduced token renames**: For findings classified as Issues or Improvements that either (i) correct a stale factual claim, OR (ii) **rename or eliminate an op-name, type-name, CLI-command-name, or mechanism token that the finding itself introduces or revises** (e.g., a finding that renames a proposed patch op `create_x_profile` → `append_story_x_record` — the old token is not *stale* in the drift-from-codebase sense, it is the spec's own design choice being revised, so case (i)'s "stale factual claim" framing does not obviously cover it), where the claim or token is restated across multiple spec sections (counts, version numbers, schema field-set counts, dependency-graph claims, named-entity references, threshold values, line-number / section citations, op / type / mechanism names the reassessment revises, or any other token being *corrected or renamed* that may recur across sections — including informational line/section references that §3.3 treats as non-authoritative, since a citation corrected in one section but not its restatements leaves the spec internally contradictory, which is worse than uniform drift), grep the spec for ALL restatements of the stale claim or renamed token BEFORE finalizing the finding's Suggestion. Each restatement site should appear in the Suggestion's Recommendation field as a parallel-instantiation enumeration (e.g., `apply at §Key Design Decisions item 6 + §Approach §B preamble + §R-7 risk narrative`). Audit-time site enumeration prevents the late-discovery cycle the Step 7 §Multi-section pre-edit grep rule (per `references/spec-writing-rules.md`) and the Step 8 post-apply confirmation grep cover as recovery — both backstops surface stale-claim or renamed-token restatements but only after the finding has been emitted to the user and the pre-apply table has been built around an incomplete site list. Parallel to skill-audit's §Site-counting for parallel-instantiation Suggestions at `.claude/skills/skill-audit/references/audit-execution-discipline.md` — both rules treat audit-time site enumeration as cheaper-than-recovery prevention; the trigger here is "stale-claim correction OR finding-introduced op/type/mechanism rename restated across sections" rather than skill-audit's "Suggestion-field phrasing implying parallel instantiation", but the same audit-trail-defect failure mode and same 30-second-per-finding verification cost apply.

## Step 6: Present Findings

**Redesign-count checkpoint (before drafting the presentation)**: Count the deliverables whose approach was materially changed by the reassessment — eliminated, replaced with a different mechanism, or restructured such that the implementation path is not a refinement of the original. Include this count as `N / total`. If `N / total > 50%`, the Substantial Redesign Flag section below MUST appear in the output immediately above Questions. If `N / total <= 50%`, omit the Substantial Redesign Flag section entirely. Emit the `N / total` count as a one-line note at the top of the Step 6 `### Classification` block regardless of whether the flag fires — e.g., `Redesign count: 1/6 deliverables materially changed (below 50% threshold; Substantial Redesign Flag omitted)` — so the checkpoint's decision is auditable from the user-facing report.

**Denominator convention**: `total` is the **pre-reassessment** deliverable count — the count in the spec as-read at Step 1. Dropped deliverables count as `materially changed` and stay in the denominator; added deliverables count as `materially changed` and increase the denominator. Rationale: the ratio measures how much of the spec the user originally wrote is changing, not how much of the spec post-reassessment is new. Use the same denominator through every emission of the redesign-count ratio in a single reassessment (initial Step 6 draft, revised post-question Step 6 output, Step 8 summary) — a reassessment that emits `1/4` in Step 6 and `1/3` in Step 8 is internally inconsistent even when both ratios fall on the same side of the 50% threshold. For specs without numbered deliverables (per SKILL.md Step 1's non-numbered-deliverables guidance: *"treat each distinct implementation section as a deliverable for validation purposes"*), the denominator counts only §-headed implementation sections within the spec's Deliverables / Approach surface — not surrounding meta-sections (§FOUNDATIONS Alignment, §Verification, §Out of Scope, §Risks).

**Material-change boundary — anchoring examples**: Examples of *refinements that do not count as material*: field renames (`content_hash` → `body_hash`), type-shape adjustments that preserve the deliverable's role (`Map<string, Node>` → `Record<string, Node>`), signature-preserving parameter reorderings, prose rewording of the deliverable's framing without changing what the implementation does. Examples of *material changes*: elimination of a deliverable, replacement of its mechanism (e.g., FTS5 replaced with a different full-text engine; SQLite replaced with a different store), restructuring that changes the set of packages or modules the deliverable touches, changing the read/write direction of data flow, introducing a new authoritative state where the original was a derived view (or vice versa). **Additional case — deliverable scope-shifted to a sibling spec while preserving the contract surface**: when a deliverable's contract text is preserved (in a cross-reference table or equivalent informational anchor) but its implementation site moves to a sibling spec's deliverables, count as material in the originating spec because the originating spec's deliverable footprint contracts. The contract preservation distinguishes this from full elimination, but the spec's own deliverable scope still shrinks. Worked example: SPEC-19 reassessment 2026-05-07 reclassified 3 of 7 deliverable rows from `NEW deliverable` to `cross-reference defined here, implemented downstream` (TS canonical-vocabularies, TS types, schema-completeness validators — all routed to SPEC-22's Tier-2 ownership); counted as 3 material changes because each row left SPEC-19's Tier-1 deliverable scope, even though the contract text remained in the spec as a cross-reference anchor. **Middle-intensity case — layer rename that restructures surface without changing mechanism**: when a deliverable renames multiple top-level layers / sections / classes AND adds new sub-semantics to them, but the underlying mechanism (code path, data sources, trim/budget/error-handling discipline) is preserved, the rename does NOT count as material *if consumers can adapt field-by-field* — i.e., each new layer name has a clear predecessor in the old shape and the transition is a mapping, not a rewrite. Worked example: context packet v1→v2 where the five top-level layers (`nucleus`, `envelope`, `constraints`, `suggested_impact_surfaces`, plus `task_header`) are renamed to completeness classes (`local_authority`, `exact_record_links`, `scoped_local_context`, `governing_world_context`, `impact_surfaces`) while the assembler's role, the trim-envelope-before-nucleus discipline, and the structured-error-on-insufficiency contract are preserved → non-material refinement. The rename DOES count as material if consumers must re-read the packet from scratch under the new shape — i.e., the mapping is not field-by-field and prior-shape mental models do not carry over. Decision rule: ask whether a consumer who knew the v1 shape can construct a correct v2 mental model by applying a rename table. If yes → refinement. If no → material change.

**Anchoring example — spec-already-redesigning-upstream**: when the spec under reassessment is itself a redesign of upstream content (an existing skill, an earlier spec, an archived design doc), the redesign-count measures ONLY material changes the reassessment introduces — not changes the spec already documents. The phrase *"by the reassessment"* in the checkpoint rule above is load-bearing here: a reassessment that refines a spec's already-documented redesign without adding/removing/restructuring deliverables has redesign-count 0/N, even when the spec itself proposes substantial redesign of the upstream material. Worked example: a reassessment of SPEC-21 (which itself proposes 5/9 material changes to the underlying `storylet-pool-authoring` skill) refines trigger conditions in two §D Phase 4 table rows, redirects the §D Phase 5 dramatic-unit-coverage axis source from `value_delta_target` to `beat_plan.beats[].state_significance`, reconciles the same wording across §Approach + §Risks + §Verification, and adds one new §Risks entry — no deliverable rows added, removed, or restructured. Redesign count: 0/9 (NOT 5/9), Substantial Redesign Flag omitted, even though SPEC-21 itself proposes 5/9 material changes to the underlying skill. The redesign-count rule sees only the reassessment's deliverable-row impact; upstream redesign that the spec already documents is invisible to this measurement. Conflation pitfall: emitting `Redesign count: 5/9 deliverables materially changed (above 50% threshold; Substantial Redesign Flag included)` at Step 6 when the 5/9 ratio actually measures the spec-vs-upstream-skill rather than reassessment-vs-spec is a category error — the Step 6 emission is user-facing and a reader will reasonably interpret it as the reassessment's impact. Always anchor the count on the question "what did THIS reassessment change in the spec's deliverable rows?" and cross-check against the §Denominator convention's `pre-reassessment deliverable count` framing — if the same deliverable row is unchanged after the reassessment, it does NOT count toward the numerator regardless of how much it changes the underlying upstream material.

**Multi-item inventory granularity**: When a deliverable contains a multi-item inventory (a table of validators, a list of MCP tools, an enumerated rule set, a typed-op vocabulary, a validator inventory with rule-derived and structural rows, **a list of substantial file-target paragraphs in a §-headed sub-track**, etc.) and some sub-items materially change while the container deliverable itself only refines (gains/loses rows, reorders, rewords the preamble), count each sub-item's material change individually toward the numerator but do NOT count the container deliverable separately. Worked example A — tabular: a Validator Framework spec with one §Validator inventory section containing 14 rows; 2 rows are materially restructured (mechanism replacement from prose-heuristic to structural-only), 4 rows are refined in wording, 8 rows unchanged. Contribution to the redesign-count ratio: 2 toward the numerator (the two restructured rows, each counting as a sub-item material change), 1 toward the denominator (the inventory itself as one deliverable among the spec's full deliverable set). This keeps the ratio interpretable — a spec whose single inventory contains many sub-items doesn't automatically exceed 50% just because the inventory section saw restructure work, nor does a spec with many small-redesign deliverables get artificially diluted by a large refined-only inventory. Applies symmetrically: added sub-items that introduce a new mechanism count toward the numerator; removed sub-items whose removal is a mechanism withdrawal (not a simple dedupe or refactor) also count.

Worked example B — list of file-target paragraphs: a documentation-track spec with two top-level §-headed deliverables (`§Track C1` and `§Track C2`), each containing a list of 4-6 substantial file-target paragraphs (each names a target file path and prescribes a 2-3 sentence edit). Track C1 reframes one paragraph (mechanism-restructured) and adds two new paragraphs (mechanism-additive); Track C2 sees only LOW-severity wording refinements across its paragraphs. Contribution to the redesign-count ratio: 2 toward the numerator (the two added Track C1 paragraphs each counting as a sub-item material change; the reframed paragraph is a material-mechanism change too — count it if its mechanism replaced rather than refined the original), 1 toward the denominator for `§Track C1` + 1 for `§Track C2` = 2 denominator total. Ratio: 2-3/2 = 100-150%. This treats the spec consistently with example A — file-target paragraph lists are inventory-shaped even when each paragraph is heavier than a table row.

> **Small-N edge case** (≤3 top-level §-headed deliverables, at least one of inventory shape with sub-item material changes): the redesign-count ratio is **denominator-sensitive** — a single track's sub-item churn can produce a 50%+ ratio even when the spec's overall character is "one track restructured, others refined." The Substantial Redesign Flag still fires per the threshold rule, but its interpretation should explicitly name which track(s) carry the restructure and which remain refinement-only — e.g., the Step 6 flag prose reads `"This reassessment proposes substantial redesign concentrated in §Track C1 (2 added file-target deliverables, 1 reframed); §Track C2 saw only LOW-severity wording refinements. Goals preserved across both tracks; implementation path changes for Track C1."` rather than the default `"substantial redesign of N/M deliverables"` framing. The named-tracks framing keeps the flag honest in the small-N case where a literal `2/2 = 100%` ratio would otherwise overclaim that the entire spec was redesigned.

**Finding-key convention**: In Step 7's Pre-Apply Verification table and Step 8's status reporting, Issues are keyed `I1, I2, …`; Improvements are keyed `M1, M2, …`; Additions are keyed `A1, A2, …`. Preserve the within-category number from this section (e.g., the third Improvement listed here becomes `M3` in Step 7). Candidate findings that get merged into another finding's recommendation during Step 6 drafting do NOT receive a Step 7 key — they dissolve into the consolidating finding's row. Key Step 7 strictly from Step 6's presented list: the first presented Improvement is `M1` regardless of any internal drafting-time labels you used before consolidation.

## Question Handling

- **Option fidelity**: Each option that names an existing type, field, or function must cite its current definition (grepped at presentation time), not a summary characterization. The user's approval binds to the option label, so an imprecise label — e.g., describing a field as `Map<string, Node>` when the actual type is `Record<string, NodeSummary>` — produces an ambiguously approved fix that the Step 7 pre-apply check must then disambiguate. Ground every option in current code before presenting.
- **Initial report**: At most 3 open-ended questions in an initial round. **Confirmation-shape questions** (y/n, or strictly binary choices with a recommended default) may be bundled as additional items in the same round when they are interdependent with the open-ended questions and would otherwise require a separate follow-up round against the same Step 7 pre-apply table. "Interdependent" means the confirmation's answer materially shapes the pre-apply verification row for the same deliverable or an adjacent one already being touched. Non-interdependent confirmation-shape questions still count against the 3-question cap and defer to follow-up. If open-ended question count exceeds 3 regardless of interdependence, prioritize blockers and defer the rest — the cap applies to open-ended shape, not to total items.
- **Interdependent questions**: Present as a single combined question with labeled option combinations.
- **Discrete options (2-4), single question**: Use `AskUserQuestion` with a recommended default.
- **Discrete options (2-4), bundled (2–3 questions in one review round)**: Prefer plain-text bullets with labeled options `(a)/(b)/…` and a recommendation per question, under a single `### Questions` heading. This reads more cleanly than multiple `AskUserQuestion` calls and lets the user answer inline (e.g., "1) a, 2) b, 3) proceed with recommendation"). Use `AskUserQuestion` only when a single discrete-option question stands alone.
- **Open-ended questions**: Present as plain text in the report.
- **Follow-up rounds**: One question at a time. If answers raise new questions or invalidate findings, present a follow-up round (same format). Repeat until resolved.
- **Delegated resolution**: If the user delegates (e.g., "you decide based on FOUNDATIONS"), resolve by reasoning against the referenced constraint. If resolution requires additional codebase investigation, perform a mini Step 3 scoped to the question. If the investigation touches >3 files, consider launching a focused Explore agent rather than manual reads. If none of the original options are ideal, propose a new option with justification — scope investigation to 1-3 targeted checks. If the new option affects dependencies or package boundaries, present as a new finding first.
- **Conditional approval**: If the user's answer approves an option contingent on a verifiable premise (e.g., "proceed with (a) as long as we truly need those three new accessors", "go with (b) if X is the right entry point"), treat the premise as a mini Step 3 scoped to the condition — grep/read the relevant code, confirm or refute the premise, and proceed only if confirmed. Surface the verification outcome explicitly in the Step 7 Pre-Apply Verification Table row for the affected finding. If the premise is refuted, re-present the affected finding with a corrected recommendation and wait for follow-up approval before applying edits. A conditional approval is not a blanket approval: the condition is part of the contract. (See also `references/spec-writing-rules.md` §Pre-Apply Verification — the Hybrid user-answered + proactive-verification row shape is the proactive variant of this rule: auditor-initiated verification of a user-answered option's premise without a user-imposed condition.)

Wait for user response before proceeding to Step 7. (In plan mode, this wait is replaced by ExitPlanMode approval — see `references/plan-mode.md`.) Findings are approved unless explicitly objected to: silence on a finding while answering Questions counts as approval; an explicit objection re-opens that finding's disposition and requires re-presenting the corrected recommendation before Step 7. SKILL.md `<HARD-GATE>` clause (a) defers to this rule — the gate is satisfied either by explicit approval/disposition for every finding OR by absence of explicit objection in the user's response.

**Auto-mode interaction**: When auto mode is active AND the findings contain no Issues (CRITICAL/HIGH severity or FOUNDATIONS violations) AND no open Questions, proceed directly to Step 7. Report the auto-mode auto-approval inline in the Step 6 presentation (e.g., "Auto mode: no Issues, proceeding to Step 7"). If any Issue is present or any Question is open, the wait-for-user gate still applies even in auto mode.
