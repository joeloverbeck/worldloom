# Gap-Filler Interview (Step 4)

The proposal (from compile mode or the fresh-mode proposal step) answers *what the pipeline does*. This step answers *what the runnable skill needs that the proposal didn't specify*.

## Protocol

One question per message. After each user answer, display:

```
Confidence: X%
Gaps: [list of remaining unknowns]
```

Target 95%. Announce the transition when reached: "I'm at 95% confidence. Moving to design."

**Auto mode compression**: Under auto mode, routine gaps (slug, user-invocable flag, sibling interop names, INDEX semantics, examples yes/no, conventional argument naming, character-slug derivation rule, and similar operational-not-substantive choices) may be pre-filled as confirmable assumptions alongside a single substantive question — the user can override any assumption in the same reply. This honors "one substantive question per message" while respecting auto mode's "minimize interruptions" directive. Non-routine gaps (Validation Rules subset, HARD-GATE policy, output schema, Canon Safety Check shape, prerequisite-file list, world-scope declaration) stay strict single-question.

## Mandatory Gaps to Close

Ask about every gap that has not already been answered by the proposal or prior context:

- **Slug** — kebab-case, matches the intended `.claude/skills/<slug>/` directory.
- **user-invocable** — true/false. Most canon-mutating skills should be invocable; some meta-tooling skills run only as callees.
- **World-State Prerequisites (mandatory per FOUNDATIONS)** — exact list of files read before the skill acts, plus the atomic-record retrieval mechanism. Examples: `WORLD_KERNEL.md`, `ONTOLOGY.md`, plus `mcp__worldloom__get_context_packet` retrieval over atomic `_source/` records (CF / CH / INV / M / OQ / ENT / SEC) — per FOUNDATIONS §Canonical Storage Layer + §Mandatory World Files. This is non-negotiable per FOUNDATIONS §Tooling Recommendation. **Bootstrap-skill carve-out**: for skills that create initial world state from nothing (pipeline heads like `create-base-world`), the block declares: (a) `docs/FOUNDATIONS.md`, (b) any pre-flight existence/collision checks on the target directory, (c) the user-input file if applicable. The absence of prior state IS the prerequisite, and this framing satisfies the "lists real files (not vague)" conformance check.
- **Context-packet `task_type` registration** — for skills that load world state via `mcp__worldloom__get_context_packet`: confirm whether a registered profile exists for the skill's task class (per MCPENH-002 or sibling-skill precedent — e.g., `propose-new-canon-facts` uses `task_type='propose_new_canon_facts'`). If yes, name the registered task_type. If no, choose: (a) block on registering a new profile before shipping, OR (b) ship using `task_type='other'` with an explicit deferred-MCPENH-ticket disclosure in the generated skill's Guardrails naming the prioritization the future profile should encode (hard-canon CFs, every INV record, every M record, relevant section records, etc.). This is one specific instance of the broader §Deferred-infrastructure architecture choice below — when multiple infrastructure surfaces are deferred together, prefer eliciting the §Deferred-infrastructure architecture gap first and let its Shape A/B/C answer cover this gap as a sub-case.
- **Deferred-infrastructure architecture** — when the source proposal references infrastructure not yet present in the codebase — checked by grepping the proposal for `mcp__worldloom__*` task_types, ID classes, Hook 3 surfaces, patch-engine ops, validator schemas, or named-but-not-existing sibling skills against the current state of `tools/` and `.claude/skills/` — elicit the user's choice between three shapes: **(A)** ship now with direct-write + manual-allocation + deferred-ticket disclosure, plus a triaged ticket set filed in `tickets/` (the §Deferred-integration tickets gap below covers the ticket-write step); **(B)** block on landing prerequisite tickets first, then ship the skill (preserves engine-routed parity from Day 1 but blocks generation on the prerequisites); **(C)** hybrid — ship with high-value tickets landed first (correctness-adjacent surfaces like retrieval-profile registration, basic ID class) but defer lower-value ones (per-class engine ops, schema validators, namespace hook extensions). This is STRICT single-question per the §Protocol Auto-mode-compression rule — Shape A vs B vs C materially reshapes the skill's Pre-flight + Guardrails + Procedure §6 ticket-write step. The §Context-packet `task_type` registration gap above is one specific sub-case of this broader question (the choice between Shape-B-style "block on registering" and Shape-A-style "ship with `task_type='other'` + ticket"); when only one infrastructure surface is deferred, eliciting the Context-packet gap alone is sufficient and this gap can be skipped. When two or more infrastructure surfaces are deferred together, this gap is the primary framing and the Context-packet gap folds into its answer. Cross-reference Procedure §6 sub-step 5(b) for the ticket-write step that consumes Shape A or Shape C answers.
- **Deferred-integration tickets** — when the §Deferred-infrastructure architecture gap above selects Shape A or Shape C, elicit the per-integration triage: for each infrastructure surface deferred (MCP task_type, ID class, Hook 3 namespace, engine op, validator schema, future sibling), confirm the ticket should be filed (file in `tickets/<NAMESPACE>-<NNN>-<slug>.md` against `tickets/_TEMPLATE.md`, with appropriate Assumption Reassessment / Architecture Check / Verification Layers / Acceptance Criteria sections per the template) OR explicitly skipped (rare; document why the deferred surface is acceptable to leave un-ticketed — e.g., the surface is a future maintenance concern not blocking shipping, or the surface is sufficiently speculative that its design should wait for the runtime to stabilize). On user approval, the write-files step's Procedure §6 sub-step 5(b) emits the tickets as part of the same parallel write batch as the skill writes. Ticket numbering is allocated by scanning `tickets/` + `archive/tickets/` for the next free integer in the chosen namespace (e.g., MCPENH-NNN, HOOK-NNN, PATCHENG-NNN per existing precedent). Skip this gap entirely when §Deferred-infrastructure architecture selected Shape B (no tickets to file at this generation pass — prerequisites already landed before the skill's generation began).

  **User-invocation pre-authorization sub-rule**: when the user's invocation arguments include explicit ticket-creation pre-authorization (e.g., a `/skill-creator` argument like "create tickets in tickets/* for any integration the skill requires" or "if you find missing infrastructure, file the tickets"), the per-integration triage may be compressed to a single confirmable summary in a gap-filler message — naming each ticket the auditor identified by namespace + slug and one-line scope, with the user able to override the list before the design-drafting batch begins. The auditor must still scan `tickets/` + `archive/tickets/` for namespace numbering and identify the precise integration surface for each ticket — only the per-ticket triage question is compressed, not the ticket-content discipline. The compression preserves the per-integration audit trail (each ticket still appears in the gap-filler message, the user still has authority to remove items) while honoring the user's pre-authorization. Worked precedent: branching-story-page-cycle's compile invocation pre-authorized ticket creation; MCPENH-011, MCPENH-012, and BSBOOT-001 were identified by the auditor and presented as a confirmable summary alongside the substantive HARD-GATE policy question rather than as three separate triage questions.

  **Parallel-implementation forward-compatible-prose sub-rule**: when the user signals parallel implementation of the deferred-integration tickets in the same generation pass (explicit "implement these tickets too" / "land them now," evidence of in-flight ticket work — e.g., a parallel agent or linter actively editing `tools/` adjacent to the skill write — or pre-authorization that explicitly extends to immediate execution rather than deferred PR work), the generated SKILL.md's interim-fallback prose for those specific tickets MUST be forward-compatible to avoid post-write staleness. Two acceptable framings: **(i) dual-state framing** — document both the interim and post-landing states explicitly in one sentence (e.g., "allocate `SAU-NNNN` via `mcp__worldloom__allocate_next_id(world_slug, 'SAU', story_slug=<story_slug>)` once MCPENH-015 lands; until then, manual scan of `audits/SAU-*.md`"); **(ii) commit-and-handoff framing** — commit to the post-landing stance with an explicit handoff note in the deferred-debt disclosure (e.g., "allocate `SAU-NNNN` via `mcp__worldloom__allocate_next_id(...)`; MCPENH-015 lands the allocator support — see Guardrails §Known integration debt for the prerequisite"). Avoid the brittle "until X lands" stance for parallel-implementation tickets — that framing assumes the ticket lands in a later PR and rots immediately when the ticket lands in the same PR (the maintainer reading the as-generated prose post-landing sees interim references that no longer apply). The §Procedure §6 reconciliation precondition catches numerical-citation drift at write time but does not catch interim-fallback drift; this sub-rule is the prevention-side check at gap-filler time. Skip this sub-rule when the §Deferred-infrastructure architecture answer was Shape B (no tickets to file at all — no interim-fallback prose to write) or when the user explicitly signaled the tickets are deferred to a later PR (the canonical Shape A stance — interim "until X lands" framing remains correct). Worked precedent: branching-story-health-audit's compile invocation produced MCPENH-015 framing as Shape A with "until MCPENH-015 lands" prose; the user/linter landed MCPENH-015 mid-generation, marked the ticket COMPLETED, and post-edited the SKILL.md to drop the manual-scan fallback — the dual-state or commit-and-handoff framings would have produced prose still valid post-landing without the post-write edit.
- **World scoping** — declare exactly one of {single-world, all-worlds, meta, meta-with-multi-world-read}. This gap closes a class of silent-global-write bugs that would otherwise hit every future canon-mutating and canon-reading skill.
  - **single-world** (canon-mutating or canon-reading): required `world_slug` argument identifies the target; ALL world-file reads and writes rooted at `worlds/<world-slug>/` — never at repo root.
  - **bootstrap** (subset of single-world): a target directory derived from arguments must NOT already exist. Two shapes — both share: target collision aborts at Pre-flight; the absence of prior state at the bootstrap scope IS the prerequisite per the §World-State Prerequisites bootstrap-skill carve-out; required arguments derive the target.
    - **per-world bootstrap** (e.g., `create-base-world`): `worlds/<world-slug>/` derived from a `world_name` argument; the world directory itself must not exist.
    - **per-nested-scope bootstrap** (e.g., `branching-story-bootstrap` — a story bundle nested inside an existing world): a nested target like `worlds/<world-slug>/stories/<story-slug>/` derived from `world_slug` + a nested-scope-slug argument; the nested target must not exist while the parent (the world) MUST exist. Pre-flight aborts on (a) parent missing OR (b) nested target already present. The classification table's "bootstrap" framing applies to both shapes; the nested-scope variant inherits the same target-collision-aborts-Pre-flight discipline plus a parent-existence check that per-world bootstrap does not need.
  - **meta-with-multi-world-read** (typically canon-reading or meta-tooling, not canon-mutating): no `world_slug` argument; reads scoped per-world via `mcp__worldloom__get_context_packet(world_slug=<each>, task_type='propose_new_worlds_from_preferences', ...)` when generating world proposals, another registered task-specific type when the generated skill matches an existing profile, or `task_type='other'` only for genuinely unclassified future skills. Writes land at a declared root-level surface (e.g., `world-proposals/`); rationale for the hybrid scope declared in the generated skill's Guardrails; empty-worlds case (no existing worlds yet) handled as a degraded-mode path with an explicit user-visible flag at the HARD-GATE deliverable.
- **Sibling interop** — which existing skills produce inputs this skill consumes; which will consume this skill's outputs. Name them explicitly. Sibling interop is realized through on-disk artifacts (proposals, cards, audit reports, sidecars) and passive labels (e.g., `downstream_routing` fields in output frontmatter). Worldloom skills are non-chaining — they never invoke other skills; the user separately invokes a downstream sibling with the upstream skill's output path as input.
- **Reverse-seam scan** — at gap-filler time, grep `.claude/skills/*/SKILL.md` and `.claude/skills/*/templates/*` for the literal token `<new-skill-slug>` (the skill being generated) PLUS the literal markers `# Seam:` and `seam to`. Hits indicate existing shipping siblings that named this skill in their inline-with-seams discipline (per the inverse of §Future-sibling parity — those siblings shipped before this one and inlined minimal schemas with seam markers pointing at this skill, expecting this skill's eventual production schemas to close them) and now need integration tickets to close those seams once this skill ships. Each hit produces TWO downstream consequences captured at write time: (1) a candidate `<NAMESPACE>-NNN` ticket via §Deferred-integration tickets, with the cited site (file path + line number + seam-marker quote) recorded in the ticket's What-to-Change section — capturing the forward-work delegation refactor; AND (2) a same-PR prose correction in the cited sibling via SKILL.md Procedure §6 sub-step 5(c) (Post-shipping sibling-skill prose correction) — replacing the "not yet shipping" / "Future-sibling seam" / "Until then, this skill inlines..." wording with a factual reference to the now-shipping skill plus a forward reference to the (1)-side ticket. The two consequences are reciprocal: the ticket captures forward work; the prose correction stops the existing sibling from falsely claiming the new skill doesn't ship. Without (2), shipping siblings retain stale "not yet shipping" claims for a now-shipping skill until the (1) ticket lands the full delegation refactor (which may be weeks or months later). Skip this gap when the grep returns zero hits. Distinct from §Future-sibling parity (forward direction — this skill names not-yet-shipping siblings) and from §Sibling interop (existing-sibling consumption / production); reverse-seam scan covers the case where an existing shipping sibling already named THIS skill as the future authority for some content. Worked precedent: branching-story-page-cycle's compile run grepped for `branching-story-page-cycle` + `# Seam:` and surfaced two seam markers in `branching-story-bootstrap` (Phase 7 SE schema + Phase 8 choice generation); the BSBOOT-001 ticket was filed to close those seams once the page-cycle skill landed.
- **Output-schema parity vs downstream-consumer parse expectations** — for each output the skill emits that a named downstream sibling will consume at parse-time (e.g., proposal cards consumed by `canon-addition`, character briefs consumed by `character-generation`), confirm the output's frontmatter schema matches the consumer's parse-time field requirements byte-for-byte OR document a divergence-handling strategy (sidecar file with consumer-shaped frontmatter, two-tier nested-block extract, or explicit user-reformulation handoff). The write-files step catches the same failure mode at template-derivation time (per SKILL.md Procedure Step 6's "Write order" sub-step for output-type templates), but raising the question at gap-filler time prevents back-loop redesign of the frontmatter shape after design-drafting approval. Applies when the named downstream sibling EXISTS at gap-filler time; when the downstream sibling is referenced but not yet shipping, see §Future-sibling parity below.
- **Future-sibling parity (downstream sibling not yet shipping)** — when the proposal references a downstream sibling that doesn't yet exist (verified by checking `.claude/skills/<sibling>/` is absent), elicit one of three shapes: **(a) inline-with-seams** — inline a minimal schema in this skill's templates with explicit `# Seam: refactor when <sibling> ships its production schema` annotations on every field that may shift, plus a Guardrails entry naming the future sibling and the parity intent; **(b) block-on-sibling** — block on landing `<sibling>` first, then ship this skill against the sibling's actual schema (preserves byte-for-byte parity from Day 1 but blocks generation on the sibling); **(c) fail-fast unimplemented seam** — ship with explicit unimplemented-seam markers (e.g., a phase that aborts with "Phase N delegates to <sibling>; not yet shipping; skill cannot complete this phase until the sibling lands") suitable when the seam is non-load-bearing for the skill's primary deliverable. The write-files step's Procedure §6 sub-step 3 sub-class (c) (Templates anticipating a future, not-yet-shipping downstream sibling) consumes Shape (a) answers; raising the question at gap-filler time prevents back-loop reauthoring of the seam discipline after design-drafting approval. This gap is structurally parallel to the §Output-schema parity gap above — same byte-for-byte concern, different existence precondition for the consumer; when both apply (some consumers exist, some don't), elicit each gap separately.

  **Multi-sibling sub-rule**: when the proposal references two or more not-yet-shipping siblings simultaneously, elicit per-sibling Shape selection rather than a single uniform Shape — the canon-mutation-stakes and consumer-stakes of each sibling may dictate different Shapes (e.g., a canon-promotion-handoff sibling typically requires Shape (a) with explicit abort-on-handoff posture because silently degrading to a non-canon resolution would erode the canon-mutation HARD-GATE, while a JIT-seam sibling or a passive-consumer audit sibling may tolerate Shape (a), (b), or (c) interchangeably). Auto-mode-compression may pre-fill Shape (a) for all siblings as a confirmable default ONLY when none of the named siblings is a canon-mutation-handoff target — those require explicit confirmation regardless of mode, because the wrong Shape on a canon-handoff sibling silently weakens the firewall the generated skill is supposed to preserve. Worked precedent: branching-story-page-cycle's compile referenced three not-yet-shipping siblings (`storylet-pool-authoring` JIT-seam, `story-fact-promotion-to-canon` canon-handoff, `branching-story-health-audit` passive-consumer); the canon-handoff sibling required explicit Shape (a) abort-on-`canon_candidate` confirmation while the JIT-seam and audit-consumer siblings were uniformly Shape (a) under auto-mode pre-fill.
- **Validation Rules applied** — which of FOUNDATIONS' 7 Validation Rules this skill enforces, and at which phase. At least 3 must be named for canon-mutating skills. For canon-reading skills whose output carries in-world knowledge, beliefs, or capabilities, at least Rule 7 is required; name additional Rules (2/3/4/5) wherever they are structurally or procedurally enforced. Rule 1 (No Floating Facts), when enforced structurally by required output-schema fields rather than a dedicated phase, should appear in the FOUNDATIONS Alignment table rather than in the Validation Rules list.
- **HARD-GATE need** — required for canon-mutating; recommended for canon-reading and meta-tooling whose deliverable exceeds ~3 files or requires explicit user review before write; optional otherwise.
- **Change-log policy** — canon-mutating skills must emit Change Log Entries (see `templates/change-log-entry.yaml`).
- **Canon Fact Record usage** — canon-mutating skills that emit new facts must produce records matching FOUNDATIONS §Canon Fact Record Schema.
- **Batch vs single-artifact output** — if the skill emits multiple artifacts per invocation (a batch), ask: (a) batch size default + user override semantics; (b) fill-priority order when requested size is below slot count; (c) empty-slot policy (preserve empty as a diagnostic signal, or substitute from another slot); (d) batch-manifest file vs inline-batch file; (e) batch-level safety check as a peer of per-artifact checks, not a replacement.
- **Examples** — select 1-2 concrete worked inputs (optional, but usually worth it for complex pipelines).
- **Supporting-file bootstrap** — does the proposal bundle required content for files outside `.claude/skills/<slug>/` that the generated skill consumes at runtime (e.g., `tickets/_TEMPLATE.md`, `tickets/README.md`, `docs/archival-workflow.md`, validator fixtures, hook scripts)? If yes, these are pipeline-level supporting files the generated skill depends on — distinct from both world-state files (which skill-creator NEVER writes per Guardrails) and from FOUNDATIONS.md (which skill-creator NEVER edits). Elicit user approval to expand scope before drafting; on approval, write them at the write-files step alongside the skill writes. On refusal, present the bundled content for the user to paste at the closeout next-steps menu.
- **Generated skill's supporting files** — split into two concerns:
  - **(a) Runtime-read supporting files** — any non-world files the generated skill reads at runtime beyond `docs/FOUNDATIONS.md` (templates, configs, hook scripts, validator fixtures, archival-policy docs)? Each must appear in the generated skill's Pre-flight Check as a readability precondition with a clear abort-on-missing error, parallel to the World-State Prerequisites block but distinct in origin (pipeline infrastructure rather than world canon). Closes the failure mode where a generated skill silently fails at first use because a required supporting file was never written or was moved.
  - **(b) First-run bootstrap supporting files** — repository infrastructure the generated skill writes once at first invocation (e.g., `<output-dir>/.gitkeep`, a two-line append to repo-root `.gitignore`, a README placeholder)? Common when the skill emits to a new root-level directory that the existing `briefs/*` + `worlds/*` gitignore pattern would otherwise miss. Each bootstrap surface must appear in the generated skill's Commit phase as a gated write (HARD-GATE-conditional, idempotent — detect-then-skip on subsequent runs); Pre-flight detects bootstrap state and records it on the batch manifest as `bootstrap_writes_required: true|false` so the user sees the deferred infrastructure write at the HARD-GATE deliverable. The bootstrap is performed by the generated skill itself at first invocation, NOT by skill-creator at the write-files step — skill-creator's supporting-file writes are limited to the §"Supporting-file bootstrap" gap (the proposal-bundled-content case). This sub-bullet covers the orthogonal case where the generated skill bootstraps its own output directory's tracking infrastructure.

## Out-of-scope concerns raised during interview

If the user raises a concern during the gap-filler interview that names a downstream sibling skill's behavior as a risk factor (e.g., "my worry is that `<sibling>` will drop this content," "I'm concerned `<sibling>`'s schema won't preserve X"), and the concern is out-of-scope for this skill (per the one-skill-per-invocation guardrail), (a) document the concern in the generated skill's Guardrails as a "Known concern to surface to maintainers" note naming the downstream sibling + the specific risk + why this skill's design minimizes but does not eliminate the risk, and (b) surface it at the closeout next-steps menu as an explicit follow-up option ("Run `skill-audit` on `<sibling>` to address the <risk>"). This keeps out-of-scope concerns auditable rather than scattered, and makes the interop contract maintainable by naming the sibling that needs attention.

## Starting Confidence (compile mode)

Before asking the first gap-filler question, compute initial confidence from the reference proposal:

**Base**: 80%

**Deduct 5% for each fully-missing item; deduct 2% for each partially-present item** (list below). Judgment rule: an item is PARTIAL when the proposal gestures at the element but doesn't satisfy the runnable-skill bar — e.g., a quality checklist where numbered validation tests were specified; rules stated in some phases but not others; a record schema sketched in prose rather than as YAML; or a **delegation-by-reference** where the proposal names a concrete existing artifact (a shipping sibling SKILL.md, a published schema, or a referenced file path) whose content IS the missing element. Delegation-by-reference counts as PARTIAL (not MISSING) because the element is knowable — the executor can load the referenced artifact — but the proposal still didn't restate it, so a gap-filler is still required to confirm adoption. Example: a proposal saying "the output format aligns with how `propose-new-canon-facts` produces proposal cards" delegates the schema legitimately → PARTIAL, not MISSING. Name each partial call explicitly ("Validation tests: PARTIAL — proposal has Artifact Quality Checklist but no numbered tests; deducting 2%") so the user can override before the first gap-filler question.

Items:
- Record or artifact schema(s) for outputs the skill emits — YAML for structured records (Canon Fact Records, Change Log Entries, candidate records consumed by downstream siblings), markdown templates for prose artifacts (ticket files, design docs, triage reports), JSON schema for validator configs. Applies equally to canon-reading skills whose outputs are structured candidate records consumed by downstream skills (e.g., proposal cards consumed by `canon-addition`). A bullet-list template where YAML frontmatter would be needed for downstream parsing counts as PARTIAL; a prose sketch where a markdown template with required sections would be needed for downstream template-fidelity enforcement also counts as PARTIAL.
- Numbered phase list with per-phase scope
- Validation / rejection tests
- Per-phase rules or FOUNDATIONS cross-references

**Add 5% for each of these present** (max +10%; bonus items do not take half-credit — they are either present or absent):
- At least one fully-worked example (input → output)
- A single-sentence Final Rule stating the pipeline's discipline

Each item — deduction OR bonus — is independently earned.

**Floor**: 50%. **Ceiling**: 90%. (95% is reached via gap-filler answers, never from the proposal alone.)

Announce the computed starting confidence to the user in the first gap-filler message. When the proposal is unusually thorough (≥85% starting), close only the remaining operational gaps (slug, interop, examples) — do not re-ask what the proposal already answers.
