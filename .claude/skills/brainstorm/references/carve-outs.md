# Carve-outs

The carve-out cluster — directed-design / directed-design batching / small-deliverable / multi-artifact-bundle / template-structured / non-plan-mode fast-track / multi-deliverable triage navigation / re-emergent interview / mid-design term-clarification / Recovery/Reset register inheritance / classification pivot. SKILL.md retains the procedural skeletons that mention each carve-out; this file is the full specification per carve-out, in firing-order across Steps 1 and 4.

## Step 1 — Directed design question carve-out (non-plan-mode)

If initial confidence is 85-94% AND either (a) the user's request is framed as a specific design decision with enumerated alternatives (i.e., the user has already stated the problem and proposed options, turning the brainstorm into an approach-selection task rather than a discovery task), OR (b) the user's request is a specific directive where the problem is fully constrained by the request text (clear deliverable, clear scope, minimal open choices — e.g., "port X from repo A into repo B, strip extraneous content, delete the reference"), skip the discovery interview and go directly to Step 3. Announce the confidence level, name any remaining gaps as assumptions to carry into the approach proposal, and let the user correct them during approach selection. This mirrors the plan-mode fast-track but applies in non-plan-mode when the user has effectively pre-conducted the interview themselves or fully constrained the problem space.

**Triage/analysis brainstorms are a common instance of this carve-out**: when the request is to evaluate a report or finding-set and produce work items (specs, tickets, or in-place doc / governance-doc edits — whatever the Step 5 deliverable classification resolves to), the discovery interview is skipped — Step 3's triage recommendation (per §"For triage/analysis brainstorms") IS the analysis, not a discovery output. Calibrate confidence from the source report plus codebase verification of its claims, and name the open design decisions as the questions the triage recommendation will surface for the user. Sub-step 8's standalone post-exploration confidence announcement still fires for triage brainstorms — render it on its own line before the triage recommendation, as the audit-trail anchor — even though the Step-2-skip decision it nominally drives is already settled by this carve-out. The finding-set can be operator-generated from codebase exploration rather than externally supplied — open-ended audit or diagnostic brainstorms ("is anything missing?", "where are the gaps?", "what workflows are we lacking?") fit this carve-out as long as the deliverable shape is verdict-bucketed work items. Sub-rules below that reference "the source report" or "the input report" apply when an external report exists; in the operator-generated case, substitute "the candidate finding-set produced during exploration" and skip sub-rules whose purpose presupposes external input (e.g., sub-step 7's prior-triage check, Step 3's parallel-agent source-report-claim verification).

## Step 4 — Classification pivot check

If the design reveals a deliverable type that differs from the Step 1 classification (e.g., "tooling configuration" now requires a new world-file type, or a spec now includes live code changes), re-state the refined classification to the user before presenting Section 1 of the design. Downstream sections (testing strategy, FOUNDATIONS alignment) follow the refined classification.

## Step 4 — Section batching threshold

**After each section**, ask: "Does this section look right?" Wait for confirmation before presenting the next section. If the user pushes back, revise that section before continuing. If the user approves 3+ sections consecutively without pushback or revisions, batch remaining sections into groups of 2-3, pausing for approval after each group rather than each section. Under auto mode, this threshold may shift to 2 consecutive approvals to reduce round-trips. Exception: keep a remaining section standalone if it is substantially more complex or higher-risk than the prior ones. Announce the batching: "You're clearly aligned — I'll present the remaining sections in groups."

Under auto mode, after 5+ consecutive approvals with no substantive pushback, single-message batches covering all remaining sections are acceptable provided no remaining section is higher-risk (the "Exception" above still applies). The "groups of 2-3" rule remains the default; the 5+-sustained-approval case is the explicit relaxation for prolonged agreement, parallel to skill-creator's convention.

## Step 4 — Directed-design batching carve-out

When Step 1 sub-step 5's directed-design carve-out fires (initial confidence ≥80% from a directed brief, Step 2 fully skipped) AND the design is medium-sized (5-10 sections — more than the §Small-deliverable carve-out's ≤4 decisions threshold but fewer than the §Multi-artifact-bundle carve-out's ≥5 substantive architectural deliverables), the first batch may include 3-4 sections without prior approvals, provided the operator announces the batching plan and its justification on the first batch (e.g., "Presenting in batches of ~3 sections — Auto Mode allows 2-3 sections per batch and the directed brief signals high engagement"). Subsequent batches follow the standard 2-3-section threshold from §Section batching threshold above. Distinct from the §Small-deliverable carve-out (which consolidates SMALL designs into one message) and from the §Multi-artifact-bundle carve-out (which structures LARGE designs into architectural tiers with per-tier approval); this carve-out covers medium-sized designs in directed-design flows where the user's directed brief was specific enough to signal high engagement but the design itself is too substantive to present as a single artifact. The HARD-GATE still applies — per-batch approval is required throughout, and the directed-design context does not change the per-section approval discipline; it only changes the initial-batch size.

## Step 4 — Small-deliverable carve-out

If the design comprises ≤4 distinct decisions or transformations AND initial confidence is ≥85%, the design may be presented as a single structured artifact (e.g., a transformations table, a bullet list of decisions, a short enumerated design summary) and approved in one turn rather than section-by-section. Under auto mode this is permitted by default; outside auto mode, announce the consolidation explicitly ("I'll present the design as a single summary rather than section-by-section because the deliverable is small enough to review at once"). The HARD-GATE still applies — explicit user approval of the consolidated design is required before any implementation action.

**What counts as a "decision"**: a *user-approveable choice point* — a moment where the user could meaningfully redirect (which fixture path, which workflow shape, what the refresh policy is). Atomic facts that follow from a parent decision (e.g., once "5 separate workflow files" is chosen, the contents of each file are not 5 additional decisions) count as one with the parent. A design with 3 logical parts each containing 2-3 sub-facts typically counts as 3 decisions, not 6-9. When the count is borderline, prefer consolidating — the gate that matters is "can the user review this in one turn", not the literal count.

## Step 4 — Multi-artifact-bundle carve-out

When the design comprises ≥5 distinct architectural deliverables (specs, large documents, or independently-reviewable artifacts) AND each deliverable is itself substantive (e.g., a multi-hundred-line spec), logical-tier batching is permitted from the first presentation turn without requiring prior-approval precedent: group deliverables by natural architectural concern (read path / write path / governance / migration, or analogous domain-specific tiers) and present each tier in one message, pausing for approval per tier. Announce the tiering plan and its justification explicitly on the first batch (e.g., "I'll walk the design in 3 tiers: Tier 1 = read path (SPEC-01/02), Tier 2 = write path (SPEC-03/04/05), Tier 3 = skill-facing contract (SPEC-06/07/08 + implementation order) — redirect if the grouping is wrong before I start"). Within a tier, sections belong to the same architectural concern and are reviewed as a unit; the consecutive-approvals threshold (3 → 2 under auto mode) governs tier-to-tier batching, not section-to-section within a tier. The HARD-GATE still applies — per-tier approval is required before writing files, and the final commit gate fires only after the last tier is approved.

Distinct from the Small-deliverable carve-out (which consolidates SMALL designs into one message); this carve-out STRUCTURES LARGE designs into coherent tiers rather than requiring N sequential per-section round trips that the literal rule would otherwise produce. Tier names are free-form and should reflect the brainstorm's natural architectural arc (read/write/migration tiers, contract-changes/implementation/world-content tiers, scope-by-deliverable-type tiers, or any analogous domain-specific shape); the naming itself isn't load-bearing — the per-tier approval gate is.

**Stand-alone sub-tier carve-out**: within a tier, if one sub-section is substantially heavier than its siblings (e.g., introduces a new skill with full Process Flow / phase contracts, specifies a multi-phase data flow, or otherwise carries reviewable surface area comparable to an entire sibling tier), the sub-section MAY be presented as a stand-alone sub-tier with its own approval gate before the rest of the tier is presented. Announce the split explicitly on tier introduction (e.g., "Tier C contains five sub-sections; C.1 introduces a new skill with full phase contracts, so I'll present C.1 stand-alone before C.2-C.5 — redirect if you'd rather see all of Tier C at once") so the user can opt out at announcement time. Default remains: tier reviewed as a unit. The split-decision is operator judgment based on sub-section weight asymmetry within a tier; over-splitting (treating every sub-section as stand-alone) defeats the carve-out's tier-batching purpose, and under-splitting (treating a heavyweight sub-section as routine) forces the user to hold disproportionate review surface in working memory.

## Step 4 — Template-structured-deliverable carve-out

When the deliverable type per Step 5 has its own canonical template (tickets following `tickets/_TEMPLATE.md`; specs following `docs/spec-drafting-rules.md` or the default spec sections; skill files; brainstorming proposals following `archive/brainstorming/canon-addition.md` / `archive/brainstorming/create-base-world.md` patterns), the template provides the section navigation; the full draft may be presented as a single artifact for approval regardless of internal item count. Step 4's enumerated section list (Overview / Architecture / Key decisions / etc.) above is the discipline for `docs/plans/<>-design.md` deliverables; for template-structured outputs the template's own sections substitute, and the per-section approval gate maps onto the consolidated draft (one approval covers the whole template). Distinct from the Small-deliverable carve-out (≤4 decisions, any deliverable type) and from the Multi-artifact-bundle carve-out (≥5 substantive deliverables → tiers); this carve-out covers the common case of a single template-structured deliverable with many small atomic line-items inside it (e.g., a ticket whose §What to Change has 6–8 numbered sub-changes that don't decompose naturally into the Step 4 section list). The HARD-GATE still applies — explicit user approval of the consolidated draft is required before writing the deliverable file.

## Step 4 — Multi-deliverable triage navigation

For triage brainstorms producing **≥2 deliverables** (no upper bound), apply the Template-structured-deliverable carve-out per-deliverable — each spec / ticket / proposal is approved as a single consolidated draft using its own template's sections. Triage approval (per Step 3 §"For triage/analysis brainstorms" and §Triage approval-with-modifications in `triage-workflow-rules.md`) covers all N deliverables together; no per-deliverable approval gate fires, regardless of N. Combine with the Non-plan-mode fast-track below — and per that section's triage-brainstorm extension, the auto-mode condition is relaxed for triage brainstorms, so a non-auto-mode triage producing ≥2 template-structured deliverables qualifies when the other three conditions are met (≥85% confidence, triage recommendation approved with named open decisions, deliverable is template-structured) — fast-track and per-deliverable Template-structured carve-out compose, allowing all N deliverables to be written in one turn with a delta summary covering the batch.

Distinct from the Multi-artifact-bundle carve-out (which structures ≥5-deliverable batches into architectural tiers with per-tier approval): the Multi-artifact-bundle carve-out's per-tier approval rule applies ONLY to non-triage design presentations; triage-approved batches do not need tiering regardless of N — the triage approval already serves the per-batch gating purpose, and a triage producing 5+ substantive deliverables uses Multi-deliverable triage navigation, not Multi-artifact-bundle tiering.

**Companion-triage-file scope clarification**: companion triage files written under `deliverable-classification.md` §Input-complexity carve-out (or the ≥2-spec / ≥3-ticket triage-file rule) do NOT count toward this rule's ≥2-deliverable threshold — they're companions to the deliverable set, not members of it. The deliverable enumeration is `spec / ticket / proposal`, not `spec / ticket / proposal / triage-file`. A triage producing 1 spec + 1 companion triage file remains a single-deliverable case for fast-track and approval-gating purposes; the more general §Non-plan-mode fast-track for template-structured deliverables (triage-brainstorm extension) below still applies and transitively covers both writes in one turn.

## Step 4 — Non-plan-mode fast-track for template-structured deliverables

When all four conditions are met — auto mode is active, initial confidence is ≥85%, a single approach has been approved with named assumptions covering remaining gaps (per Step 1 sub-step 5's directed-design carve-out), AND the deliverable is template-structured — the consolidated-draft approval may be collapsed with the approach approval. Present a delta summary or design rationale in the same turn as the file write, treating approach approval as transitively covering the consolidated draft. The user can redirect the rewrite delta or the write itself before the next assistant turn, preserving alignment without a separate approval round-trip. This is the non-plan-mode counterpart to the Fast-track plan-mode flow rule in `confidence-emission.md` §Plan-mode fast-track interactions; both rules acknowledge that when the approach has been approved with named assumptions, the consolidated draft is a refinement of the approved approach rather than a new design surface. The HARD-GATE remains satisfied by approach approval; the Template-structured-deliverable carve-out's standing requirement (explicit user approval of the consolidated draft) is met transitively.

**Triage-brainstorm extension**: for triage/analysis brainstorms (per Step 3 §"For triage/analysis brainstorms"), the auto-mode condition is not required — triage-recommendation approval transitively covers the consolidated-draft write in any mode, because the triage recommendation already served as the Step 3+4 design presentation and the template-structured deliverable (spec / tickets) is its faithful expansion rather than a new design surface. The other three conditions still hold (≥85% confidence, triage recommendation approved with named open decisions, template-structured deliverable). The auto-mode condition remains required for the non-triage approach-selection case, where the consolidated draft is the first time the user sees the full design surface.

**Material-deliverable-shape check still fires before same-turn write**: even when the four conditions (or the triage-brainstorm-extension's relaxed three) are met, the material-deliverable-shape forks check from SKILL.md Guardrails §User pre-authorization patterns is not bypassed by the fast-track — if any of forks (a)–(d) triggers (deliverable count crossing 1↔multi boundary; deliverable type changing class; ≥2x expansion in deliverable count under the same triage cycle; addition of a previously-unmentioned deliverable carrier, including mandatory-by-rule companion triage files for ≥2-spec / ≥3-ticket triages and `specs/IMPLEMENTATION-ORDER.md` becoming newly required for multi-spec output), prefer `AskUserQuestion` over named-assumptions to confirm the shape before write. The fast-track governs message flow (same-turn write is permissible); §User pre-authorization patterns governs whether confirmation is needed first; the two rules compose without subsumption, and the material-deliverable-shape check is the explicit gate that the fast-track's "same-turn write" framing must satisfy. Worked precedent: a triage brainstorm whose ChatGPT-Pro source proposal yielded 4 specs + `IMPLEMENTATION-ORDER.md` + a mandatory companion triage file under the fast-track satisfied fork (d) for the companion triage file; the operator proceeded with 5 named assumptions despite the rule, replicating the anti-pattern §User pre-authorization patterns' worked precedent already warns about. Cross-reference at this firing site prevents that recurrence by surfacing the gate where operators executing the fast-track will encounter it.

## Step 4 — Re-emergent interview during design

For complex deliverables (umbrella-spec amendments, multi-artifact triages, cross-spec reconciliations), specific design decisions sometimes surface during Step 3 approach selection or Step 4 design presentation rather than during initial Step 2 discovery. When the user asks a discovery-style question or requests enumeration of open decisions during Step 3/4 (e.g., "ask me the questions that need to be settled to amend SPEC-X"), conduct a constrained interview applying Step 2 rules (one question per message, prefer multiple-choice when answer space is bounded, name your uncertainty, respect user expertise, recommend an option when delegated). Label the questions for cross-referenceability (A, B, C, ... or numbered) so the consolidated decision registry that follows can cite them in the design presentation. The HARD-GATE still applies — implementation does not begin until the design (incorporating the newly-settled decisions) is approved. Distinct from Step 2's confidence-driven interview, which runs once before Step 3; this re-emergent form runs after design implications surface and the decisions it settles feed directly into the design rather than into approach selection.

## Step 4 — Mid-design term-clarification

When the user asks a clarifying question about a term or concept the assistant introduced in the design presentation (term-clarification, not discovery-style or enumeration-request), answer inline before continuing to the next tier or section. Use a self-contained explanatory mode (diagram, worked example, or short prose) appropriate to the term's scope. Do not collapse this into the §Re-emergent interview during design protocol above — term-clarification is one explanation, not a labeled-question sequence. Distinct from §Re-emergent interview during design (which fires when the user requests enumeration of open decisions or asks a discovery-style question requiring a constrained interview); term-clarification is a single-shot explanation of an already-introduced term that the design presentation under-defined. Common shape: the assistant uses a coined term ("finalize-emitted only", "stand-alone sub-tier") in design prose and the user asks "what do you mean by X?" — the right response is one explanatory paragraph or diagram, then continuing the tier/section flow.

## Step 4 — Mid-design scope-narrowing

When the user requests scope narrowing AFTER one or more design sections have been approved but BEFORE the design doc is written (or after — in which case update in place), recompute the design under the narrowed scope and announce the deltas before re-presenting. If the narrowing is consumer-enumeration-driven (per SKILL.md Step 1 sub-step 7 capability-expansion rule), name the dropped surface elements with re-evaluation triggers per the Out of Scope discipline — each dropped element should carry a concrete condition for re-evaluation (which consumer materializing, which validator finding, which authoring pain point) so a future audit or implementation pass can deterministically decide whether to lift the deferral. The design doc update lands in place (not as a new doc) unless the user explicitly asks for a fresh doc; cross-reference the narrowing rationale inline as a brief note at the top of the updated doc (typical form: "narrowed same-day after consumer-enumeration check confirmed only N Tier 1 consumers; see Out of Scope section for dropped items + re-evaluation triggers").

Distinct from §Re-emergent interview during design (which fires when the user requests enumeration of open decisions or asks a discovery-style question requiring a constrained interview) and from §Mid-design term-clarification (which is a single-shot explanation of an already-introduced term). Scope-narrowing addresses a different shape — the user accepts the architecture but requests reduced surface area, typically prompted by consumer-enumeration insight that arrived after design approval. The narrowing is NOT a register-shift (the chosen approach remains valid), so §Recovery/Reset register inheritance does not apply; the narrowing is also NOT a term clarification (no new term needs explaining). Treating it as either would mis-route the response.

Worked precedent: SPEC-45 brainstorm (2026-05-18) — full Phase 1+2 design (15-19 tickets) was presented section-by-section and approved across three batches (Overview+Architecture, Key Decisions+Data Flow+Edge Cases, Testing+FOUNDATIONS); user then surfaced the consumer-enumeration question ("what will be the consumers of this state provenance?"); investigation confirmed one Tier 1 hard consumer (story-fact-promotion-to-canon Phase 1 file-walk); user requested narrowing; design doc was updated in place to reflect 6-7 ticket scope with dropped items (5 → 3 edges, 3 → 1 MCP helpers, 0 → 0 context-packet surface augmentations) listed under Out of Scope with explicit re-evaluation triggers per dropped item; SPEC-45 spec was then authored against the narrowed design rather than the original.

## Step 4 — Recovery/Reset register inheritance

For brainstorms whose chosen approach represents a structural-correction register (Step 2 §Recovery/Reset Brainstorms-flavored, or user language emphasizing "fundamental change" / "pivot" / "rebuild" / "permanent source of brittleness"), Step 3's "Always include a radical option" discipline extends through Step 4's sub-scope decisions within the approved approach. Default each sub-scope decision to the most aggressive position consistent with the approach's register (atomize more rather than less; eliminate legacy surfaces rather than preserve them; simplify execution rather than gold-plate it); offer conservative alternatives as user-approveable fallbacks rather than silent defaults. A user-framed mid-Step-4 pushback that simplifies, expands, or radicalizes the scope is evidence that the initial presentation was mis-calibrated — treat it as a register-calibration signal, not a neutral revision event. This discipline applies to atomic sub-scope decisions (what to include, what to retire, whether to generalize) within a chosen approach; it does NOT override Step 3's approach-selection gate (a user who wants to switch approaches mid-Step-4 is signaling an approach-selection gap, handled by revisiting Step 3).

## Step 4 — Plan mode interaction

**If plan mode is active**: Per-section approval is replaced by whole-plan approval via `ExitPlanMode`. Present the key design decisions inline in the conversation before writing the plan file, so the user can course-correct before the plan is finalized. For complex designs, present in 1-2 messages, grouping related sections. Pause after the first message to check for course corrections before continuing. The goal is conversation-level checkpoints, not per-section gates. In plan mode, the confidence-reached announcement and approach proposal may be folded into the same message as the design presentation when the approach is architecturally constrained (single viable option).
