# Triage Workflow Rules

Supporting rules for triage/analysis brainstorms beyond the core structure in `triage-recommendation-structure.md`. Covers verification discipline, approval-with-modifications, decision reversal, pragmatic-softening, upstream commitments, question-labeling, multi-file implementation, and output-citation verification.

## Parallel-agent verification pattern

When the source report contains ≥5 specific codebase claims (file:line references, schema-field assertions, tool-existence claims, validator/op presence claims), prefer parallel Explore agents over sequential investigation — one agent per finding-cluster, each verifying its cluster's claims with verbatim quoting and line-numbered citations. The agents' verbatim reports satisfy §Output-citation verification's agent-delegated-reads clause for any file:line references the deliverable later persists from those reports. Parallel agents scale linearly with finding count; sequential investigation degrades non-linearly because the operator's working memory must hold cross-cluster context that a fresh agent doesn't need. Distinct from Step 1 sub-step 7's general "Launch Explore agents for broad surveys" guidance (which covers context exploration for the interview): this rule is triage-specific and tied to source-report-claim verification at hypothesis granularity rather than broad surveys.

Worked precedent: a triage brainstorm on an 11-finding seventh-iteration audit report spawned seven parallel agents (one per finding cluster + one for machine-layer survey); the agents returned verbatim quotes covering ~30 file:line citations that the resulting spec + companion triage file persisted directly, without requiring per-citation operator re-verification.

## Schema/contract-claim verification before triage emission

When the triage recommendation introduces schema enums, axis values, field shapes, validator predicates, op-kind names, hook semantics, cost or scope estimates used to rank approaches or to justify a recommendation between options, or any structural or quantitative claim about the codebase that goes beyond what the source report asserts and is used to justify a verdict's modification scope OR a recommendation's ranking among approaches, verify each such claim against the source (Read the schema/contract file, grep the cited enum/predicate, live-grep the affected import sites, or sample the affected files to confirm sync/async coherence / count / shape) BEFORE emitting the triage. Agent-delegated verification (per §Output-citation verification's agent-delegated-reads clause) satisfies the requirement when the verifying agent's report contains the verbatim quote.

This is the symmetric output-side rule for the input-side §Diagnostic/analysis reference files verification of source-report claims at Step 1 sub-step 1: input-side verification catches misleading claims the operator inherits from the source; this rule catches misleading claims the operator authors into the triage. Both are especially load-bearing under §User pre-authorization patterns (Guardrails), where the triage recommendation is the user's only pre-write checkpoint and an unverified claim propagates into a pre-authorized deliverable without further review. Distinct from §Parallel-agent verification pattern above (which prescribes the verification METHOD for source-report claims at ≥5-claim thresholds — the present rule covers the symmetric operator-introduced surface regardless of claim count) and from §Output-citation verification below (which fires before persisting the deliverable rather than before emitting the triage; the present rule is the prevention, the output-citation rule is the backstop when the triage-time check misses). Verifying an operator-introduced schema claim costs ~30 seconds; the cost is amortized across the modification-scope fields the verification would otherwise propagate into unverified.

Worked precedent: a triage brainstorm's accept-with-modification verdict introduced a claim about `SREL.axis ∈ {factional, hierarchical, institutional-adjacent values}` to justify an institutional-propagation cue extension; the SREL.axis enum is actually 14 strictly-interpersonal values (`trust` / `fear` / `desire` / ... / `hostility`) with no factional or institutional axis (verified at `.claude/skills/_shared-templates/story-state-contract.md` §4.4b); the user pre-authorization activated on the triage with this wrong claim, and only §Output-citation verification at spec-drafting time caught it before the spec persisted the wrong design. The triage-time check would have caught it before user-facing emission.

## Triage approval-with-modifications

When the user approves the triage shape but supplies one or more refinement clarifications (fold deliverable X into deliverable Y, change deliverable type, drop a dismissed item, add a follow-up consideration, soften or sharpen scope on a specific item), treat the response as approval under the refined shape. Recompute deliverable counts (and the Step 5 triage-file threshold and any deliverable-type-conditional rules), then proceed to Step 4 / Step 5 under the refined shape without re-prompting for full triage approval. Distinct from approach-selection challenge (which redoes Step 3 from first principles per the "If the user challenges an option's dismissal" rule) and from constraint-clarification on a non-triage approach proposal (which is governed by the "If the user clarifies a constraint or assumption" rule) — triage refinement clarifications sharpen the approved triage rather than reject it, parallel to the approach-clarification shape but applied at the triage gate.

**Hybrid case — approach-selection producing a triage-shaped deliverable**: when a brainstorm reaches a triage-shaped deliverable (≥3 tickets, ≥2 specs, or a mixed batch — see `deliverable-classification.md`) via approach-selection (§Approach proposal) rather than triage-recommendation (§"For triage/analysis brainstorms"), the approach-clarification rules at §"If the user clarifies a constraint or assumption" AND this rule's recompute clause BOTH apply — they describe the same operational state (proceed under the refined shape without re-prompting) and produce the same outcome. Cite which assumption / clarification the user sharpened so the audit trail covers both paths.

Worked precedent: a brainstorm proposed Approach B with item 4 = "compact §3 across pages"; the user accepted Approach B but pushed back on item 4 citing an external-LLM cold-context constraint, simultaneously selecting the approach AND clarifying a constraint that re-shaped the triage's deliverable set (7 tickets, §3-reduction sub-deliverable dropped) — under the hybrid case rule, the operator proceeded to ticket authoring without re-prompting for approval, citing the sharpened assumption explicitly in the deliverable summary.

## Triage decision reversal — ripple-effect scan

When a user clarification REVERSES a triage item's recommendation (rather than refining it), scan the rest of the triage for items that were grouped with, rationalized against, or scoped relative to the reversed item. State explicitly which related items still stand under their own rationale and which need re-evaluation. Distinct from §Triage approval-with-modifications above (which sharpens an input the analysis already used through user refinement clarifications): a reversal flips a conclusion the analysis produced, and the rest of the triage may rest on the same flipped conclusion. Distinct from approach-dismissal challenge (which redoes Step 3 from first principles when the user disagrees with a conclusion) and from constraint-clarification (which adds precision to an input rather than reversing a conclusion).

Worked precedent: a triage grouped Fixes 1, 2, 5, 12 as "Tier 1 — critical for stated constraints" with shared rationale; the user's clarification reversed Fix 1 (drop the recommendation); the ripple-effect scan confirmed Fixes 2, 5, 12 still stood under independent rationale (they protected story-local engine state, not the world-canon surface Fix 1 had touched), preventing a silent cascade-drop.

**A single user response can carry both shapes.** When a refinement clarification promotes an item the triage recommended deferring (e.g., an out-of-report finding flagged as "flag only, don't action"), treat it as §Triage approval-with-modifications (recompute the deliverable scope) AND run this section's ripple-effect scan — the promoted item may have been rationalized-against relative to other triage items. Applying both is correct, not redundant; the "Distinct from" framing separates the rules' default cases, not their co-occurrence on one response.

## Pragmatic-softening disclosure

When recommending a softer form of a proposal than what the analysis supports, explicitly classify the softening: (a) **structural** — justified by problem shape (e.g., "not every fact-type carries this axis"); (b) **pragmatic** — justified by retrofit / migration / cost concerns on existing artifacts, OR by ongoing-maintenance-cost concerns on artifacts the brainstorm would introduce (e.g., "this workflow adds recurring attention surface without proportional value for this repo's shape"). Structural rationales focus on whether the proposal FITS the project's shape at all; pragmatic rationales focus on the COST of adopting or maintaining it.

The trigger fires at four sites:

1. The per-approach internal design choice (e.g., "use mechanism X instead of structurally-cleaner mechanism Y because Y would require touching every existing record").
2. The inter-approach recommendation when one approach is downweighted relative to another partly on retrofit / migration / cost grounds (e.g., recommending Approach 2 over Approach 3 because Approach 3's "blast radius across the pipeline is disproportionate" — that framing IS a pragmatic softening, regardless of whether Approach 3 is structurally superior).
3. Sub-scope decisions within an already-approved approach when the chosen sub-scope is the less-aggressive option among structurally-distinguishable alternatives (e.g., "preserve existing artifact granularity rather than re-author at the cleaner granularity, because re-authoring is expensive").
4. Deliverable-deferral decisions where one or more triaged items are routed to a follow-up spec / ticket / brainstorm partly on retrofit / migration / scope-doubling / cost grounds rather than included in the immediate deliverable (e.g., deferring a structurally-cleaner cluster of new validators to a follow-up spec because folding them into the immediate spec would roughly double its scope — `(pragmatic)` if the deferral rests on cost considerations the operator could revisit under different constraints, `(structural)` if the deferred surface is genuinely scope-distinct from the immediate deliverable).

When a deferral is BOTH scope-distinct AND cost-deferred, prefer the label that names the LOAD-BEARING reason the immediate spec doesn't include it — `(structural)` when the deferred surface is genuinely a separate spec the immediate one can't subsume regardless of cost, `(pragmatic)` when the cost is the only reason the immediate spec can't fold it in.

Present pragmatic softenings as user-approveable tradeoffs, not author-side decisions. The classification is an **extension** of the recommendation's 1-3-sentence justification budget, not a replacement — softening detection adds a clause; brevity does not displace disclosure. Pragmatic softenings tend to leak into new-scope (new worlds, new work) where the retrofit cost doesn't apply; disclose the leak so the user can apply scope-integrity pressure if they prefer paying retrofit cost for new-scope rigor. Structural softenings need no special disclosure — they're inherent to the problem.

**Worked contrast** — audit-failing form: `Approach 2. Approach 3 is correct in spirit but its blast radius across the pipeline is disproportionate to the problem.` (cost framed as author-side dismissal); audit-passing form: `Approach 2 — pragmatic softening: Approach 3 is structurally cleaner; recommended only because retrofit cost across <enumerated artifacts> is high. Under no-migration-constraint conditions, Approach 3 likely wins — flag if that constraint applies.` (cost named as user-approveable tradeoff).

### Extension to written deliverables

When the brainstorm produces specs, tickets, or a triage file, propagate the `(structural)` / `(pragmatic)` labels into the written outputs at the sites where the softening lands — typically the spec's "Risks & Open Questions" section (each pragmatic risk noted as `(pragmatic — <reason>)`), the triage file's "Dismissed items" section (each dismissal reason tagged `(structural)` or `(pragmatic)`), and the triage file's "Deferred to follow-up specs" / "Deferred to follow-up tickets" sections (each deferral reason tagged `(structural)` or `(pragmatic)`, parallel to the dismissed-items convention — site (4) softenings land here). The conversation-time disclosure is the prevention; the written-deliverable label is the audit-trail backstop that survives to future readers. Without the propagation, a future reader reviewing the deliverable sees only the reason ("too complex for v1") without the label that distinguishes "structural — inherent to problem" from "pragmatic — would be revisited under different cost conditions"; the latter signals a re-evaluation candidate when constraints change, the former signals a settled design choice.

**Verdict-category applicability**: the `(structural)` / `(pragmatic)` tag applies to `reject` AND `defer` verdicts whose rationale is a softening choice (the operator chose to dismiss or schedule-out rather than recommend immediate inclusion); structural rejections and structural deferrals may carry the tag for parallelism with pragmatic ones but are not required to. `defer` verdicts especially benefit from the tag — pragmatic deferrals (scope-doubling, retrofit cost) signal re-evaluation candidates when constraints change, while structural deferrals (the deferred surface is genuinely scope-distinct) signal settled scope-partitioning. `confirms-existing-position`, `already-resolved`, and `refuted-by-verification` verdicts (per `triage-recommendation-structure.md` §Verdict types) are not softening choices — they align with prior project decisions or record a verification outcome rather than dismissing or deferring a recommendation — and do not need the tag.

## Upstream-commitment check

When an approach proposes modifying a surface that the explored references explicitly document as `verbatim` / `unchanged` / `inlined from canonical source X` / `not regenerated per instance` / `kept in sync with sibling Y`, flag this in the approach's tradeoff section before recommending. Format: `Upstream commitment: <source-file>:<line-range> commits this surface as <verbatim|canonical|unchanged>. Confirm whether the commitment is operational (workflow constraint forces verbatim — e.g., external-LLM cold context, sibling-skill cross-load) or stylistic (was verbatim by convenience and can be relaxed) before recommending the modification.` Distinct from §Pragmatic-softening disclosure (which acknowledges retrofit cost on a strictly-cleaner option) and from the FOUNDATIONS-alignment check at the top of Step 3 (which checks canon-related approaches against Rule 1-7): upstream-commitment check fires when the proposed change directly contradicts a documented commitment in the explored material, regardless of whether the topic is canon-related.

**Why**: the audit-trail anchor function of Step 1 sub-step 1's summary requirement assumes the operator NOTICED commitments documented in the explored material; without an explicit check at approach-proposal time, a documented-as-verbatim commitment can be in context yet still get proposed-for-modification, forcing user pushback and a Step 3 round-trip.

Worked precedent: a brainstorm proposed compacting §3 Prose Craft Contract across page plans, contradicting `.claude/skills/_shared-templates/page-plan.md:11-14` which explicitly commits §2 / §3 / §19 as `inlined verbatim from reports/prose-quality-instructions.md`; the operator had read the canonical template during exploration but did not run an upstream-commitment check at approach-proposal time, so the contradiction reached the user who pushed back with the operational constraint (the external prose renderer has no cross-plan state). Catching this at approach-proposal time would have prevented the round-trip.

## Question-labeling discipline for approval asks containing numbered items

When the triage, approach list, or design contains numbered items (fixes, recommendations, options, items in a triage tier table), do NOT label judgment-call questions with bare numbers ("Question 1", "Question 2"). Use letters (Question A / Question B) or topic-prefixed labels (`Q-mode-scoping:`, `Q-content-policy:`) so the user's reply can't conflate question-number with item-number. Collision is maximal when the question is about ONE of the numbered items (e.g., a question about Fix 19's scope) — the user's `1)` reply may then refer to either your Question 1 or to Item 1 in the underlying triage, and the assistant has no reliable way to tell which. Disambiguating labels remove that ambiguity at the labeling layer rather than at the response-parsing layer.

## Partial-answer / question-conflation handling

When the user's reply to a multi-question approval addresses only some questions, OR appears to interpret a question as about a different topic (e.g., conflating "Question 1" with "Item 1" in the triage), do NOT proceed under defaults for the un-answered or misinterpreted questions. Acknowledge what was answered cleanly, identify what is still open or appears to have been misinterpreted, and re-ask only the open questions in the next message. Distinct from §Triage approval-with-modifications: that rule covers refinement of approved triage shape; partial-answer covers literal absence of answer for one or more sub-questions in the same approval round, or conflation of one question with a different topic. Pairs with the question-labeling discipline above — well-labeled questions reduce conflation incidence; partial-answer handling addresses the residue when conflation still occurs.

**Whole-batch deferral/rejection.** A related shape: when the user defers or rejects an *entire* question batch (rather than partially answering it) to supply clarifying context first, do not proceed under defaults — ask what they want to clarify, treat the supplied context as a constraint-clarification or an option-dismissal challenge (routing to the Step 3 §"If the user clarifies a constraint or assumption" and §"If the user challenges an option's dismissal" rules respectively), then reformulate and re-ask the still-open questions. Distinct from the partial-answer case above (which handles a literal partial answer to the batch); whole-batch deferral supplies no answer at all and instead sharpens the input the questions rest on.

## Output-citation verification

Before persisting any deliverable that cites specific FOUNDATIONS section headings, file:line references, contract section IDs, or sibling-skill conventions by name, verify each cited reference against the source (Read the target file or grep the cited section heading).

**Agent-delegated verification** (e.g., an Explore-agent that quotes the cited content verbatim with file:line references in its report) satisfies the verification requirement when the agent's report contains the verbatim quote of the cited content — the agent's quote is the auditable evidence, parallel to Step 1 sub-step 3's §Read-satisfaction rule for input reads. Direct Read or grep remains required when the operator persists a citation whose verbatim form is NOT present in any agent report in the current session. Verifying a citation costs ~30 seconds; verifying the citation set for a full spec or triage is bounded by the size of the cited set. Unverified output citations are durable defects that propagate until a future reader notices them.

This rule is parallel to Step 1 sub-step 1's INPUT-claim verification rule (the **Diagnostic/analysis reference files** sub-bullet) for the source report AND to §Schema/contract-claim verification before triage emission above for operator-introduced claims in the triage recommendation: INPUT verification catches misleading claims the operator inherits from the source; the triage-time rule catches misleading claims the operator authors into the triage before user-facing emission; the present rule catches misleading citations the operator authors into the persisted deliverable as a backstop when the triage-time check missed.

**Sibling-precedent citation** extends across two source classes: (a) **sibling spec** — the operator read a completed sibling spec in this session that cites the same FOUNDATIONS section name in a published FOUNDATIONS Alignment table; (b) **sibling-skill SKILL.md FOUNDATIONS Alignment table** — the operator read a sibling skill's SKILL.md in this session (most Category 2 / 2b / 2c / 3 skills publish a FOUNDATIONS Alignment table mapping principles to skill phases) and the table cites the same FOUNDATIONS section name by name. Either source class satisfies verification for the cited section name, with the caveat that the sibling artifact could itself have drifted from FOUNDATIONS.md between its authoring and this session. Bare in-prose mentions of canonical section names in shared templates (e.g., `.claude/skills/_shared-templates/*.md`) outside a published FOUNDATIONS Alignment table are WEAKER precedent and still require direct FOUNDATIONS verification when the cited section is load-bearing for a MEDIUM-or-higher-severity claim in the deliverable — the distinction is between alignment-table precedent (machine-checkable structure that maps principles to phases) and prose-mention precedent (where context can be mis-read). Prefer direct verification when the FOUNDATIONS read is already in scope; sibling-precedent citation (either source class above) is the satisfying source when Step 1 sub-step 3's triage-brainstorm carve-out has skipped the FOUNDATIONS read AND the citations would otherwise require re-reading the source the carve-out skipped.

## Multi-file triage implementation discipline

When triage produces edits across multiple files (typical for canon-pipeline-proposal modifications, multi-spec amendments, or architecture-amendment cascades), apply these conventions:

### 1. Task tracking

For triage implementations producing edits OR creates across ≥3 files (file-create operations count toward the threshold equally with file-edits — both produce silent-spinner periods that per-file tracking interrupts, and both produce per-file audit-trail entries the user can scan after the fact), create one TaskCreate task per file at implementation start, mark each `in_progress` when beginning that file's edits, `completed` when the file's edits are done. This makes the user-visible spinner reflect actual progress through the triage rather than going silent for the duration of the implementation, and creates an audit trail the user can scan to see which files have been touched. For triage implementations spanning only 1-2 files, task tracking is optional — the per-file granularity is too coarse to justify the ceremony.

**Composition with Step 4's small-deliverable carve-out**: task tracking is also optional when Step 4's small-deliverable carve-out applied (≤4 design decisions, bounded-sequence implementation) AND each file edit is itself a small bounded operation (single Edit / Write / one-shot install / short shell command) — inline progress prose announced per file or per phase serves the audit-trail purpose without per-file TaskCreate ceremony, and the spinner-reflection function is served by the bounded operation count rather than by task transitions. The rule remains mandatory for genuinely silent-spinner cases (long-running edits, multi-step per-file workflows, single file edits whose completion spans minutes of internal work).

Worked precedent: a 4-finding mechanical-fix triage producing edits across 6 files (2 docs + 1 source + 1 test + 1 lockfile + 2 new scripts) where each file's edit was a single Edit/Write call plus one `npm install` — Step 4 small-deliverable carve-out applied, all six operations bounded, inline progress prose announced each fix; per-file TaskCreate would have added ceremony exceeding its spinner-reflection value, and the harness's system-reminder nudges during this batch were the empirical signal that the literal ≥3-file rule lacked a composition with the small-deliverable carve-out.

### 2. File-by-file ordering

Apply edits file-by-file, not finding-by-finding. Within each file, apply edits top-to-bottom. File order should follow dependency: files defining schemas / templates / vocabularies first, files consuming them later. This minimizes (a) re-opening the same file across non-adjacent finding numbers, (b) `old_string` collision risk when a finding's edit in file A creates text that another finding's `old_string` in file B was constructed from in memory rather than from a fresh Read, and (c) cognitive context-switching between files. Within-file edits MAY be batched in parallel Edit tool calls when each `old_string` is unique and non-overlapping, per the same discipline skill-audit applies during user-directed follow-up implementation.

### 3. Cross-file legacy-string sweep

When implementation involves renaming a term, restructuring a schema field, or replacing a vocabulary across multiple files, after applying primary edits per file run a single cross-file grep sweep for ALL old-vocabulary tokens (rename targets + their plural / adjective / hyphenated / compound variants + any related phrasing the triage implies). Apply remaining residues immediately. Do NOT mark implementation complete until the sweep returns clean for all renamed tokens. The sweep is procedurally required, not optional — it catches the long-tail residues that per-file editing misses, especially in LLM prompts, acceptance tests, and example tables that paraphrase rather than directly cite the schema being renamed. Parallel to skill-audit's §Cascade edits Cascade-scan discipline for terminology renames during user-directed implementation; consult that section's "search for semantic variants, not just exact strings" guidance when constructing the sweep's grep patterns.

### 4. Authoring-time site enumeration for vocabulary-affecting triages

When a multi-file triage's primary edit operates on a vocabulary (deletion, rename, restructure) — whether the triage produces tickets with `Files to Touch` lists OR in-place edits with an approved site list inline — live-grep the affected tokens (and their semantic variants per sub-rule 3's grep-shape guidance) BEFORE finalizing the approved site set. The deliverable should land with an exhaustive site enumeration so the user does not have to authorize scope-expansion mid-batch. This is the authoring-time counterpart to sub-rule 3's implementation-time sweep — sub-rule 3 catches old-vocabulary residues during implementation; this sub-rule catches site-list under-enumeration during authoring. Both serve the same audit-trail goal: deliverables that match the actual change surface, not a partial view of it.

**External-enumeration adoption sub-case**: when the triage adopts an external site enumeration (from a spec deliverable's own enumeration, a prior triage file, a source-report finding-list, or any other authoring artifact), re-run the underlying semantic-variant grep before finalizing the approved sites — the external enumeration may have used narrower vocabulary patterns (literal-string criteria only) than the user's principle covers, and adopting it verbatim defers residue detection to post-implementation sweep where same-skill residue requires inline operator judgment and cross-skill residue forces approved-scope expansion mid-implementation. Catching this at authoring time prevents the user from having to authorize scope-expansion mid-batch and forces re-calibration of subsequent deliverables in the batch under the expanded discipline.

### 5. Mid-implementation user edits to written deliverables

When the system surfaces a `<system-reminder>` indicating the user has modified a previously-written deliverable in the batch (or a sibling artifact like the triage manifest), treat the user's edit as a binding sub-correction. Adopt the implied discipline (expanded scope, refined assumption, relocated path, archived status) into subsequent deliverables in the batch without re-prompting; surface the adopted change in brief inline prose at the start of the next deliverable's task so the audit trail reflects the adaptation. Distinct from §Triage approval-with-modifications (Step 3, fires at the triage approval gate when the user clarifies the triage shape), §Triage decision reversal (Step 3, fires when the user reverses a triage conclusion), and §Deliverable pivot (Step 5, fires when the user redirects deliverable TYPE). This rule fires when the user sharpens an already-written deliverable's content while the rest of the batch is still being produced.

## When triage produces multiple deliverables

When triage produces **multiple deliverables** (N specs, N tickets, or a mix), the single triage approval gates all N — do not re-prompt for approval per deliverable. Each deliverable still independently satisfies its own format requirements (spec-drafting-rules.md for specs, `tickets/_TEMPLATE.md` for tickets), but no per-item user approval is required. The Step 6 Next Steps menu is presented once per triage, summarizing all N produced deliverables. For spec deliverables, `specs/IMPLEMENTATION-ORDER.md` (if the file exists; see `deliverable-classification.md` for fallback handling) gets a single update encompassing all N specs. When the deliverable count crosses the multi-deliverable triage thresholds (≥2 specs or ≥3 tickets), the Step 5 triage-file rule also applies — write `docs/triage/YYYY-MM-DD-<topic>-triage.md` once per triage, summarizing source/accepted/dismissed/follow-ups.
