# Brainstorm

Confidence-driven collaborative brainstorming. Interviews you until it understands what you **actually want** — not what you think you should want — then proposes approaches, builds a design, and lets you choose what happens next.

<HARD-GATE>
Do NOT write any code, scaffold any project, invoke any implementation skill, or take any implementation action until you have presented a design and the user has explicitly approved it. This applies to EVERY topic regardless of perceived simplicity.

(See Guardrails §User pre-authorization patterns for the contingent-authorization carve-out: when the user's initial request pre-authorizes a deliverable contingent on the brainstorm's verdict, presenting the triage-recommendation or design IS the HARD-GATE-satisfying approval — no separate post-presentation round-trip is required.)
</HARD-GATE>

## Process Flow

```
Read context (reference file + detect topic type)
         |
         v
Confidence-driven interview loop (target: 95%)
         |
         v
Propose 2-3 approaches with tradeoffs
         |
         v
Present design section by section, get approval per section
         |
         v
[If canon-related or story-canon-related] Validate against FOUNDATIONS.md
         |
         v
Write design doc to docs/plans/
         |
         v
Next-steps menu (user chooses)
```

**In plan mode**: design doc writes to the plan file instead of `docs/plans/`, and `ExitPlanMode` replaces the next-steps menu.

**Triage/analysis brainstorms**: the interview loop and the propose-approaches + present-design-section-by-section steps are replaced by a single triage recommendation — see Step 1 sub-step 5 (triage carve-out) and Step 3 §"For triage/analysis brainstorms".

## Step 1: Read Context

1. **Reference file**:

   **Trigger quick-reference** (the prose below is authoritative; this table is a fast path to the emit-timing anchor — match the request shape, then read the matching sub-case below):

   | Request shape | Summary-emit trigger |
   |---|---|
   | Pure file reference(s) only (`reference_path` arg or inline file path) | After the first read-batch that resolves the references |
   | Inline-pasted prose only (no file to read) | Before the first exploration read |
   | Both — mixed file + inline-pasted prose | Before the first exploration read (stricter trigger wins) |

   **Summary-emit timing (load-bearing)**: After the FIRST read-batch that resolves the user's core references, emit a 2-3-sentence summary of what they contain as user-facing text — BEFORE any further exploration (codebase exploration, FOUNDATIONS read, sibling-skill reads) and BEFORE the next tool call. Never defer it into a later analysis, classification, triage, or reassessment message; the early summary is the user's audit-trail anchor for verifying reference understanding before downstream work begins. When exploration unfolds across multiple read batches (codebase exploration interleaved with FOUNDATIONS reads, sibling-skill reads, example-artifact reads), the rule still fires after the first batch that resolves the core references — subsequent reads inform later analysis but do not restart or defer the summary. Multiple references read in one batch may share a single summary block. When a reference was read in chunks because it exceeded the Read tool's token limit (per the **Oversized files** sub-case below), the summary must also carry that sub-case's chunked-read coverage attestation — the chunk count plus an explicit full-coverage statement — not merely a line count, since a bare line count ("834 lines") implies completeness without audit-trailing that the read was chunked. For a multi-item reference report (a numbered finding-set, a tiered proposal list), the summary states the report's *shape* — item count, tier structure, executive position — in 2-3 sentences rather than enumerating each item; the per-item detail belongs in the triage recommendation (Step 3), not the summary. When the user's core reference is pasted directly into the request body as prose rather than supplied as a file (see the **Inline-pasted prose content** sub-case below), no read-batch resolves the core references, so the trigger's anchor shifts to "before the first exploration read" in place of "after the first reference-resolving read" — the never-defer-into-a-later-message prohibition is unchanged.

   - **`reference_path` argument**: If provided, read the entire file. Extract key claims, proposals, and open questions from it.
   - **Inline references**: If the user references files inline in their request text (rather than via the `reference_path` argument), treat those files as reference material with the same read-and-summarize treatment. Multiple inline references are common; read all of them. **Inline-pasted prose content**: when the user pastes the reference content *directly as prose in the request body* — external research output (ChatGPT / Claude / external-agent text), a report excerpt, a finding-set — rather than naming a file path or an inline file reference, there is no file to read: the content is resolved by reading the request itself. The summary-emit-timing rule above still applies, but its trigger has no reference-resolving read to fire after, so the summary fires BEFORE the first exploration read (codebase exploration, FOUNDATIONS read, sibling-skill reads), with "before exploration begins" as the anchor. Deferring it into a later analysis / classification / triage message is still forbidden. **Mixed-reference precedence**: when the request contains BOTH inline-pasted prose content AND file references (the common shape for triage/analysis brainstorms where a prior session's findings are quoted verbatim in the request alongside a named source report), apply the stricter trigger — the inline-pasted prose's "before first exploration" anchor takes precedence over the file reference's "after first read-batch" anchor. Emit the summary block BEFORE the first exploration tool call, covering both the inline-pasted content's shape (item count, tier structure, executive position) and the file reference's shape (the latter by name + line count + section structure derivable from a metadata-only check like `wc -l <path>` or section-header `grep -n "^##"` if the file is large; metadata-only checks are permitted as part of the pre-summary preparation since they do not constitute "exploration" in the rule's sense — exploration begins at the first content-resolving Read). After the summary block, exploration proceeds normally — but the summary anchor is established BEFORE any content-resolving Read fires. Worked precedent: a triage brainstorm whose request quoted SPEC-47's §Out of Scope content verbatim (inline-pasted prose) AND named `reports/new-story-structures-proposal.md` (file reference) deferred the summary entirely under ambiguous trigger interpretation; the explicit precedence rule above forecloses that deferral.
   - **Oversized files**: If a reference file exceeds the Read tool's token limit (currently 25000 tokens), read in sequential offset/limit chunks until the full file is covered, and note the chunked-read approach explicitly in the reference-file summary, naming the chunk count and a coverage attestation (e.g., "reference file read in 3 chunks of ~350 lines each; full coverage") so the audit trail records the read was complete. "Read the full file (N lines)" alone implies completeness but does not audit-trail the chunked-read approach — a future reader cannot distinguish a complete chunked read from a partial-read claim. Prefer a quick size check (e.g., `wc -l <path>` or `ls -lh <path>`) before issuing the first Read on a reference file you suspect may be large — this engages the chunked path on the first call rather than after a token-limit error, which is the empirically-observed friction pattern when the size is unknown at first-Read time. For files an order of magnitude larger where chunked reading is impractical, prefer a section-targeted approach: extract section headers via grep first, then read the sections most relevant to the brainstorm topic.
   - **Path resolution**: If a user-referenced inline filename does not resolve directly, glob the parent directory for the closest match (pluralization, hyphen drift, capitalization) before asking the user to re-specify. Announce the path correction inline (e.g., `Resolved 'post-pilot-retrieval-refinement.md' to 'post-pilot-retrieval-refinements.md' from globbed parent directory.`) whenever the resolved path differs from the user-typed string.
   - **Sibling skills**: If inline references include sibling skills (skills in the same pipeline or workflow), note their input/output interfaces (consumed/produced files, shared terminology, intermediate artifacts) and ensure the new design is compatible.
   - **Diagnostic/analysis reference files**: Treat claims about codebase state (e.g., "agent lacks profile X", "component Y is opt-in") as hypotheses to verify during codebase exploration (sub-step 7), not as established facts. Flag any claims that contradict what exploration reveals — communicate these corrections prominently to the user before proceeding to triage or approach proposal. For triage brainstorms specifically, `references/triage-recommendation-structure.md` defines where these corrections land — reframing corrections in the triage lead, the rest in the out-of-report findings sub-section.

2. **Topic classification**: Determine which category this brainstorm falls into:
   - **canon-related**: Designs that affect the world model itself or the canon-handling logic that operates on it — new pipelines, changes to how canon facts are validated/derived/scoped, new world-file types, modifications to invariants/ontology/relation handling, anything that produces or mutates `WORLD_KERNEL.md`, `ONTOLOGY.md`, or `_source/<subdir>/*.yaml` records (CF / CH / INV / M / OQ / ENT / SEC) per FOUNDATIONS §Canonical Storage Layer.
   - **story-canon-related**: Designs that affect story-bundle pipeline skills or the records they produce under `worlds/<slug>/stories/<slug>/_source/`.
   - **tooling-adjacent**: Project tooling that does not change canon semantics — CLI cosmetics, doc generators, build/test scripts, dev ergonomics. **Tie-break — tooling work that touches canon-handling logic**: when tooling work (MCP retrieval, validators, hooks operating on canon records, contract docs governing canon storage) does not itself produce or mutate canon records but operates on the surface that does, classify as `canon-related` — not `tooling-adjacent` — so the sub-step 3 FOUNDATIONS-read guidance engages. Parallel for story-canon: tooling work that touches story-handling logic classifies as `story-canon-related`. **Tie-break — content-generation-pipeline tooling**: validators, schemas, or retrieval (MCP) operating on content-generation-pipeline artifacts — character proposals/dossiers (NCP / NCB / CHAR), diegetic artifacts, or story-bundle content — that feed `canon-addition` classify as `canon-related` (story-content tooling as `story-canon-related`), even though those artifacts are not themselves `_source/` canon records, so the sub-step 3 FOUNDATIONS-read guidance engages (the deterministic-vs-LLM-judgment boundary and §Tooling Recommendation are load-bearing for such work). This mirrors skill-audit's Category 2b / 2c (canon-reading / story-pipeline content-generation) in `.claude/skills/skill-audit/references/cross-skill-consistency.md` §Skill Category Classification.
   - **non-implementation**: No code changes — process, workflow, strategy, skill design, tooling configuration. A brainstorm *about* pipeline machinery — reconciling existing specs / tickets / triage files that govern a pipeline, rather than producing or mutating world records, story records, or pipeline skills — is classified here. **Tie-break — triage producing a *new* spec or tickets governing a pipeline**: a triage/analysis brainstorm whose deliverable is a *new* spec or tickets governing a canon- or story-canon pipeline is classified by **subject matter** (`canon-related` / `story-canon-related`) — not `non-implementation` — so the sub-step 3 FOUNDATIONS-read guidance engages.

   After classifying, state the classification to the user — a single short sentence when unambiguous, or a brief justification (2-3 sentences) when genuinely ambiguous.

3. **If canon-related OR if the topic directly concerns FOUNDATIONS.md principles**: Read `docs/FOUNDATIONS.md`. You will need it in Steps 3 and 4 to validate proposed approaches against canon principles. For tooling-adjacent topics (post-tie-break — CLI cosmetics, doc generators, build/test scripts, dev ergonomics), the FOUNDATIONS read is optional. For story-canon-related topics, FOUNDATIONS reading is RECOMMENDED but optional: read it when the design engages §Story Bundles or Rules 1 / 4 / 5 / 7, or when Phase 4.5 routing (story-canon → world-canon promotion) is in scope. **Read-satisfaction**: the Read requirement is satisfied by FOUNDATIONS content loaded into this session's context by any prior operation — direct Read tool invocation, prior-skill pre-flight, system-reminder injection, or agent-delegated reads (e.g., an Explore-agent verification pass that quotes FOUNDATIONS verbatim with section/line citations sufficient to populate Step 4's FOUNDATIONS Alignment table). Re-read only when content is not in context (compaction, context rotation) or when the audit-table cells need principle citations the prior load didn't surface. **Triage-brainstorm carve-out**: the Read may also be skipped when the brainstorm is a triage/analysis brainstorm AND the operator commits to not citing FOUNDATIONS principles in any verdict's rationale field — codebase / contract grounds suffice for rationale. If a finding later surfaces a principle dependency, re-read at that point. Including a FOUNDATIONS Alignment table in the deliverable (per Step 4 §Sections to cover item 7) is a principle dependency under this clause — see `references/triage-workflow-rules.md` §Output-citation verification for the three satisfaction paths. A triage brainstorm whose deliverable IS a spec but whose verdicts rest on mechanical evidence (bug presence, code/contract drift, fixture rot, vocabulary inconsistency) qualifies for the carve-out — the spec's FOUNDATIONS Alignment section is verification, not verdict generation.

4. **Confidence calibration from reference material and request**: If the reference file provides a comprehensive design (rationale, decisions, structure, adaptation notes), set initial confidence based on how much of the problem space it covers. A thorough reference file may start confidence at 70-85%, reducing the interview to closing operational gaps. The same calibration applies to the user's initial request text — if the request includes detailed problem analysis, specific evidence, root cause identification, and a clear ask, calibrate initial confidence from the request itself, not just from reference files. If the user's request includes root cause analysis, proposed solution, code locations, and FOUNDATIONS justification, set initial confidence to 85-95%. The interview becomes a gap-closing exercise (1-2 targeted questions about scope or edge cases), not a discovery process. Do not ask motivational questions ("what problem does this solve?") when the user has already demonstrated deep understanding of the problem. Research findings (sub-step 6) and prior conversation context also contribute to confidence by narrowing the solution space before the interview begins.

5. **Interview skip threshold**: If Step 1 exploration and research bring confidence to 95%+ before the interview starts, skip Step 2 entirely and proceed directly to Step 3. Announce the confidence level and note that exploration resolved all gaps. For the 85-94% case (directed-design carve-out / triage brainstorms), see `references/carve-outs.md` §Step 1 — Directed design question carve-out for the conditions under which the discovery interview is also skipped.

6. **External research**: If the topic requires domain knowledge beyond the codebase (academic algorithms, industry best practices, competing architectures, scaling solutions), launch research agents BEFORE the interview. The user's request may explicitly call for research or the problem may implicitly require it. Summarize findings for the user before asking interview questions. If codebase exploration (sub-step 7) produces a clear root cause with concrete code-path evidence, external research may be skipped even if the user suggested it. Note the skip decision when presenting findings. When external research has already been completed and supplied as a reference file (or pasted directly into the request body as prose per the **Inline-pasted prose content** sub-case in sub-step 1), the research-skip announcement is satisfied by the reference summarization step (sub-step 1) — no separate skip announcement is needed. Note any corrections the summarization surfaces explicitly, since those corrections are the empirical-findings equivalent that would otherwise have been announced from new research. If the user's interview answer explicitly requests research or reveals a domain that requires it, pause the interview to launch research agents before continuing.

7. **Project context**: Explore existing implementations relevant to the topic before starting the interview — this context informs better questions. For tooling/process topics, examine existing instances of the thing being designed. For codebase topics, check relevant files, specs, tickets, brainstorming proposals, or world files. Launch Explore agents for broad surveys when needed. For brainstorms triggered by frustration or repeated failure, also explore the history of attempted fixes — patterns of repeated remediation attempts, escalating complexity, or accumulated workarounds are signals that the approaches (Step 3) should include radical options (reset, strip, rebuild) alongside incremental fixes. For triage/analysis brainstorms whose input is a report or finding-set, explicitly check whether that report — or an earlier version of it — was already triaged into an existing spec, ticket, or `docs/triage/` file; if so, frame the current triage as a delta against that prior decision record rather than a fresh pass, so accepted items already implemented and items already deliberately rejected are not silently re-proposed. Additionally — even when the report itself was never triaged — scan `archive/specs/` (and `git log` for recently-merged specs) for sibling specs in the report's subject domain that may already have implemented or rejected some of its findings: recently-landed work can shift the baseline the report describes, so frame affected findings as a delta against that landed work rather than re-proposing already-implemented or already-rejected items. This is especially important when the user references recent merges or PRs, or when the report's claims postdate or run concurrent with in-flight pipeline work; it generalizes the additive-architecture `archive/specs/` scan immediately below to the triage case, where the report's findings can overlap just-merged specs even though no new record classes / fields / vocabulary are being added. For additive-architecture brainstorms (proposals that add new record classes / schema fields / vocabulary / pipeline stages), also scan `archive/specs/`, `archive/brainstorming/`, and `archive/plans/` for prior decisions about adjacent territory — particularly any work that was archived after rollback. For **capability-expansion brainstorms** (proposals that add new retrieval surface / schema fields / edge types / context-packet surfaces / shared library functions that downstream callers will read), explicitly enumerate the current and near-term consumers BEFORE proposing approaches. For each proposed surface element, name at least one concrete current or near-term consumer (skill name + phase, validator name + check, audit pattern + use case). Surface elements without a named consumer default to Out of Scope or to the audit-driven-backfill discipline (Approach C-style — incremental adds keyed to concrete consumer triggers; see Guardrails §YAGNI's operational test). The consumer enumeration is the empirical input to the approach scoring in Step 3 (which then surfaces consumer counts per approach via the Consumers annotation).

8. **Confidence checkpoint**: After all context reading is complete and before deciding whether to enter Step 2, announce the post-exploration confidence in one sentence (e.g., "Post-exploration confidence: ~90% — reference file is exhaustive, scope fully specified by user request"). Render the announcement on its own line or as a clearly separated single-sentence paragraph. See `references/confidence-emission.md` §Firing matrix for the full discipline across the five confidence-emission sites.

## Step 2: Confidence-Driven Interview

This is the core of the skill. Your goal is to reach **95% confidence** about what the user actually wants before proposing solutions.

### The Protocol

After each user answer, display a confidence block:

```
Confidence: X%
Gaps: [list of remaining unknowns]
```

Keep asking questions until confidence reaches 95%. Then announce: "I'm at 95% confidence. Moving to approaches."

The block format applies when the interview actually runs (1+ question) in a non-auto-mode session, OR whenever the interview runs 3+ questions in any mode. For auto-mode prose alternative (0-2 question interview), plan-mode transition markers, and the full firing matrix across all five confidence-emission sites including the canonical assumption format, see `references/confidence-emission.md`.

### Interview Rules

1. **One question per message.** Never ask multiple questions at once.
2. **Prefer multiple-choice questions** when the answer space is bounded. Open-ended is fine when it isn't. Use `AskUserQuestion` with labeled options for multiple-choice interview questions, approach selection, and section approval prompts when its schema is already available in the session. Inline numbered options are an acceptable fallback when AskUserQuestion is deferred. In plan mode, inline numbered options are preferred since the conversation flow is faster.
3. **Probe motivations before solutions.** Ask "What problem does this solve?" and "What happens if we don't do this?" before "What do you want built?" The user's first request often describes a solution, not the problem.
4. **Challenge premature specificity.** If the user jumps to implementation details early, ask why that specific approach matters. Often the constraint is softer than stated.
5. **Detect "should want" vs "actually want".** Watch for buzzword-heavy descriptions; over-scoped requests; vague success criteria ("it should be good" — probe for what "good" means concretely); solutions stated as requirements ("I need a microservice" — do they need a microservice, or do they need X capability?).
6. **Name your uncertainty.** When you display gaps, be specific: "I don't know whether this needs to handle edge case X" is useful. "I need more information" is not.
7. **Respect user expertise.** If the user gives a clear, well-reasoned answer, don't re-ask the same thing in different words. Advance.
8. **Handle delegation gracefully.** If the user says "I'm not sure" or "you decide," treat it as a delegation: re-evaluate the options against FOUNDATIONS.md and project constraints, present your reasoned recommendation, and advance confidence accordingly. Do not re-ask the same question.
9. **Verify user technical premises before acting on them.** When the user emits a technical premise that is load-bearing for the recommendation — claims about library deprecation status, version compatibility, feature presence, performance characteristics, external-tool behavior, or any factual assertion about external systems — verify the premise via package-metadata lookup (`npm view`, lockfile inspection), documentation check, or targeted codebase exploration before adapting the recommendation to it. The 30-second verification cost prevents recommending against a true premise the user momentarily mis-stated. Worked precedent: a triage-brainstorm re-delegation contained the premise "the mdast library is deprecated now"; `npm view unified deprecated` / `npm view remark-parse deprecated` returned empty (all packages current under active unifiedjs maintenance); correcting the premise before reassessing the options preserved the recommendation's analytic ground.
10. **Present empirical findings before asking questions.** When codebase exploration or simulation runs produce concrete findings (data tables, root cause evidence, confirmed/refuted hypotheses), present a concise evidence summary before the first interview question. Structure: hypothesis, evidence (table or list), verdict per hypothesis, then the question.

See `references/confidence-emission.md` for the Confidence Scoring Guide, Plan Mode Interview discipline, and full firing matrix.

### Early Exit

If the user says something like "just go" or "that's enough questions", respect it. Announce your current confidence, list remaining gaps as assumptions you'll make, and proceed to Step 3. Mark those assumptions explicitly in the design so the user can correct them.

### Recovery/Reset Brainstorms

When the brainstorm is triggered by frustration indicators ("huge mistake", "wrong approach", "start over", "strip everything", "remove all"), adjust the interview:

1. **Validate the diagnosis before accepting it.** The user may be catastrophizing after a bad run, or missing that the system is more salvageable than they think. Present what exploration revealed — both what's broken AND what's working — before agreeing with a scorched-earth instinct.
2. **Focus confidence on "what's actually broken?"** before "what's the fix?" The confidence target shifts from requirements discovery to failure-mode agreement. Key gaps to close: is the problem structural (architecture) or tactical (configuration, content design, missing inputs)? Is the user's frustration proportional to the evidence?
3. **Always include a radical option.** When proposing approaches (Step 3), ensure at least one option represents the user's most aggressive instinct (strip, delete, rebuild). Even if you recommend a less radical path, validating the radical option as a real choice respects the user's judgment and prevents the feeling of being talked out of something.

## Step 3: Propose Approaches

Present **2-3 distinct approaches** with:

- **Name**: A short descriptive label
- **How it works**: 2-4 sentences
- **Tradeoffs**: What you gain, what you give up

After listing the approaches, close with a recommendation: name the chosen option upfront, then justify in 1-3 sentences. The recommendation is a global decision (which option to take), not a per-approach attribute — keep it out of the per-approach bullet list.

**Sub-variant splitting.** When an option's `How it works` describes two-or-more internally distinct paths with materially different costs / risks / blast radius, split into sibling options or labeled sub-rows (`C1`, `C2`, ...) rather than bundle under one option. A user's selection of an ambiguous option forces an immediate clarification round; sub-variant splitting at presentation time absorbs that cost into authoring rather than deferring it into a re-prompt.

**If canon-related or story-canon-related** (not tooling-adjacent): For each approach, note which FOUNDATIONS.md principles it aligns with or tensions it creates. Use format: `Foundations: <principle name> (aligns), <principle name> (tensions — [reason])`.

**If capability-expansion** (per Step 1 sub-step 7 capability-expansion rule): For each approach, annotate `Consumers: N verified (<consumer-list>), M speculative (<deferred-consumer-list>)` using the consumer enumeration produced at Step 1 sub-step 7. An approach that surfaces N tickets for fewer than N/3 verified consumers is presumptively over-scoped and should be ranked accordingly in the recommendation — the consumer count is load-bearing for the trade-off analysis, not decorative metadata. The N/3 heuristic is a starting point; adjust based on observed brainstorm outcomes.

**If the problem space is fully constrained** (e.g., a reference document provides a proven design, or requirements eliminate alternatives), present a single approach. Include a one-sentence rationale on the same turn that explicitly names the constraint that narrows the solution space. Do not invent artificial alternatives. In plan mode with a single viable approach, the rationale may be embedded in the plan file's Context section rather than presented as a separate conversational step.

**For triage/analysis brainstorms** where the deliverable is a set of work items (tickets, specs, or in-place doc / governance-doc edits), the "approaches" step is replaced by presenting the triage recommendation: which items warrant action, which are dismissed, and why. The user's approval of the triage recommendation serves the same gating purpose as choosing an approach. For triage brainstorms producing a template-structured deliverable, the triage recommendation also serves as the Step 4 design presentation — Step 4's section-by-section gate does not run; see `references/carve-outs.md` §Non-plan-mode fast-track for template-structured deliverables (Triage-brainstorm extension).

**Pre-recommendation confidence anchor**: before emitting the recommendation, render Step 1 sub-step 8's post-exploration confidence announcement on its own line as the audit-trail anchor — see `references/confidence-emission.md` §Firing matrix.

**Recommended triage-recommendation structure**: structure each triage item with (i) **verdict** (one of the 7 types: `accept` / `accept-with-modification` / `reject` / `defer` / `already-resolved` / `confirms-existing-position` / `refuted-by-verification`), (ii) **rationale** (1-2 sentences naming the FOUNDATIONS / codebase / contract grounds), and (iii) the conditional sub-field (`modification scope` for `accept-with-modification` / `alternative path` for `reject` / `deferred_to` for `defer` / `verification source` for `refuted-by-verification`). Group items by verdict bucket; close with deliverable-shape recommendation + named assumptions. See `references/triage-recommendation-structure.md` for the full specification.

See `references/triage-workflow-rules.md` for: **parallel-agent verification pattern** (≥5 codebase claims → parallel Explore agents); **schema/contract-claim verification before triage emission** (operator-introduced claims in triage must be verified before user-facing emission); **triage approval-with-modifications** (refinement clarifications recompute deliverable counts without re-prompting); **triage decision reversal — ripple-effect scan** (clarification reversing a verdict triggers scan for rationale-coupled items); **pragmatic-softening disclosure** (four sites where structural vs pragmatic softening must be classified, with extension to written deliverables); **upstream-commitment check** (flag proposed modifications to surfaces documented as verbatim/canonical/unchanged); **multi-deliverable triage approval gating** (single triage approval covers all N deliverables; no per-deliverable re-prompting).

**If the user challenges an option's dismissal**, do a fresh analysis from first principles rather than defending the prior reasoning. If the new analysis reverses the dismissal, state explicitly where the prior reasoning was incomplete. A revised approach (e.g., phased combination) is a valid output of this re-analysis.

**If the user clarifies a constraint or assumption** (rather than challenging an option's dismissal or signaling a register shift — see Step 2 §Recovery/Reset Brainstorms), redo the approach proposal under the refined constraint without restarting Step 2. The user has sharpened the input to the trade-off analysis, not invalidated the discovery work; the prior interview state is preserved while the approach scoring re-runs. Cite which assumption was sharpened so the user can confirm the read. **Re-presentation depth**: when the constraint clarification does not change which approach wins, a brief confirmation paragraph naming the sharpened assumption and stating that the recommendation still holds is acceptable — full re-presentation of all 2-3 approaches is reserved for clarifications that flip the recommendation. If the constraint clarification eliminates one or more approaches but leaves the recommendation unchanged (the eliminated approaches were dominated under the new constraint; the recommended approach survives — typically with refinement that simplifies its form), brief confirmation also applies: name the eliminated approaches and why they fall away alongside the sharpened assumption. Full re-presentation is reserved for cases where the constraint flips the recommendation OR surfaces a previously-unconsidered approach that now dominates. Worked precedent: a design brainstorm presented Approaches A/B/C with C recommended (single-pass migration with `migration_attestation` precedent); the user clarified "no production stories exist", eliminating A (hard cut, new bundles only — class-gated validator dispatch is unnecessary without production state) and B (soft co-existence — co-existence window is unnecessary without legacy bundles) and simplifying C (the migration tool is no longer needed because there is nothing to migrate); Approach C survived as the recommendation in simplified form, so brief confirmation applied rather than full re-presentation.

For question-labeling discipline and partial-answer / question-conflation handling on multi-question approval asks, see `references/triage-workflow-rules.md`.

**Wait for user to choose or ask questions.** Do not proceed until the user picks an approach (or asks you to refine/combine).

## Step 4: Present Design

**Plan mode**: Skip per-section gates. Present key decisions in 1-2 messages with conversation-level checkpoints, then write to plan file. See `references/carve-outs.md` §Step 4 — Plan mode interaction.

**Classification pivot check**: If the design reveals a deliverable type that differs from the Step 1 classification (e.g., "tooling configuration" now requires a new world-file type, or a spec now includes live code changes), re-state the refined classification to the user before presenting Section 1 of the design. Downstream sections (testing strategy, FOUNDATIONS alignment) follow the refined classification.

Once an approach is chosen, present the design **section by section**. Scale each section to its complexity — a sentence for trivial parts, up to 200 words for nuanced parts.

Sections to cover (skip irrelevant ones):

1. **Overview**: What this design achieves in 1-2 sentences
2. **Architecture / Structure**: How the pieces fit together
3. **Key decisions**: Important choices and why
4. **Data flow / Process**: How information moves through the system
5. **Edge cases**: Known tricky scenarios and how they're handled
6. **Testing strategy**: How to verify this works (if canon-related, story-canon-related, or tooling-adjacent)
7. **FOUNDATIONS.md alignment**: Table of relevant principles and how the design respects them. Mandatory for canon-related and story-canon-related. Optional for tooling-adjacent — include when the design touches canon-handling logic, world-file persistence, canon-validation surfaces, or other concepts mapped to specific FOUNDATIONS principles; a 3-5 row table is usually sufficient. Omit when truly irrelevant (e.g., cosmetic CLI tweaks). Selection criteria: each row should state the principle, its stance (`aligns` / `tensions` / `N/A`), and a one-line rationale citing the specific design mechanism that honors or breaks the principle. Prefer 3-5 load-bearing rows over exhaustive enumeration. Omit principles that are merely not-violated — the default is non-violation, so only list principles the design actively engages (or actively tensions). **Use `N/A` as a defensive stance only when the principle's domain is one a reader would reasonably expect the design to engage (same FOUNDATIONS cluster, adjacent surface, similar topic) but the design intentionally does not — defensive disclosure beats silent omission in that case. Do not pad the table with N/A rows for principles outside the design's domain entirely.** **Citation-verification reminder**: cited section names in this table trigger `references/triage-workflow-rules.md` §Output-citation verification — if the Step 1 sub-step 3 triage-brainstorm carve-out skipped the FOUNDATIONS read at input, satisfy the verification either by re-reading FOUNDATIONS.md now, or by confirming each cited section name appears verbatim in a sibling spec's published FOUNDATIONS Alignment table OR a sibling-skill SKILL.md's published FOUNDATIONS Alignment table read in this session (sibling-precedent citation is satisfying only when the sibling artifact actually has the table — verify before relying on it).

Section names are suggestions. Rename or combine sections to match the topic's natural structure. The key requirement is per-section approval, not specific section names.

**After each section**, ask: "Does this section look right?" Wait for confirmation before presenting the next section. If the user pushes back, revise that section before continuing. For section-batching thresholds — default of 1 section per batch, expanding to groups of 2-3 sections after 3 consecutive approvals (or 2 consecutive approvals under auto mode), with single-message relaxation after 5+ consecutive approvals under auto mode — see `references/carve-outs.md` §Step 4 — Section batching threshold.

**Verify operator-introduced design premises before persisting them.** When the design names a specific field, file path, schema shape, or API surface from the codebase, verify the reference exists before incorporating it into the design document or spec. The 30-second verification cost (Read or grep the cited file or schema) prevents premise-falsification in the implementation phase. Parallels Step 2 Interview Rule 9 (which covers user-emitted premises) and the triage-workflow schema/contract-claim verification rule in `references/triage-workflow-rules.md` (which covers triage-time claims) — this rule extends the same discipline to operator-authored design content, where the premise enters the audit trail via the design doc or spec rather than via the interview register. **In directed-design / fast-track flows where the discovery interview is skipped** (Step 1 sub-step 5; `references/carve-outs.md` §Step 1 — Directed design question carve-out), the design is presented to the user *before* persistence, so the buffer between presentation and write that would otherwise absorb a post-hoc premise correction is gone: verify the codebase-surface premises the *presented* design rests on during Step 1 exploration (before presentation), not deferred to persist-time. Presenting a design that carries a hedged, unverified premise ("possibly a schema touch — I'll verify before writing") is the symptom this prevents — the premise should be resolved before the user reads the design, not after.

For the carve-out cluster — **small-deliverable**, **multi-artifact-bundle** (with stand-alone sub-tier sub-rule), **template-structured-deliverable**, **multi-deliverable triage navigation** (with companion-triage-file scope clarification), **non-plan-mode fast-track for template-structured deliverables** (with triage-brainstorm extension), **re-emergent interview during design**, **mid-design term-clarification**, **mid-design scope-narrowing**, **Recovery/Reset register inheritance**, and **plan mode interaction** — see `references/carve-outs.md`.

## Step 5: Persist the Deliverable

After design approval, do NOT apply changes or implement the design until the user selects an implementation option from the Step 6 menu. The design doc is typically the deliverable of this skill — implementation is a separate act that requires the user's explicit choice. Exception: for inline-implementation tasks (see the first deliverable category in `references/deliverable-classification.md`), the deliverable is the in-conversation design + post-execution summary, and no design doc is persisted.

**Quick triage** (find the matching shape, then read the corresponding bullet in `references/deliverable-classification.md` for the full rules):

**Worktree-root anchoring (load-bearing)**: every output destination in the table below is written relative — when invoked inside a git worktree, resolve each path against the **worktree root**, not the main repository root (per Guardrails §Worktree discipline). Construct the write path from the worktree root at write time, and after writing, confirm the file landed under the worktree root before presenting the Step 6 menu. This is the point of need: the persistence step is where the path is built, so re-anchor here rather than relying on the Guardrails reminder alone.

## Step 6: Next Steps Menu

Present the user with options for what to do next:

```
Design doc written to docs/plans/YYYY-MM-DD-<topic>-design.md

What would you like to do next?
1. Write an implementation plan (invoke writing-plans skill)
2. Create a spec from this design (write to specs/)
3. Start implementing directly
4. Done for now — I'll review the design doc later
```

Use AskUserQuestion when its schema is already available in the session. Inline numbered options (as shown above) are an acceptable fallback when AskUserQuestion is deferred. If the user picks an option that invokes another skill, invoke it. If they pick "done", end the session.

**If plan mode is active**: Call `ExitPlanMode` instead of presenting the next-steps menu. The user will direct next steps after approving the plan.

**If the deliverable category produces a post-deliverable-phase menu** (system spec, umbrella spec driving sibling amendments, triage producing ≥2 specs / ≥3 tickets, implementation tickets, new canon-pipeline proposal, or any deliverable whose Step 6 menu options describe post-deliverable-writing NEXT phases — reassess, decompose to tickets, implement, done — rather than the deliverable-writing itself): present the menu unconditionally, even when the deliverable was just written inline. For spec/ticket/proposal deliverables specifically, writing the file is PRE-implementation — the user has not yet directed reassess/decompose/implement, the menu's options ARE those named-next-phase choices, and skipping the menu silently strips the user's named options. The deliverable-categories enumeration above is authoritative for this rule; consult `references/deliverable-classification.md` for the per-category Step 6 menu templates. **Spec/ticket/triage deliverables carry mandatory summary-disposition lines beyond the four menu options** that the generic menu above has no slots for: surface the implementation-order disposition (`updated specs/IMPLEMENTATION-ORDER.md ...` | `skipped — file not present and below fresh-create threshold (<3 specs and no hard 2-spec dependency)` | `created fresh ...`) and the companion-triage-file disposition. **For a triage producing ≥2 specs or ≥3 tickets the companion triage file is mandatory** (per `references/deliverable-classification.md` §Triage-file composition / §Triage producing ≥2 specs or ≥3 tickets) — the disposition is `Companion triage file: <path>` with no decline option. The `declined — verdicts landed in spec §<sections>` disposition applies only at the *single-deliverable* count when the §Input-complexity carve-out fires (≥8 evaluated items in the source report) and you choose not to write the file. **The companion-triage-file disposition applies only when the spec/ticket deliverable arose from a triage flow.** When the deliverable is a directed-design brainstorm that produced a single spec (not a triage evaluating a report into deliverables), there is no companion triage file at all: emit `Companion triage file: N/A — not a triage flow` or omit the line entirely, rather than forcing one of the triage-framed dispositions above. **When the deliverable DID arise from a triage flow but produced a single spec/ticket from fewer than 8 evaluated items** (so the §Input-complexity carve-out does not fire and the triage file is skipped by default), emit `Companion triage file: skipped by default — triage flow producing a single deliverable below the ≥8-item carve-out threshold (<N> items evaluated); the spec + in-chat recommendation are sufficient history.` — do NOT borrow the `N/A — not a triage flow` phrasing, since this WAS a triage flow. The implementation-order disposition still applies in this case (a directed-design spec still updates or skips `specs/IMPLEMENTATION-ORDER.md`). Both triage dispositions are mandated by `references/deliverable-classification.md` — its `IMPLEMENTATION-ORDER.md`-absent and triage-file-declined cases each instruct you to note the decision in the Step 6 summary. Emit these disposition lines as prose preceding the menu; the menu itself may be inline numbered options or `AskUserQuestion` — inline is the natural fit for spec/ticket/triage deliverables because the disposition prose has no `AskUserQuestion` option slots and already breaks the AskUserQuestion-only flow, so the "use AskUserQuestion when its schema is available" preference above does not force the menu into option form here.

**Otherwise, if implementation was completed inline** (carve-out — applies only when the menu's options would be redundant with the just-completed work: skill-design deliverables where writing the SKILL.md IS the implementation; small inline ops/setup tasks where no further phase is contemplated; reconcile-existing-spec/ticket/triage-in-place deliverables where the edits ARE the completed work and no post-deliverable phase exists): skip the menu and summarize what was done. This carve-out and the post-deliverable-phase rule above are mutually exclusive — categorize the deliverable by the post-deliverable-phase enumeration first; the inline-completion skip fires only when the categorization places the deliverable outside that enumeration.

## Guardrails

- **YAGNI ruthlessly**: Remove unnecessary features from all designs. If a proposed approach has optional extras, strip them unless the user explicitly asked for them. Operational test for capability-expansion brainstorms (per Step 1 sub-step 7's capability-expansion rule): for each proposed surface element (new helper / field / edge / packet surface), name at least one concrete current or near-term consumer. Elements without a named consumer are "optional extras" under this rule and default to Out of Scope. Per-element consumer naming complements the Step 1 capability-expansion exploration rule by enforcing the same discipline at approach-authoring time, and composes with the Step 3 Consumers annotation by ensuring no approach reaches the recommendation step with un-justified surface elements.
- **One question at a time (discovery interview)**: During the Step 2 discovery interview, ask one question per message — never batch questions there. This is non-negotiable for the interview loop, but it does NOT restrict `AskUserQuestion`, whose multi-question schema (1–4 questions) is the sanctioned form for batching independent approach-selection, section-approval, or scope-narrowing decisions outside the discovery loop (per Step 2 Interview Rule 2).
- **No implementation before approval**: The hard gate at the top means exactly what it says (subject to the §User pre-authorization patterns carve-out below).
- **FOUNDATIONS.md is authoritative**: For canon-related and story-canon-related topics, if a proposed approach violates a Foundation principle, flag it immediately. Do not propose approaches that violate Foundations without explicitly calling out the violation and getting user sign-off.
- **Worktree discipline**: If working in a worktree, all file paths use the worktree root.
- **No scope inflation**: The design covers what was asked for. Resist the urge to add "while we're at it" improvements.
- **Respect early exit**: If the user wants to skip ahead, let them. List your assumptions clearly.
- **Blocker discovery during implementation**: If implementation reveals a worldloom limitation, architectural issue, or cost / scope re-estimate that blocks the brainstorm's deliverable OR invalidates the triage-time recommendation ranking among approaches, present the blocker (or corrected estimate), options, and recommendation. If the fix is small enough to do inline (< 50 lines of change AND does not change a public interface — package exports, schema fields, hook surfaces — AND does not require modifying a package other than the one being implemented in), fix it and continue. Otherwise — separate architectural concern, public-interface change, or cross-package modification — create a ticket and either (a) work around the limitation in the current deliverable with a documented constraint, or (b) implement the fix if the user approves the scope expansion. **For cost / scope re-estimates that invalidate triage-time ranking**: surface the corrected estimate, re-rank approaches under the new estimate, and re-prompt the user via `AskUserQuestion` if the rank changes; the audit-time prevention for cost-claim falsification lives at `references/triage-workflow-rules.md` §Schema/contract-claim verification before triage emission (the present rule is the recovery when audit-time verification missed).
- **Auto mode definition**: Auto mode applies to this skill when any of the following holds: (a) a system reminder contains "work without stopping for clarifying questions" or equivalent phrasing instructing continuous operation; (b) the user issues an explicit directive ("just go", "don't stop to ask", "proceed without questions", or analogous); (c) a harness-supplied `auto_mode: true` argument is set. Once detected, the brainstorm-internal relaxation rules at `references/confidence-emission.md` §Auto-mode prose alternative, `references/triage-workflow-rules.md` §Triage approval-with-modifications (named-assumptions + design-approval gate default), `references/carve-outs.md` §Step 4 — Section batching threshold (3 → 2 consecutive approvals + 5+-sustained-approval single-message relaxation), §Small-deliverable carve-out (auto-mode default), §Multi-deliverable triage navigation's fast-track composition condition, §Non-plan-mode fast-track for template-structured deliverables, and Guardrails §Auto mode interaction (below) all apply. The HARD-GATE at the top of the skill is never relaxed by auto mode. This definition is brainstorm-internal — sibling meta-tooling skills (skill-creator, mcp-integration-audit, etc.) carry their own auto-mode rules in their own contexts and are not bound by this definition.
- **Auto mode interaction**: Under auto mode, (a) present the Next Steps menu unless implementation was already completed inline, (b) approach selection and section approval gates still hold — auto mode does not bypass user alignment, (c) the batching threshold in Step 4 may shift from 3 to 2 consecutive approvals to reduce round-trips. The HARD-GATE at the top of the skill is never relaxed by auto mode.
- **User pre-authorization patterns**: When the user's initial request includes contingent authorization for the deliverable (e.g., "create a spec in specs/*", "write a brief if X holds", "implement if changes are warranted"), the HARD-GATE is satisfied by the triage-recommendation (for triage brainstorms) or design presentation (for non-triage brainstorms) — no separate post-presentation approval is required. The user has pre-authorized the deliverable contingent on the brainstorm's verdict; presenting the verdict is the moment that activates the pre-authorization. Distinct from auto mode (which is about skipping clarifying questions, not bypassing approval gates) and from `references/carve-outs.md` §Non-plan-mode fast-track for template-structured deliverables (which collapses approach-approval into the consolidated-draft write under specific conditions). When user pre-authorization AND the §Non-plan-mode fast-track triage-brainstorm extension BOTH apply (the common shape for triage brainstorms with pre-authorized deliverables), §User pre-authorization satisfies the HARD-GATE and §Non-plan-mode fast-track governs the message flow (same-turn write); the two rules compose and neither subsumes the other. Worked precedent: SPEC-35 triage brainstorm — user pre-authorized "create a spec in specs/*" contingent on the triage verdict; triage recommendation presented + named assumptions surfaced satisfied the HARD-GATE without a separate approval round-trip. The user can still redirect between triage presentation and the deliverable-write by issuing a counter-instruction; absent that, the pre-authorization is the approval. Pre-authorization satisfies the approval gate but does not preclude — and for a material-deliverable-shape fork actively calls for — a scope-narrowing `AskUserQuestion` before the write; see `references/triage-recommendation-structure.md` §Close-out decision tree — `AskUserQuestion` vs named-assumptions for the gap-shape × pre-authorization-state routing. **Exception — reversing a prior committed user decision**: when Step 1 sub-step 7's delta-framing reveals that the triage recommendation *reverses a decision the user themselves previously committed to* (a `docs/triage/` decision record, an archived-spec rejection, a finding deliberately rejected on stated grounds), pre-authorization does NOT extend to silently overturning that prior decision. Surface the reversal prominently AND pose a direction-confirmation `AskUserQuestion` (a substantive fork among the live options — e.g., proceed-with-reversal / honor-the-prior-decision / hybrid — not a bare approval ask) before writing the deliverable. Presenting the verdict still satisfies the HARD-GATE; this exception adds a confirmation gate specific to user-decision reversal, parallel to `references/triage-workflow-rules.md` §Triage decision reversal but firing when the operator's recommendation (not a user clarification) is the reversing force.
