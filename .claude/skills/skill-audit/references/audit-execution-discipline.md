# Audit Execution Discipline

These rules govern how Step 1 (Step 1a reads the target skill; Step 1b loads this reference) is executed and how all auxiliary tool calls — across the entire audit and any follow-up implementation — must be announced and batched.

## Read-satisfaction

The Read requirement is satisfied by in-context content from any prior operation in the current session — direct Read tool invocations, skill-invocation-embedded content (when the target skill was invoked earlier in the session and its full body was injected via that invocation), or system-reminder inclusions (parallel to Step 2's rule for alignment documents and Step 3's self-audit "re-read regardless of prior reads" rule). Re-read only when content is not in context (e.g., after compaction or context rotation) or when the in-context version is suspected stale. If the target skill was modified during the current session (via user-directed follow-up implementation from a prior audit, or any other in-session edit), re-read is mandatory. *The Edit-tool precondition for follow-up implementation is separate and stricter — see `references/follow-up-implementation.md` Common path step 3.*

## Path resolution

If the exact path does not resolve, glob for `<path>*/SKILL.md` (appending wildcard + `/SKILL.md`). If that also fails, try `<path>**/SKILL.md`. If exactly one match is found, use it and note the correction. If zero or multiple matches, stop and report the error.

## Auxiliary investigation (permitted, with required announcement)

Beyond reading the target SKILL.md, you may additionally: (a) list contents of the target skill's directory and of any directly-referenced sibling directories; (b) diff files against named reference sources when the target's text claims a reference-source relationship (e.g., "copy from skill-creator's own templates" — check whether those templates actually ship and whether sibling skills have drifted from them); (c) glob for shared-surface files (`archive/*/`, `brainstorming/*.md`, `worlds/*/`) when a potential finding hinges on their presence or naming. Each auxiliary investigation must support a specific hypothesis about the target skill's behavior — do not probe speculatively.

## Pre-finalization verification

Before finalizing any finding whose Suggestion or Skill-gap field claims that content is absent, missing, or undocumented OR mis-cites a specific location at MEDIUM or higher severity — phrasings like *"Add X"*, *"Document the missing Y"*, *"There is no documented Z"*, *"no fallback exists"*, *"the skill never mentions W"*, *"Tighten X at §Y"*, *"the cited §Z section says..."*, *"Update the wording at §Y"*, *"§Y currently reads..."*, plus pipeline-state absence claims like *"does not exist at HEAD"*, *"no hook/validator/op covers X"*, *"tools/<package>/ has no Y"*, *"<file-path> does not exist in the repo"*, *"not implemented at HEAD"* — verify the absence OR the location-citation by Read of the cited file or grep of the referenced section. When an audit-target SKILL.md prose CLAIMS a pipeline-state condition (e.g., the audited skill says `Hook 7 blocks the write` in declarative present tense), an audit finding whose premise depends on that claim's accuracy MUST verify the pipeline state at finalization time via fresh grep against the tool/file path — not rely on session memory of an earlier verification (e.g., a grep run earlier in the same session by a sibling skill like `/mcp-integration-audit`) that may have gone stale between the earlier verification and this audit's finalization. The two trigger families share the same audit-trail-defect failure mode: an absence claim that is wrong propagates into the implementation phase as a finding the executor cannot apply (the missing content is actually present), and a location-citation claim that is wrong propagates as a finding whose primary edit cannot land at the cited site (the content the audit Suggestion targets actually lives elsewhere). Both errors force premise-falsification recovery at implementation time per `references/follow-up-implementation.md` §Re-evaluation; both are catchable at audit-time with the same verification operation (Read or grep of the cited file or section). The verification is an auxiliary investigation under the rule above; it requires hypothesis-first announcement (e.g., `Investigating whether the cited reference already documents the fallback: reading references/world-state-prerequisites.md to verify before finalizing Issue 1.`). Without this verification, audit-phase claims rely on session memory of which content the operator HAPPENED to encounter rather than on which content the file actually carries — the two are not the same. The operator can fail to load a reference at session time and treat that absence-from-context as absence-from-documentation, emitting a misleading finding that the implementation phase has to retract via Re-evaluation (per `references/follow-up-implementation.md` §Re-evaluation premise-falsification trigger).

**Site-counting for parallel-instantiation Suggestions**: when a Suggestion field implies a parallel-instantiation pattern (phrasings like *"Add a parallel line at the meta-tooling section for symmetry"*, *"mirror this in all class-specific checks"*, *"apply at every site that documents X"*, *"extend the same rule to the canon-reading and meta-tooling sub-sections"*), grep for the underlying convention's terminology — INCLUDING semantic variants per `references/cascade-and-summary-discipline.md` §Cascade-scan discipline (search for renamed terms, semantic variants, count-phrase variants where applicable) — to enumerate the actual site count BEFORE finalizing the audit. Each parallel site discovered should appear in the Suggestion as `<finding>.a / <finding>.b / ...` rather than left implicit. The grep takes the same shape as the cascade-scan-discipline rule (exact-string + semantic variants where applicable); over-grepping is cheap, under-grepping forces implementation-phase scope-decision judgment that audit-time site enumeration would have foreclosed. Distinct from the absence-and-location-citation triggers above: those verify whether the cited content exists; site-counting verifies whether the cited count is exhaustive. Both share the same audit-trail-defect failure mode (forcing implementation-phase recovery), and both are catchable at audit-time with the same verification operation. Catching site count at audit time prevents implementation-time scope-EXPANSION that the existing `Mid-implementation primary-edit scope-narrowing` rule (per `references/follow-up-implementation.md`) cannot cover — that rule addresses NARROWING (audit-over-promised); scope-EXPANSION is the symmetric recovery (audit-under-promised, per `references/follow-up-implementation.md` §Mid-implementation primary-edit scope-expansion). Worked precedent: skill-creator audit (this session) — Improvement 2's Suggestion named two sites (`references/foundations-conformance-check.md` line 34 + "Add a parallel line at the meta-tooling section for symmetry"); implementation-time cascade-scan grep for the underlying convention's variant phrasing ("monotonic-ID outputs at pipeline scope") surfaced a third parallel site at `references/skill-design-drafting.md`'s Pre-flight Check guidance, forcing implementation-time scope-expansion to `2.a / 2.b / 2.c` that audit-time site-counting would have caught directly. Second worked precedent: skill-audit self-audit (this session) — the prior branching-story-turn-cycle audit's Improvement 3 (jq extraction pattern) verification grep surfaced `references/pre-flight-and-prerequisites.md` line 24, which the auditor classified as complementary-hit at audit-phase finalization despite the line restating the `patches[N].payload.record` convention WITHOUT the planned jq pattern; implementation-phase cascade-scan re-surfaced the same line and the auditor recognized it as a parallel-restatement-site needing the jq pattern, forcing scope-expansion to `3.c`. The classification criterion below would have prevented the misclassification at audit time.

**Classification criterion for grep hits at audit time** (companion sub-rule for §Site-counting and the §Convention-restatement / §Declarative-vs-procedural triggers below): when a verification grep returns multiple terminology hits, classify each hit into one of three outcomes BEFORE finalizing the site list — (1) **parallel-restatement-site**: the hit shows the same convention restated WITHOUT the planned new content (literal command pattern, new enforcement note, new field, new clause). Add as `<finding>.<next-letter>` co-equal primary site. (2) **complementary-hit**: the hit shows the same convention restated WITH content that is naturally compatible with the planned change — the new feature can be added at the planned sites without needing a parallel addition at this site for consistency. Record in the Phase 6 audit output (or post-implementation cascade-scan visibility line per `references/cascade-and-summary-discipline.md` §Complementary-hit confirmation pattern) without keying. (3) **unrelated-mention**: the hit matched on shared vocabulary but the hit's concern is tangential to the planned change. Exclude from both the site list and the complementary-hit list. **Decision rule**: if the planned new content would be added at this site to harmonize across the file, it's a parallel-restatement-site; if the planned new content would be redundant or off-topic at this site, it's complementary or unrelated. Common misclassification: treating a hit as complementary because its surrounding prose appears "consistent" with the planned change, when in fact the hit IS one of the restatement sites where the new content belongs. The decision rule's harmonization test catches this: ask whether the planned new content WOULD belong at this site if a future operator read the file looking for the convention — if yes, it's a parallel-restatement-site.

**Convention-restatement check** (companion trigger for primary+cascade Suggestions): when a Suggestion field uses primary+cascade framing AND the targeted Primary section contains an enumeration list (categorized examples, named classes, ordered rules — e.g., a classification table row's Behavior column listing produced artifacts; a heuristic rule listing detection examples), grep the same file at audit time for OTHER enumeration sites that name the same items. The grep target is the enumeration's distinctive terminology (e.g., `tickets, specs, plans, triage files, validator configs` as a literal phrase, OR cardinal-list members like `reports, recommendations, pipeline-level work artifacts`). Each restatement site should appear in the Suggestion as a co-equal primary (`<finding>.a / <finding>.b / ...`) rather than left for implementation-phase scope-expansion. Distinct from the parallel-instantiation trigger above (which keys on Suggestion-field phrasing); this trigger keys on the targeted file's structural restatement pattern. Worked precedent: skill-audit on skill-creator (this session) — Improvement 1's Suggestion named `references/context-and-classification.md` §Pipeline Classification's meta-tooling row Behavior column (Primary) + a cascade in `foundations-conformance-check.md` (Cascade); the same convention's enumeration is restated in §Classification Heuristics rule 4 in the same file as the Primary; audit-time §Site-counting did not trigger because Suggestion phrasing was primary+cascade, not parallel-instantiation; rule 4 was caught only at implementation-time cascade-scan, forcing scope-expansion to Improvement 1.b. Audit-time §Convention-restatement enumeration would have caught it directly. Recurrence pattern: this is the second precedent where a primary+cascade Suggestion targeting an enumeration-bearing section produced an implementation-phase scope-expansion that audit-time enumeration would have foreclosed (the first being the skill-creator-audit precedent cited at §Site-counting above).

**Extended trigger — FOUNDATIONS Alignment / Phase-by-Principle mapping tables**: the rule's "OTHER enumeration sites that name the same items" criterion is the primary trigger for sibling-enumeration cascades; an additional shape that the criterion does not literally capture is **FOUNDATIONS-Alignment-style Phase-by-Principle mapping tables**. Meta-tooling skills (and most Category 2c story-pipeline skills) carry a FOUNDATIONS Alignment table whose rows enumerate, per Principle, which Phases participate in enforcing that Principle (typically as `| Principle | Phase column | Mechanism column |`). When a primary edit at a specific Phase introduces a new enforcement-surface participation — e.g., adding a coverage-criterion item to Phase N that makes Phase N a new enforcement surface for Principle X — the corresponding row's Phase column needs Phase N added AND the Mechanism column needs the new enforcement mechanism acknowledged. The grep target is the targeted Phase's identifier (`Phase 1`, `Phase 6 sub-step 5`, `Pre-flight step 6`) across the file's table-shaped sections; the row whose Principle the primary edit's mechanism enforces is the cascade target. This sub-trigger fires in addition to the primary trigger; both should be applied together when the target file has both enumeration-list sections AND a Phase-by-Principle mapping table. Worked precedent: skill-audit on commitment-block-authoring (this session) — Issue 1.a added item 15 to Phase 1's coverage-target list (an enumeration-list extension that the primary trigger correctly identified), making Phase 1 a new §6.1 enforcement surface; the FOUNDATIONS Alignment table's §Story Bundles §6.1 row needed `Phase 1` added to its Phase column AND its Mechanism column extended to acknowledge cast-role coverage; the primary trigger's "name the same items" criterion did not literally cover the Alignment table (Phase 1's coverage targets and the Alignment table's Phase-by-Principle rows enumerate different items), so the cascade was caught at implementation-phase full-file Read rather than audit-phase enumeration, forcing execution-time scope-expansion via `Issue 1.cascade-b`. This extended trigger would have caught the Alignment-table cascade directly at audit time.

**Declarative-vs-procedural restatement check** (companion trigger for single-primary Suggestions targeting data-loading / retrieval / output conventions): when a Suggestion changes a documented convention (a tool prescription, a mechanism prescription, a load-bearing prose pattern about how data is loaded / retrieved / output) at one Phase-N procedural site AND the target SKILL.md OR any reference file the target SKILL.md loads at Pre-flight has a `§World-State Prerequisites` (or equivalently-named declarative-prerequisites) section, grep the declarative section for the same convention's terminology. When a parallel mention is found, the declarative-section site is a co-equal primary — list as `<finding>.a` (procedural) and `<finding>.b` (declarative) in the Suggestion field. Distinct from §Site-counting above (which keys on Suggestion-field phrasing implying parallel instantiation — Suggestions that already name "mirror"/"apply at every site"/"extend the same rule" patterns) and from §Convention-restatement check above (which keys on the targeted Primary section being an enumeration list — categorized examples, named classes, ordered rules); this trigger keys on the target SKILL.md's structural pattern of restating data-loading / retrieval / output conventions across declarative-prerequisites and procedural-phase registers. Catching at audit time prevents the implementation-phase scope-expansion the §Mid-implementation primary-edit scope-expansion rule (per `references/follow-up-implementation.md`) handles as recovery. Worked precedent: skill-audit on branching-story-turn-cycle (this session) — Improvement 3's Suggestion was single-primary phrasing targeting Pre-flight step 9 (procedural; the convention being changed was the active-records loading mechanism; not enumeration-bearing); neither §Site-counting nor §Convention-restatement fired; the implementation-phase cascade-scan grep for the convention's terminology (`active_records`, `state_snapshot.active`, `get_records`, `Load parent`) surfaced the SKILL.md's §World-State Prerequisites bullet (in the prior session's SKILL.md layout) naming the same convention via "Parent's `state_snapshot.active_records` resolved to their `_source/<class>/*.yaml` files" as a co-equal primary, forcing scope-expansion to `3.a / 3.b`. The new trigger would have caught the parallel site at audit time. Second worked precedent: skill-audit on branching-story-turn-cycle (later in the same session) — Improvement 3 (jq extraction pattern) Suggestion was "Append a parenthetical literal command pattern to both occurrences" targeting `references/phase-9-validation-gates.md` line 41 + SKILL.md Phase 10 step 7; the SKILL.md no longer has its `§World-State Prerequisites` section directly (it has been restructured into `references/pre-flight-and-prerequisites.md`), so the prior trigger condition ("target SKILL.md has") did not fire; the implementation-phase cascade-scan grep surfaced `references/pre-flight-and-prerequisites.md` line 24 (declarative-prerequisites bullet documenting the same `patches[N].payload.record` convention without the literal jq pattern) as a co-equal primary, forcing scope-expansion to `3.a / 3.b / 3.c`. The extended trigger (covering reference files loaded at Pre-flight) would have caught the parallel site at audit time. This precedent shows that the original SKILL.md-only scope assumption is invalidated when skills restructure their declarative-prerequisites content out of SKILL.md into a reference file. Generalizes beyond the worked example: many skills across all five Skill Categories document data-loading conventions in BOTH a §World-State Prerequisites declarative section AND in Phase-N procedural steps that prescribe the loading; when one site's wording changes, the other typically needs the same change.

**Composition with §Site-counting**: when both §Site-counting and §Convention-restatement fire on the same finding (Suggestion phrasing implies parallel instantiation AND targeted Primary section is an enumeration list), a single grep covering the underlying convention's terminology — including label-variant + count-phrase-variant per `references/cascade-and-summary-discipline.md` §Cascade-scan discipline — satisfies both triggers; both rules want the same enumeration evidence, and running two separate greps duplicates work without surfacing additional sites. Distinct from the case where only one trigger fires (Suggestion implies parallel instantiation but Primary section is not an enumeration list; or vice versa) — there a single grep is still appropriate but only one trigger formally fires. Worked precedent: skill-audit on brainstorm (this session) — Improvement 1's Suggestion used parallel-instantiation phrasing ("Apply at four positions in the line-176 paragraph") AND the targeted Primary section IS an enumeration list (the verdict-bucket enum); a single grep for verdict-bucket label variants + count-phrase variants enumerated all four sites in one scan, satisfying both triggers without duplicate work. **Composition with §Declarative-vs-procedural restatement check**: when §Site-counting and the §Declarative-vs-procedural trigger co-fire (Suggestion phrasing implies parallel instantiation AND the target SKILL.md or any reference file the target SKILL.md loads at Pre-flight has a §World-State Prerequisites bullet paralleling the targeted Phase-N step), the grep targets overlap — both want the convention's terminology — so one grep covers both. When §Convention-restatement and §Declarative-vs-procedural co-fire instead, the grep targets may differ in shape (§Convention-restatement greps the enumeration's distinctive terminology; §Declarative-vs-procedural greps the convention's mechanism terminology), and two distinct greps may be needed when the enumeration's terms and the mechanism's terms aren't lexically coincident.

**Sub-key labeling boundary — parallel-instantiation vs primary + cascade**: the `<finding>.a / <finding>.b / ...` Suggestion-field convention above is RESERVED for parallel-instantiation primary sites — co-equal primary edits where each `.a` / `.b` corresponds to a distinct primary-edit row in the post-implementation summary table (per `references/cascade-and-summary-discipline.md` §Quick-reference — row-keying by shape, the `1 finding → multiple co-equal parallel edits (same semantic change applied at N sites)` shape). When a Suggestion field instead contains a single primary edit PLUS one-or-more planned cascades (the `1 finding → primary edit + cascade(s)` shape, keyed `N` baseline + `N.cascade-a / N.cascade-b / ...` at implementation time per the same Quick-reference row-keying table), use descriptive prefixes — `Primary: ...` and `Cascade(s): ...` — rather than `<finding>.a` and `<finding>.b`, so the audit-phase Suggestion previews the implementation-phase row-keying convention rather than conflating it with parallel-instantiation labeling. Reusing `.a / .b` for primary-plus-cascade-summary creates a mid-flow translation between the audit's `1.a / 1.b` framing and the implementation's `1 + 1.cascade-*` row-keying that a future reader cross-checking the audit Suggestion against the post-implementation summary has to mentally reconcile. The Cross-Skill Scan section's form (3) / form (6) phrasings (`Cascade planned for implementation: ...` / `cascade(s) keyed <finding>.cascade for implementation`) already preview the cascade keying explicitly — the Suggestion-field labeling should match. Worked precedent: skill-audit on storylet-pool-authoring (this session) — Improvement 1's Suggestion used `1.a — In SKILL.md HARD-GATE block precondition (a) ... 1.b — Cascade: the same gap exists in the four sibling Category 2c skills' HARD-GATE blocks ...` framing; the implementation-phase row-keying correctly emitted `Improvement 1` (baseline) + `Improvement 1.cascade-a` through `Improvement 1.cascade-d` (4 sibling cascades), but the `1.a / 1.b` audit-phase labels read at audit time as parallel-instantiation sub-keys and required mental translation. Under this rule, the same Suggestion would read `Primary: In SKILL.md HARD-GATE ... Cascade(s): the same gap exists in the four sibling Category 2c skills' HARD-GATE blocks ...`, previewing the `1 + 1.cascade-*` row-keying directly.

**Co-located sub-edits within one paragraph**: when the N parallel-instantiation positions are co-located within a single paragraph or contiguous block (e.g., 4 micro-positions in one dense paragraph applying the same semantic change — adding a 5th enum value to a 4-position enum-restatement paragraph), prefer ONE summary row (not sub-keyed) — the edit lands as one bounded operation and N sub-keyed rows would over-decompose what is logically one edit. Sub-key with `<finding>.a / <finding>.b / ...` only when the parallel positions are in distinct sections, separated by significant non-edited content, OR when each position warrants distinct status-table reasoning (different file paths, different semantic implications, different cascade dependencies). Decision rule: if the executor would naturally name them as one edit ("I added the 5th enum value across the four sub-positions in line 176"), use one row; if as multiple edits ("I added the 5th enum value at line 176; separately, at line 240; separately, at line 305"), sub-key. Worked precedent: skill-audit on brainstorm (this session) — Improvement 1's Suggestion named four sub-positions in line 176 (verdict enum, rationale clause, scope clause, grouping enum) for a 5th-verdict-bucket addition; the audit-phase Suggestion explicitly chose NOT to sub-key (citing "they're all in line 176 — one edit task with four micro-positions, not four separate edit tasks at distinct sites"); the implementation phase landed as one `Improvement 1` row with the four sub-positions named in the reason field — under this rule, that judgment is the canonical handling rather than an improvisation.

For audit-phase Cross-Skill Scan section emissions in form (3) (`Cascade planned for implementation: ...` — see SKILL.md §Cross-Skill Scan), perform per-finding sibling investigation (Read the sibling's parallel section, or grep the sibling's SKILL.md for the relevant terminology) before naming each finding as a cascade-target candidate. If no investigation is performed for a given finding, do NOT name that finding as a cascade candidate — leave the cascade-or-no-cascade determination to implementation-phase per-finding scanning (see `references/cascade-and-summary-discipline.md` §Cascade edits). Hand-waving "shared-surface trigger" claims that name multiple findings as cascade candidates without per-finding sibling investigation produce both over-naming (findings the audit listed but no cascade exists at sibling — the implementation phase has to retract them) AND under-naming (findings that DO cascade but the audit didn't list because the operator didn't think to check that finding — the implementation phase has to add them). Both are audit-trail defects: the audit report claims one cascade landscape, the post-implementation summary records a different one, and a future reader cannot reconcile the two without reading the implementation flow's per-finding scan outcomes.

The 30-second-per-finding verification cost prevents the implementation-phase retraction cycle that the Re-evaluation rule covers when premise-falsification slips through. **Pre-finalization verification is the prevention; Re-evaluation is the recovery.** Both should exist, but catching at audit time is preferable because the audit report is what the user reads to decide whether to authorize implementation — a wrong premise in the report can lead the user to authorize an implementation they would have declined had the report been accurate, or to decline an implementation they would have authorized had the audit named the right cascades.

**LOW-severity coverage gap**: the MEDIUM-or-higher threshold above is a deliberate cost-benefit tradeoff — over-verification at audit time of LOW findings would inflate audit cost without proportional benefit. LOW findings with absence-claim phrasings nonetheless carry residual premise-falsification risk; the implementation-phase Re-evaluation rule (per `references/follow-up-implementation.md`) is the safety net rather than incidental cascade-scan discovery. Auditors who notice that a LOW finding's claim might be wrong (e.g., "I'm not certain the skill doesn't say X") are encouraged to verify ad-hoc despite the rule-mandated threshold — the 30-second cost is the same; only the rule's mandatory trigger is severity-gated. Worked precedent: skill-audit on skill-audit (this session) — a prior implementation phase discovered Improvement 6's premise-falsification (the audit claimed `target_page_length` source was unspecified, but the SKILL.md frontmatter arguments doc already documented the default) at cascade-scan time rather than at audit-time verification, because the finding's LOW severity didn't trigger the mandatory pre-finalization check; ad-hoc verification at audit time would have caught it.

## Recommended at audit start

When the target skill ships a `references/` or `templates/` subdirectory, list the directory contents as the audit's first auxiliary action. This surfaces the full file structure so per-finding Suggestion fields can cite exact file paths (per the Suggestion specificity sub-rule in `references/report-conventions.md`) and the implementation phase doesn't have to discover file structure mid-flow via cascade scan. The listing still requires a hypothesis-first announcement under the rule below (e.g., `Investigating which references/ files this skill ships: listing the skill directory.`). Skip this recommendation only when the target skill is structurally a single SKILL.md with no subdirectories.

## Announcement rule

Applies to any tool call beyond the target Read. Announce hypothesis-first as user-facing text IMMEDIATELY BEFORE the tool call. Format: `Investigating <hypothesis>: <grep/read/diff/list> <target> to verify.` Examples:

- `Investigating whether templates/ actually ship in this skill: listing the skill directory.` (setup-feeling action — routine directory listing at audit start still counts as auxiliary investigation and needs announcement)
- `Investigating whether sibling meta-tooling skills reference changed terminology: grepping .claude/skills/*/SKILL.md for the affected tokens.` (substantive follow-up investigation mid-audit)

Routine setup actions (listing the target directory, loading sibling files referenced from SKILL.md) require announcement just as substantive investigations do — the rule draws no line between "interesting" and "boring" auxiliary calls. Tool `description` fields do NOT satisfy this rule — they don't render in the transcript where reproducibility needs them. Hypothesis-first phrasing makes the audit trail reproducible; a reader can reconstruct what was being tested vs. which tool answered it.

## Batched tool-call announcements

When multiple tool calls are batched in a single assistant turn (parallel tool-call batching per the Edit-ordering rule in `references/follow-up-implementation.md`), ONE announcement covering the batch is acceptable if all calls investigate the same hypothesis. Example: `Investigating whether X and Y both ship: listing both directories.` covers a 2-call batch with one announcement when the hypothesis is joint. If calls investigate DISTINCT hypotheses, each needs its own announcement in the same pre-batch prose: `Investigating whether X ships: listing the directory. Separately investigating the Y convention: grepping siblings.` — two hypotheses, two announcements, one batch. The batch-one-announcement shortcut is for shared-hypothesis batching only; it is not a general dispensation to elide announcements. The rule applies symmetrically to audit-phase investigations and implementation-phase verifications: when a follow-up implementation batches an edit-region re-read with a sibling-scan grep in the same parallel tool-call batch, both hypotheses need announcement (e.g., `Verifying the Step 5 edit landed: re-reading the new sub-section. Separately investigating sibling drift: grepping meta-tooling skills for the new terminology.`) — verification IS a hypothesis ("did the edit produce the intended state?") even when it feels like a passive check rather than an active investigation, and bundling it under a sibling-scan announcement obscures which tool answered which hypothesis.

## Cascade-scan batching across multiple findings

Cascade scanning produces TWO distinct artifacts emitted at different times: **(a)** a pre-grep per-finding hypothesis announcement (e.g., `Investigating Improvement 1's cascade targets: grepping for <term>`) — emitted as user-facing text immediately before the parallel grep batch; and **(b)** a post-grep per-finding outcome line (per the Quick-reference cascade-scan outcome by shape table in `references/cascade-and-summary-discipline.md` — `Finding N: <count> hits found, all accounted for as primary sites...`) — emitted as the per-finding cascade-scan visibility line before the post-implementation summary table. Both are required for full audit-trail reproducibility; emitting only the outcome line drops the hypothesis context that lets a future reader reconstruct what was being tested, and emitting only the announcement drops the verifiable result a future reader needs to confirm the scan ran. The common implementation-phase case — cascade scans for N findings batched into one parallel tool call — constitutes **distinct hypotheses (one per finding), not one shared hypothesis**. Each finding's cascade scan investigates "are there cascade targets for THIS finding's primary edit?", which is a per-finding question even when the greps run in parallel for efficiency. Announce each finding's scan separately in the pre-batch prose, naming the finding and its scan concern: `Investigating Improvement 1's cascade targets: grepping for <term-1>. Separately investigating Improvement 3's cascade targets: grepping for <term-2>. Separately investigating Feature 1's cascade targets: grepping for <term-3>.` Collapsing these into a single umbrella announcement like "Investigating cascade-scan targets across all findings" breaks the per-finding reconcilability that the post-implementation summary's `N.cascade` keying depends on — a reader of the summary must be able to trace each cascade row back to its planning-phase scan, and a shared umbrella announcement forces guess-work at the mapping. When the scan outcomes diverge per finding (some produce cascades, some produce complementary hits, some produce no hits — per the Quick-reference cascade-scan outcome table in `references/cascade-and-summary-discipline.md`), per-finding announcements before the batch let the per-finding outcome lines after the batch land on an already-established per-finding frame. **Prefer parallel tool-call batching** (one Bash invocation per finding's grep, sent as multiple tool blocks in a single assistant turn) over single-Bash-command batching (greps stitched with `&&` and `echo` section headers). The parallel-tool-call form bounds each finding's output independently; the single-Bash form risks total-output truncation when combined hits are large, forcing re-runs that pollute the audit trail and break the per-finding announcement-to-result reconcilability. Single-Bash stitching may look efficient (one tool call instead of N) but trades that for an unbounded combined-output budget — the truncation failure mode is non-obvious until it fires, and the recovery (separate re-run for the truncated finding) leaves the audit trail with a delayed result that the original announcement-to-result pairing no longer covers cleanly.
