# Audit Execution Discipline

These rules govern how Step 1 (Step 1a reads the target skill; Step 1b loads this reference) is executed and how all auxiliary tool calls — across the entire audit and any follow-up implementation — must be announced and batched.

## Read-satisfaction

The Read requirement is satisfied by in-context content from any prior operation in the current session — direct Read tool invocations, skill-invocation-embedded content (when the target skill was invoked earlier in the session and its full body was injected via that invocation), or system-reminder inclusions (parallel to Step 2's rule for alignment documents and Step 3's self-audit "re-read regardless of prior reads" rule). Re-read only when content is not in context (e.g., after compaction or context rotation) or when the in-context version is suspected stale. If the target skill was modified during the current session (via user-directed follow-up implementation from a prior audit, or any other in-session edit), re-read is mandatory. *The Edit-tool precondition for follow-up implementation is separate and stricter — see `references/follow-up-implementation.md` Common path step 3.*

## Path resolution

If the exact path does not resolve, glob for `<path>*/SKILL.md` (appending wildcard + `/SKILL.md`). If that also fails, try `<path>**/SKILL.md`. If exactly one match is found, use it and note the correction. If zero or multiple matches, stop and report the error.

## Auxiliary investigation (permitted, with required announcement)

Beyond reading the target SKILL.md, you may additionally: (a) list contents of the target skill's directory and of any directly-referenced sibling directories; (b) diff files against named reference sources when the target's text claims a reference-source relationship (e.g., "copy from skill-creator's own templates" — check whether those templates actually ship and whether sibling skills have drifted from them); (c) glob for shared-surface files (`archive/*/`, `brainstorming/*.md`, `worlds/*/`) when a potential finding hinges on their presence or naming. Each auxiliary investigation must support a specific hypothesis about the target skill's behavior — do not probe speculatively.

## Pre-finalization verification

Before finalizing any finding whose Suggestion or Skill-gap field claims that content is absent, missing, or undocumented OR mis-cites a specific location at MEDIUM or higher severity — phrasings like *"Add X"*, *"Document the missing Y"*, *"There is no documented Z"*, *"no fallback exists"*, *"the skill never mentions W"*, *"Tighten X at §Y"*, *"the cited §Z section says..."*, *"Update the wording at §Y"*, *"§Y currently reads..."* — verify the absence OR the location-citation by Read of the cited file or grep of the referenced section. The two trigger families share the same audit-trail-defect failure mode: an absence claim that is wrong propagates into the implementation phase as a finding the executor cannot apply (the missing content is actually present), and a location-citation claim that is wrong propagates as a finding whose primary edit cannot land at the cited site (the content the audit Suggestion targets actually lives elsewhere). Both errors force premise-falsification recovery at implementation time per `references/follow-up-implementation.md` §Re-evaluation; both are catchable at audit-time with the same verification operation (Read or grep of the cited file or section). The verification is an auxiliary investigation under the rule above; it requires hypothesis-first announcement (e.g., `Investigating whether the cited reference already documents the fallback: reading references/world-state-prerequisites.md to verify before finalizing Issue 1.`). Without this verification, audit-phase claims rely on session memory of which content the operator HAPPENED to encounter rather than on which content the file actually carries — the two are not the same. The operator can fail to load a reference at session time and treat that absence-from-context as absence-from-documentation, emitting a misleading finding that the implementation phase has to retract via Re-evaluation (per `references/follow-up-implementation.md` §Re-evaluation premise-falsification trigger).

**Site-counting for parallel-instantiation Suggestions**: when a Suggestion field implies a parallel-instantiation pattern (phrasings like *"Add a parallel line at the meta-tooling section for symmetry"*, *"mirror this in all class-specific checks"*, *"apply at every site that documents X"*, *"extend the same rule to the canon-reading and meta-tooling sub-sections"*), grep for the underlying convention's terminology — INCLUDING semantic variants per `references/cascade-and-summary-discipline.md` §Cascade-scan discipline (search for renamed terms, semantic variants, count-phrase variants where applicable) — to enumerate the actual site count BEFORE finalizing the audit. Each parallel site discovered should appear in the Suggestion as `<finding>.a / <finding>.b / ...` rather than left implicit. The grep takes the same shape as the cascade-scan-discipline rule (exact-string + semantic variants where applicable); over-grepping is cheap, under-grepping forces implementation-phase scope-decision judgment that audit-time site enumeration would have foreclosed. Distinct from the absence-and-location-citation triggers above: those verify whether the cited content exists; site-counting verifies whether the cited count is exhaustive. Both share the same audit-trail-defect failure mode (forcing implementation-phase recovery), and both are catchable at audit-time with the same verification operation. Catching site count at audit time prevents implementation-time scope-EXPANSION that the existing `Mid-implementation primary-edit scope-narrowing` rule (per `references/follow-up-implementation.md`) cannot cover — that rule addresses NARROWING (audit-over-promised); scope-EXPANSION is the symmetric recovery (audit-under-promised, per `references/follow-up-implementation.md` §Mid-implementation primary-edit scope-expansion). Worked precedent: skill-creator audit (this session) — Improvement 2's Suggestion named two sites (`references/foundations-conformance-check.md` line 34 + "Add a parallel line at the meta-tooling section for symmetry"); implementation-time cascade-scan grep for the underlying convention's variant phrasing ("monotonic-ID outputs at pipeline scope") surfaced a third parallel site at `references/skill-design-drafting.md`'s Pre-flight Check guidance, forcing implementation-time scope-expansion to `2.a / 2.b / 2.c` that audit-time site-counting would have caught directly.

For audit-phase Cross-Skill Scan section emissions in form (3) (`Cascade planned for implementation: ...` — see SKILL.md §Cross-Skill Scan), perform per-finding sibling investigation (Read the sibling's parallel section, or grep the sibling's SKILL.md for the relevant terminology) before naming each finding as a cascade-target candidate. If no investigation is performed for a given finding, do NOT name that finding as a cascade candidate — leave the cascade-or-no-cascade determination to implementation-phase per-finding scanning (see `references/cascade-and-summary-discipline.md` §Cascade edits). Hand-waving "shared-surface trigger" claims that name multiple findings as cascade candidates without per-finding sibling investigation produce both over-naming (findings the audit listed but no cascade exists at sibling — the implementation phase has to retract them) AND under-naming (findings that DO cascade but the audit didn't list because the operator didn't think to check that finding — the implementation phase has to add them). Both are audit-trail defects: the audit report claims one cascade landscape, the post-implementation summary records a different one, and a future reader cannot reconcile the two without reading the implementation flow's per-finding scan outcomes.

The 30-second-per-finding verification cost prevents the implementation-phase retraction cycle that the Re-evaluation rule covers when premise-falsification slips through. **Pre-finalization verification is the prevention; Re-evaluation is the recovery.** Both should exist, but catching at audit time is preferable because the audit report is what the user reads to decide whether to authorize implementation — a wrong premise in the report can lead the user to authorize an implementation they would have declined had the report been accurate, or to decline an implementation they would have authorized had the audit named the right cascades.

**LOW-severity coverage gap**: the MEDIUM-or-higher threshold above is a deliberate cost-benefit tradeoff — over-verification at audit time of LOW findings would inflate audit cost without proportional benefit. LOW findings with absence-claim phrasings nonetheless carry residual premise-falsification risk; the implementation-phase Re-evaluation rule (per `references/follow-up-implementation.md`) is the safety net rather than incidental cascade-scan discovery. Auditors who notice that a LOW finding's claim might be wrong (e.g., "I'm not certain the skill doesn't say X") are encouraged to verify ad-hoc despite the rule-mandated threshold — the 30-second cost is the same; only the rule's mandatory trigger is severity-gated. Worked precedent: skill-audit on skill-audit (this session) — a prior implementation phase discovered Improvement 6's premise-falsification (the audit claimed `target_page_length` source was unspecified, but the SKILL.md frontmatter arguments doc already documented the default) at cascade-scan time rather than at audit-time verification, because the finding's LOW severity didn't trigger the mandatory pre-finalization check; ad-hoc verification at audit time would have caught it.

## Recommended at audit start

When the target skill ships a `references/` or `templates/` subdirectory, list the directory contents as the audit's first auxiliary action. This surfaces the full file structure so per-finding Suggestion fields can cite exact file paths (per the Suggestion specificity sub-rule in `references/report-conventions.md`) and the implementation phase doesn't have to discover file structure mid-flow via cascade scan. The listing still requires a hypothesis-first announcement under the rule below (e.g., `Investigating which references/ files this skill ships: listing the skill directory.`). Skip this recommendation only when the target skill is structurally a single SKILL.md with no subdirectories.

## Announcement rule

Applies to any tool call beyond the target Read. Announce hypothesis-first as user-facing text IMMEDIATELY BEFORE the tool call. Format: `Investigating <hypothesis>: <grep/read/diff/list> <target> to verify.` Examples:

- `Investigating whether templates/ actually ship in this skill: listing the skill directory.` (setup-feeling action — routine directory listing at audit start still counts as auxiliary investigation and needs announcement)
- `Investigating whether sibling meta-tooling skills reference changed terminology: grepping .claude/skills/*/SKILL.md for the affected tokens.` (substantive follow-up investigation mid-audit)

Routine setup actions (listing the target directory, loading sibling files referenced from SKILL.md) require announcement just as substantive investigations do — the rule draws no line between "interesting" and "boring" auxiliary calls. Tool `description` fields do NOT satisfy this rule — they don't render in the transcript where reproducibility needs them. Hypothesis-first phrasing makes the audit trail reproducible; a reader can reconstruct what was being tested vs. which tool answered it.

## Batched tool-call announcements

When multiple tool calls are batched in a single assistant turn (parallel tool-call batching per the Edit-ordering rule in `references/follow-up-implementation.md`), ONE announcement covering the batch is acceptable if all calls investigate the same hypothesis. Example: `Investigating whether X and Y both ship: listing both directories.` covers a 2-call batch with one announcement when the hypothesis is joint. If calls investigate DISTINCT hypotheses, each needs its own announcement in the same pre-batch prose: `Investigating whether X ships: listing the directory. Separately investigating the Y convention: grepping siblings.` — two hypotheses, two announcements, one batch. The batch-one-announcement shortcut is for shared-hypothesis batching only; it is not a general dispensation to elide announcements. The rule applies symmetrically to audit-phase investigations and implementation-phase verifications: when a follow-up implementation batches an edit-region re-read with a sibling-scan grep in the same parallel tool-call batch, both hypotheses need announcement (e.g., `Verifying the Step 5 edit landed: re-reading the new sub-section. Separately investigating sibling drift: grepping meta-tooling skills for the new terminology.`) — verification IS a hypothesis ("did the edit produce the intended state?") even when it feels like a passive check rather than an active investigation, and bundling it under a sibling-scan announcement obscures which tool answered which hypothesis.

## Cascade-scan batching across multiple findings

Cascade scanning produces TWO distinct artifacts emitted at different times: **(a)** a pre-grep per-finding hypothesis announcement (e.g., `Investigating Improvement 1's cascade targets: grepping for <term>`) — emitted as user-facing text immediately before the parallel grep batch; and **(b)** a post-grep per-finding outcome line (per the Quick-reference cascade-scan outcome by shape table in `references/cascade-and-summary-discipline.md` — `Finding N: <count> hits found, all accounted for as primary sites...`) — emitted as the per-finding cascade-scan visibility line before the post-implementation summary table. Both are required for full audit-trail reproducibility; emitting only the outcome line drops the hypothesis context that lets a future reader reconstruct what was being tested, and emitting only the announcement drops the verifiable result a future reader needs to confirm the scan ran. The common implementation-phase case — cascade scans for N findings batched into one parallel tool call — constitutes **distinct hypotheses (one per finding), not one shared hypothesis**. Each finding's cascade scan investigates "are there cascade targets for THIS finding's primary edit?", which is a per-finding question even when the greps run in parallel for efficiency. Announce each finding's scan separately in the pre-batch prose, naming the finding and its scan concern: `Investigating Improvement 1's cascade targets: grepping for <term-1>. Separately investigating Improvement 3's cascade targets: grepping for <term-2>. Separately investigating Feature 1's cascade targets: grepping for <term-3>.` Collapsing these into a single umbrella announcement like "Investigating cascade-scan targets across all findings" breaks the per-finding reconcilability that the post-implementation summary's `N.cascade` keying depends on — a reader of the summary must be able to trace each cascade row back to its planning-phase scan, and a shared umbrella announcement forces guess-work at the mapping. When the scan outcomes diverge per finding (some produce cascades, some produce complementary hits, some produce no hits — per the Quick-reference cascade-scan outcome table in `references/cascade-and-summary-discipline.md`), per-finding announcements before the batch let the per-finding outcome lines after the batch land on an already-established per-finding frame. **Prefer parallel tool-call batching** (one Bash invocation per finding's grep, sent as multiple tool blocks in a single assistant turn) over single-Bash-command batching (greps stitched with `&&` and `echo` section headers). The parallel-tool-call form bounds each finding's output independently; the single-Bash form risks total-output truncation when combined hits are large, forcing re-runs that pollute the audit trail and break the per-finding announcement-to-result reconcilability. Single-Bash stitching may look efficient (one tool call instead of N) but trades that for an unbounded combined-output budget — the truncation failure mode is non-obvious until it fires, and the recovery (separate re-run for the truncated finding) leaves the audit trail with a delayed result that the original announcement-to-result pairing no longer covers cleanly.
