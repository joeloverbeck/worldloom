# Cascade Edits and Post-Implementation Summary

These rules govern cascade scanning during follow-up implementation and the structure of the post-implementation summary that records what landed.

## Cascade edits

After planning the primary edit(s) for a finding, scan the rest of the file for related text that uses the same terminology, references the same concept, or would become inconsistent if only the finding's target text is changed. Apply cascade edits alongside the finding's primary edit. Cascade discovery may happen at two valid points: (a) per-finding during planning (preferred — matches the scan-after-planning flow above and keeps cascade + primary in the same batch step), or (b) during post-edit verification as a backstop when the per-finding scan missed something. When a cascade is discovered in post-edit verification, apply it immediately and note it in the post-implementation summary as usual.

**Cascade-target Edit-tool precondition**: cascade targets surfaced by the per-finding scan in files not yet Read in this session require a fresh session-level Read before the cascade Edit can be applied — grep / Bash / search-tool output that quotes the file's content does NOT satisfy the Edit tool's `File has not been read yet` validator. See `references/follow-up-implementation.md` §Common path step 3 for the full Edit-tool precondition rule and the enumerated list of non-satisfaction paths; the precondition applies to cascade-target files just as it applies to primary-edit targets.

**Verification-backstop labeling**: when a cascade is caught by the verification backstop rather than planning-time scanning, prefix its reason field with `verification-backstop catch:` so the audit trail records where the per-finding scan missed. The backstop working is a success; the backstop being the only thing that caught the miss is a tuning opportunity for the planning-time scan discipline — the explicit label preserves both signals. No new outcome class is needed in the cascade-scan-outcome taxonomy for backstop catches; the label is a reason-field annotation on an existing `cascade` outcome. The verification backstop is not a replacement for per-finding scanning — it catches misses; it does not absolve the planning step. Note cascade edits in the post-implementation summary as "cascade from finding N."

**Audit-phase Read coverage as scan-satisfaction**: when the operator Read related files end-to-end during the audit phase (Steps 1-2 plus auxiliary investigation per `references/audit-execution-discipline.md` §Auxiliary investigation) and the relevant content remains in context at implementation time, that Read coverage satisfies the per-finding cascade-scan requirement for findings whose primary edit is local to the Read'd region. Report the satisfaction with the canonical phrasing `Finding N: scan satisfied by audit-phase Read coverage of <file-list>; no related text outside the primary edit; no cascade.` This is structurally distinct from the eight scan-outcome patterns enumerated below — those patterns assume a fresh per-finding scan ran at implementation time; audit-phase Read coverage is a prior-phase scan-satisfaction shortcut available when the audit phase already loaded the relevant surface. For findings touching enum-counts, renamed terms, or terminology likely to recur outside the Read'd region, run a fresh Bash grep at implementation time per the existing per-finding scan discipline — Read coverage does not substitute when the scan target is keyword-distributed across the codebase, because the operator's mental scan over a Read'd file is unreliable for distributed terminology that appears in unexpected sections. The shortcut is for primary-local findings (the edit changes one paragraph in one section, with no terminology that recurs elsewhere), not for cross-cutting changes.

**Batch-level extension**: when the operator performs a full-file implementation-start Read of the target SKILL.md (per the Edit-tool precondition in `references/follow-up-implementation.md` §Common path step 3), that Read satisfies the per-finding cascade-scan requirement for ALL findings whose primary edit is local to the file AND whose cascade-scan target is keyword-distributed within the same file. Findings touching enum-counts, renamed terms, or terminology likely to recur outside the target file still require their own greps per the existing distributed-terminology exception. Report the batch-level satisfaction with the canonical phrasing `Per-finding cascade scans: findings X, Y, Z scan-satisfied by implementation-start full-file Read of <file-path>; remaining findings A, B ran fresh greps for <reason>.` The batch-level extension is the natural composition of the per-finding shortcut above when one full-file Read covers all primary-edit regions simultaneously; emitting N per-finding shortcut lines for the same Read is permissible but verbose, and the batch-level form preserves the same audit-trail evidence in one line.

## Execution-time scope-expansion labeling

When a cascade is applied to a site that the per-finding planning scan correctly classified as `complementary-hit` (the existing text remained accurate; no cascade was strictly required for consistency-preservation), but the executor decides at edit-application time to upgrade the site to a cascade-equivalent edit anyway — for clarity, harmonization with the primary edit's new content, or improved cross-reference discoverability — prefix its reason field with `execution-time scope-expansion:` rather than `verification-backstop catch:`. The semantic distinction is load-bearing: `verification-backstop catch:` signals that the planning-time scan MISSED a needed cascade and verification caught it (a tuning opportunity for planning-scan discipline); `execution-time scope-expansion:` signals that the planning-time scan CORRECTLY classified the site as complementary AND the executor exercised judgment-call discretion to upgrade it (a judgment-call territory the rules can't fully predict in advance). Both labels are reason-field annotations applied to a `cascade`-keyed row in the post-implementation summary table, but the distinct outcome class `execution-time scope-expansion` is enumerated in the §Quick-reference cascade-scan outcome by shape table because the planning-time vs execution-time decision IS observable to the reader and load-bearing for tuning interpretation. A future audit reading `verification-backstop catch:` rows asks "how can the planning-scan discipline catch this in the future?"; reading `execution-time scope-expansion:` rows asks "do these judgment-call upgrades reveal a pattern worth codifying?". Symmetric with §Mid-implementation cascade scope-narrowing in `references/cross-skill-consistency.md` — the same execution-time-judgment-vs-planning-time-classification gap is addressed there for the narrowing direction (audit-promised-too-much, executor narrows) and here for the expansion direction (planner-correctly-deferred, executor expands). Worked precedent: skill-audit on `propose-new-worlds-from-preferences` (this session) — 3 cascade rows on Improvements 1 + 2 were applied at edit-application time after the per-finding scan had correctly classified the sites (HARD-GATE block line 19, Process Flow Pre-flight entry line 26, Process Flow Phase 14 entry) as `complementary-hit`; under the prior single-label convention they were marked `verification-backstop catch:` despite no scan actually missing anything; under this rule they would be marked `execution-time scope-expansion:` to preserve the distinction.

## Intra-skill vs cross-skill cascades

Cascades may be **intra-skill** (same skill's `SKILL.md` → its own `references/*.md` or `templates/*.md`) or **cross-skill** (target skill → sibling skill). Both use `N.cascade` keying in the post-implementation summary and follow the same scan-during-planning discipline above. The audit-phase Cross-Skill Scan section of the report template and the implementation-phase cross-skill sibling-scan operation (see `references/cross-skill-consistency.md`) apply ONLY to cross-skill cascades — they do NOT fire for intra-skill cascades, which are handled by the standard cascade discipline alone. When deciding whether a cascade is intra-skill or cross-skill, check whether the cascade-target file lives under the same skill directory as the primary edit: same directory → intra-skill; different skill directory → cross-skill.

## Per-finding cascade scan visibility

When per-finding scanning produces no related text for any finding in the batch, report the absence as a single per-batch line BEFORE the post-implementation summary table (e.g., "Per-finding cascade scans: no cascades needed for any of N findings.") so the audit trail records that the scan happened. When some findings produced cascades and others did not, the cascade rows (`N.cascade`) cover the affirmative cases and the per-batch line need only mention the findings whose scans found nothing (e.g., "Per-finding cascade scans: findings 2 and 5 produced no cascades."). The line is procedural, not a status row — it confirms the scan was run, parallel to the cross-skill scan's "Scanned via grep — no inconsistencies" announcement.

## Decision tree (per finding in the batch)

Apply this routing before reading the Mixed-outcome batches discipline below:
- Scan found nothing → eligible for the per-batch no-hits line
- Scan found primary sites only (planned `N.a` / `N.b` instantiations) → per-finding `primary-site` line, NOT collapsed into per-batch no-hits
- Scan found complementary hits → per-finding `complementary-hit` line
- Scan found cascade targets → `N.cascade` row in status table

Less-common outcomes (multi-outcome / restructure-scope / encompassed-by-restructure / scope-narrowed-cascade / execution-time scope-expansion) are enumerated in the Quick-reference cascade-scan outcome by shape table below.

## Mixed-outcome batches

When a batch contains findings with different cascade-scan outcomes — some producing no hits, others producing complementary hits (per the Complementary-hit confirmation pattern sub-rule below), others producing primary-site confirmations, and/or others producing actual cascades — use the per-finding form (`Finding N: <count> hits found in <file-list>, confirmed complementary (<reason>); no cascade.` for complementary hits; `Finding N: <count> hits found, all accounted for as primary sites ...; no extraneous cascade.` for primary-site confirmations; `N.cascade` rows for actual cascades) for EACH finding whose scan produced hits, AND the per-batch `Per-finding cascade scans: findings X and Y produced no cascades.` line covering ONLY the no-hits findings. The per-batch line is reserved for the no-hits case; do NOT collapse complementary-hit or primary-site-confirmation findings into it — each non-empty outcome takes its own per-finding line. This preserves audit-trail reconstruction: a reader must be able to enumerate each finding's scan outcome from the summary, and compressing complementary hits into "no cascades needed" hides the fact that hits were found and reviewed.

## Primary-site confirmation pattern

A scan may find hits that are ALREADY-PLANNED primary edit sites rather than new cascades. This is distinct from both "scan found nothing" and "scan found cascade N.cascade." Example: a terminology-harmonization finding (Improvement N) is planned as N parallel instantiations (`N.a`, `N.b`, ...); the cascade scan for that finding greps the same term and finds exactly those N sites — no extras. Another example: a primary edit's cascade scan for related terminology finds one hit, but that hit IS the co-equal primary already keyed elsewhere in the summary. Report this pattern as `Finding N: <count> hits found, all accounted for as primary sites (<optional brief site list>); no extraneous cascade.` This preserves audit-trail visibility that the scan ran AND that the hits were reviewed and confirmed as planned primaries, without creating spurious `N.cascade` rows or misreporting "scan found nothing" when it actually found the expected sites.

## Complementary-hit confirmation pattern

A scan may also find hits that are NEITHER planned primary sites NOR cascade requirements — they are related existing content that happens to be consistent with (not modified by) the planned change. This is distinct from all three prior outcomes: "scan found nothing" (no hits), "primary-site confirmation" (hits are planned primaries), and "scan found cascade N.cascade" (hits require mirroring the primary). Example: a finding that tightens a rule in one section scans related terminology across the file and finds the same terminology used correctly in a sibling section where the existing text remains valid under the new rule — the sibling text is complementary, not a primary site, not a cascade target. Report this pattern as `Finding N: <count> hits found in <file-list>, confirmed complementary (<one-phrase reason, e.g., "definitional comment, not operational rule" or "parallel register, already consistent with the new rule">); no cascade.` This preserves audit-trail visibility that the scan ran and that the hits were reviewed and verified consistent, distinguishing from (a) the "no hits" per-batch line (scan found nothing at all), (b) primary-site confirmation (hits ARE the planned primaries), (c) cascade rows (hits require modification), and (d) restructure-scope pattern (Feature IS the scan scope; see sub-rule below). The eight scan-outcome patterns together — no-hits / primary-site / complementary-hit / cascade / execution-time scope-expansion / restructure-scope / encompassed-by-restructure / scope-narrowed-cascade — cover the full space of scan results and keep the audit trail reconstructible.

## Restructure-scope pattern

For Feature-level architectural restructures whose scope IS the target's surface reorganization (new file creation, extraction to `references/`, file split, consolidation), the per-finding cascade scan concept is circular — the entire target's surface is affected by the restructure itself, so "scan for related text affected by the primary edit" does not meaningfully narrow. Report as `Finding N: restructure scope self-contained; encompassed-findings' primary-edit scans are reported separately under their own finding rows.` This is distinct from no-hits (no scan was warranted because nothing was textually local) and from cascade (where a primary edit needs mirror fixups elsewhere). The restructure IS the scan scope; do NOT collapse the Feature into the per-batch no-hits line, which is reserved for findings whose primary edit is textual-local. Each encompassed finding still carries its own per-finding scan line under its own finding number, per the Restructure-encompassing findings sub-rule in `references/follow-up-implementation.md` §Edit ordering. When an encompassed finding's content was baked directly into the Feature's restructure (rather than emitted as an independent edit), use the `encompassed-by-restructure` outcome — see the corresponding row in the Quick-reference table below.

## Multi-outcome per finding

When a single finding's scan produces hits that split across multiple outcome patterns (common case: a terminology-harmonization finding with parallel primary instantiations whose scan matches both the planned sites AND related non-target phrasing that stays consistent), compose a combined per-finding line that names each outcome with its hit count and its brief reason: `Finding N: <total> hits — <count-A> <outcome-A> (<reason-A>); <count-B> <outcome-B> (<reason-B>); <verdict — "no cascade" or "N cascade rows follow">.` The rule-of-thumb "exactly one outcome per finding" above applies when the scan's hits fall cleanly into one pattern; multi-outcome scans preserve the per-outcome breakdown so the audit trail records that hits of each kind were found and reviewed. Distinct from the Mixed-outcome batches rule above (which governs different findings in the same batch each having their own single outcome); this sub-rule governs one finding whose own hits span multiple outcomes. Multi-outcome per finding is a **composition** over the eight canonical outcome patterns, not a ninth pattern — the enumeration in the Complementary-hit confirmation pattern sub-rule remains complete. Worked instantiation: a terminology-harmonization finding applied at 4 parallel sites (`N.a`/`N.b`/`N.c`/`N.d`) scans for the same phrase across the file and finds 8 hits — 4 at the planned primary sites (`primary-site` outcome) and 4 at related phrasing that uses the same vocabulary but references different semantics (`complementary-hit` outcome); reports as `Finding N: 8 hits — 4 primary sites (lines L1/L2/L3/L4 — the planned N.a/N.b/N.c/N.d instantiations); 4 complementary (lines M1/M2/M3/M4 — related phrasing with different semantics, unchanged under the finding's rule); no extraneous cascade.` A 3-outcome instantiation demonstrates that the composition scales to any arity: a finding whose scan produces 1 planned primary site + 1 cascade-target hit (keyed N.cascade) + 1 complementary hit on unrelated-but-consistent existing content reports as `Finding N: 3 hits — 1 primary site (L1 — the planned Step 5 prose edit); 1 cascade (L2 — Process Flow diagram, keyed N.cascade); 1 complementary (L3 — step-name reference in HARD-GATE bullet; no per-message constraint in prose); 1 cascade row follows.` The 3-outcome form extends the 2-outcome pattern by appending a third `<count> <outcome> (<reason>)` clause before the verdict — no structural change to the canonical form.

## Cascade-scan discipline — search for semantic variants, not just exact strings

When the primary change is a count, a renamed term, or a structured label, grep BOTH the exact old string AND its semantic variants. For a count change (e.g., "11 → 12"), also search for the number rendered elsewhere: tabular summary rows, alignment tables, process-flow diagrams, prose paraphrases that state the count in different phrasing, ordinal forms ("twelfth"), and word-form spellings ("twelve").

**Adding or removing an enumeration value (a new Category, a new Phase, a new Rule, a new step) IS structurally a count change** — the count-phrase variants ("three categories", "four phases", "five rules", "these N categories", "one of these N items") are a class of cascade target distinct from the enum-LABEL variants and easy to miss when the primary edit is framed as "add a new label" rather than "increment a count". When the primary change is enum-addition or enum-removal, grep for BOTH (a) enum-label variants (existing `Category 1` / `Category 2` patterns AND the new label, e.g., `Category 2b`); AND (b) count-phrase variants (`Three categories` / `three categories` / `these N` / `one of these N` / `classify into N buckets`). Common count-phrase patterns to grep alongside the label patterns: cardinal number-word ("three", "four"), digit form ("3", "4"), ordinal form ("third", "fourth"), and the bracket prose ("one of these N", "these N items"). **Use case-insensitive grep for count-phrase-variant searches** (e.g., `grep -in 'three sub-classes'` or `grep -nE '[Tt]hree sub-classes'`). Sentence-initial capitalization at introducer-line variants is the most common miss-pattern; case-sensitive grep silently skips the capitalized form (e.g., `Three sub-classes` at a section's introducer line) while matching the lowercase form in body prose. Worked precedent: skill-audit on skill-audit (this session) — an Improvement that added Category 2b to a 3-category enumeration; the planning-time scan covered enum-label variants but missed count-phrase variants ("Three categories" at the rubric line, "these three categories" at the trailing-reference line); the verification backstop caught both as 2 cascade rows keyed `N.cascade-f` / `N.cascade-g` with `verification-backstop catch:` reason prefix. Adding enum-addition to the explicit count-change framing would have caught these at planning time. Second worked precedent: skill-audit on skill-creator (this session) — Improvement 3 added a fourth sub-class (d) to a 3-sub-class enumeration; the planning-time scan used case-sensitive `grep -nE 'three sub-classes'` and missed the sentence-initial-capitalized "Three sub-classes" at the sub-step 3 introducer line; the verification backstop caught it as `Improvement 3.cascade`. Case-insensitive grep at planning time would have caught it directly.

For a renamed term, also search for its plural, its adjective form, hyphenated variants, and compound constructions. For a structured label (e.g., `cf_id`), also search for prior names it may have used, its singular/plural siblings (`cf_ids`, `cf_refs`), and prose references that name the concept without the exact label.

For **new cross-references** — text that introduces a reference to a section name, field name, or file path that the original edit did not itself define (e.g., adding "Record this in the audit report's Parameters Interpretation Note" where that named section may not exist in the target's template) — there is no "old string" to grep for, so the scan shape inverts: for each new reference the edit introduces, verify during per-finding planning that the referent RESOLVES AT EXACT-STRING-MATCH against existing content in the target skill's shipped files (SKILL.md + templates/ + references/) — including capitalization, punctuation, whitespace, and header-hash count for markdown anchors; key name and quote style for YAML keys. Near-miss resolution — conceptually valid but lexically divergent (e.g., `§Place-type / polity composite handling` vs the actual `§Place-type / Polity Composite Handling` heading) — fails grep discoverability in future audits and forces a verification-backstop rework cycle. When the new cross-reference targets content YOU are creating in the same batch, draft the referent text FIRST (including its exact capitalization and punctuation), then copy-paste the exact string into the reference to eliminate drift. If it doesn't resolve, choose one of three repairs at planning time: (a) rename the new reference to an existing referent, (b) add the referent (as a template section or file, with its own cascade row), or (c) soften the reference to name acceptable alternative placement ("either as a standalone Section X or folded into Section Y"). Catching this at planning time prevents the verification backstop from being the primary detection mechanism for this shape.

For **structured-template targets** (proposal cards, batch manifests, dossiers — any file combining YAML frontmatter with a markdown body that renders the frontmatter concepts in tables, formulas, or worked examples), scan BOTH registers on any frontmatter schema change: (i) the frontmatter enum / field definition that the primary edit targets; AND (ii) the body-level rendering sections where the field is exemplified in tables, formulas, prose paraphrases, or worked examples. A frontmatter enum expansion without body-section update leaves the template internally inconsistent — the schema and its rendering disagree — and the body rendering IS part of the template's schema surface, not decorative explanation. Common two-register miss: adding a new value to a YAML enum in frontmatter, then discovering at verification that the template body has a table row and/or a formula string referencing the prior enumeration; both need updating to match the new schema. The verification backstop catches these misses, but per-finding scanning should aim to catch them at planning time. Over-scan is cheap; under-scan pushes the miss to the verification backstop, where the skill explicitly disallows it as a substitute for per-finding scanning.

For **terms whose meaning is context-dependent on a section's framing** (e.g., a failure-mode code that fires at both submit-time and retrieval-time, an enum value valid at multiple workflow phases, an option that applies in both pre-flight and post-completion), scan parallel-context sections for the term's absence as well as its presence. When a term is correctly used in section A (e.g., a §"Pre-apply / commit errors" row covering submit-time `index_stale`) AND a parallel-context section B exists where the same term would naturally also belong (e.g., §"Retrieval-time errors" or a §Pre-flight retrieval bullet covering retrieval-time `stale_index`), verify section B has its own framing of the term. Section B's absence of the term is a planning-time miss that the verification backstop will catch as a `verification-backstop catch:` cascade — preferable to catch at planning time. Decision rule: if a term has TWO distinct firing contexts in the operational world (both observable in the source material the skill consumes) AND only ONE is currently documented, the absent context is a section-context-completeness gap. Worked precedent: skill-audit on canon-addition (this session) — Issue 6's planning-time scan caught the create-base-world/references/engine-envelope-shape.md §6 cascade target (submit-time `index_stale` row needed a retrieval-time `stale_index` sibling row at the same section); the verification backstop caught the canon-addition/references/retrieval-tool-tree.md §Pre-flight gap (no retrieval-time `stale_index` recovery bullet next to `get_context_packet`, despite `get_context_packet` being the most common firing point for the retrieval-time variant) and produced an `Issue 6.cascade-b` row with `verification-backstop catch:` reason prefix. The two-context shape (submit-time vs retrieval-time for the same conceptual error) is the canonical example.

## Post-implementation summary

After all edits, present a summary table or list showing the status of each finding: "implemented", "superseded by finding N", "cascade from finding N", "co-edit with finding N", or "skipped (reason)". Additionally, for meta-findings whose suggestion is realized by other findings' primary edits rather than by a dedicated edit, use `implemented (realized via findings M, N, ...)` naming the contributing findings explicitly. This gives the user a clear per-finding status rather than requiring them to infer outcomes from the edit sequence.

## Severity-count line (optional)

After the status table, you MAY include a one-line count summary of the form `N audit findings → N primary edits + N cascades = N edit rows; M CRITICAL / X HIGH / Y MEDIUM / Z LOW combined`. Cascade rows inherit severity from their originating finding for counting purposes. Sub-keyed primary rows (`N.a`, `N.b`, `N.c`) each inherit severity from the parent finding for counting purposes, parallel to cascade rows — the M/X/Y/Z distribution reflects edit-row severity, not finding severity, so a finding with 2 co-equal primaries and 1 cascade contributes 3 rows to the distribution (not 1). Discarded rows (`now-moot — discarded`) appear in the status table for audit-trail visibility but are excluded from the severity-count line's edit-row distribution — count only rows that represent actual edit work (primary + sub-keyed primary + cascade), not rows that merely record that a finding was retracted during re-evaluation. The line is optional — omit when the status table's row count is small enough to enumerate at a glance (≤4 rows); include when the table has 6+ rows or when mixed-outcome batches produce cascade+primary combinations worth aggregating. The canonical decomposition (audit findings → primary edits + cascades = edit rows) preserves audit-trail reproducibility better than a single edit-row count, and is the recommended default; alternative shapes are acceptable when internally consistent but should preserve the audit-findings vs primary-edits vs cascades decomposition (e.g., `13 audit rows → 13 edit rows = 13 edit rows` collapses three distinct counts — 6 findings, 10 primaries, 3 cascades — into a single conflated count and loses the decomposition value the canonical form preserves). **Double-check before presenting** (parallel to `references/report-conventions.md` §Severity-count double-check applied to the audit-phase report): count primary edits, sub-keyed primary edits (`N.a` / `N.b` / ...), and cascades (`N.cascade` / `N.cascade-a` / ...) against the status table; verify the sum (primaries + cascades) equals the total edit-row count; verify the per-severity distribution (CRITICAL / HIGH / MEDIUM / LOW) sums to the same total; verify discarded `now-moot` rows are excluded from the edit-row count per the existing exclusion rule. If a correction is needed after presenting, strike the incorrect line and restate. Implementation-phase severity-count lines compound errors easily — a single arithmetic slip can produce wrong primary count, wrong total, and wrong per-severity distribution simultaneously, and the line's grep-searchability for future audits relies on correct counts.

**Restructure-encompassing arithmetic**: when the implementation includes a Feature-level architectural restructure that encompasses other findings' content (per `references/follow-up-implementation.md` §Restructure-encompassing findings), each encompassed finding's status row DOES count as a primary status row in the severity-count line — even though its physical edit is shared with the encompassing Feature's Write. The reason: the status table has a distinct row per encompassed finding (keyed by section-prefixed number, status pointing to the new file path where its content lives), and the severity-count line's `primary edits` term tallies status-table primary rows rather than distinct Edit-tool invocations. Using "primary status rows" instead of "primary edits" in the line's wording makes this explicit and preserves the §Double-check arithmetic invariant (`primary status rows + cascade rows = total status rows`). Worked example: `Feature 1 encompasses Issues 1 + 2 + Feature 2`; status table has 10 rows (Feature 1 + Feature 1.cascade-a + 3 encompassed-finding rows pointing to Feature 1's Write [Issue 1 / Issue 2 / Feature 2] + 5 independent primary rows [Improvements 1.a / 1.b / 2 / 3 / 4]); canonical line: `8 audit findings → 9 primary status rows + 1 cascade = 10 status rows; 1 CRITICAL / 3 HIGH / 4 MEDIUM / 2 LOW combined`. The 9 primary status rows decomposes as `5 independent primaries + 2 sub-keyed primaries (Improvement 1.a/1.b) + 2 encompassed-finding rows whose physical edit is Feature 1's Write` — but the line aggregates them all as `primary status rows` because each row is its own status-table entry that the reader will count when reconciling. Without this clarification, the implementation-phase author tends to undercount (only tallying distinct Edit-tool calls), producing a severity-count line whose arithmetic doesn't sum (e.g., `6 + 1 = 10` instead of `9 + 1 = 10`); the §Double-check rule would catch this if applied, but the underlying counting convention needs to be unambiguous before the double-check can succeed. Worked precedent: skill-audit on branching-story-bootstrap (this session) — the implementation-phase severity-count line read `8 audit findings → 6 distinct primary edits + 1 cascade = 10 status rows`, which doesn't satisfy `6 + 1 = 10`; the underlying gap was that 3 encompassed-finding rows (Issue 1 / Issue 2 / Feature 2) were not counted as primary edits because their physical edit was Feature 1's Write rather than independent SKILL.md edits. The corrected canonical form `9 primary status rows + 1 cascade = 10 status rows` would have satisfied the §Double-check invariant directly.

Shape is a judgment call; consistency within a single report matters more than a specific count schema.

## Quick-reference — row-keying by shape

Consult the Worked example block below for edge cases and rationale.

| Shape | Row keys | Status field |
|---|---|---|
| 1 finding → 1 edit | `N` | `implemented` |
| 1 finding → multiple co-equal parallel edits (same semantic change applied at N sites) | `N.a`, `N.b`, ... | `implemented` on each (do NOT add co-edit notation) |
| 1 finding → primary edit + cascade(s) | `N` + `N.cascade` (or `N.cascade-a` / `N.cascade-b` for multiple cascades) | `implemented` on primary; `cascade from finding N — <reason>` on cascade rows |
| 1 finding → new file/section creation + intra-file cross-reference pointer(s) | `N` + `N.cascade` (or `N.cascade-a` / `N.cascade-b` for multiple pointers) | `implemented` on primary (the file/section creation); `cascade from finding N — added cross-reference pointer at <site>` on cascade rows. Specialization of the row above; see Rule of thumb (companion) and the §Worked example "New reference file creation with required intra-skill pointers" entry below for full specification |
| Multiple findings → one shared edit | one row per finding, each keyed by its own number | `implemented (co-edit with finding M)` on each row, naming partners |
| Multiple findings → adjacent passages batched into one Edit tool call (or any other shape where each finding has its own distinct text fragment co-located with others) | one row per finding, each keyed by its own number | `implemented` on each row (baseline; do NOT use co-edit notation — passage granularity is the criterion, not tool-call granularity) |
| Meta-finding → no dedicated edit; realized by other findings' primary edits | `N` (finding keyed by its own number; no sub-keys) | `implemented (realized via findings M1, M2, ...)` naming the contributing findings |
| Feature-level architectural restructure encompassing other findings' content | `N` | `implemented — <restructure description>; encompasses findings M1, M2, ...` naming the findings whose content physically lives in the new structure |

Rule of thumb: condensing multiple parallel edits into a single summary row with a bulleted list of sites is non-compliant — use one row per edit. The sub-letter keying IS the co-equality signal; do not add redundant co-edit notation to it.

**Rule of thumb (companion — new file/section creation + pointer pattern)**: when a finding creates a new file or section AND existing files must be updated with cross-reference pointers for the new content to be discoverable, the file/section creation is the primary and each pointer is a cascade — NOT co-equal primaries. Co-equal primaries (`N.a` / `N.b`) apply only when the Finding's Suggestion names two or more substantive content creations as co-equal outputs. The pointer edit lacks primary semantic authority: its content (a ~30-word sentence naming the new file/section and its purpose) is dictated by the primary's existence, name, and purpose. Decision rule instantiation: if you removed the primary, the pointer becomes meaningless (nothing to point at); if you removed the pointer, the primary still makes sense — the pointer depends on the primary, not vice versa. See §Worked example "New reference file creation with required intra-skill pointers" below for the full specification.

List cascade edits as separate table rows keyed `N.cascade` (where N is the originating finding's number); the status column contains `cascade from finding N — <concise reason: one or two lines max, naming both the touched location and the substantive change>`. If a single finding requires multiple primary edits in different sections of the target skill (neither edit is a cascade of the other — both are co-equal owners of the suggestion), key them `N.a`, `N.b`, etc. Reserve `N.cascade` for edits that merely keep related text consistent with a primary change. When two or more separate findings are resolved by a single shared text edit (their Suggestions collapse onto the same passage), keep each finding as a distinct row in the summary table — key each by its original finding number and use the status `implemented (co-edit with finding M)` on each row to name the partners. Do NOT re-key them as sub-letters; `N.a`/`N.b` is reserved for one-finding-multiple-edits only. This preserves the finding-to-edit relationship so a reader of the status table can reconcile it against the audit's finding count. This keeps per-edit granularity consistent across audits.

**Anti-pattern (avoid)**: cascade-row reason fields exceeding 2 lines with embedded rationale about why a cascade was missed at planning time, or with rule-citations explaining the discipline that should have caught the miss. Such rationale belongs in the per-finding cascade-scan visibility line ABOVE the status table (per §Per-finding cascade scan visibility), not in the row reason. The row reason should be `cascade from finding N — verification-backstop catch: <touched location>; <substantive change>` — the visibility line carries the why; the row carries the what. When a verbose reason field is tempting because the substantive change has multi-step rationale, split the rationale across two emit points: the per-finding visibility line records the planning-time miss explanation and rule citation; the row reason records only the location + change summary. Worked precedent: skill-audit on skill-creator (this session) — the implementation phase's `Improvement 3.cascade` row reason was 4-5 lines long, embedding planning-scan-miss rationale and §Cascade-scan discipline rule-citation that belonged in the visibility line; the rule's "one or two lines max" wording allowed but didn't structurally prevent the over-stuffing. The split-emit pattern (visibility line carries why; row carries what) keeps both surfaces grep-discoverable for future audits without forcing readers of the status table to parse multi-paragraph reason fields.

## Worked example — status field by case

- Baseline (N findings, N independent edits): row `Improvement 1` → status `implemented`; row `Improvement 2` → `implemented`; row `Improvement 3` → `implemented`. No sub-lettering, no co-edit notation, no cascades. This is the default shape when each finding has its own independent text change and nothing cross-cuts.
- One finding, three edits: row `Improvement 1.a` → status `implemented`; row `Improvement 1.b` → `implemented`; row `Improvement 1.c` → `implemented`. The keying itself signals co-equality; do NOT add `(co-edit with Improvement 1.b/1.c)` to the status field.
- One finding, N parallel instantiations of the same semantic change (no primary): row `Improvement N.a` → `implemented`; row `Improvement N.b` → `implemented`; ...; row `Improvement N.g` → `implemented`. When a single finding's suggestion ("standardize phrasing X across the file") is applied to multiple parallel locations of the same target text, the edits are co-equal — none is "primary" with the others as "cascades." `N.cascade` requires a primary semantic change at one location with related-text fixups elsewhere; parallel instantiations of the same change lack that primary/cascade relationship and use `N.a`/`N.b`/... instead. Rule of thumb: if you can swap the order of any two edits without changing the meaning of the others, they are parallel co-equals, not primary-plus-cascade.
- Three findings, one shared edit: row `Improvement 1` → `implemented (co-edit with Improvements 4, 7)`; row `Improvement 4` → `implemented (co-edit with Improvements 1, 7)`; row `Improvement 7` → `implemented (co-edit with Improvements 1, 4)`. Each row names the other partners.
- One finding, two cascades in different sections: row `Improvement 3` → `implemented`; row `Improvement 3.cascade-a` → `cascade from Improvement 3 — <reason A>`; row `Improvement 3.cascade-b` → `cascade from Improvement 3 — <reason B>`. The `cascade-a / cascade-b` suffixes mirror the `N.a / N.b` pattern for primary edits and preserve per-edit granularity. When two cascades from the same finding are tightly coupled (the same conceptual change in adjacent text), it is acceptable to merge into a single `N.cascade` row instead.
- One finding, two co-equal primaries with one cascade each: row `Improvement N.a` → `implemented`; row `Improvement N.b` → `implemented`; row `Improvement N.cascade-a` → `cascade from Improvement N — <reason dependent on N.a>`; row `Improvement N.cascade-b` → `cascade from Improvement N — <reason dependent on N.b>`. When a finding has multiple co-equal primaries AND each primary has its own cascade(s), compose the `N.a/N.b` pattern with the `N.cascade-a/N.cascade-b` pattern. The `cascade-a`/`cascade-b` suffixes DO NOT have to align with the primary suffixes — a cascade's letter ordering reflects its own dependency position, not the primary it follows. Name the dependency explicitly in the reason field (e.g., "cascade from Improvement N — mirrored to sibling template per structural-identity claim; follows N.b primary") so a reader can reconstruct which primary each cascade depends on. Worked instantiation: a finding whose suggestion applies to two co-equal locations (the target skill's main file AND a paired sibling template) where each primary has its own dependent fixup — the main-file primary (`N.a`) has a cascade in a validation section (`N.cascade-a`) that cross-references the new content, and the template primary (`N.b`) has a cascade in a structurally-paired sibling template (`N.cascade-b`) that mirrors the change per a structural-identity claim. Either cascade could be applied before or after its companion primary; what matters is that each cascade's reason field names the primary it depends on so the reader can reconstruct the dependency graph from the status table alone.
- One finding, two co-equal primaries with a single cascade from one primary (asymmetric): row `Improvement N.a` → `implemented`; row `Improvement N.b` → `implemented`; row `Improvement N.cascade` → `cascade from Improvement N — follows N.a primary; <substantive reason naming touched location and change>`. When a multi-primary finding has exactly one dependent cascade rooted in only ONE of the primaries (e.g., verification-backstop catch that softens a new cross-reference introduced by `N.a` without touching `N.b`'s section), the single-suffix `N.cascade` key is acceptable PROVIDED the reason field explicitly names which primary the cascade follows ("follows N.a primary" / "follows N.b primary"). The letter-suffix `N.cascade-a` form is reserved for the multi-cascade case above; using it for a single cascade would imply an absent `N.cascade-b` and mislead the reader. Worked instantiation: a finding whose two primaries split across two phases (`N.a` in Phase 0, `N.b` in Phase 2) where only the Phase 0 primary introduced a new cross-reference that required a follow-up softening — the softening is one cascade, rooted in `N.a`, keyed `N.cascade` with reason "follows N.a primary; Phase 0 reference softened to name alternative placement." Decision rule: number of cascades determines suffix. Zero cascades → no cascade row. Exactly one cascade → `N.cascade` with reason naming the dependency. Two or more cascades → `N.cascade-a` / `N.cascade-b` / ... per the paired-cascade example above.
- Two findings, same file but different lines: row `Improvement 2` → `implemented`; row `Improvement 5` → `implemented`. Both rows are baseline `implemented`; do NOT use co-edit notation. Co-edit is reserved for a single shared text edit resolving multiple findings, not separate edits at different locations in the same file. If a reader wants to see that two findings touched the same file, that relationship is discoverable from the status-row reasons (which name the touched locations), not from the status field itself. Attempting to repurpose co-edit for same-file-different-lines conflates "shared text" with "shared file" and breaks the reader's ability to reconcile row counts against the audit's finding count.
- Two findings, adjacent passages batched into one Edit tool call: row `Improvement 2` → `implemented`; row `Improvement 3` → `implemented`. Both rows are baseline `implemented`; do NOT use co-edit notation. A single Edit tool call can replace one old_string with a new_string that inserts two or more distinct semantic blocks (e.g., a definition list for finding A and a table for finding B at the same insertion point). Tool-call granularity is NOT the co-edit criterion — passage granularity is. If the two new blocks could be described in independent sentences ("Improvement 2 added the family enumeration; Improvement 3 added the user-label mapping table"), they are separate edits despite being co-located and tool-batched. Co-edit is reserved for cases where one continuous passage simultaneously serves multiple findings (e.g., a subsection whose prose covers two findings in one breath, or a table whose rows collectively answer two findings). Rule of thumb: if you can point at distinct text fragments and say "this fragment resolves A, that fragment resolves B," they are separate edits; if the same fragment resolves both, it is co-edit.
- Two cascades from different findings batched into one Edit tool call: row `Issue N.cascade` → `cascade from Issue N — <reason>; batched in same Edit with Issue M.cascade`; row `Issue M.cascade` → `cascade from Issue M — <reason>; batched in same Edit with Issue N.cascade`. Both cascade rows stay keyed under their own originating findings; the batching is captured in the reason field, parallel to the primaries-batched pattern in the preceding example. Do NOT re-key as a single shared `N+M.cascade` row — that breaks the finding-to-edit reconcilability the keying preserves. Decision rule: batching is a tool-call optimization, not a keying criterion. Whether two cascades are in one Edit or two, each cascade row stays under its originating finding's number; the only thing that changes is whether the reason field names the batch partner. Worked instantiation: during canon-addition audit implementation, the SKILL.md Output section edit served BOTH Issue 1.cascade-a (clarificatory-retcon skips new-CF artifact — cascading from Issue 1's Clarificatory-Retcon Variant primary in accept-path.md) AND Issue 3.cascade (attribution-form extension — cascading from Issue 3's Placement convention primary in accept-path.md); keyed as two separate cascade rows with `batched in same Edit with Issue X.cascade` notes in each reason field. Distinguishes from co-edit (one passage resolves multiple findings — not applicable here; the Output section edit has distinct fragments for each cascade's concern) and from meta-finding (no dedicated edit — not applicable here; each cascade has its own identifiable fragment).
- One cascade batched with multiple primary edits from other findings into one Edit tool call: row `Issue N.cascade` → `cascade from Issue N — <reason naming what the cascade adds and why the primary depends on it>; batched in same Edit with Issue X primary, Improvement Y primary, and Improvement Z primary`. The cascade row stays keyed under its originating finding (Issue N); the batching is captured in the reason field naming each batch partner regardless of whether the partners are cascades or primaries. Decision rule: batching is a tool-call optimization, not a keying criterion (parallel to the preceding two-cascades-batched example) — whether the partners are cascades or primaries does not affect the cascade's keying, only the reason field's batch-partner enumeration. Worked instantiation: during storylet-pool-authoring audit implementation (this session), the templates/predicate-dsl.md edit was a single Edit tool call containing FOUR distinct concerns — Issue 1's primary (DSL expansion with documented extensions), Improvement 2's primary (new §Location-role matcher pattern section), Improvement 4's primary (new §Runtime evaluation mapping section), AND Issue 4's cascade (new §Obligation matcher schema section, supporting the storylet-record.yaml inline cross-reference); keyed as `Issue 4.cascade` with reason field `cascade from Issue 4 — added §Obligation matcher schema section to templates/predicate-dsl.md to support the storylet-record.yaml cross-reference; batched in same predicate-dsl.md Edit with Issue 1, Improvement 2, and Improvement 4 primary edits`. Distinguishes from co-edit (one passage resolves multiple findings — not applicable here; the predicate-dsl.md edit has four distinct sections, each serving its own finding) and from the preceding two-cascades-batched pattern (cascade-with-cascade — not applicable here; the partners are three primaries and one cascade, not two cascades).
- Cross-skill cascade vs cross-skill parallel: when a primary change in the target skill MUST be mirrored to a sibling skill's parallel file to preserve a stated structural-identity claim (e.g., "structurally identical to `<sibling>/templates/...`"), the sibling's edit is a cascade — key `N.cascade` (single mirror) or `N.cascade-a` / `N.cascade-b` (multiple mirrors). The sibling edit lacks primary semantic authority; it follows the target. In contrast, when a Finding's Suggestion explicitly names the sibling as a co-equal target ("update both paired templates"), the sibling edits are parallel primary edits — key `N.a`, `N.b`, `N.c`, `N.d` across all co-equal locations. **Third branch — shared-surface-trigger discovery**: when a sibling edit is required because a shared-surface trigger (per `references/cross-skill-consistency.md` §Concrete shared-surface triggers — shared terminology that appears in multiple skills, an alignment-convention statement, a consumer-side schema dependency, or any other surface enumerated there) creates an implicit cascade dependency, the sibling's edit is a cascade — key `N.cascade`, parallel to the structural-identity-claim case. This applies whether the sibling's content "follows" the target edit byte-for-byte (structural-identity case) OR the sibling has its own independent instance of the same semantic change discovered via sibling-scan (shared-surface-trigger case — e.g., parallel post-SPEC-13 staleness in a sibling SKILL.md discovered via defensive grep, where both target and sibling have their own stale references that need the same semantic update). Decision rule: if the sibling edit is discovered by sibling-scan or any §Concrete shared-surface triggers list rule rather than explicitly named in the Finding's Suggestion as a co-equal target, key as `N.cascade`. Otherwise, the original decision rule applies: if the sibling edit's content is dictated by the target edit's content (the sibling just copies the new text), it is a cascade; if both edits instantiate a shared semantic change AND the Finding's Suggestion explicitly names them as co-equal targets, they are parallel primary edits. When in doubt, prefer cascade keying — it preserves the finding-to-primary-edit relationship and makes the target-skill's authoritative role explicit.
- New reference file creation with required intra-skill pointers: row `Feature N` → `implemented`; row `Feature N.cascade-a` → `cascade from Feature N — pointer in SKILL.md <section>: added "see <new-file-name>" cross-reference`; row `Feature N.cascade-b` → `cascade from Feature N — pointer in references/<sibling-reference>.md <section>: added "see <new-file-name>" cross-reference`. When a finding creates a new reference file (or template, or any content file that other files must discover via cross-reference for the new content to be load-bearing), the file creation is the primary edit and each cross-reference pointer added in existing files is a **cascade**, keyed `N.cascade` (single pointer) or `N.cascade-a` / `N.cascade-b` / ... (multiple pointers). The pointer edits lack primary semantic authority — their content (a ~30-word sentence naming the new file and its purpose) is dictated by the new file's existence, name, and purpose, which the primary edit established. Decision rule instantiation: if you removed the new-file-creation primary, the pointer edits become meaningless (there is nothing to point at); if you removed one pointer but kept the primary, the other pointer and the primary still make sense — the pointers depend on the primary, not on each other. This is an **intra-skill** cascade shape (same skill's SKILL.md + references mirrored by the new file's existence), distinct from the cross-skill structural-identity-claim case in the preceding example. Worked precedent: canon-addition PA-17 Feature 1 — new file `references/phase-15a-checkpoint-grep-reference.md` (primary) + cross-reference pointer in SKILL.md §Phase 15a write-phase progress discipline (`Feature 1.cascade-a`) + cross-reference pointer in `references/accept-path.md` §Phase 15a sub-step 4 (`Feature 1.cascade-b`). Decision rule: parallel primaries (`N.a` / `N.b`) would apply only if the Finding's Suggestion named two or more file creations as co-equal outputs; here the Suggestion named ONE new file plus pointers-as-byproduct, so primary-plus-cascades is correct.
- Meta-finding resolved by other findings' primary edits: row `Issue 1` → `implemented (realized via Improvement 1 and Issue 2)`; row `Improvement 1` → `implemented` (baseline); row `Issue 2` → `implemented` (baseline). When a finding's suggestion is strategic or architectural (e.g., "inline load-bearing content," "unify terminology across sections," "reduce duplication") and its implementation is emergent from the primary edits of OTHER findings rather than a dedicated edit of its own, use this shape. The row uses the finding's own number with no sub-keys — it has no dedicated edit to key. Distinct from co-edit: co-edit requires one shared passage resolving multiple findings; here multiple DIFFERENT passages, each for its own finding, collectively resolve the meta-finding. Decision rule: if finding N has no text uniquely attributable to it, and the edits that resolve N are all primary edits for other findings, use the meta-finding shape. If finding N has at least one text fragment uniquely attributable to it (even if tiny), use `N.a` + co-edit or `N.cascade` instead. The status's parenthetical MUST name every contributing finding by its section-prefixed key so the audit trail is reconstructible from the status table alone.
- Feature-level architectural restructure encompassing other findings' content: row `Feature 1` → `implemented — 7 references files created + SKILL.md rewritten as thin entry point; encompasses Issues 1-3 and Improvements 1-5 whose content lives in the new references/` (baseline with descriptive reason naming the encompassed findings); row `Issue 1` → `implemented — primary edit in references/preflight-and-prerequisites.md §Oversize-File Protocol` (baseline with location pointing to new file); row `Improvement 3` → `implemented — primary edit in references/phases-7-8-validate-and-commit.md §HARD-GATE Response Mapping` (baseline with location pointing to new file). When a Feature's suggestion IS an architectural restructure (file extraction, new directory creation, file split or merge) and that restructure physically houses other findings' content, key the Feature with its own number and use the status `implemented — <restructure description>; encompasses findings M1, M2, ...` naming the encompassed findings explicitly; each encompassed finding stays keyed by its own section-prefixed number with its status pointing to the specific new file path its content lives in. Decision rule: distinct from meta-finding shape — meta-findings have NO dedicated edit (status says `realized via findings ...`), while restructure-encompassing Features HAVE a dedicated architectural edit (the file creation / SKILL.md rewrite itself) plus encompassed content. Distinct from co-edit — co-edit requires a single shared passage resolving multiple findings; here the Feature's architectural edit (creating the new files) and each encompassed finding's content edit (the actual text inside each file) are physically distinct fragments living in different new files. The Feature's status-row reason explicitly names the encompassed findings so a reader of the status table can reconstruct the encompassing relationship without reading the edited files.
