# Follow-up Implementation

After the audit report is presented, the user may request implementation of specific suggestions. At that point, edit the target skill file directly — the "report only" guardrail applies only to the audit phase, not to user-directed follow-up.

## Common path (checklist)

1. Check if any skill file covered by findings (SKILL.md plus any `references/*.md` or `templates/*.md` files cited in the audit's per-finding Suggestion or Skill gap fields) has either changed since the audit report OR carries a claim premise that re-reading at implementation time would falsify (see §Re-evaluation below for both trigger conditions) → if yes, run **Re-evaluation** (below).
2. Read user request: partial ("implement 1, 3") vs. full ("implement all" / "implement recommended" — synonymous).
3. Apply edits in document order (top → bottom); scan each for **cascades** before applying. **Before any Edit call in this batch, ensure the target file has been Read in the current session via a Read tool invocation — the Edit tool's `File has not been read yet` validator REQUIRES a session-level Read regardless of in-context content from any of: (i) skill-invocation-embedded loading (slash-command body injection, when the target skill was invoked earlier in the session and its full body was embedded in the prompt); (ii) grep / Bash / search-tool output (cascade-scan greps, prior greps, command-output inclusions that quote file content); (iii) web-fetch and other tool-result inclusions that surface file content via a tool other than Read (e.g., MCP retrieval responses that include file content). If only such non-Read in-context content is available (no explicit Read), run a fresh Read first; otherwise every Edit in this batch will fail with the validator error and need a Read-then-retry recovery. The precondition applies to ALL files the implementation batch will Edit — primary-edit targets AND cascade-target files surfaced via the per-finding cascade scan; when the per-finding scan grep returns hits in a file whose content is in context only via grep output, run a fresh Read of that file's relevant region before applying the cascade Edit. Worked precedent: skill-audit on canon-addition (this session) — Improvement 4's cascade-scan grep surfaced `references/retrieval-tool-tree.md:52` as a cascade target; the file's content was in context only via the grep output; the cascade Edit was batched alongside two primary edits at files Read earlier in the session and failed with `File has not been read yet`; recovery was a 30-second targeted Read followed by a single Edit retry. The pre-Edit Read of cascade targets prevents this recovery cycle. For files exceeding the Read tool's per-call token cap (~25k tokens currently), any chunked Read (`offset` + `limit` parameters) of the file in the current session satisfies the validator — the validator checks whether a Read tool was invoked against the file path, not whether the full file body was returned in any single call. Read the regions covering each finding's primary edit; multiple chunked Reads of the same file accumulate, and one prior chunked Read at any region of the file is sufficient to satisfy the precondition for an Edit at any other region. Worked precedent: skill-audit on branching-story-bootstrap (this session) — SKILL.md was 25,169 tokens (just over the 25k Read cap); the implementation phase read the file in three offset/limit chunks covering lines 1-220, 220-490, and 488-688; all 5 Edits across those chunks applied without `File has not been read yet` errors because each Edit's region was within at least one of the chunked Reads — and the validator would have accepted Edits at any region given any one prior chunked Read on the file path.**
4. Re-read all edited files; run the **post-edit verification** pass (5 checks for non-meta-tooling targets; 6 checks when the target is a meta-tooling skill) — see `references/post-edit-verification.md`.
5. Present the **post-implementation summary**: per-batch cascade-scan line FIRST — confirms the scan ran even when it found nothing; see the `Per-finding cascade scan visibility` sub-rule in `references/cascade-and-summary-discipline.md` — THEN the table (Finding | Severity | Status). Placing the cascade-scan line AFTER the table breaks the audit-trail ordering: readers should see scan discipline confirmed before they interpret table rows.
6. If a stated structural-identity claim in the target forces a sibling-file mirror, apply the **cross-skill cascade** (keyed `N.cascade` in the summary).
7. Separately, if the target is meta-tooling and any edit touched shared terminology or conventions, run the **cross-skill sibling scan** (with a named scan method) and document in the summary. Steps 6 and 7 are independent — a single implementation may require either, both, or neither — see `references/cross-skill-consistency.md`.

   **Document the scan outcome with the canonical line for its shape (applies to step 7).** The Quick-reference table immediately below enumerates five canonical-line forms keyed by target classification + scan outcome, with explicit form-letter labels (a)–(e) so audit reports and post-implementation summaries can reference forms unambiguously. Use the literal phrasing shown in code spans verbatim — paraphrased variants (e.g., "the sibling-scan operation does not apply" in place of `Scan not performed — <reason>`) break grep-searchability for future audits tracing scan discipline across sessions. The five forms cover the full matrix: form (a) scan-not-performed (non-meta-tooling, no scan needed); form (b) scan-ran-clean (either category, scan ran and found no inconsistencies — covers the historically-named non-meta-tooling defensive-scan-clean case that closed a prior matrix gap); form (c) defensive-scan-skipped (meta-tooling no-shared-surface, judgment-determined skip); form (d) scope-narrowed (either category, scan ran and narrowed to zero cascades); form (e) cascade-applied (either category, scan ran and at least one cascade was applied). The form-letter assignments preserve the historical (a) and (b) naming used in `references/cross-skill-consistency.md` §Skill Category Classification (where Category 2 / 2b / 2c descriptions cite `form (b)` for scan-ran-clean and Category 3's skip case cites `form (a)` for scan-not-performed); the (c) / (d) / (e) letters are net-new explicit assignments for previously-unlabeled forms. Audit-phase Cross-Skill Scan section forms (1)–(6) in `SKILL.md` use a parallel-but-distinct numbering system specific to audit-phase outcomes — do not conflate audit-phase form (1) with implementation-phase form (a), etc.

## Re-evaluation

If any skill file covered by findings (SKILL.md plus any `references/*.md` or `templates/*.md` files cited in the audit's per-finding Suggestion or Skill gap fields) has either (a) **changed** between the audit report and any follow-up-implementation batch — whether from an external edit (a different session or user action outside the audit flow), a previous partial-implementation batch in this same session, or a user-directed edit to the target between report and follow-up — OR (b) been **re-Read at implementation time and revealed that the audit's stated premise about the file's content no longer matches the current state** (most commonly: an audit Suggestion claiming X is missing turns out wrong because X was already present at audit time but the auditor did not load that file before drafting the finding — see `references/audit-execution-discipline.md` §Pre-finalization verification for the audit-phase prevention pattern), re-evaluate each finding against the current state before applying edits.

**How to check**: before applying any edits in the implementation batch, re-Read the file regions covered by each finding's primary edit. Two distinct trigger conditions:

- **File-change detection**: if the audit's quoted old-string text is no longer at the cited location, the file has changed. Re-evaluation required.
- **Premise-falsification detection**: if the audit's Suggestion or Skill-gap field claims X is missing but the re-Read shows X is present (or the inverse — claims X is present but re-Read shows X is absent), the audit's premise is falsified even though the file itself did not change between audit and implementation. Re-evaluation required.

The per-finding cascade scan during edit application is NOT a substitute for the region re-Read covering each finding's primary-edit location; cascades may serve as a backstop when a finding's primary-edit text is terminologically related to other content, but the primary detection mechanism for both file-change and premise-falsification is the explicit pre-edit region re-Read.

Discard obsolete findings, adapt shifted ones, and renumber survivors. Announce the re-evaluation explicitly before applying any edits in the new batch: "Re-evaluating N remaining findings against the current state..." (use "current state" rather than "modified target file" since the trigger is now broader than file modification) followed by a one-line outcome per finding (`still-valid` / `target-shifted — adapted` / `premise-falsified — adapted` / `now-moot — discarded`). When no edits have touched the target files between the report and the current batch AND no premise-falsification was detected at the region re-Read, the full per-finding announcement may be replaced by a single confirmation line (e.g., "No target edits since audit and no premise-falsification detected; proceeding without re-evaluation.") or omitted entirely. The full per-finding announcement is required only when at least one finding triggered re-evaluation under either condition.

**Same-session-unchanged carve-out**: When the target file is known unchanged in the same session (no external edits, no prior partial-implementation batch in this session, no system-reminder of mid-flow modification) AND its relevant regions are in context from prior session reads (e.g., audit-phase Reads at Step 1, plus any Pre-finalization verification re-Reads from Step 6), the implementation-start region re-Read at "How to check" above may be skipped; the shortcut single-confirmation-line still applies because premise-falsification is structurally impossible without file changes. The strict reading of the rule (region re-Read always required regardless of context-availability) produces ceremonial re-Reads with zero new information when the file is structurally unchanged in-session; this carve-out makes the optimization explicit. The carve-out does NOT apply when ANY of: a prior partial-implementation batch in this session edited the target, an external edit landed mid-flow (per system-reminder or other tool-call evidence), the audit's quoted old-string text is no longer in context (compaction, context rotation, large intervening read pushing earlier content out of the window), or the operator is uncertain whether the file changed — in any of those cases the explicit region re-Read is required regardless of session-level "unchanged" claims. Worked precedent: skill-audit on skill-creator (this session) — the implementation phase emitted the shortcut confirmation line directly without a separate implementation-start region re-Read because the audit-phase Reads at Step 1 had loaded the affected regions and no in-session edits had touched them; the file was indeed unchanged and no premise-falsification surfaced; under this carve-out the shortcut was structurally safe. Pair this carve-out with the §Common path step 3 Edit-tool precondition: that precondition is satisfied by any prior session Read; this carve-out adds the parallel rule that the Re-evaluation re-Read may also be satisfied by audit-phase Reads when the file is known unchanged.

**Premise-falsification can surface at TWO distinct points**: (a) at the upfront region re-Read (the rule's primary detection mechanism above), or (b) at per-finding cascade-scan time when the scan's grep returns hits that disprove the audit's claimed-absent content (the upfront re-Read covers the audit's cited regions; the cascade scan often covers a wider terminology surface, including content the audit didn't cite, where premise-falsification can surface late). The single-confirmation-line shortcut requires that BOTH passes complete cleanly. If premise-falsification surfaces during cascade scanning after the shortcut has been emitted, retract the shortcut explicitly with a re-evaluation amendment (`Re-evaluation amendment: <Finding> triggered premise-falsification at cascade-scan time — adapted Suggestion to <new wording>; <still-valid / target-shifted — adapted / now-moot — discarded>.`) BEFORE applying the affected finding's edits, parallel to the upfront re-evaluation announcement format. The retroactive note in the post-implementation summary's reason field is a backstop, not a substitute for the amendment announcement. Worked precedent: skill-audit on branching-story-bootstrap (this session) — the implementation phase emitted the shortcut confirmation line at start; Improvement 6's premise-falsification (the audit's claim that `target_page_length` source was unspecified, vs. the SKILL.md arguments doc already documenting it) only surfaced during the per-finding cascade-scan grep; under this rule, the shortcut should have been retracted via amendment before applying the affected edits, rather than noted post-hoc in the cascade-scan section.

**Discarded-row reason field**: discarded rows in the post-implementation status table use the canonical status `now-moot — discarded` followed by a brief reason field naming what changed (e.g., `now-moot — discarded; references/X.md was rewritten between audit and implementation to assume Y had landed`). The reason field is required, parallel to the cascade-row reason convention — both serve audit-trail reproducibility.

## Partial implementation

If the user requests specific findings (e.g., "implement 1 and 3"), check whether skipped findings depend on implemented ones. If so, note the dependency and ask whether to include the dependent finding. If the user requests implementation without naming specific findings (e.g., "implement all", "implement recommended", "implement suggestions", or any similar inclusive phrasing — all synonymous under the default semantics), skip dependency checking and apply every finding in document order except those explicitly tagged `— skip`, `— informational`, or `— no change needed` in the audit report.

## Finding identifier convention

Findings are identified by section-prefixed numbering from the Report Template (`Issue 1`, `Issue 2`, ...; `Improvement 1`, `Improvement 2`, ...; `Feature 1`, ...). Each section has its own 1-based counter. When the user requests "implement 1 and 3", default interpretation is "Issue 1 and Issue 3"; if the audit has fewer Issues than the requested number, confirm the section before proceeding ("did you mean Improvement 1 and Improvement 3?"). For the post-implementation summary table, prefer section-prefixed row keys (`Issue 1`, `Improvement 1`, `Feature 1`) so the reader can reconcile row counts to the audit's per-section counts at a glance; flat-continued numbering (1–N across all sections) fuses two schemes and is discouraged.

## Edit ordering

Apply edits in document order (top to bottom) to minimize line-number shifts invalidating later edits. **Parallel Edit tool-call batching** (multiple Edit blocks sent in a single tool call) is equivalent to sequential document-order application when each `old_string` is unique and non-overlapping — Edit matches on exact string content, not line position, so shifts from one edit cannot invalidate another's match. Prefer parallel batching when old_strings are unique and non-overlapping; fall back to sequential only when an edit's `new_string` would be re-matched by a later edit's `old_string` (creating ambiguity) or when the edits touch overlapping text regions. This tool-call-granularity optimization is distinct from the sub-letter `N.a` / `N.b` "parallel edits" pattern documented in the post-implementation summary section — that pattern is about semantic co-equality of edits serving one finding; the optimization here is about tool-call execution shape.

For multi-file targets (skills with `references/` or `templates/` sub-directories where findings distribute across multiple files), batch all edits within one file before moving to the next — do NOT interleave by finding number across files. File-batch order may follow the target's own load order (as listed in its SKILL.md Procedure steps), Phase/Step order, or alphabetical order of filenames — any order that avoids per-file re-reads between findings and keeps each file's cascade scan localized. Within each file, apply edits top-to-bottom per the primary rule.

If applying an earlier finding renders a later finding moot (e.g., the target text no longer exists), skip the moot finding and note it in the post-edit verification as "superseded by finding N." If an Edit call fails with "String to replace not found in file," the most common causes are (a) a prior edit in the same batch shifted the target text, or (b) the `old_string` was constructed from memory rather than from a fresh Read and doesn't match the baseline exactly. In either case, use Grep or a targeted Read to find the current text, then retry with the corrected `old_string`. **Proactive prevention for cause (b)**: when drafting an `old_string` for an edit at a location that was Read earlier in the audit phase but not in the current implementation batch, prefer constructing the `old_string` from a fresh targeted Read of the region (5-15 lines with a few lines of flanking context) rather than from in-context content carried over from the audit phase. Audit-phase Read content is reliable for semantic understanding but unsuitable for byte-exact text construction — whitespace, numeric prefixes, list-item markers, and trailing punctuation are easily misremembered, and the failure mode is silent until the Edit tool reports "String to replace not found in file." The fresh Read takes seconds and preempts the recovery cycle named above. Skip this hedge when (i) the edit's location was already re-Read in the same implementation batch (e.g., the Re-evaluation rule's region re-Read just ran for a triggered finding and the target is in the re-Read region), or (ii) the `old_string` is short enough that a visual cross-check against in-context content reliably catches a byte mismatch. The hedge is a draft-time complement to cause (b)'s recovery, not a replacement for it. If an edit inserts a new numbered step, renumber all subsequent steps and verify that the output summary or other sections referencing step numbers are updated accordingly. When an edit inserts or removes a numbered item, scan preceding edits in the same batch for cross-references to the shifted numbers and fix them in the same edit or immediately after.

## Restructure-encompassing findings

When a Feature-level finding prescribes an architectural restructure (new file creation, extraction to `references/`, file split, consolidation) that encompasses the surface area of other findings' primary edits, apply the Feature's restructure first and bake each encompassed finding's content into the new structure as it is being created. Status-key each encompassed finding by its normal number with its primary-edit location pointing to the new file path (e.g., `implemented — primary edit in references/phase-6-canon-safety-check.md`); key the Feature itself with a descriptive reason naming the restructure scope and the encompassed findings (see the dedicated Quick-Reference row and Worked example in `references/cascade-and-summary-discipline.md` §Post-implementation summary).

This is distinct from the meta-finding shape (which has no dedicated edit); the Feature HAS a dedicated architectural edit (the file creation itself), but that edit physically houses other findings' content. Without this pattern, strict document-order application forces the monolithic-edit-then-restructure double-work path — other findings' content lands in the monolithic SKILL.md first, then has to be moved into the new references/ files when the restructure runs, rewriting the same content twice. Applying the restructure first and baking in during file creation avoids the double-work.

## Mid-implementation primary-edit scope-narrowing

If per-instantiation investigation at implementation time reveals that a planned primary edit site has a categorically different shape than the audit suggestion implied (e.g., a suggested "mirror in all class-specific checks" would not make semantic sense for one class because that class's surface shape rules the proposed change out), it is acceptable to narrow the primary-edit scope. Announce the scope-narrowing explicitly in user-facing text before applying the remaining primaries, naming the excluded site and the categorical-different-shape reason: `Primary-edit scope decision: <excluded site> excluded because <reason>; applying primary at <remaining sites>.` Status-key the row(s) you DID apply per the normal `N.a` / `N.b` / ... convention with a sub-key count reflecting actual applied sites (not originally-implied sites).

Do NOT silently skip divergent primary sites — the announcement preserves the audit trail that an audit-suggestion-to-implementation gap existed and was resolved with judgment rather than by oversight, and it lets a future reader reconstruct why the post-implementation summary has fewer primary rows than the audit's Suggestion field implied.

This is distinct from Re-evaluation (which addresses target-file changes OR premise-falsification between audit and implementation) and from Partial implementation (which addresses user-specified finding subsets); primary-edit scope-narrowing is operator-directed at implementation time when the audit suggestion's site count was implicit or interpretable. Symmetric with Mid-implementation cascade scope-narrowing in `references/cross-skill-consistency.md` — the same reasoning ("categorical-different surface shape, absent parallel section, sibling-coherence-breaking content" adapted to within-target instantiations) applies to primary edits as to cascades.

Worked precedent: a skill-creator audit's Improvement 1 suggested adding a fourth scope label and "mirror in Step 6 canon-reading checks" — implementation-time investigation revealed canon-mutating skills don't write at root-level surfaces, so the fourth label can't apply to canon-mutating's Step 6 check; scope was narrowed to canon-reading + meta-tooling Step 6 sites (3 primaries — Step 4 gap-filler + Step 6 canon-reading + Step 6 meta-tooling — keyed `1.a` / `1.b` / `1.c`) with the canon-mutating site explicitly excluded and the reason announced before applying.

## Mid-implementation primary-edit scope-expansion

If per-instantiation investigation at implementation time reveals that an additional parallel primary edit site exists that the audit suggestion did not enumerate (e.g., a Suggestion implying a 2-site pattern but a cascade-scan grep at implementation time surfaces a third parallel site documenting the same convention with variant terminology), it is acceptable to expand the primary-edit scope. Announce the scope-expansion explicitly in user-facing text before applying the expanded primary set, naming the additional site and the audit-to-implementation gap reason: `Primary-edit scope decision: <additional site> added because <reason — typically "audit's Suggestion implied N sites; cascade-scan grep at implementation time surfaced this additional parallel site documenting the same convention with variant terminology">; applying primary at <expanded sites>.` Status-key the row(s) per the normal `N.a` / `N.b` / ... convention with a sub-key count reflecting actual applied sites (not originally-implied sites); in the reason field of one row (typically the added site's row), name the audit-to-implementation expansion explicitly so a future reader can reconstruct why the post-implementation summary has more primary rows than the audit's Suggestion field implied.

Do NOT silently add divergent primary sites — the announcement preserves the audit trail that an audit-suggestion-to-implementation gap existed and was resolved with judgment rather than by oversight, parallel to scope-narrowing's silently-skip prohibition.

This is distinct from Re-evaluation (which addresses target-file changes OR premise-falsification between audit and implementation) and from Partial implementation (which addresses user-specified finding subsets); primary-edit scope-expansion is operator-directed at implementation time when the audit suggestion's site count was understated. Symmetric with §Mid-implementation primary-edit scope-narrowing above (audit-over-promised, narrowed at implementation) and with §Execution-time scope-expansion labeling in `references/cascade-and-summary-discipline.md` (the cascade-side analogue: planning-time scan correctly classified a site as `complementary-hit`, executor decides at edit-application time to upgrade it to a cascade-equivalent edit). The four corners of the 2x2 matrix (primary vs cascade × narrow vs expand) are: scope-narrowing on primary (this file, §above) + scope-narrowing on cascade (`references/cross-skill-consistency.md` §Mid-implementation cascade scope-narrowing) + scope-expansion on cascade (`references/cascade-and-summary-discipline.md` §Execution-time scope-expansion labeling) + scope-expansion on primary (this section). The primary-side prevention for scope-expansion lives at audit time per `references/audit-execution-discipline.md` §Pre-finalization verification §Site-counting for parallel-instantiation Suggestions — site-counting at audit time prevents implementation-phase scope-expansion; this scope-expansion rule is the recovery when audit-time site-counting was nonetheless incomplete.

**Recovery for unannounced scope-expansion**: if the operator realizes during the post-implementation summary phase that scope-expansion was applied without the upfront announcement, the canonical recovery is to (a) record the expansion in the affected row's reason field with a `post-hoc scope-expansion:` prefix naming the audit-to-implementation gap, AND (b) note the missed announcement in the per-finding-scan-visibility section as `post-hoc scope-expansion recovery applied at row N.b — upfront announcement missed`. The recovery preserves audit-trail reproducibility; silent expansion (no reason-field record at all) violates the rule's underlying audit-trail discipline. This recovery is a fallback, not a substitute for the upfront announcement — the prevention pattern remains preferred. Symmetric with the silently-skip prohibition for cascade scope-narrowing (`references/cross-skill-consistency.md` §Mid-implementation cascade scope-narrowing) — both rules treat undocumented scope changes as audit-trail defects requiring explicit recovery rather than tacit acceptance.

Worked precedent: a skill-creator audit's Improvement 2 (this session) suggested extending the conformance-check N/A authorization at one cited line (`references/foundations-conformance-check.md` line 34) plus "Add a parallel line at the meta-tooling section for symmetry" (line 43) — implying a 2-site pattern. Implementation-time cascade-scan grep for the underlying convention's variant phrasing ("monotonic-ID outputs at pipeline scope") surfaced a third parallel site at `references/skill-design-drafting.md`'s Pre-flight Check guidance, which documented the same allocator distinction with different terminology. Scope was expanded to 3 primaries (`2.a` / `2.b` / `2.c`) with the third site's row reason naming the audit-to-implementation expansion: "added because audit's Suggestion implied 2 sites; cascade-scan grep at implementation time surfaced this additional parallel site documenting the same convention with variant terminology."
