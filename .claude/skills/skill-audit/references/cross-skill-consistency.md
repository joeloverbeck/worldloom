# Cross-Skill Consistency

If the target skill is part of a multi-skill workflow AND any finding affects interfaces shared with sibling skills, scan sibling skills for inconsistencies. Report cross-skill inconsistencies as Issues. Skip when all findings are internal to the target skill.

## Skill Category Classification

Load-bearing for sibling-scan applicability and FOUNDATIONS-alignment expectations. Five categories of target skill (Categories 1, 2, 2b, 2c, 3), with distinct sibling-scan and FOUNDATIONS-alignment expectations:

- **(1) Meta-tooling** — `brainstorm`, `skill-creator`, `skill-audit`, `skill-consolidate`, `skill-extract-references`, `mcp-integration-audit`. These operate on the pipeline itself (skills, design docs, audit discipline, consolidation/extraction operations on existing skills). FOUNDATIONS-alignment is N/A per Step 4 (they do not touch canon/world-model design). Sibling-scan is APPLICABLE as defensive default whenever an edit touches shared terminology, conventions, or tag semantics — even when no shared-surface trigger explicitly fires (the Extends-to-user-directed-edits-on-meta-tooling-skills sub-rule below codifies this).
- **(2) Canon-pipeline-adjacent** — `propose-new-worlds-from-preferences`, `propose-new-canon-facts`, `propose-new-characters`, `canon-facts-from-diegetic-artifacts`, `continuity-audit`, `reassess-spec`, `spec-to-tickets`. These produce inputs that downstream canon-mutating skills consume (proposal cards, audit reports, retcon proposals, tickets, specs). FOUNDATIONS-alignment APPLIES per Step 4 (they govern canon-pipeline proposals, specs, or tickets). Sibling-scan is APPLICABLE for consumer-side schema dependencies (per the Concrete shared-surface triggers list); a defensive sibling scan is RECOMMENDED even when no shared-surface trigger fires, because cross-pipeline schema drift between proposal-pipeline siblings is a real risk (e.g., one propose-new-X skill's frontmatter convention drifting from a sister skill's). Use form (b) `Cross-skill sibling scan: Scanned: <list> via <method> — no inconsistencies.` when the defensive scan runs clean (per the Common path checklist sub-clause "When the target is NOT meta-tooling but a defensive scan was run anyway" in `references/follow-up-implementation.md`).
- **(2b) Canon-reading content-generation** — `character-generation`, `diegetic-artifact-generation`. These produce hybrid-file content artifacts (character dossiers, diegetic-artifact files) under `worlds/<slug>/characters/` and `worlds/<slug>/diegetic-artifacts/` that READ canon (CFs / INVs / M / SEC records) and consult Mystery Reserve firewalls but do NOT mutate canon — though their outputs CAN be inputs to a downstream canon-addition run if a future canonization of a specific NPC or artifact is requested. Primary mutation surface is `worlds/<slug>/characters/` or `worlds/<slug>/diegetic-artifacts/` — distinct from Category 2's pipeline-input surfaces (proposals, audits, tickets, specs) and from Category 3's `_source/<subdir>/*.yaml` canon records. FOUNDATIONS-alignment APPLIES per Step 4 (Rules 2 / 3 / 4 / 7 govern dossier and artifact construction — material-reality citation, capability stabilizers, distribution conformance, mystery-firewall discipline). Sibling-scan is RECOMMENDED-as-defensive-default when an edit touches consumer-side schema or shared-surface triggers (parallel to Category 2's posture); a defensive sibling scan is acceptable even when no trigger fires, because cross-skill drift between paired hybrid-file producers (character dossier ↔ diegetic-artifact frontmatter, both engine-routed via `append_*_record` ops) is a real risk. Use form (b) `Cross-skill sibling scan: Scanned: <list> via <method> — no inconsistencies.` when the defensive scan runs clean.
- **(2c) Story-pipeline content-generation** — `story-character-profile`, `branching-story-bootstrap`, `branching-story-turn-cycle`, `branching-story-scene-plan`, `branching-story-scene-prose-attach`, `commitment-block-authoring`, `branching-story-health-audit`, `story-fact-promotion-to-canon`, `story-promotion-closeout` (the nine story-pipeline skills per FOUNDATIONS §Story Bundles §7). These produce story-bundle records (STCHAR / STENT / STINT / SF / BEL / SE / OBL / CNSQ / THR / SREL / STLOC / STOBJ / DA / BR / PG / CHC / SLT plus auxiliary SLB / SAU / SP / RSP ledgers) under `worlds/<slug>/stories/<slug>/` that READ world canon (CFs / INVs / M / SEC records via `mcp__worldloom__list_records` + `get_context_packet`) and consult Mystery Reserve firewalls but do NOT mutate world canon — except via `story-fact-promotion-to-canon`'s explicit handoff to `canon-addition` (HARD-GATE preserved). Primary mutation surface is `worlds/<slug>/stories/<slug>/` — distinct from Category 2b's `worlds/<slug>/characters/` and `worlds/<slug>/diegetic-artifacts/` surfaces, from Category 2's pipeline-input surfaces, and from Category 3's `_source/<subdir>/*.yaml` canon records. FOUNDATIONS-alignment APPLIES per Step 4 and `FOUNDATIONS §Story Bundles` (Rule 1 governs story-record schemas including the predicate DSL parsability gate, Rule 4 governs branch-isolation at story scope, Rule 5 governs consequence-capacity per page, Rule 7 governs mystery-firewall on story-local resolutions). Sibling-scan is RECOMMENDED-as-defensive-default for the inter-skill-pipeline shared surfaces these skills depend on, all canonically defined in `.claude/skills/_shared-templates/story-state-contract.md` (the shared story state contract per FOUNDATIONS §Story Bundles §5b): (i) the closed predicate DSL grammar (contract §5; consumed by `branching-story-turn-cycle`'s runtime SLT eligibility and `commitment-block-authoring`'s precondition authoring); (ii) the STENT `role_in_story` closed list (contract §3a / §4; seeded by `branching-story-bootstrap` and consumed by `commitment-block-authoring`'s cast-usage and `branching-story-turn-cycle`'s actor grounding); (iii) the `PG.state_snapshot` field schema (contract §4.2; produced by `branching-story-bootstrap` + `branching-story-turn-cycle` and consumed by every state-changing skill at hard-gate validation); (iv) the RSP card schema (`worlds/<slug>/stories/<slug>/audits/SAU-<integer>/remediation-storylet-proposals/`, produced by `branching-story-health-audit`'s remediation mode and consumed by `commitment-block-authoring`'s `audit_repair` mode); (v) the content-policy block — now inlined verbatim into each scene plan's Content Policy section per the scene-plan contract (no longer a shared `templates/content-policy.txt` surface). Use form (b) `Cross-skill sibling scan: Scanned: <list> via <method> — no inconsistencies.` when the defensive scan runs clean.
- **(3) Canon-mutating** — `canon-addition`, `create-base-world`. These write canon records via the patch engine (CF / CH / INV / M / OQ / ENT / SEC records into `_source/`). FOUNDATIONS-alignment FULLY APPLIES per Step 4 (the skill governs canon records). Sibling-scan is generally NOT applicable unless an explicit structural-identity cascade exists (per the Cross-skill cascade rule below — e.g., a template comment claiming "structurally identical to `<sibling>/templates/...`"); the canon-mutating skills do not produce shared-surface artifacts in the same way Category 1 + 2 skills do. When sibling-scan IS skipped on a Category 3 target, use form (a) `Cross-skill sibling scan: Scan not performed — target is canon-mutating; consumer-side dependencies already verified at audit phase`.

These categories are referenced by Step 2 (FOUNDATIONS read), Step 4 (FOUNDATIONS alignment), the Cross-skill cascade and Cross-skill sibling scan rules below, the Common path checklist's canonical-line forms (`references/follow-up-implementation.md`), and the post-edit verification check 6 gate (`references/post-edit-verification.md`). When a new skill is added to the worldloom pipeline, classify it into one of these five categories (Categories 1, 2, 2b, 2c, 3) before deciding which sibling-scan and alignment rules apply. Edge cases (a skill that produces both canon records AND adjacent artifacts, or a skill that arguably fits two categories) should be classified by primary mutation surface — what does the skill mostly write to? — with the secondary classification noted as an edge-case footnote in the skill's Guardrails block.

## Two distinct sibling-skill operations

These are governed by this guardrail — they are independent and either, both, or neither may apply on any given implementation:

- **Cross-skill cascade** applies to ANY target skill (meta-tooling or canon-mutating) when EITHER a stated structural-identity claim in the target (e.g., a template comment reading "structurally identical to `<sibling>/templates/...`") makes a sibling edit mandatory to preserve the claim, OR a shared-surface trigger (per §Concrete shared-surface triggers — shared terminology, alignment-convention statement, consumer-side schema dependency) creates an implicit cascade dependency where the sibling has its own instance of the same semantic change discovered via sibling-scan. Keyed `N.cascade` in the post-implementation summary; sub-rule lives in the Quick-Reference row-keying section in `references/cascade-and-summary-discipline.md` under `Cross-skill cascade vs cross-skill parallel` (third branch covers the shared-surface-trigger case). In the structural-identity-claim case the sibling edit follows the target edit's content (no independent drift-check is needed because the content is dictated); in the shared-surface-trigger case the sibling edit instantiates the same semantic change independently of the target's primary edit (the sibling-scan discovers parallel staleness or convention drift), but is still keyed as a cascade because the discovery mechanism is sibling-scan rather than the Finding's Suggestion explicitly naming the sibling.
- **Cross-skill sibling scan** applies as a defensive drift-check across sibling skills, with applicability determined by the Skill Category Classification above: REQUIRED-as-defensive-default for Category 1 (meta-tooling) targets when an edit touches shared terminology / conventions / tag semantics; RECOMMENDED-as-defensive-default for Category 2 (canon-pipeline-adjacent), Category 2b (canon-reading content-generation), and Category 2c (story-pipeline content-generation) targets when an edit touches consumer-side schema or shared-surface triggers (and acceptable defensively even when no trigger fires); generally NOT applicable for Category 3 (canon-mutating) targets unless an explicit structural-identity cascade exists. Runs grep / read / diff across sibling skills (primarily within the same category — meta-tooling targets scan meta-tooling siblings, canon-pipeline-adjacent / canon-reading content-generation / story-pipeline content-generation targets scan their respective siblings) to confirm the change doesn't leave sibling skills inconsistent with the target. Scan method must be named in the announcement; an unexecuted scan must be announced as `Scan not performed — <reason>`, not fabricated as executed.

A single implementation may require cross-skill cascade, cross-skill sibling scan, both, or neither. The two are operationally independent: cascade is about mirroring dictated content to preserve a claim; scan is about verifying the absence of drift. Confusing them — escalating a simple cascade into a full sibling-scan protocol, or skipping a mandatory cascade because "scan is meta-tooling only" — has been a real source of friction. The sub-rules below elaborate each operation.

## Concrete shared-surface triggers

A finding affects a shared surface when it changes any of the following:
- `docs/plans/*.md` design-doc output path or frontmatter conventions (produced by `brainstorm`)
- `docs/triage/*.md` triage-file format (produced by `brainstorm` for multi-deliverable triages and for standalone deferred-deliverable triage decision records)
- `brainstorming/*.md` canon-pipeline proposal structure (produced by `skill-creator` in fresh mode; consumed by `skill-creator` in compile mode)
- `archive/*/` archival destination paths or naming conventions
- `specs/*.md` or `tickets/*.md` structure and numbering conventions — worldloom does not yet ship with these directories; check for presence before flagging, and if absent, skip this bullet
- Shared terminology that appears in multiple skills
- Output format consumed by a downstream skill in the same pipeline (e.g., `brainstorming/*.md` proposals consumed by `skill-creator`; `docs/plans/*.md` design docs consumed by follow-up implementation skills)
- Shared template files referenced by multiple sibling skills — especially when a template carries an explicit "structurally identical to `<other-skill>/templates/...`" claim or comment. Schema drift between such templates is the failure mode: if finding N adds, removes, or repurposes a field in one skill's template, the sibling's matching template needs the same change to preserve the structural-identity claim. Catch this at per-finding planning time, not via the post-edit verification backstop.
- **Consumer-side output-schema dependencies** — when a finding introduces references to specific field names, section names, or structural conventions produced by a sibling skill's output (e.g., a character-dossier section name like "Epistemic Position §Known firsthand", a canon-addition CF-id format, a proposal-card frontmatter field) — the reference is a schema dependency on the sibling, even when the target skill is NOT meta-tooling and the finding makes no explicit structural-identity claim. This sits between Cross-skill cascade (which requires either a stated structural-identity claim in the target OR a shared-surface trigger creating an implicit cascade dependency, per the Cross-skill cascade vs cross-skill parallel decision rule's third branch) and Cross-skill sibling scan (which is meta-tooling-gated). For non-meta-tooling targets, verify the referenced schema against the sibling's current template with a point-of-reference read (scan method (b) Read, or (d) Diff when the reference is structured) rather than a full sibling scan. **For multi-term existence verification** — confirming a sibling template exposes several named fields or a named taxonomy in a single check — method (a) Grep is an acceptable alternative to Read or Diff: grep for all referenced terms in one call, confirm the sibling exposes them, skip the full-file read. Prefer Read or Diff when the verification is about field-level semantics (what a field means, how it's populated, what values it takes) rather than field-level existence (whether the field is exposed at all). Announce the verification with the same hypothesis-first pattern: "Investigating whether `<sibling-skill>`'s current template still exposes `<field-or-section-name>`: reading `<sibling-path>` to verify." (or `grepping for <terms>` when using method (a) for multi-term existence). Record the verification outcome in the Cross-Skill Scan section of the audit report using the existing first-form ("Scanned: `<sibling-path>` via read — schema confirmed, no finding adjustment needed") or second-form ("Scanned: `<sibling-path>` via read — sibling's section has been renamed to X, adjusted finding wording") format — substitute "via grep" in place of "via read" when the method was grep.
- **Documented alignment-convention statements** — when one skill's documentation explicitly declares a convention that siblings "should be kept aligned on", "mirror", or "follow the same pattern as", treat any finding that touches the conventioned content as a shared-surface trigger. The alignment statement itself is the interface; the conventioned content is the shared surface. Example: `canon-addition/SKILL.md` §Pre-flight Check Large-file method states *"The three skills should be kept aligned on the convention; future canon-addition runs that discover additional anchor patterns for new file shapes should update this section so siblings can mirror"* — any finding adding to the anchor-pattern list triggers a cross-skill cascade planning step at audit phase, even when the target skill is non-meta-tooling. Distinct from the "Shared template files with structural-identity claim" trigger above (which covers template-level content mirroring via an explicit "structurally identical to `<other-skill>/templates/...`" comment); alignment-convention statements cover SKILL.md / reference-file content conventions that are declared-shared-by-prose rather than declared-identical-by-template-comment. Audit-phase handling: include the Cross-Skill Scan section with the third form (`Cascade planned for implementation: <sibling-file> per <alignment-convention statement quote>`) OR, if the auditor investigates siblings during the Auxiliary investigation window and scope-narrows, the fourth form (`Scanned: <list> via <method> — cascade-target candidates found; per-sibling investigation narrowed scope (<reason>); no sibling cascade planned.`). Catching this at audit phase prevents the implementation-phase mid-flow discovery pattern where the shared-surface impact first surfaces during per-finding cascade scanning. **Per `references/audit-execution-discipline.md` §Pre-finalization verification, perform per-finding sibling investigation before emitting form (3) — naming a finding as a cascade candidate without verifying the sibling actually has the parallel content produces the over-naming and under-naming defects described in that section, both of which the implementation phase has to retract or augment via Re-evaluation.**
- **Cross-references introduced to a sibling skill's section, file, or documented convention** — even when the target skill's edit does not modify the sibling, the cross-reference itself creates a forward dependency (the cited section / file / convention must continue to exist for the reference to remain valid) that future audits should be able to trace. This is a weaker shared-surface relationship than structural-identity cascade (the "Shared template files" trigger above) or alignment-convention cascade (the preceding bullet) — no sibling edit is required, and no drift risk exists at the moment of the edit — but the audit trail benefits from explicit recording. Audit-phase handling: include the Cross-Skill Scan section with the fifth form (`Cross-reference to sibling convention noted: <sibling-file>/<section>; no cascade or drift to address — finding cites the sibling's existing convention rather than dictating a sibling edit.`). At implementation phase, no sibling edit is applied; the post-implementation summary records the cross-reference as a brief note rather than an `N.cascade` row. Distinct from Cross-skill cascade (which dictates a sibling edit) and from Cross-skill sibling scan (which checks for drift in shared content); cross-reference noting is a citation discipline, not a mutation discipline. Worked precedent: brainstorm's §Multi-file triage implementation discipline cites `skill-audit's §Cascade edits Cascade-scan discipline` as its parallel convention — the citation creates a forward dependency on skill-audit's section name; future skill-audit audits should grep brainstorm for that citation when considering renaming the section.

When triggered, list the scanned sibling skills in the audit report alongside what (if anything) was adjusted. If no inconsistency was found between siblings, state "Scanned: <skill list> — no inconsistencies between siblings." (per §Quick-reference form (1) — covers both the all-clean case and the one-directional-gap case where siblings are consistent among themselves but the target lags an established sibling convention; in the one-directional-gap case, append a trailing rationale clause naming the convention and noting the audit's primary findings will close the gap without requiring sibling edits). This makes the scan auditable. When a finding identifies a required cross-skill cascade but no sibling SCAN was run during the audit phase (typical of non-meta-tooling targets where the sibling-scan operation doesn't apply), use the Cross-Skill Scan section's third form — "Cascade planned for implementation: <sibling-file> per <structural-identity claim>" — and keep the cascade itself as an `N.cascade` row in the post-implementation summary once implementation runs.

## Mid-implementation cascade scope-narrowing

If per-sibling investigation at implementation time reveals that a planned cascade target has a categorically different surface shape than the audit assumed — for example, the sibling already handles the same concern via a different mechanism (a different section structure, a different reference-file split, an inline method the audit did not notice), or the sibling's paralleled section is absent entirely, or cascading the target's content would break the sibling's own internal coherence — it is acceptable to narrow the cascade scope. Announce the scope-narrowing explicitly in user-facing text before applying the remaining cascades, naming the excluded sibling and the dissimilar-shape reason (e.g., "Cascade scope decision: `canon-addition/SKILL.md` already has a more elaborated Large-ledger method focused on ID-allocation scanning, a different gap-shape than the other two siblings; applying cascade only to the two reference files whose gap exactly mirrors the target's"). Do NOT silently skip divergent cascade targets — the announcement preserves the audit trail that an audit-plan-to-implementation gap existed and was resolved with judgment rather than by oversight, and it lets a future reader reconstruct why the post-implementation summary has fewer `N.cascade` rows than the audit's Cross-Skill Scan section promised.

This is distinct from Re-evaluation (which addresses target-file changes OR premise-falsification between audit and implementation) and from Partial implementation (which addresses user-specified finding subsets); scope-narrowing addresses a planning-time-to-execution-time gap in the CASCADE side of a finding when sibling state differs from the audit's assumption (see Mid-implementation primary-edit scope-narrowing in `references/follow-up-implementation.md` §Edit ordering for the parallel primary-side rule that addresses the same gap-shape on the primary side, when target instantiations — not sibling state — differ from the audit's assumption).

The rule applies symmetrically in two directions. **Audit-over-promised**: the audit identified a cross-skill cascade target (Cross-Skill Scan section's third or fourth form was emitted) and implementation-time per-sibling investigation revealed the planned cascade should be narrowed (categorical-different shape, absent parallel section, sibling-coherence-breaking content). **Defensive-over-discovered**: the audit identified no cross-skill cascade (Cross-Skill Scan section omitted because no shared surfaces were touched), but implementation-time defensive scanning surfaced a candidate that per-sibling investigation then narrowed back to no cascade. Both cases use the same canonical post-implementation line (`Cross-skill sibling scan: Scanned: <sibling-list> via <method> — scope narrowed per Mid-implementation cascade scope-narrowing rule (<reason per excluded sibling>); no sibling cascade applied.`). In the defensive-over-discovered case, the reason field should explicitly note that the candidate was surfaced at implementation time rather than at audit time (e.g., `defensive implementation-phase scan surfaced <sibling> as candidate; per-sibling investigation revealed <reason>`) — this preserves the audit-to-implementation gap as load-bearing evidence rather than burying the over-discovery as if the audit had identified the candidate.

## Scan methods

Pick one based on the finding's shape:
- (a) **Grep** for the changed terminology or convention across `.claude/skills/*/SKILL.md` when the finding changes a word-level convention (a tag name, a section heading, a keyword, a status label).
- (b) **Read** a sibling's SKILL.md end-to-end when the finding touches that sibling's declared interfaces or outputs (inputs the sibling consumes, artifacts it produces, templates it references).
- (c) **Glob + check** when the finding changes a shared-path convention (`archive/*/`, `brainstorming/*.md`, `worlds/<slug>/`, `docs/plans/*.md`, `docs/triage/*.md`).
- (d) **Diff** a shared template or structured file byte-by-byte against the sibling's parallel file when verifying a "structurally identical to `<other-skill>/templates/...`" identity claim or detecting schema drift. Prefer this over Read when the two files are parallel enough that line-by-line comparison is more informative than end-to-end reading — common for YAML templates and structured reference files.

## Scan target — meta-tooling targets only

When the target is a meta-tooling skill (skill-creator, skill-audit, skill-consolidate, brainstorm, and similar), the scan's audit target is *other meta-tooling siblings*, not *generated skills that instantiate the meta-tooling skill's template* (character-generation, diegetic-artifact-generation, propose-new-canon-facts, etc.). Matches in generated skills are confirmations that the generated skill correctly instantiates the meta-tooling convention — they are NOT sibling inconsistencies. If a grep matches a generated skill, spot-check that the generated usage is consistent with the convention being edited; do not cascade the edit to the generated skill (that's the meta-tooling skill's job at its next invocation, when it re-authors generated files from the updated template).

Name the method used in the scan announcement so the result is reproducible (e.g., "Scanned `brainstorm`, `skill-creator` via grep for `templates/` references — no inconsistencies" or "Scanned `create-base-world` via read of `templates/*.yaml` + diff against generic source — no inconsistencies"). A scan announcement without a named method is not auditable.

## The announcement must reflect work actually performed

Writing "Scanned via grep for X" when no grep was executed violates the audit-trail discipline — even when the auditor's reasoning about the terms being skill-internal turns out to be correct. If the auditor concludes a scan is unnecessary without running the named method, the announcement must read `Scan not performed — <reason>` (e.g., "Scan not performed — changed terms are load-bearing only for skill-creator's internal guidance; no sibling meta-tooling skill documents these conventions"). A scan-not-performed announcement surfaces the possibility that the reasoning is wrong and a sibling DOES use the term; a fabricated "Scanned via grep" announcement buries that possibility under a false method claim that a future reader, trusting the trail, will not re-verify.

## Extends to user-directed edits on meta-tooling skills

The sibling-scan discipline also applies when user-directed follow-up implementation modifies a meta-tooling skill itself (e.g., brainstorm, skill-creator, skill-audit, mcp-integration-audit) and the edit touches shared terminology, conventions, or tag semantics — even when the edit is not driven by a finding in the current audit report. This includes NEW conventions being introduced by the edit (e.g., a new filename convention, a new tag name, a new enum value) — the scan's purpose is to verify the new convention does not conflict with existing sibling content, regardless of whether the convention was pre-existing or net-new. Before finalizing such an edit, grep sibling meta-tooling skills for references to the changed terminology or convention, and document the scan in the post-implementation summary ("Scanned siblings: <list> — no inconsistencies" or "<list> — adjusted X in Y").

## Quick-reference — Audit-phase Cross-Skill Scan section forms

Parallel to the Quick-reference — Cross-skill sibling scan canonical line by shape table in `references/follow-up-implementation.md` (which covers implementation-phase forms (a)–(e)); this table covers the six audit-phase forms (1)–(6) enumerated as inline prose in `SKILL.md` §Cross-Skill Scan. Use this table for fast-path form selection at audit time; the SKILL.md prose remains authoritative for edge cases, rationale, and the per-form sub-rules (e.g., form (3)'s pre-finalization-verification requirement per `references/audit-execution-discipline.md` §Pre-finalization verification, form (6)'s grep-searchability phrasing).

| Form | Condition | Canonical line |
|---|---|---|
| (1) | Scan ran across siblings, no drift requiring sibling action (covers both the all-clean case and the one-directional-gap case where siblings are consistent among themselves but the target lags an established sibling convention) | `Scanned: <sibling-skill-list> via <method> — no inconsistencies between siblings[; <optional rationale naming what was checked and why no sibling edit is required — including the case where siblings are consistent among themselves but the target lags an established sibling convention so the audit's primary findings will close the gap one-directionally>].` |
| (2) | Scan ran, surfaced an inconsistency to fix at audit phase | `Scanned: <list> — adjusted X in Y.` |
| (3) | No audit-phase scan; cascade identified through finding-shape alone (per-finding sibling investigation required before drafting per `references/audit-execution-discipline.md` §Pre-finalization verification) | `Cascade planned for implementation: <sibling-file> per <structural-identity claim or shared-surface trigger>.` |
| (4) | Scan ran during Auxiliary investigation; cascade-target candidates surfaced; per-sibling investigation narrowed scope to zero cascades | `Scanned: <list> via <method> — cascade-target candidates found; per-sibling investigation narrowed scope (<reason per excluded sibling>); no sibling cascade planned.` |
| (5) | Finding's primary edit introduces a cross-reference to an existing sibling convention without modifying the sibling — section IS included even though no scan ran and no cascade was identified (per SKILL.md report template's OMIT-rule's third inclusion trigger; the cross-reference is itself the shared-surface trigger requiring audit-trail recording) | `Cross-reference to sibling convention noted: <sibling-file>/<section>; no cascade or drift to address — finding cites the sibling's existing convention rather than dictating a sibling edit.` |
| (6) | Audit-phase scan ran AND found one or more cascade targets (with or without other clean siblings — N=0 clean siblings is acceptable when all scanned siblings have cascade targets) | `Scanned: <list> via <method> — <N> sibling(s) clean; <M> sibling(s) found cascade target(s) at <site-list>; cascade(s) keyed <finding>.cascade for implementation.` |

The numeric form-labels (1)–(6) parallel the implementation-phase letter-labels (a)–(e) — distinct numbering systems specific to each phase, not interchangeable; do not conflate audit-phase form (1) with implementation-phase form (a). Use the literal phrasing in the canonical-line column verbatim — paraphrased variants break grep-searchability for future audits tracing scan discipline across sessions.
