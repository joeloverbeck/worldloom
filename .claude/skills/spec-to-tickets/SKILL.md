# Spec to Tickets

Break a worldloom spec into a series of small, actionable implementation tickets that a human reviewer can merge one at a time, validated against the current codebase and aligned with FOUNDATIONS.md.

<HARD-GATE>
Do NOT Write any ticket file at `tickets/<NAMESPACE>-<NNN>.md` until ALL of the following hold:

(a) Pre-flight has verified `docs/FOUNDATIONS.md`, `tickets/_TEMPLATE.md`, `tickets/README.md`, and `<spec_path>` are all readable; if any is missing the skill aborts before Step 1.

(b) Step 2 (Codebase Validation) has completed, and every surfaced Issue (missing file, renamed type, stale skill reference, broken Deps chain, FOUNDATIONS-violating assumption) has an explicit user disposition — fix before decomposition, defer to a follow-up ticket with a named dependency, reject with rationale, expand scope in place (when validation surfaced materially understated spec scope; the spec narrative is not edited, but the decomposition is sized against the wider implementation surface the codebase actually requires), or drop as moot (when the deliverable's named target doesn't exist in the codebase AND the deliverable's intent is satisfied by sibling deliverables or is structurally a no-op under the actual codebase shape).

(c) Step 4 has emitted the decomposition summary table in chat (numbered tickets with Title, Scope, Effort, Deps, FND, Notes columns) AND the user has explicitly approved it, OR the auto-mode auto-approval condition has fired (auto mode active AND Step 2 surfaced no Issues AND no reassessment findings were deferred).

(d) Every `Deps` reference in the proposed decomposition resolves to a ticket that will actually be produced in this run, or to a pre-existing ticket/spec path verified at Pre-flight (for paths known at session start: `<spec_path>` and the four mandatory Pre-flight files) OR at Step 4 before HARD-GATE fires (for cross-spec Deps paths introduced during Step 3 decomposition — typically `specs/<sibling-spec>.md`, `archive/specs/<archived-spec>.md`, or pre-existing `tickets/<NAMESPACE>-NNN.md` paths produced in prior batches). Pre-flight cannot verify paths that haven't been introduced yet; Step 4's Cross-spec Deps verification sub-step (see §Step 4) closes the temporal gap before user approval clears the gate.

This gate is authoritative under Auto Mode or any other autonomous-execution context — invoking this skill does not constitute approval of the decomposition. The skill may only proceed to Step 5 (batched ticket writes) once every gate condition above holds simultaneously.
</HARD-GATE>

## Process Flow

```
Pre-flight: Verify required files readable (FOUNDATIONS.md, tickets/_TEMPLATE.md,
            tickets/README.md, <spec_path>); derive+confirm <namespace> if omitted.
       |
       v
Step 1: Mandatory reads (spec file, tickets/_TEMPLATE.md, tickets/README.md,
        docs/FOUNDATIONS.md)
       |
       v
Step 2: Codebase validation (full OR abbreviated spot-check when /reassess-spec
        ran in-session). Surface Issues; await per-Issue disposition.
       |
       v
Step 3: Decompose the spec (reviewable-diff sizing, dependency mapping,
        priority ordering, deliverable-coverage enforcement)
       |
       v
Step 4: Present decomposition summary table in chat; await user approval
        (or auto-mode auto-approval when Step 2 was clean)
       |
       +-- [HARD-GATE fires here — see top of skill]
       |
       v
Step 5: Batched ticket writes (one or a few assistant messages, N Write tool
        calls in parallel, one per ticket at tickets/<NAMESPACE>-<NNN>.md)
       |
       v
Step 6: Final summary (cross-ticket dependency verification, deliverable
        coverage mapping, dependency graph, suggested implementation order).
        Do NOT commit.
```

## Inputs

**Required:**
- `spec_path` — path to the spec file (e.g., `specs/SPEC-03-patch-engine.md`). Must exist and be readable at Pre-flight.

**Optional:**
- `namespace` — ticket namespace prefix (e.g., `SPEC03PATENG`). If omitted, the skill proposes one derived from the spec ID and abbreviated title and asks the user to confirm or override before Step 1.

## Output

- **Ticket files at `tickets/<NAMESPACE>-<NNN>.md`** — one per reviewable diff, each following the exact structure in `tickets/_TEMPLATE.md` (Status, Priority, Effort, Engine Changes, Deps, Problem, Assumption Reassessment, Architecture Check, Verification Layers, What to Change, Files to Touch, Out of Scope, Acceptance Criteria, Test Plan).
- **Decomposition summary table** — emitted in chat at Step 4 before any Write.
- **Final summary** — emitted in chat at Step 6 (cross-ticket dependency verification, deliverable coverage mapping, dependency graph, suggested implementation order).

This skill does **not** emit Canon Fact Records, Change Log Entries, adjudication records, or any YAML structured output. Tickets are markdown documents for human review.

## World-State Prerequisites

Before this skill acts, it MUST read (per FOUNDATIONS.md §Tooling Recommendation):

- `<spec_path>` — the target spec file, entire contents. Read at Step 1.
- `tickets/_TEMPLATE.md` — the canonical ticket structure; every ticket produced in Step 5 must follow this template exactly. Read at Step 1.
- `tickets/README.md` — the ticket authoring contract; defines required sections and mandatory pre-implementation checks. Read at Step 1.
- `docs/FOUNDATIONS.md` — the non-negotiable design contract. Skip if read earlier in this session and unmodified. Agent-delegated reads (Explore-agent reports that quote FOUNDATIONS sections verbatim with line refs) satisfy the skip criterion when the agent's coverage matches the FOUNDATIONS sections cited by the spec's §FOUNDATIONS Alignment + this spec's deliverables — parallel to skill-audit's `references/audit-execution-discipline.md` §Read-satisfaction.
- `docs/HARD-GATE-DISCIPLINE.md` — read on demand at Step 2 when a spec deliverable touches skill HARD-GATE semantics or canon-write ordering.
- Every file path, skill directory, tool reference, and spec reference extracted from the target spec — read on demand at Step 2 as part of codebase validation.

This skill operates at **pipeline scope** — canon-pipeline-adjacent: it produces tickets that feed implementation, not world canon, so FOUNDATIONS-alignment applies even though it writes no world-level content itself. It reads any file under `specs/`, `archive/specs/`, `.claude/skills/`, `tools/`, `docs/`, and `tickets/`. It does **not** read world-level canon (`worlds/<slug>/`) — specs describe pipeline/tooling work, not world-canon work. If a future spec genuinely requires world-canon context to validate, that's a classification-shift signal, not a prerequisite-list gap.

## Pre-flight Check

Before Step 1, verify:
1. `docs/FOUNDATIONS.md` exists and is readable.
2. `tickets/_TEMPLATE.md` exists and is readable.
3. `tickets/README.md` exists and is readable.
4. `<spec_path>` (from argument 1) exists and is readable. If the argument is a glob (e.g., `specs/SPEC-27*`), resolve it first: exactly one match → use it and note the resolution; zero or multiple matches → abort with a clear error or ask the user to disambiguate.
5. `<namespace>` (from argument 2) is provided, OR if omitted, derive one from the spec ID and abbreviated title (e.g., `specs/SPEC-03-patch-engine.md` → `SPEC03PATENG`) and ask the user to confirm or override before Step 1.
6. If a worktree root is active, all paths resolve from the worktree root, not the main repo root.

If any of checks 1–4 fails, abort with a clear missing-file error before Step 1. If check 5 is ambiguous (spec ID parsing fails), ask the user for the namespace directly.

## Step 1: Mandatory Reads

Read ALL of these before any analysis:

1. **The spec file** (from `spec_path`) — entire file.
2. **`tickets/_TEMPLATE.md`** — the canonical ticket structure; every ticket produced must follow this template exactly.
3. **`tickets/README.md`** — the ticket authoring contract; understand the required sections and pre-implementation checks.
4. **`docs/FOUNDATIONS.md`** — skip if read earlier in this session and unmodified. Agent-delegated reads (Explore-agent reports that quote FOUNDATIONS sections verbatim with line refs) satisfy the skip criterion when the agent's coverage matches the FOUNDATIONS sections cited by the spec's §FOUNDATIONS Alignment + this spec's deliverables — parallel to skill-audit's `references/audit-execution-discipline.md` §Read-satisfaction.

Parse the spec's metadata: Phase, Status, Dependencies, Blocks, Problem Statement / Approach / Deliverables / FOUNDATIONS Alignment / Verification / Out of Scope / Risks, and all deliverable sections. **Non-numbered deliverables**: if the spec uses named sections instead of numbered deliverables (e.g., `SPEC-05 Hooks Discipline` — Part A / Part B / Part C), treat each distinct implementation section as a deliverable for decomposition purposes.

## Step 2: Codebase Validation

Before decomposing, validate the spec's assumptions against the actual worldloom codebase.

### Full Validation Path (default)

- **Grep/Glob** for every file path referenced in the spec — confirm it exists at the stated path. Targets: spec files (`specs/*`), skill files (`.claude/skills/*/SKILL.md` and references under `references/`), doc files (`docs/*`), tool files (`tools/*`), hook scripts, and world files only if the spec explicitly references world-level paths.
- **Grep** for every skill name, tool name, MCP tool name, hook name, validator name, and YAML schema key referenced in the spec — confirm they are real and current. **Apply this with equal rigor to schema fields named in the spec's *proposed corrections / fix prose*, not only fields the spec names as already-existing** — a record-field a spec proposes to *write* still needs its host record's schema confirmed to define it (worked precedent: SPEC-26 D1 proposed "create a replacement `STINT` with `derived_from`"; `STINT` has no `derived_from` field — only `supersedes` — and the wrong field propagated into a written ticket before the user caught it post-Step-6). Distinguish existing schema references (must exist now) from proposed ones (the spec proposes to write them); both need validation, because a wrong field in a proposed fix propagates through decomposition into a ticket exactly as a wrong field in a bug claim does — the §Codebase truth guardrail names this "a skill failure." This carries `reassess-spec` §3.1 (existing-vs-proposed-path distinction) and §3.2 ("field existence and naming" / "record-field-name drift") into Step 2; consult `reassess-spec/references/codebase-validation.md` for the fuller discipline.
- **Grep** for every FOUNDATIONS principle, Validation Rule, or Canon Fact Record field the spec cites — confirm the section/rule still exists in `docs/FOUNDATIONS.md` with the claimed semantics.
- **Check** cross-spec dependencies (`Dependencies` / `Blocks` fields) resolve to real spec paths under `specs/` or `archive/specs/`.
- **Command-surface verification**: grep the relevant `package.json` / Makefile / justfile for every script/command name referenced in the spec's Verification section OR likely to land in tickets' Commands sections (e.g., `pnpm --filter <pkg> test`, `npm run typecheck`, `cargo test`). Flag non-existent scripts before ticket drafting so Commands sections don't reference vaporware. **Routing for missing-script findings** (mirrors Abbreviated Spot-Check (f) routing below; the routing is symmetric across both paths): when a missing script is found, choose one of three explicit routes: (i) **substitute** an existing script that covers the same surface (e.g., `npm run build` covers typecheck when the package's build script invokes `tsc`); (ii) **add** the missing script as a sub-deliverable of the relevant ticket (when adding the script is in scope for the spec); (iii) **flag** it as an Issue at Step 2 for user disposition (when neither substitute nor add is appropriate). Document the chosen route inline in the Step 2 user-facing summary (e.g., `Command-surface: ✓ — npm run typecheck missing; substituted npm run build (covers tsc).`) so the route is auditable.
- **New-class / new-op / new-id-class / new-field / restructured-field parity scan**: when the spec introduces a new record class, patch-engine operation kind, ID class, schema node-type, a new field on an existing record class or schema, OR a material restructuring of an existing field's shape (e.g., `string` → structured object, scalar → enum, single value → array — any change that turns existing consumers' field-reading code into broken assumptions), pick an analogous *existing* sibling — a sibling class for a new class/op/id-class/node-type, or the host record/schema for a new-or-restructured field — and grep the codebase for every registry, parser, overlay, schema file, contract-doc surface, enumeration site, and producing/consuming skill that sibling occupies across `tools/*/src/**` and `.claude/skills/**` (id-prefix pattern, node-type constant, op-kind enum membership, pre-apply / commit / index / retrieval registrations, latent helper infrastructure). The bullets above confirm the surfaces the spec *names* exist; this scan confirms the spec *named all* the surfaces. Under-enumeration of the machine-layer seam — the most common way a spec's deliverable list silently understates a ticket's true Files to Touch — routes per the same gradient the Abbreviated Spot-Check (g) gives: route it through Step 2's Issue-disposition flow (typically `expand-scope-in-place`) when it changes the spec's intent or scope materially; for under-enumeration that does not change spec intent — a latent unwired helper, an obviously schema-paired file — the operator may add the site directly to the relevant ticket's Files to Touch with a Step 6 note, without a separate Step 2 Issue presentation (it is a documented ticket-authoring scope adjustment, not a "surfaced Issue" under HARD-GATE clause (b)). This adapts the cross-package-count-grep and blast-radius discipline `reassess-spec` documents at its `references/codebase-validation.md`.
- **Flag** any stale reference, missing file, renamed entity, non-existent script, or FOUNDATIONS-violating assumption as an **Issue** — with one carve-out: **mechanical-drift corrections** propagate silently into tickets without Issue disposition. Distinguish:
  - **Substantive drift** (renamed type, removed file, semantics shifted, non-existent script with no `build`-style substitute, FOUNDATIONS-violating assumption, schema field that doesn't exist on the named record class) → flag as Issue requiring user disposition per the five options above.
  - **Mechanical drift** (path convention swap where narrative intent is unambiguous, e.g., spec lists test paths under `tools/<pkg>/src/<dir>/*.test.ts` but tests actually live under `tools/<pkg>/tests/<dir>/*.test.ts`; capitalization variants of an unambiguous symbol; file extension normalization; version-bumped helper module rename where the new location is unambiguously the same artifact) → propagate the corrected reference silently in tickets (per §Guardrails §Codebase truth — tickets must carry validated paths regardless); note the propagation inline in the Step 2 user-facing summary with a `Mechanical-drift corrections to propagate (not Issues; per §Codebase truth guardrail)` line enumerating each affected ticket and the corrected path. Decision rule: if a competent operator reading both the spec's path and the codebase's actual path would immediately see that they refer to the same artifact (no semantics change, no scope change), the drift is mechanical; if the divergence raises a question about what the spec actually intends (rename vs. removal vs. typo vs. genuine API shift), the drift is substantive and routes through Issue disposition. Worked precedent: SPEC-30 (2026-05-15) test-path drift `tools/validators/src/<dir>/*.test.ts` → `tools/validators/tests/<dir>/*.test.ts` across six deliverables (D1, D3, D4, D5, D7, D10); the corrected `tests/` paths propagated silently into all six tickets with one inline summary line, rather than six Issue cycles each disposing the same routine path correction.
- Present Issues to the user before proceeding to Step 3. For each Issue, obtain an explicit disposition from one of five options: **fix-before-decomposition** (small spec correction lands first, then decompose against the corrected spec); **defer-to-follow-up-ticket** (with a named dependency); **reject-with-rationale** (spec too materially wrong to decompose this round; route back to `/reassess-spec`); **expand-scope-in-place** (validation surfaced materially understated spec scope; the spec's intent is preserved, but tickets are sized against the wider implementation surface the codebase actually requires — the spec is not edited, the decomposition is); **drop-as-moot** (applicable when the spec deliverable's named target — file, module, barrel, config section — doesn't exist in the codebase AND the deliverable's intent is satisfied by sibling deliverables OR is structurally a no-op under the actual codebase shape; the operator drops the deliverable from the decomposition with a Step 2 summary note naming the missing target and the sibling deliverables that cover the intent; distinct from `reject-with-rationale` which routes the spec back through `/reassess-spec` for substantive re-design, and from the mechanical-drift carve-out below which covers path/symbol-rename cases where the artifact exists at a different location). Worked precedent: SPEC-23 (2026-05-13) Workstream 1 — "three SLT contract↔schema mismatches" was dispositioned as **expand-scope-in-place** to "full SLT schema rebuild + retire five validators" after codebase validation surfaced the schema's full pre-rebuild divergence (`record_version`, `arc_contract`, `effect_model`, `stop_policy` blocks the post-rebuild contract forbids). Second worked precedent: SPEC-44 (2026-05-18 session) — D13 `tools/patch-engine/src/ops/index.ts (or barrel) — Remove 7 exports` was dispositioned as **drop-as-moot** because no `index.ts` barrel exists in `tools/patch-engine/src/ops/` (ops are imported directly via filename by `commit/temp-file.ts`); D13's intent (remove references to deleted ops) was satisfied automatically by D4-D10 (the file deletions themselves); D13 dropped from decomposition with a Step 2 summary note rather than routed through Issue disposition.

**Brainstorm-produced specs**: when `<spec_path>` was produced by the `brainstorm` skill earlier in the current session (brainstorm's triage flow runs its own codebase exploration as part of producing a spec), the Full Validation Path remains the path — brainstorm's triage validation is less systematic than `/reassess-spec`'s §3.x discipline and does not qualify the spec for the Abbreviated Spot-Check Path. The operator may treat brainstorm's in-context codebase exploration as already-gathered evidence for the specific bullets it demonstrably covered, while still running fresh greps for everything brainstorm did not explicitly verify — notably the schema-field validation in the second bullet above, since brainstorm's spec-drafting does not guarantee proposed-fix-prose fields were schema-checked. **Companion triage file**: a multi-item brainstorm triage also writes a companion `docs/triage/<date>-<topic>-triage.md` file whose follow-up-items section (the items the triage identified but did not action) is a recurring cross-spec-follow-up source — check it during decomposition and surface its follow-ups in the Step 6 cross-spec follow-ups list (§Step 6 item 4) alongside the spec's §Risks section.

**Composition (brainstorm produced + `/reassess-spec` ran on same spec in-session)**: when both clauses apply — the spec was produced by `brainstorm` earlier in the current session AND `/reassess-spec` was subsequently run on it in the same session with all findings resolved — `/reassess-spec`'s §3.x discipline supersedes the brainstorm-validation gap retroactively. Proceed with the Abbreviated Spot-Check Path, since the rigorous reassessment satisfies the validation discipline the Brainstorm-produced specs clause was designed to enforce. The `/reassess-spec` session's resolved findings constitute evidence equivalent to (or stronger than) the Full Validation Path's grep-pass for the bullets reassess-spec covered; running Full Validation a third time would pay the 4-5× wall-clock cost the Abbreviated path was designed to avoid without surfacing new evidence. The composition rule resolves the literal-reading ambiguity between the Brainstorm-produced specs clause above (*"the Full Validation Path remains the path"*) and the Abbreviated Spot-Check Path clause below (*"If `/reassess-spec` was run on this spec in the current session and all findings were resolved, Step 2 validation may be abbreviated to a targeted spot-check"*) — under composition, the Abbreviated Path wins because reassess-spec's §3.x rigor closes the validation gap brainstorm leaves open. Worked precedent: SPEC-47 (2026-05-19 session) — brainstorm produced SPEC-47, `/reassess-spec` ran on it with 3 Issues + 1 Improvement + 1 Addition all applied via auto-mode + recommended-disposition path; the subsequent `/spec-to-tickets` invocation applied this composition rule, used the Abbreviated Spot-Check Path with checks (a)-(g) all passing, and produced 17 tickets without re-running Full Validation. The composition does NOT apply when `/reassess-spec` ran but some findings were deferred by the user — that case routes per the deferred-findings handling below; nor when only brainstorm ran without subsequent reassessment — that case routes per the Brainstorm-produced specs clause above.

### Abbreviated Spot-Check Path (when `/reassess-spec` ran in-session)

If `/reassess-spec` was run on this spec in the current session and all findings were resolved, Step 2 validation may be abbreviated to a targeted spot-check. 3–5 greps is sufficient. Spot-checks must verify at least:

- **(a) Primary references**: the spec's primary skill/tool/type references still exist at the stated paths.
- **(b) Schema version**: if the spec modifies a structured output schema (Canon Fact Record fields, Change Log Entry fields, proposal card schema), verify the schema hasn't drifted since reassessment.
- **(c) Sibling specs**: no new specs added under `specs/` reference the same skills or tools.
- **(d) Additive extension check**: for specs extending an existing output schema, consumers of that schema have been updated, or the extension is additive-only (new optional field with a default).
- **(e) Rename/removal blast radius**: for tickets renaming/removing a skill, tool, hook, validator, or schema field, grep pipeline-wide (`tools/`, `.claude/skills/`, `docs/`, `specs/`) for every symbol being renamed/removed. If any area has >0 matches but is not in the ticket's Files to Touch, either (i) add it to Files to Touch, or (ii) split those sites into a follow-up ticket with an explicit dependency.
- **(f) Command-surface verification**: grep the relevant `package.json` / Makefile / justfile for every script/command name referenced in the spec's Verification section OR likely to land in tickets' Commands sections (e.g., `pnpm --filter <pkg> test`, `npm run typecheck`, `cargo test`). Flag non-existent scripts before ticket drafting so Commands sections don't reference vaporware. Example failure this catches: a spec lists `pnpm --filter @worldloom/world-mcp typecheck` as a verification command, but the package's `scripts` block defines only `build`, `test`, `clean` — the `typecheck` reference would silently survive decomposition and surface only when an implementer tries to run the ticket's Commands section. **Routing for missing-script findings**: when (f) finds a missing script, choose one of three explicit routes: (i) **substitute** an existing script that covers the same surface (e.g., `npm run build` covers typecheck when the package's build script invokes `tsc`); (ii) **add** the missing script as a sub-deliverable of the relevant ticket (when adding the script is in scope for the spec); (iii) **flag** it as an Issue at Step 2 for user disposition (when neither substitute nor add is appropriate). Document the chosen route inline in the spot-check summary's (f) entry (e.g., `(f) ✓ — npm run typecheck missing; substituted npm run build (covers tsc).`) so the route is auditable.
- **(g) New-class / new-op / new-id-class / new-field / restructured-field spot-check**: when the spec introduces a new record class, patch-engine operation kind, ID class, schema node-type, a new field on an existing record class or schema, OR a material restructuring of an existing field's shape (e.g., `string` → structured object, scalar → enum, single value → array — any change that turns existing consumers' field-reading code into broken assumptions), spot-check that the analogous existing sibling's full registry seam — for a new class/op/id-class/node-type, the sibling class's id-prefix pattern, node-type constant, op-kind enum, parser / overlay / index / retrieval registration sites across `tools/*/src/**`; for a new-or-restructured field, the host record/schema's schema files, contract-doc surface, validators, and producing/consuming skills — is covered by the spec's deliverables — parallel to (e)'s rename/removal blast-radius spot-check, and applicable even when `/reassess-spec` ran. Route any gap per (e): add the site to the relevant ticket's Files to Touch, split it into a follow-up ticket with an explicit dependency, or flag it as an Issue at Step 2.

After spot-checks, render the exercised sub-checks as a compact inline list before moving to Step 3 (e.g., `Spot-checks: (a) ✓, (b) ✓, (c) skipped — no new sibling specs, (d) ✓, (e) N/A — no renames, (f) ✓, (g) N/A — no new class`). This proves each applicable sub-check ran and surfaces N/A cases explicitly.

If `/reassess-spec` was run but some findings were **deferred** by the user, treat deferred items as out-of-scope for ticket decomposition. Note them in the Step 6 final summary as "deferred reassessment findings that may warrant separate tickets." Do not silently incorporate deferred findings into ticket scope.

## Step 3: Decompose the Spec

Analyze the spec and identify discrete work units:

- Each ticket must represent a **reviewable diff** — small enough for comfortable manual review.
- Map **dependencies** between tickets (which must be done before which). Name them in each ticket's `Deps` field.
- Determine **priority ordering** — what to implement first, based on dependency graph and criticality.
- Ensure **every spec deliverable is covered** — no silent skipping. If a deliverable seems wrong or unnecessary, flag it using the 1-problem / 3-options / 1-recommendation format rather than omitting it. Three categories of deliverable are exempt from per-deliverable ticket production:
  - **No-change deliverables**: deliverables that explicitly state no changes are needed (e.g., "No new skill", "No new hook"). Note their existence in the Step 4 summary if non-obvious; produce no ticket.
  - **Cross-spec consumer-side deliverables**: deliverables that are consumed by a sibling spec's tickets rather than producing a discrete output in this spec's tickets — e.g., SPEC-04's §Phase 14a migration is consumed by SPEC-06's canon-addition rewrite; SPEC-04's §Validator inventory Rule 3 skill-judgment row is consumed by SPEC-06's same rewrite. The changes ARE needed, but they happen in another spec's decomposition. Note the cross-spec ownership in the Step 4 summary's Notes column as `cross-spec: <sibling-spec-id> decomposition` and in Step 6's deliverable coverage mapping as `not ticketed (cross-spec: <sibling-spec-id> ...)`. Distinct from the no-change category — the changes ARE needed, just not here. Misclassifying a cross-spec consumer-side deliverable as "needs a ticket here" produces a malformed cross-spec dependency where a ticket in this batch claims to deliver work that another spec's decomposition will actually deliver.
  - **Distributed deliverables** (see the Distributed deliverable pattern below): single conceptual deliverables encoded as a contract distributed across multiple implementation tickets rather than as a discrete chunk. Documented per-ticket; produce no separate "container" ticket for the distributed contract.
- **Inferred deliverable**: a deliverable named or implied by the spec's §Approach or §Verification but absent from §Deliverables. Produce a ticket per the standard pattern; document the inference in the ticket's Assumption Reassessment section with an explicit citation to the §Approach or §Verification reference that motivates the ticket (worked example: SPEC-09's create-base-world enforcement is mentioned in §Approach Move 2 — *"create-base-world enforces this at genesis"* — and named in §Verification 11, but absent from §Deliverables; produce a ticket with Assumption Reassessment item *"§Deliverables does NOT enumerate create-base-world; however, §Approach Move 2 explicitly names the enforcement and §Verification 11 names the test"*); flag the inference in the Step 4 summary's Notes column with the prefix `inferred from <section>` (e.g., `inferred from §Approach Move 2 + §Verification 11`). Distinct from the three exempt categories above — inferred deliverables ARE ticketed; the inference attribution is what makes the routing auditable. Distinct from a CRITICAL Issue at Step 2: when the §Approach/§Verification reference is unambiguous, inference is the right routing; when the reference is ambiguous or the implied deliverable would expand the spec's scope, route through Step 2's Issue-disposition flow instead.
- Use the spec's **"Out of Scope"** or equivalent non-goals section to populate each ticket's Out of Scope field — these are pre-validated non-goals.
- When multiple spec deliverables share the same file set and cannot be implemented independently, merge them into a single ticket. Note merged deliverables in the Step 4 summary table Notes column.
- Conversely, when a **single spec deliverable is too large for one reviewable diff** (it spans, say, a contract section + a JSON schema + a validator + multiple skill emitters), split it into multiple tickets decomposed by logical sub-concern — e.g., write path vs. read/verify path. Note the split in the Step 4 summary Notes column, and show it in Step 6's deliverable coverage mapping as `D<n>→00x+00y`. Worked example: SPEC-26 D3 (`SE.resolution` block + prose-attach `choice_consequence_visibility` check) split into a schema/write-path ticket and a prose-receipt/read-path ticket, the read-path ticket depending on the write-path ticket. Distinct from the **Distributed deliverable** pattern below: distributed is a contract distributed-by-design across tickets with no single owner; a size-driven split has each sub-ticket owning a discrete, independently-reviewable slice of the one deliverable.
- When all deliverables modify the **same file** OR land under the **same new package/directory**, decompose by logical section or module, not by file or directory boundary. Each ticket targeting a different section/module is a valid reviewable diff. Note the shared file or package in the Step 4 summary rather than repeating it per-ticket.
- **Intra-batch shared-file create-then-modify chains**: when ticket B's Files to Touch contains a `(modify)` entry for a file that ticket A's Files to Touch contains as `(new)` within the same batch, declare `Deps: A` on B explicitly. The file-creation is a load-bearing structural dependency (B fails at implementation time if A has not landed yet — the file the modifier targets does not exist on disk), distinct from §Step 6 item 5 §Shared-file overlaps across independent tickets, which covers parallel-add-to-registry patterns where each ticket adds its own slot to a pre-existing file. The Step 5 Pre-Write Files-to-Touch existence verification's within-batch new-file caveat is the composition-time backstop; the §Step 6 item 1 symmetric undeclared-Deps detection is the summary-time backstop. Worked precedent: a Phase C decomposition where ticket 006 creates `tools/world-index/tests/story-bundle-edges.test.ts` (`(new)`) and sibling tickets 007-013 each append per-class test blocks (`(modify)` on the same path); 007-013 must declare `Deps: 006` so the implementation order is structurally enforced rather than left to the §Step 6 item 5 mechanical-merge framing (which is for parallel modifies of a pre-existing file, not for create-then-modify chains). The shared-file enumeration at §Step 6 item 5 then correctly excludes the chain because its tickets carry `Deps`.
- When tests or end-to-end validation exercise multiple deliverables simultaneously and cannot be split per-deliverable, a single validation ticket depending on all implementation tickets is a valid decomposition. When a serial dependency DAG allows such a validation ticket to depend on the transitive-head ticket that composes all upstream work (e.g., a CLI ticket that wires every parser and CRUD module), listing just that transitive head as the validation ticket's sole `Deps` is acceptable and recommended over enumerating every upstream ticket — the DAG structure is already reconcilable from the upstream tickets' own `Deps` fields. Note the multi-dependency (or transitive-head dependency) in the Step 4 summary. See §Spec-Integration Ticket Shape below for the structural pattern this case instantiates.
- When a spec's §Cross-track / §Documentation / §Skill-side documentation deliverable touches multiple files that need atomic landing once upstream tickets ship — README updates, architectural-doc updates, skill-reference-file updates that reference all upstream surfaces coherently — a single cross-cutting docs ticket depending on the implementation tickets is a valid decomposition. Distinct from the validation-ticket pattern (which exercises code through tests): docs tickets verify documentation coverage through grep-proofs against the post-implementation tree. See §Cross-Cutting Docs Ticket Shape below for the structural pattern this case instantiates.
- **Distributed deliverable**: When a single conceptual deliverable is encoded as a contract distributed across multiple tickets rather than as a discrete chunk, list it in the Step 4 summary's Notes column as `distributed across <ticket-list>` and document the per-ticket contribution in Step 6's deliverable coverage mapping. Worked example: SPEC-04's §Per-run-mode applicability matrix is conceptually one deliverable but is encoded as `applies_to` predicates on every validator module across the structural-validators ticket plus the rule-validators ticket, then consumed by the engine pre-apply filter in the integration ticket — the matrix lives ACROSS three tickets, not in any one. This is a valid decomposition pattern; do not force-fit a discrete ticket for a contract that lives across the implementation. A second instance of the Distributed pattern is the **revision marker / migration-posture contract** deliverable that some specs include (typically named *"C-X.1 Spec landing commit serves as the SPEC-NN revision marker"*): the contract declares WARN-then-FAIL semantics for a subset of the spec's upstream implementation deliverables, and each affected upstream ticket carries the migration-posture handling for its own surface (the WARN-mode rollout for one revision cycle, then FAIL discipline). Classify as `distributed across <ticket-list>` per the standard pattern; do NOT classify as a "No-change deliverable" just because the marker itself has no separate ticket — the migration-posture handling IS the implementation work, distributed across the named upstream tickets. Worked example: SPEC-49 (2026-05-19 session) D-CX.1 (*"Spec landing commit serves as the SPEC-49 revision marker; legacy bundles run under compatibility-mode WARN posture for A.1, A.3, B.3, B.4 for one full revision cycle"*) → `distributed across <A.1 ticket>, <A.3 ticket>, <B.3 ticket>, <B.4 ticket>` in the Step 6 deliverable coverage mapping. The two worked examples cover the pattern's two common shapes: SPEC-04 illustrates `contract-via-field-predicates` (the matrix encoded as `applies_to` predicates on each validator module); SPEC-49 D-CX.1 illustrates `contract-via-per-ticket-migration-posture-handling` (the WARN/FAIL discipline encoded in each upstream ticket's implementation). Both are valid Distributed-deliverable instances; the surface encoding differs but the rule's classification (`distributed across <ticket-list>` rather than a separate "container" ticket) is the same. Distinct from the multi-deliverable-merge case (§"merge them into a single ticket"): merge is many-deliverables-into-one-ticket; distributed is one-deliverable-across-many-tickets.
- **Sub-assertion deliverable**: When a deliverable's intent is structurally a verification assertion of another deliverable's implementation (typically framed in the spec as "no code change required" because the existing surface already provides the underlying behavior and only test coverage is needed), fold it into the sibling implementation ticket's Acceptance Criteria + Test Plan rather than producing a separate ticket. Note the consolidation in the Step 4 summary's Notes column as `D-X folded into D-Y as verification assertion (no code change)` and in Step 6's deliverable coverage mapping as `D-X→00y (folded as verification assertion)`. Worked precedent: SPEC-47 (2026-05-19 session) — D-A9 *"Verify Hook 3 covers the new `_source/plans/` and `_source/emotions/` subdirs at integration test (no code change required)"* folded into ticket 017 (D-X1+D-X2 capstone integration test); Hook 3's generic regex pattern at `tools/hooks/src/hook3-guard-direct-edit.ts` already covers the new subdirs (`**/stories/<slug>/_source/**/*.yaml`), so only test-side verification was needed; the consolidation was recorded in the Step 4 summary as `D-X1+D-X2 (+D-A9)`. Distinct from the **No-change deliverables** exempt category above — sub-assertion deliverables DO require action (a test-side assertion added to the sibling's acceptance criteria), just no production code action; the action lands in the sibling ticket rather than as a separate ticket. Distinct from the **multi-deliverable-merge** case (§"merge them into a single ticket"): merge requires shared file set + cannot-be-implemented-independently; sub-assertion deliverables typically don't share files with their host (the sub-assertion has zero production files; the host has the integration test file). Distinct from the **Distributed deliverable** pattern above: distributed is one-deliverable-across-many-tickets (each ticket carries a piece of the contract); sub-assertion is one-deliverable-consolidated-into-another-ticket (the assertion piggybacks on the host's existing test surface).

### Spec-Integration Ticket Shape

Phase-level integration tickets — whose scope IS the spec's §Verification section, exercising every prior implementation ticket end-to-end — are a recurring worldloom pattern (one capstone per spec across the SPEC-01..SPEC-08 bundle; analogous capstones for SPEC-09 and future specs). Name the shape explicitly when decomposing:

- **What it is**: a single trailing ticket whose acceptance criteria enumerate the spec's §Verification bullets as test sub-cases. It introduces no new production code; it exercises the pipeline composed by the earlier tickets.
- **What it must contain**:
  - A fixture-world copy strategy that keeps the real `worlds/<slug>/` tree untouched (e.g., `fs.cpSync` to a temp root) so the test never mutates canon.
  - Re-enumerated expected counts (not hardcoded), computed from the fixture at test start. Hardcoded counts become stale as canon grows; re-enumeration stays valid over time.
  - One assertion per spec §Verification bullet (counts, determinism, incremental, drift, schema stability — whichever the spec names). Treat the spec's bullets as the capstone ticket's test matrix.
  - A wall-clock perf assertion when the spec names a performance gate (e.g., SPEC-08 Phase 1's <30s threshold); leave the spec's aspirational target as a dev-loop expectation rather than a CI gate.
- **How `Deps` resolves**: prefer the transitive-head convention above (single `Deps: <transitive-head-ticket>`) over enumerating every upstream ticket. The DAG already records the full chain. **Linear-chain vs parallel-branch DAGs**: the transitive-head convention works only when the upstream DAG is a linear chain — the head's own `Deps` transitively reach every prior ticket. When the upstream DAG has parallel branches (typical: a §Cross-Cutting Docs Ticket Shape docs ticket runs parallel to skill-integration tickets that the docs ticket does not depend on), no single ticket is the transitive head. In that case, the capstone's `Deps` must enumerate the **leaf set** — every leaf ticket whose own transitive `Deps` collectively cover the full upstream chain. For a typical worldloom spec producing per-class foundations + per-class validators + shared validators + skill integrations + cross-class docs + capstone, the leaf set is the skill-integration leaves + the docs ticket (so the capstone depends on them, and they each transitively reach foundations and validators). Worked precedent: SPEC-42 (this session) — capstone SPEC42STOSTADEB-015 was written with `Deps: SPEC42STOSTADEB-014` (the docs ticket) per the transitive-head convention; the docs ticket reaches 001/002/003/005/006/007 transitively but NOT 008/009/010/011/012/013 (skill-integration leaves parallel to docs). Correct `Deps` for the parallel-branch shape: `010, 011, 012, 013, 014` — the docs ticket plus the four skill-integration leaves whose transitive `Deps` cover the foundations + validators + shared validators chain.

### Cross-Cutting Docs Ticket Shape

Cross-cutting documentation tickets — whose scope IS the spec's §Cross-track / §Documentation / §Skill-side documentation deliverable, landing the docs surface atomically once all upstream implementation tickets have shipped — are a recurring worldloom pattern (e.g., README §Tools count updates, `docs/MACHINE-FACING-LAYER.md` retrieval-tool-scope rows, skill-reference-file phase-by-phase guidance). Name the shape explicitly when decomposing:

- **What it is**: a single trailing ticket whose Files to Touch are markdown docs (READMEs, architectural docs, skill reference files) — no production code. Acceptance is verified through grep-proofs against the post-implementation tree (e.g., `grep -E "tool-1|tool-2" tools/X/README.md` returns matches; `grep -n "registers N tools" tools/X/README.md` confirms the count update).
- **What it must contain**:
  - One Files to Touch entry per docs surface the cross-track deliverable names.
  - Acceptance Criteria as grep commands that target post-implementation state — exact-string matches for renamed/new symbols, count assertions for status-line updates.
  - Out of Scope entries naming the implementation surfaces this ticket does NOT touch (production code, tests, schema files) so reviewers know docs-only is the contract.
- **How `Deps` resolves**: list every implementation ticket whose surface the docs reference. Unlike §Spec-Integration Ticket Shape (where transitive-head dependency suffices for linear-chain DAGs because the DAG composes — see §Spec-Integration Ticket Shape §How `Deps` resolves for the parallel-branch qualification that adding this cross-cutting docs ticket can trigger), docs tickets reference each surface independently — the README §Tools list grows by one bullet per implementation ticket; the architectural docs add one row per new tool. Enumerating every upstream ticket in `Deps` makes the docs-to-surface relationship explicit and avoids ambiguity if an upstream ticket is dropped or renumbered.
- **When NOT to use this shape**: if every docs change can be co-located with its implementing ticket without staleness windows (e.g., when each implementation ticket owns its own README bullet AND no count-line or cross-tool table requires global awareness), per-ticket docs is cleaner. Use a cross-cutting docs ticket when ≥1 docs surface requires all upstream surfaces to exist coherently before it can land — typical triggers are status-line counts (`registers N tools`), cross-tool comparison tables, and skill-reference-file phase guidance that recommends multiple new tools in one prose breath.

## Step 5: Batched Ticket Writes

**Harness-emitted TaskCreate reminders during this step**: the harness may emit "TaskCreate hasn't been used recently" gentle reminders during Pre-flight → Step 5 → Step 6 execution. The §Task-tracking optionality clause below is the formal justification for not acting on them in bounded single-Write-per-ticket batches — per-file `TaskCreate` ceremony would over-decompose what the §Pre-Write Rehearsal's verbal commitment (Write count + AR-item-count preview + Files-to-Touch verification) already covers. ### Pre-Write Rehearsal (Mandatory)

In the assistant turn immediately preceding the batched-writes turn, state out loud the exact number of Write tool calls that will land in the next response (e.g., *"Next response will contain 9 parallel Write tool calls — one per ticket."*). The Write turn that follows MUST contain that exact count and nothing else. If the count statement and the Write turn diverge — including the failure mode of *"I'll send the first Write now and continue the others in subsequent messages"* — STOP and re-batch. The pre-rehearsal converts the structural tool-call discipline into a verbal commitment one turn earlier; the audit trail then reflects both the commitment and its execution, and the violation is visible before the first Write call lands rather than after the Nth. This step is the prevention; the §Batch All Write Calls sub-rule below is the spec; the recurring-failure precedents in that sub-section are the historical evidence motivating this gate. For a multi-batch plan (per §Batch All Write Calls in One Message — 10+ tickets or large bodies), the rehearsal turn states the per-batch counts for the whole plan up front (e.g., *"Next response: 5 Write calls (tickets 001-005); the response after: 5 Write calls (tickets 006-010)"*); each subsequent Write turn must then contain exactly its stated count and nothing else.

**Pre-Write AR-item-count preview (recommended for ≥5 tickets)**: in the same pre-rehearsal turn, after the Write-count statement, emit a one-line per-ticket AR-item-count preview naming the surviving template items and their final renumbered positions — e.g., *"AR item counts: 001 → 5 (1 codebase, 2 doc, 3 cross-skill boundary, 4 FOUNDATIONS principle, 5 Canon Safety surface); 002 → 5; 003 → 4; 004 → 6 (+ template item 7 rename blast radius); 005 → 4; 006 → 4; 007 → 5 (+ template item 6 schema extension); 008 → 5; 009 → 4"*. The preview forces the operator to enumerate the surviving Assumption Reassessment items per ticket BEFORE the Writes land, surfacing missing-item-4 / missing-item-5 / off-by-one renumbering as the operator counts each ticket's items. The literal announcement converts the mental Verify sub-step (per the §Assumption Reassessment Process step (3) Select → Rewrite → Verify sequence below) into a tool-call-equivalent verification surface in the audit trail before the Write tool call lands — parallel to the established `mcp-integration-audit` Phase 3 Pre-Write announcement requirement (`.claude/skills/mcp-integration-audit/SKILL.md` §Phase 3) which makes the same announcement mandatory for its smaller batch sizes. **Threshold**: recommended for batches of ≥5 tickets where parallel-composition load is highest; optional for ≤4 tickets where mental verification cost is trivial. **Conditional-item determination (sub-step before COUNT composition, mandatory format constraint)**: Before composing each ticket's COUNT, apply the §Step 6.2(c) per-ticket-type granularity triggers per ticket against the planned Files-to-Touch + Problem + Architecture Check intent — (a) FOUNDATIONS principle / Validation Rule cited or motivated → item 4 must be in the count; (b) HARD-GATE / canon-write ordering / Canon Safety Check surface touched per the per-ticket-type granularity (modifications or renames within `tools/validators/src/structural/`, `tools/validators/src/rules/`, `tools/hooks/`, or `tools/patch-engine/src/`; NOT MCP schema-discovery surfaces, MCP capability text, test fixtures, docs files, or skill prose that references but does not modify a Canon Safety surface) → item 5 must be in the count; (c) existing output schema extended → item 6 must be in the count; (d) skill / tool / hook / validator / schema field renamed or removed → item 7 must be in the count. The COUNT is the sum of always-required items (1-3) PLUS applicable conditional items. The §Strict count/enumeration matching sub-rule below then ensures the composed COUNT and the enumerated list agree. Without this conditional-item determination sub-step, strict-matching is satisfied when both sides agree regardless of whether the count itself reflects all applicable conditional triggers — a wrong-count-with-internally-consistent-naming failure mode strict-matching cannot detect. Worked precedent: SPEC-43 (2026-05-18 session) — Pre-Write AR-item-count preview for ticket 012 emitted COUNT=4 with internally-consistent enumeration; the §Step 6.2(c) post-Write backstop caught item 5 missing because ticket 012 modifies `snapshot-replay-equality.ts` and `state-snapshot-integrity.ts` (both structural validators under `tools/validators/src/structural/` per the per-ticket-type granularity rule). The post-Write catch cost one corrective Edit. Applying the conditional-item determination sub-step at preview time would have surfaced the missing item 5 before the Write landed, eliminating the corrective Edit at Step 6. **Strict count/enumeration matching (mandatory format constraint)**: the preview format `N → COUNT (enumeration)` requires COUNT items to be enumerated inside the parentheses, one per item, each named. A statement like *"009 → 4 (1, 2, 3 cross-skill: ...)"* is malformed — the count says 4 but only 3 items are enumerated. The correct form names the 4th item explicitly: *"009 → 4 (1 codebase, 2 spec, 3 cross-skill boundary, 4 FOUNDATIONS §Story Bundles §4a)"*. When the operator cannot name COUNT distinct items, the count itself is wrong — re-count before emitting the preview. The strict-matching constraint is what makes the preview structurally preventive rather than ceremonially performative: a format that allows COUNT and enumeration to disagree lets the operator satisfy the format superficially while missing the very gaps the preview is meant to surface. The §Step 6.2(b) numbering-continuity grep and §Step 6.2(c) conditional-menu-item check remain authoritative post-Write backstops; this preview is the structural prevention that catches gaps earlier. Worked precedent: SPEC-35 (prior session) — 9-ticket batch where compose-time mental verification missed 2 malformed numbering cases (007: `1 2 3 6`; 008: `1 2 3 4 7`) AND 3 conditional-item omissions (001/002 missing item 5; 007/009 missing item 4); all caught at Step 6.2 but cost 5 corrective Edits. The pre-Write AR-item-count preview would have surfaced all 5 gaps before the Writes landed. Second worked precedent: SPEC-42 (this session) — 15-ticket batch where the preview format `"009 → 4 (1, 2, 3 cross-skill: ...)"` was emitted with COUNT/enumeration mismatch for tickets 004 / 009 / 013 (each predicted count 4 but enumerated only 3 items); all 3 missing-item-4 cases for FOUNDATIONS-principle restatement were caught at §Step 6.2(c) post-Write backstop but cost 3 corrective Edits. The strict-matching constraint above would have surfaced all 3 gaps at preview time — the operator would have had to name a 4th item or correct the count to 3, either of which would have surfaced the missing FOUNDATIONS-principle item before the Writes landed.

**Pre-Write Files-to-Touch existence verification + Test Plan command sanity check**: in the same pre-rehearsal turn, after the Write-count statement and the AR-item-count preview above, run two existence checks across the batch's composed tickets before the batched Write calls land. **(i) Files-to-Touch**: for every `(modify)` Files-to-Touch entry across the composed tickets, run `test -f <path>` (or equivalent path-existence check — batched `ls`, `find`, or any other tool that produces the same exists/doesn't-exist evidence per path; parallel to the §Step 6 dependency consistency rule's `Use test -f (or equivalent path-existence check)` form) against the working tree. Any unresolved path means either (a) a typo in the cited filename — correct in the composition buffer before Write, OR (b) the cited path doesn't exist at HEAD (the file was renamed, moved, or archived between codebase validation at §Step 2 and ticket composition at §Step 5, OR the operator inferred a plausible-sounding path without grounding it in `tools/` enumeration). `(new)` entries are excluded by definition (the file is being introduced by the ticket and is not expected to exist yet). **Within-batch new-file caveat (per-entry, not per-file)**: the `(new)` exclusion above is per-ticket-entry, not per-file across the batch. When an `(modify)` Files-to-Touch entry points to a file that is created `(new)` by another ticket in the same batch, the existence check passes ONLY when the modifying ticket explicitly declares `Deps: <creating-ticket>`. Without the Deps declaration, the check fails because the implicit ordering dependency is structurally missing — declare Deps explicitly per §Step 3 §Intra-batch shared-file create-then-modify chains, OR change `(modify)` to `(new)` on the dependent ticket and reconcile the file-content overlap at composition time. Misclassifying a within-batch creates-then-modifies chain as "all new files excluded" lets the chain ship with declarably-incomplete `Deps` fields that the §Step 6 item 1 symmetric undeclared-Deps detection then has to flag (recovery), so the existence check at composition time is the prevention. **(ii) Test Plan commands**: for every script-invoking command cited in any ticket's Test Plan (e.g., `npm test --prefix <package>`, `npm run <script>`, `node tools/<package>/dist/src/cli/<binary>`), verify the script or binary exists in the cited package's `package.json` (or on disk under `dist/`) via `node -e "console.log(require('./<package>/package.json').scripts)"` (for npm scripts) or `test -f <binary-path>` (for CLI binaries). Citing scripts that don't exist forces user-side rework parallel to fabricated Files-to-Touch paths — both errors share the same root cause (citing-without-verifying at composition time) and the same fix shape (a pre-Write existence check). Resolve all mismatches in the composition buffer before the batched Write calls land. This rule extends the established `Cross-spec Deps verification (before HARD-GATE fires)` discipline at §Step 4 above (which runs `test -f` on every cross-spec `Deps:` path before user approval) to the symmetric Files-to-Touch + Test Plan command surfaces composed at §Step 5; the three checks together (Deps at Step 4, Files-to-Touch + Test Plan commands at Step 5 pre-rehearsal) close the existence-verification gap across every codebase-referencing field a ticket carries. Promotes the §Step 5 line 248 Files-to-Touch directive (*"exact paths validated against the codebase (new or modify)"*) and the §Step 6 final-rule (*"every ticket's Files to Touch matches the current codebase"*) from prose-level requirements to structural enforcement. Parallel to the established `mcp-integration-audit` Phase 7 Pre-Write Files-to-Touch existence verification + Pre-Write Test Plan command sanity check (`.claude/skills/mcp-integration-audit/SKILL.md` §Phase 7), which makes the same verification mandatory at the smaller ticket-emitting boundary. Worked precedent: an `/mcp-integration-audit` invocation — `tickets/MCPENH-057.md`'s Files-to-Touch cited `tools/world-mcp/tests/server/describe-envelope-schema.test.ts` (the actual test lives at `tools/world-mcp/tests/tools/describe-envelope-schema.test.ts`) and Test Plan cited `npm test --prefix tools/validators -- predicate-dsl-grammar-parity` plus `node tools/validators/dist/src/cli/run-tests.js` (neither command shape resolves — the actual package manifests define only package-local `npm run build` and `npm test` scripts); the user/linter corrected both post-Write. The same failure mode applies more heavily to spec-to-tickets's larger batches where parallel-composition load is higher and the number of cited paths and commands across the batch multiplies the failure surface.

**Recovery protocol after a rehearsal violation**: if the count statement and the Write turn diverge (rehearsal said N, turn contained K<N Writes), the next assistant turn MUST contain ZERO Write tool calls — it is a pure acknowledgment turn that names the violation, restates the remaining count (N-K), and declares the next turn's batched-recovery commitment. The turn AFTER the acknowledgment then emits the (N-K) Writes in one parallel batch. Do NOT emit a single Write in the acknowledgment turn "to keep momentum" — that re-instantiates the original anti-pattern and produces a sequential-one-at-a-time recovery that defeats the rehearsal's prevention purpose. The plain-prose "STOP and re-batch" instruction above is parseable as "emit the next single Write, then catch up with a batch after that"; this protocol disambiguates by requiring a zero-Write acknowledgment turn between the violation and the batched recovery. Worked precedent: SPEC-31 (this session) — operator rehearsed 14, emitted ticket 001 alone, then acknowledged the violation in the next message AND emitted ticket 002 alone (violation 2), then acknowledged the second violation AND emitted 12 in parallel. The recovery would have been one turn shorter had the acknowledgment turns been zero-Write turns followed by a single batched-recovery turn.

**Task-tracking optionality**: per-ticket `TaskCreate` / `TaskUpdate` tracking is OPTIONAL — the §Pre-Write Rehearsal's verbal commitment (Write count + AR-item-count preview + Files-to-Touch verification) provides the equivalent audit-trail discipline for bounded single-Write-per-ticket batches. Use `TaskCreate` only when ticket composition spans long internal work (research, dependency analysis, multi-step authoring) that the Pre-Write Rehearsal cannot cover. Parallel to `brainstorm`'s §Multi-file triage implementation discipline §Task tracking optionality clause (which carries the analogous "bounded single-operation per file → tracking optional" composition for triage implementations).

**Flow**: compose every ticket's full content in mind first, THEN emit all Write calls together in 1-2 batched messages (N parallel Write tool calls per message; or 2-3 batches for 10+ tickets / large bodies / batches that would exceed the harness's reliable parallel-tool-call budget per the §Batch All Write Calls in One Message sub-rule below — the sub-rule's splitting criteria — body-size-aware, ticket-count-aware, and parallel-tool-call-budget-aware — together authorize a third batch when individual assistant messages would otherwise exceed legibility or exceed the per-message parallel-emission ceiling). Do NOT alternate compose → Write → compose → Write per ticket — that produces N sequential one-Write-per-message sends, which the §Batch All Write Calls in One Message sub-rule below explicitly forbids. The flow distinction is what the rule requires; the per-ticket field list and content composition that follow this Flow directive describe WHAT to put in each ticket, but the WHEN-to-emit timing is the batched-after-all-composed shape — not interleaved with composition.

For each approved ticket, compose its full content following `tickets/_TEMPLATE.md` exactly. Every ticket MUST include:

- **Status**: PENDING
- **Priority**: HIGH / MEDIUM / LOW (based on dependency order and criticality)
- **Effort**: Small / Medium / Large
- **Engine Changes**: None or a list of affected or newly-introduced areas (for worldloom: which skills, tools, hooks, packages, or docs are touched or added). For tickets that introduce (rather than modify) a pipeline piece, still populate `Engine Changes: Yes` with the introduced piece named; follow with "no impact on existing <X>" when the new piece lives in isolation.
- **Deps**: Other tickets or specs this depends on
- **Problem**: What user-facing or architecture problem this solves
- **Assumption Reassessment** (with today's date): items 1–3 always required; items 4+ from `tickets/_TEMPLATE.md` are a menu. Process in three explicit steps before emitting the ticket's Write call: **(1) Select** the menu items that match this ticket's scope. **(2) Rewrite each selected item's number** to its position in the surviving list, starting at 4 — a template item labeled `6.` may become `4.` in one ticket and `5.` in another, depending on which neighbors survived. The menu's labels are reset by this step, not preserved. **(3) Verify** the final list reads `1, 2, 3, 4, 5, …` with no gaps. Lists like `1, 2, 3, 14` or `1, 2, 3, 6` are malformed output — they signal that step (2) was skipped, with selected items still wearing their menu labels. Worked example: a ticket that selects template items 1, 2, 3 (always required) plus item 6 (schema extension) writes them as `1, 2, 3, 4` — item 6's `6.` is rewritten to `4.` because it's the 4th surviving item in this ticket's list. The Step 6.2(b) check catches gaps after the fact, but fixing them requires one Edit per malformed ticket; catching them via the Select → Rewrite → Verify sequence at Step 5 is cheaper.

- **Verification Layers**: map each invariant to its proof surface (codebase grep, schema validation, skill dry-run, FOUNDATIONS alignment check, etc.). For single-layer tickets, state why additional mapping is not applicable.
- **What to Change**: numbered sections with specific implementation details
- **Files to Touch**: exact paths validated against the codebase (new or modify)
- **Out of Scope**: explicit non-goals — what this ticket must NOT change
- **Acceptance Criteria**:

  - **Invariants**: must-always-hold architectural and data-contract invariants
- **Test Plan**:

### Batch All Write Calls in One Message

Send **a small number of assistant messages containing parallel Write tool calls (one per ticket)**, not N sequential one-Write-per-message sends. For typical spec sizes (up to ~9 tickets) **with moderate ticket bodies (~100-200 lines each)**, a single batched message is the target; for 10+ tickets OR for any decomposition where ticket bodies are very large (~300+ lines each, common for full-package-introduction tickets that include package.json snippets, multi-file `What to Change` sections, and detailed Verification Layers), 2-3 batched messages are acceptable so individual assistant messages stay legible. Each ticket file write is independent because each creates a new file, so they can run concurrently. A single batched message with N Write calls costs one round-trip; N sequential one-Write-per-message sends cost N round-trips — the ban is on per-ticket sequential messaging, not on any multi-batch approach. Compose every ticket's full content first, then emit all Write calls in batched messages.

**Splitting criteria (three, not just body-size-aware)**: the decision of how many batched messages to use is governed by three criteria that compose:
- **(i) Ticket count** — >9 tickets in the decomposition → consider 2-3 batches so the per-message Write-call count stays manageable.
- **(ii) Ticket body size** — ticket bodies >300 lines each (full-package-introduction tickets, foundations tickets with many Files-to-Touch, etc.) → consider 2-3 batches so individual assistant messages stay legible.
- **(iii) Parallel-tool-call budget** — when the operator's harness reliably emits ≤N parallel tool calls per assistant message (some harnesses cap or unreliably-emit parallel tool calls above ~5-7 per message; the ceiling varies by harness configuration), the rehearsal commitment must not exceed that ceiling. If the rehearsal says *"8 parallel Write calls"* but the harness reliably emits ≤6, the rehearsal commitment will diverge from the emitted count and fire the §Recovery protocol after a rehearsal violation. The fix is to split at the parallel-tool-call-budget ceiling at rehearsal time, not at recovery time: prefer two batches of 5+5 (or 6+4) over one batch of 10 committed and 6 emitted. When uncertain about the harness's reliable parallel-tool-call ceiling, prefer smaller batches (4-6 per message) over larger ones that risk count divergence.

The three criteria compose: a 15-ticket decomposition with 300-line bodies under a 5-call parallel-budget harness lands as 3 batches of 5 (criteria i + ii + iii all reinforcing). A 6-ticket decomposition with 150-line bodies under any parallel-budget harness lands as 1 batch (none of the criteria triggers a split). The pre-rehearsal commit count should match the operator's actual parallel-emission capability under all three criteria, not the theoretical maximum under only criterion (i) and (ii).

**Worked precedents (recurring failure mode)**:

- **SPEC-21 (2026-05-08 session)**: 7 tickets emitted as 7 sequential one-Write-per-message sends despite this rule; correct shape would have been 1 batched message with 7 parallel Write calls (single round-trip), or 2 batched messages given that 1 ticket exceeded 300 lines and 2 others were near-300. Cost: 7× round-trips and ~5× wall-clock vs. the 1-2-message canonical shape; output correctness preserved (all 7 tickets landed with correct content), but the audit-trail signal is that the operator composed ticket 1 → wrote ticket 1 → composed ticket 2 → wrote ticket 2 ... rather than composing all 9 first and batching the writes.
- **SPEC-23 (2026-05-13 session)**: 9 tickets emitted as 9 sequential one-Write-per-message sends despite the SPEC-21 precedent having been added to this section in the interim. The operator framed the flow as *"two batches for legibility"* but each Write call landed in its own assistant message; the prose framing did not produce parallel batching. This is the second occurrence of the same anti-pattern in ~5 days, demonstrating that prose-only enforcement (Flow directive + this sub-rule + a single worked precedent) is insufficient. The §Pre-Write Rehearsal (Mandatory) gate at the top of §Step 5 is the structural prevention introduced after the SPEC-23 recurrence; the verbal-commitment-one-turn-earlier shape makes the violation visible in the audit trail before the first Write call lands rather than after the Nth.
- **SPEC-42 (2026-05-17 session)**: 15-ticket batch rehearsed as `"response 1 = 8 Write calls (tickets 001-008); response 2 = 7 Write calls (tickets 009-015)"`; response 1 actually emitted 6 parallel Write calls (the harness's reliable parallel-tool-call ceiling was ≤6), firing the §Recovery protocol after a rehearsal violation. This is a **new failure-mode shape** distinct from the SPEC-21 / SPEC-23 sequential-one-Write-per-message pattern: the operator DID emit parallel sends (not sequential) but committed to a count that exceeded the harness's reliable parallel-tool-call budget. The §Recovery protocol handled it correctly (zero-Write acknowledgment turn + 5-Write recovery batch + 4-Write final batch), but the underlying cause was the rehearsal's omission of criterion (iii) parallel-tool-call-budget-aware splitting from its commit-count decision. The §Splitting criteria (three, not just body-size-aware) sub-section above is the structural response — adding parallel-tool-call-budget as an explicit splitting criterion forces the rehearsal to commit to a count the harness can reliably emit, preventing the parallel-but-undercount failure mode at commit-time rather than handling it via the recovery protocol.

After the parallel batch returns, verify every ticket file was created. If any Write call failed (typo in path, permissions error, or other I/O failure), retry that ticket with the corrected argument immediately — do not proceed to Step 6 until all ticket files exist at their intended paths. If a system-reminder or external tool indicates that a ticket file was modified between your Write call and Step 6 (e.g., by a linter hook, a user keystroke, or a parallel editor save), treat the external edits as authoritative — do not revert them. Step 6's cross-ticket dependency verification must run against the edited content, and any sibling ticket whose path, symbol, or count references the externally-edited ticket may need follow-up adjustment before the final summary is emitted. The follow-up adjustment also applies when the external edit corrects a stale codebase assumption (missing file, non-existent script, renamed symbol) that sibling tickets independently share — not just when siblings lexically reference the edited ticket. The trigger is "does the corrected assumption affect the sibling's truthfulness?", not "does the sibling mention the edited ticket by name?". **Apply the corrections via Edit calls to the affected sibling ticket files BEFORE emitting Step 6's final summary** — "follow-up adjustment" means edit-now-then-summarize, not document-only-and-defer-to-future-session. Step 6 documents the corrections retrospectively under a dedicated line; it is not a hand-off to a later session. Record the parallel-stale-assumption correction in the Step 6 final summary under a dedicated line alongside the external-edit note so the audit trail captures both the triggering edit and the proactive sibling cleanup.

**Two cases distinguish parallel-stale-assumption applicability**: (i) **Symbol-correction case**: the external edit corrects symbol-level facts (function names, schema fields, formula contents, file counts, type signatures, file paths) that siblings share — apply parallel-stale-assumption corrections via Edit calls before emitting Step 6, since siblings making the same wrong claim need fixing now. (ii) **Status-flip-only case**: the external edit reflects post-implementation reality on one ticket (Status: PENDING → COMPLETED, past-tense Problem framing, Verification Layers rewritten to truthfully describe what was actually verified at implementation time) but siblings remain PENDING with future-tense framing — pre-correction is OPTIONAL; PENDING siblings describing future-state verification (post-prerequisite-landing) are not currently making false claims, and the implementer can correct each sibling when it transitions to COMPLETED. The two cases can co-occur — an external edit may both flip status to COMPLETED AND correct symbol-level facts; in that case apply (i)'s sibling corrections regardless of (ii)'s optional-pre-correction discipline. Document the case-by-case judgment explicitly in the Step 6 external-edit note (e.g., *"case (ii) status-flip; no sibling pre-correction needed because PENDING tickets correctly describe future-state verification"* OR *"case (i) symbol-correction on field X; corrections applied to siblings A, B, C"*) so a future reader can reconstruct why pre-correction was applied or skipped.

**Sibling-scope-claim case (distinct from parallel-stale-assumption)**: (iii) when the external edit makes substantive claims about which sibling tickets are live (e.g., adds an Assumption Reassessment item naming a subset of the batch as *"draft references not live tickets"*, or marks a ticket as redacted-by-user-decision), the skill does NOT delete, rename, or relabel sibling tickets unilaterally based on such a claim. Note the discrepancy in user-facing prose at the next assistant turn (e.g., *"Post-summary external edit on `<NAMESPACE>-NNN` claims `<NAMESPACE>-MMM` and `<NAMESPACE>-PPP` are draft references not live; those ticket files remain on disk — confirm intended scope before proceeding to implementation."*) and defer action to user. Case (iii) is about scope intent and requires explicit confirmation before sibling tickets are deleted, archived, or downgraded; cases (i) and (ii) are about content correctness and status neutrality respectively. Applicable at both pre-Step-6 and post-Step-6 timing — when the case (iii) edit lands after Step 6, the surfacing prose pairs with the *"note it in user-facing text"* discipline at the post-Step-6 paragraph immediately below. Worked precedent: SPEC-23 (2026-05-13 session) — post-summary external edit on `SPEC23STOSTACON-001` added an Assumption Reassessment item claiming *"active same-family tickets currently exist only for `SPEC23STOSTACON-001` through `SPEC23STOSTACON-007`. Draft references to `SPEC23STOSTACON-008` / `SPEC23STOSTACON-009` are retained only as spec-level future decomposition labels; they are not live ticket dependencies in this run."* The skill had no case (iii) prose at the time and the operator missed the user-facing surfacing line; this case-(iii) section was added as the structural response.

**Post-Step 6 external edits**: external mutations may continue to land *after* the Step 6 final summary has been emitted — common cases include auto-archival hooks that move a COMPLETED ticket from `tickets/` to `archive/tickets/` and trigger linter rewrites of sibling tickets' `Deps:` paths from `<NAMESPACE>-NNN` to `archive/tickets/<NAMESPACE>-NNN.md`. The Step 6 summary's dependency-existence verdict captures the state at emission time; it is NOT authoritative for any sibling ticket whose `Deps` references a ticket that was externally mutated post-summary. When such an edit is surfaced via system-reminder *after* Step 6, note it in user-facing text (e.g., "Post-summary external edit detected on `<NAMESPACE>-NNN`; sibling `Deps` paths may have been rewritten — re-verify before proceeding to implementation.") so the user sees the gap explicitly. **Carve-out — harness-confirmed user awareness**: when the surfacing system-reminder itself states the user is already aware of the edit (e.g., "This change was intentional ... Don't tell the user this, since they are already aware"), this gap-notification note may be omitted — surfacing it would be redundant and would contradict the harness signal. The carve-out covers only this FYI-style gap-notification; it does NOT extend to the case (iii) sibling-scope-claim note above, which is a scope-confirmation *request* the user must answer, not a redundant awareness FYI. The case (i) / (ii) / (iii) sibling-impact triage still runs internally regardless of the carve-out, and any sibling correction it identifies is still applied. When a post-Step-6 external edit is a parallel-stale-assumption / symbol-correction edit (case (i) above) rather than an auto-archival / `Deps`-rewrite, apply the same case (i) / (ii) / (iii) triage as the pre-Step-6 rule: determine whether sibling tickets independently share the corrected assumption, and if they do, name the affected siblings in the user-facing note (re-emitting Step 6 is still not done — but the sibling impact is surfaced explicitly rather than silently transferred to the user). The skill does NOT retroactively re-emit Step 6 in a fresh assistant turn; ownership of post-summary reconciliation transfers to the user at this point. This boundary is deliberate — re-emitting a Step 6 summary every time a downstream linter touches a ticket would create an unbounded re-emission loop.

## Step 6: Final Summary

After writing all files:

1. **Verify cross-ticket dependency consistency**: For each `Deps` reference, confirm the depended-on ticket actually produces what the dependent ticket needs (types, skills, modules, files). Use `test -f` (or equivalent path-existence check) on every `Deps` path at summary-emission time so the verdict captures any auto-archival that happened mid-flow — e.g., a COMPLETED ticket relocated from `tickets/<NAMESPACE>-NNN.md` to `archive/tickets/<NAMESPACE>-NNN.md` between Step 5's Write and this summary. When the original `Deps` path no longer resolves but its archive counterpart does, treat the dependency as resolved (auto-archive is path migration, not deletion) and note the path migration in the dependency-verification table. If a dependency is broken (e.g., ticket 005 depends on a skill output from 003 but 003's scope doesn't define it; or a `Deps` path no longer resolves at either the original or the auto-archive location), flag the inconsistency. **Symmetric undeclared-Deps detection (intra-batch create-then-modify chains)**: for each ticket's Files to Touch `(modify)` entries, grep sibling tickets' Files to Touch for the same path as `(new)`; when a sibling creates the file in this batch, the modifying ticket MUST declare `Deps:` on the creator per §Step 3 §Intra-batch shared-file create-then-modify chains. Missing `Deps:` → flag the inconsistency before emitting the final summary; the modifying ticket either declares Deps on the creator or changes its `(modify)` Files-to-Touch entry to `(new)` and reconciles the file-content overlap at composition time. The Step 5 Pre-Write Files-to-Touch existence verification's within-batch new-file caveat is the composition-time prevention surface; this check is the summary-time backstop for the cases where the operator bypassed the existence check by treating within-batch creates as if they were excluded `(new)` entries across siblings.

2. **Template fidelity check**: for each written ticket, confirm (a) every required section from `tickets/_TEMPLATE.md` is present (Status, Priority, Effort, Engine Changes, Deps, Problem, Assumption Reassessment, Architecture Check, Verification Layers, What to Change, Files to Touch, Out of Scope, Acceptance Criteria, Test Plan), and (b) the Assumption Reassessment section uses sequential numbering starting at 1. Numbering-continuity command: `awk '/^## Assumption Reassessment/,/^## Architecture Check/' tickets/<NAMESPACE>-NNN.md | grep -oE '^[0-9]+'` (numbers extracted by grep alone — no awk field-split needed; this avoids the harness-substitution risk that affects `$1`-style references in skill body text when a positional namespace argument is bound). Output should be a strictly sequential integer sequence `1 2 3 ...`. Any gap (e.g., `1 2 3 6`) is a malformed Assumption Reassessment — the Step 5 Select → Rewrite → Verify sequence's step (2) (rewrite each selected menu item's number to its position in the surviving list, starting at 4) was not applied. Fix the offending ticket's numbering before emitting the final summary.

   (c) **Conditional menu-item completeness** (semantic sub-check; not satisfied by the (b) grep): for each ticket, scan its body (Problem, Architecture Check, What to Change, Files to Touch, Acceptance Criteria) for content that triggers a `tickets/_TEMPLATE.md` conditional menu item, and verify the corresponding item is present in Assumption Reassessment:
      - FOUNDATIONS principle / Validation Rule cited or motivated → template item 4 (FOUNDATIONS principle restatement) must be present.
      - HARD-GATE / canon-write ordering / Canon Safety Check surface touched → template item 5 must be present. **Per-ticket-type granularity**: in practice, item 5 fires for tickets modifying or renaming structural validators (`tools/validators/src/structural/`), rule validators (`tools/validators/src/rules/`), hooks (`tools/hooks/`), or patch-engine op wiring (`tools/patch-engine/src/`); item 5 does NOT fire for tickets touching MCP schema-discovery surfaces, MCP capability text, test fixtures, docs files, or skill prose that references but does not modify a Canon Safety surface. The decision rule is whether the modified surface gates canon or story-bundle record writes at engine pre-apply time; if yes, item 5 fires. Worked precedent: SPEC-35 (this session) — tickets 001/002 (`observer-firewall.ts` / `branch-isolation.ts` validator modifications) and 004 (`non_propagation_tag_shape` validator rename) required item 5; tickets 003 (MCP behavior), 005 (skill prose only), 006 (MCP capability text), 007 (MCP schema-discovery wiring), 008 (test fixtures), and 009 (docs edit) did not. Catching the granularity via this per-ticket-type rule at audit time prevents the operator-judgment cost the SPEC-35 session paid (5 ticket-by-ticket judgment calls on whether item 5 fires).
      - Existing output schema extended (CF / CH / proposal package / character dossier / DA / story-bundle record) → template item 6 must be present.
      - Skill / tool / hook / validator / schema field renamed or removed → template item 7 (rename/remove blast radius) must be present.
      - Reassessment exposes adjacent contradictions → template item 8 must be present (when applicable).
   For each absent-but-applicable conditional item, edit the ticket to add it BEFORE emitting the final summary. The (b) sequential-numbering grep catches gaps but not omissions of applicable conditional items — a ticket with sequential numbering 1, 2, 3 passes (b) even when its body explicitly motivates a FOUNDATIONS principle that template item 4 should restate. Worked precedent: SPEC-31 (this session) — tickets 004 (motivating principle: §Tooling Recommendation) and 005 (motivating principle: §Story Bundles §4a) passed the (b) numbering grep with 1 2 3 and 1 2 3 4 respectively, but were missing template item 4. The (c) semantic sub-check catches both before final summary.

3. **Deliverable coverage mapping**: List each spec deliverable and the ticket that covers it (e.g., `D1→001, D2→001` for a merge, `D3→003+004` for a size-driven split per §Step 3). Verify all spec deliverables are accounted for. If any deliverable is missing, flag it. If the spec uses phases or named sections instead of numbered deliverables (e.g., `Phase 2a`, `Part B`), adapt the mapping to use the spec's organizational scheme — for named sections, use section names directly (e.g., `§Package location → 001, §SQLite schema → 002`).

4. List:
   - All ticket files created (paths).
   - The dependency graph (which tickets block which).
   - Suggested implementation order.
   - **Deferred `/reassess-spec` findings**, if any, noted as "may warrant separate tickets" (findings the user explicitly chose to defer at reassessment time).
   - **Cross-spec follow-ups**, if any, surfaced by the spec's Risks section, the companion `docs/triage/` file's follow-up-items section (for brainstorm-produced specs — see §Step 2 §Brainstorm-produced specs), or discovered during decomposition — concerns requiring action in other specs or artifacts, not in this batch. The two categories are distinct: deferred findings may become tickets after user disposition; cross-spec follow-ups require one of three routing patterns:
     - **(a)** `/reassess-spec` on an existing active or archived spec, when the follow-up shifts that spec's scope or recommendations. When the cross-spec follow-up corrects a reference to a file or symbol this batch's tickets will create, modify, or delete, name the sequencing relationship explicitly — typically "run AFTER ticket NNN lands" so the follow-up reassessment surfaces the affected reference with full evidence backing (a reassessment that runs before the deletion / rename / creation lands cannot evidence the corrected state). When the follow-up is purely informational (no in-batch deliverable affects the referent), no sequencing constraint applies.
     - **(b)** **Draft a NEW spec file** to lift dormant amendment commitments (common worldloom pattern: amendments living inside a sibling spec's §C clauses + `specs/IMPLEMENTATION-ORDER.md` Phase-tier scheduling that never got their own decomposable spec), then route through `/reassess-spec` + `/spec-to-tickets` on the new spec in a subsequent session. Surface this in the Step 6 summary as "cross-spec follow-up requires drafting `<proposed-path.md>` first" so the user sees the multi-step path at decomposition time rather than discovering it via follow-up question. Also note any implied load-bearing cross-ticket dependency: when the new spec's future tickets must be added as `Deps` entries on tickets produced in THIS batch, name the specific tickets (by their `<NAMESPACE>-NNN` IDs) so the directive can be embedded in the new spec's prose when it is drafted.
     - **(c)** Separate skill invocation or documentation edit outside the spec-to-ticket pipeline (e.g., `/skill-consolidate`, direct `docs/` edits, `specs/IMPLEMENTATION-ORDER.md` status-row maintenance for newly-created specs).

     **Decision criterion (a) vs (c) for docs-drift cases**: When a cross-spec follow-up is a docs-drift correction (a stale reference, a renamed symbol carried over in prose, a retired-validator name still cited in `docs/FOUNDATIONS.md` / a sibling spec / a doc) AND the affected docs surface is owned by an active doc-updates spec (e.g., SPEC-07 Part B in worldloom), prefer routing pattern **(a)** — route through that spec's reassessment + decomposition cycle so the doc edit lands with attribution, preserves the spec → ticket → doc audit chain, and avoids competing with the active spec's scope. When the docs-drift fix is genuinely standalone (not in any active spec's scope) AND ≤3 lines, prefer routing pattern **(c)** — direct doc edit. Decision criterion: "is there an active spec whose scope already covers this docs surface?" If yes → (a); if no → (c). When in doubt, prefer (a) — the over-routing cost (a slightly delayed doc fix landing through a spec cycle) is lower than the under-routing cost (a doc edit that scope-collides with an active spec's pending decomposition).

5. **Shared-file overlaps across independent tickets**: enumerate files that ≥2 tickets in the batch each modify (where no `Deps` relationship exists between them) — typically registry files, central enums, shared constants modules where each ticket adds its own slot. Format: `<file> modified by tickets <ticket-list> — implementers should coordinate slot ordering / array-entry placement; conflicts are mechanical (different lines, no semantic overlap)`. This complements item 1's `Deps`-based dependency consistency check by surfacing implicit coordination needs across siblings the dependency graph doesn't connect — item 1 catches `Deps`-declared relationships; this item catches the symmetric case where independence is declared but coordination is still needed. Worked precedent: SPEC-38 (this session) — tickets 010/011/012 (three independent validator additions, all `Deps: None`) each modify `tools/validators/src/public/registry.ts` (each adds its own import + array entry) and the paired `tests/{rules,structural}/registry.test.ts` files (each extends the name-list assertion); the Step 6 summary surfaced this as a free-form sentence about "mechanical merge conflicts" via authorial improvisation. With this item, the surfacing is prescribed rather than improvised.

Do NOT commit. Leave files for user review.

## Validation Rules This Skill Upholds

- **Rule 1: No Floating Facts** — enforced at Step 2 (codebase validation). When a spec's deliverables introduce canon-impacting mechanisms (new CF Record fields, new Change Log Entry shapes, new validator thresholds, new canon-safety checks), the skill flags missing scope / prerequisites / limits / consequences as Issues before decomposition. Most Rule 1 enforcement is inherited from upstream `reassess-spec`; this skill's contribution is catching Rule 1 drift introduced *between* reassessment and ticket decomposition.
- **Rule 5: No Consequence Evasion** — enforced at Step 3 (decomposition). Second-order effects of a spec deliverable that the spec didn't address become either (a) additional tickets in the decomposition, or (b) explicit Out-of-Scope entries with a named follow-up ticket or spec dependency. The decomposition must not leave a second-order effect unaddressed and unacknowledged.
- **Rule 6: No Silent Retcons** — enforced at Step 5 (ticket writes). Every ticket that modifies existing pipeline code (skills, tools, hooks, validators, schemas) must cite the retcon justification in its Assumption Reassessment section — what existing behavior is changing, what the new behavior is, and why the change is warranted. Silent "update X to Y" tickets without retcon attribution fail this rule.
- **Rule 7: Preserve Mystery Deliberately** — enforced at Step 2 (codebase validation) for any spec deliverable touching validators, hooks, canon-safety check surfaces, or Mystery Reserve firewall logic. A spec that would silently resolve a Mystery Reserve entry or weaken the MR firewall triggers a CRITICAL Issue that blocks decomposition until the user dispositions it.

## Guardrails

- **FOUNDATIONS alignment is mandatory**: Never approve a ticket decomposition that violates a FOUNDATIONS principle, even if requested — flag the conflict as a CRITICAL Issue at Step 2 and wait for user disposition.
- **Template fidelity**: Every ticket must use `tickets/_TEMPLATE.md` exactly — no ad-hoc sections, no missing required fields, no "simplified" variants. If the template needs to evolve, that is a separate spec, not an inline improvisation.
- **Ticket fidelity**: Never silently skip a spec deliverable. If a deliverable seems wrong, use the 1-problem / 3-options / 1-recommendation format and ask the user — do not omit it.
- **Codebase truth**: File paths, skill names, tool names, and schema references in tickets must be validated against the actual codebase, not assumed from the spec. Stale references propagated from a spec through a ticket are a skill failure.
- **Reviewable size**: Each ticket should be small enough to review as a single diff. When in doubt, split further. A 15-file change touching 4 skills is not a reviewable diff.
- **Explicit dependencies**: Use the `Deps` field to declare inter-ticket dependencies; never leave implicit ordering. Every `Deps` entry must resolve to either a ticket produced in this run or a pre-existing ticket/spec path confirmed at Pre-flight.
- **No canon writes**: This skill never writes to `worlds/<slug>/` files, `CANON_LEDGER.md`, `INVARIANTS.md`, or any world-level canon file. Tickets are pipeline-level artifacts. If a ticket's implementation would touch canon, that work happens in `canon-addition`, not here.
- **No spec edits**: This skill never edits the source spec file. Spec refinement is `reassess-spec`'s job. If decomposition reveals a spec defect, flag it as an Issue at Step 2 and route the fix back through `reassess-spec`.
- **Auto-mode gate still applies**: Auto mode does not bypass the HARD-GATE. Auto-mode may auto-approve the Step 4 summary only when Step 2 surfaced no Issues AND no reassessment findings were deferred.
- **Worktree discipline**: If invoked inside a git worktree, all paths — reads, writes, globs, greps — resolve from the worktree root, not the main repo root.
- **Do not `git commit` from inside this skill**: Writes land in the working tree; the user reviews the diff and commits.

## Final Rule

A ticket decomposition is not complete until every spec deliverable maps to a ticket (including inferred deliverables produced per §Step 3's Inferred deliverable rule with explicit `inferred from <section>` attribution) OR to an explicit non-goal OR to a documented cross-spec consumer-side / distributed-deliverable / no-change category per Step 3's deliverable-coverage rule, every ticket's Deps resolve to a real target, every ticket's Files to Touch matches the current codebase, and every FOUNDATIONS-impacting deliverable has been validated against FOUNDATIONS.md before the ticket was written.
