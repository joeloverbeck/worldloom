## Problem Statement

`reports/story-related-upgrades.md` was regenerated by an external review after being fed `docs/FOUNDATIONS.md`, `.claude/skills/_shared-templates/story-state-contract.md`, and the seven landed story-pipeline skills. This is a genuine second pass: SPEC-25 already triaged an *earlier* version of the same file (produced from initial brainstorming docs), and the refreshed version both drops the now-moot items and surfaces new ones grounded in the landed skill prose. It proposes 15 changes across four priority tiers (P0×5, P1×4, P2×4, P3×2). Reassessment against the actual codebase recalibrates it:

- **The five P0 schema-reference claims are confirmed real and still present in the working tree.** SPEC-24 finalized the JSON schemas and contract §4 — but the `branching-story-turn-cycle` and `branching-story-health-audit` *skill prose* was never reconciled to them. SPEC-25's `STSTAT` work even edited `branching-story-turn-cycle/SKILL.md:239` while leaving the stale death/incapacity bullets at `:243-247` directly below it untouched. P0 is the completion of SPEC-24's incomplete sweep, and it *aligns with* decisions SPEC-24 already made — SPEC-24 explicitly rejected `status` fields on `STINT` and `SREL`, which is exactly the corrected wording the report recommends.
- **The report's strongest structural items are now implementable because SPEC-25 built their substrate.** The causal-dependency threat scan needs `CHC.grounded_in` (SPEC-25 D5); expected-witness validation needs replayable `STSTAT` (SPEC-25 D1); the `record_age` predicate builds on predicate DSL v2 + alias binding (SPEC-25 D4); uniform debt reasoning needs `OBL`/`CNSQ` `urgency` (SPEC-25 D3). All four landed. SPEC-26 is the successor that adds the *checks and resolution structures* on top.
- **Two report items are over-reach and are trimmed; two are rejected.** `SE.resolution.reason_class` has no downstream consumer; `urgency_at_least` duplicates an existing predicate filter; the health-audit `sifting` mode is authorial opportunity-surfacing rather than coherence enforcement (and SPEC-25 already explicitly rejected it as "P2 #13 semantic audit mode"); the SLT coverage matrix's load-bearing finding duplicates an existing health-audit check.

**Enabling fact (carried from SPEC-25):** there are **zero production story bundles**, so every schema edit here is a pure greenfield change with no migration or retrofit cost. Consequently every rejection in §Out of Scope is **structural**, not a pragmatic / migration-cost softening.

The eight accepted deliverables each close, or make enforceable, a coherence invariant the architecture depends on:

1. **Skill prose references fields that do not exist.** `branching-story-turn-cycle/SKILL.md:243/245/247` instruct superseding `STINT` "to abandoned/transferred", `SREL` "status becomes severed or mourning", and `STOBJ.controlled_by` — but `STINT` and `SREL` have no `status` field and `STOBJ` has `owner`/`current_location`, not `controlled_by` (verified against `story-state-contract.md` §4 and `tools/validators/src/schemas/story-{relationship,object}.schema.json`). `branching-story-health-audit/SKILL.md:186` names a finding `relationship_change_without_basis` against an `SREL.basis` field that does not exist (the schema uses `derived_from`). A skill instruction that names a non-existent field is unexecutable.
2. **Branch-locality is tested two incompatible ways.** `branching-story-health-audit/SKILL.md:168` (`global_author_pool_branch_dependency`) uses a crude "`created_at_page` is non-null" test, while `commitment-block-authoring/SKILL.md:224-225` correctly recognizes that root-of-tree records (created at `PG-1`, in every branch's `branch_path`) are globally visible. The crude test falsely flags valid global-author-pool blocks that reference genesis records.
3. **Non-accept outcomes are not structurally explicit.** `SE.outcome_route` records *which route* an action took, but the *result within that route* — did the `attempt` succeed or fail? — lives only in `world_logic_rationale` prose and the `state_delta`. It is not directly auditable, and there is no structured contract for prose-attach to verify the outcome was made visible to the player.
4. **No check detects a clobbered dependency.** When a turn's `state_delta` closes or supersedes a record, nothing verifies that an emitted `CHC`, an open `OBL` counterparty, a visible affordance, or an eligible `SLT` precondition did not depend on it. This is Rule 5 (No Consequence Evasion) at story scope, currently unenforced.
5. **Witness propagation is mandated but not checkable.** `branching-story-turn-cycle` Phase 4 is *mandatory* for events involving secrecy / betrayal / deception / violence / law / status / public ritual, and Phase 9 check 3 "verifies coverage" — but there is no *expected-witness computation*, so "coverage" can only mean "some `BEL` records were drafted", not "every entity who would witness this is accounted for."
6. **Causal pressure cannot mature in the predicate DSL.** `branching-story-health-audit` hard-codes debt-aging thresholds (`ignored_debt_beyond_urgency`), but an `SLT` precondition cannot express "this debt has been open ≥ N pages" — so storylet eligibility cannot respond to *how long* a pressure has been ignored without re-introducing act timers.
7. **Player agency surface is implicit.** `branching-story-turn-cycle`'s action-source-legality check (Phase 9 additional check 1) must know which `STENT` the player controls and whether the player may act on knowledge the viewpoint character lacks — today it infers this per turn. `branching-story-bootstrap` does not even enumerate the sections it writes into `STORY_KERNEL.md`.

### Key design decisions

- **Considered adding `status` fields to `STINT` and `SREL` to make the turn-cycle prose executable; chose to fix the prose instead** because SPEC-24's per-property audit already evaluated and explicitly rejected those fields — `STINT` closure is append-only supersession-to-closed, and `SREL` change is supersession of `axis`/`value`/`valence`/`description`. The bug is the skill prose, not a missing field.
- **Considered ChatGPT-Pro's full `SE.resolution` block (`result` / `reason_class` / `player_visible_feedback`); chose `result` + `player_visible_feedback` only** because `result` makes non-accept outcomes auditable for replay / prose-attach / promotion, and `player_visible_feedback` is the contract the new prose-attach check verifies — but `reason_class` (capability / opposition / resource_limit / …) has no identified downstream consumer and would violate §Story Bundles §5b schema-minimalism.
- **Considered ChatGPT-Pro's `SE.perception` block for witness discipline; rejected it** because the expected-witness pass is achievable as deterministic validation over `STSTAT.location`, event targets, active `BEL`, and active `DA`/`STOBJ` evidence — all of which already exist post-SPEC-25. The report itself recommends this restraint.
- **Considered implementing the causal-dependency threat scan as an executable `tools/validators/` validator; chose skill-prose checks** because `branching-story-health-audit` Phase 2's six existing sub-phases (2a–2f) are all skill-prose structural replay, not tool validators — a seventh sub-phase matching that architecture is structurally consistent, and `CHC.grounded_in` (SPEC-25 D5) already supplies the machine-readable substrate the check reads.
- **Considered ChatGPT-Pro's `urgency_at_least` predicate; rejected it** because predicate DSL v2's existential predicates (`any_obligation_open`, `any_consequence_pending`, …) already accept an optional `urgency?` filter argument — `urgency_at_least` would be a redundant second spelling of the same constraint. Only `record_age` is genuinely inexpressible today.
- **Considered ChatGPT-Pro's full `STORY_KERNEL.md` Player Agency Contract (six bullets); chose the three load-bearing bullets** (agency surface, write-in envelope, viewpoint limits) because the other three either restate `FOUNDATIONS.md` (impossible-action policy) or are authorial taste (control style, consequence-visibility promise) with no consumer. The kept three are routing inputs `branching-story-turn-cycle`'s action-source-legality check currently infers.
- **Considered ChatGPT-Pro's health-audit `sifting` mode and SLT coverage matrix; rejected both** — see §Out of Scope. `sifting` is opportunity-surfacing, not coherence enforcement (and SPEC-25 already rejected it once); the coverage matrix's one load-bearing finding (`slt_pool_debt_blind_spot`) duplicates the existing Phase 2c `unactionable_debt`.

## Approach

Eight deliverables (D1–D8). D1–D2 are skill-prose / contract-prose correctness fixes with no machine-layer change; D3 is the one structural schema change; D4–D5 are skill-prose coherence checks built on existing SPEC-25 substrate; D6 is a predicate DSL extension; D7 is a `STORY_KERNEL.md` authored-prose section; D8 reconciles `docs/FOUNDATIONS.md`.

Per the standing directive carried from SPEC-25, every accepted change enumerates its non-negotiable updates to **(a)** the story-state contract, **(b)** the MCP / patch-engine / allocator surface, and **(c)** the validator JSON schemas and structural / rule logic — plus the consuming story-pipeline skills. Where a deliverable touches none of (a)/(b)/(c), that is stated explicitly.

The seven story-pipeline skills in scope: `branching-story-bootstrap`, `branching-story-turn-cycle`, `branching-story-prose-attach`, `commitment-block-authoring`, `branching-story-health-audit`, `story-fact-promotion-to-canon`, `story-promotion-closeout`. Plus the two shared templates: `.claude/skills/_shared-templates/story-state-contract.md` and `.claude/skills/_shared-templates/page-plan.md`.

Recommended implementation order: **D1 → D2 → D3 → D4 → D5 → D6 → D7 → D8**. D1 and D2 are zero-risk prose fixes closing confirmed live bugs and are independent of everything else — they can land immediately as correctness hotfixes. D3 is the largest single change (the only schema/validator/template touch) and is sequenced before the skill-prose checks that pair with it. D8 lands last so it reconciles the final contract state.

### D3 — `SE.resolution` block + prose-attach `choice_consequence_visibility`

Make non-accept outcomes structurally explicit and verify the outcome is made visible in prose. This is the spec's only structural schema change.

**Contract** (`story-state-contract.md` §4.3 `SE` schema): add an optional `resolution` block:
```yaml
resolution:
  result: success | partial_success | failure | impossible | transformed | held_for_promotion*
  player_visible_feedback: >*
    One-sentence statement of what the player should be able to perceive about
    why the action resolved this way.
```
- `resolution` is **required** when `SE.outcome_route` is `attempt`, `accommodate`, or `world_block`; optional/absent otherwise.
- Add the `route_resolution_consistency` constraint table to the §4.3 prose:
  - `accept` → `result` absent
  - `attempt` → `result ∈ {success, partial_success, failure}`
  - `accommodate` → `result ∈ {partial_success, transformed}`
  - `world_block` → `result ∈ {impossible, failure}`
  - `promotion_hold` → `result` absent or `held_for_promotion`
  - `terminal` → `result ∈ {success, partial_success, failure, transformed}` or absent
- `reason_class` is **not** added — see §Out of Scope.

**MCP / schema / validator**:
- `tools/validators/src/schemas/story-event.schema.json` — add the `resolution` object to `properties` (the file is `additionalProperties: false`, so the field must be declared). Express the route→result constraint and the conditional-required-ness with JSON Schema `allOf` / `if` / `then` so `record_schema_compliance` enforces it automatically; only fall back to a dedicated structural validator if the conditional logic proves un-expressible in AJV 2020 (see Risks).
- `tools/patch-engine/` — no op change: `create_se_record` already exists and validates payloads against `story-event.schema.json`; the updated schema is sufficient. Confirm `mcp__worldloom__describe_envelope_schema` surfaces the new field (it reads the schema).

**Skills**:
- `branching-story-turn-cycle` — Phase 1 (route resolution) drafts `SE.resolution` for `attempt` / `accommodate` / `world_block` routes; Phase 7 (page plan) carries `resolution.player_visible_feedback` into the page-plan event section.
- `.claude/skills/_shared-templates/page-plan.md` — the event section (confirm the section number against the template; the report cites "§7") gains a required `resolution.player_visible_feedback` line. This section is not one of the verbatim-inlined sections, so it is freely editable.
- `branching-story-prose-attach` — add a seventh deterministic check `choice_consequence_visibility: PASS | WARN | FAIL`: `PASS` = prose makes the selected action, route, and immediate consequence legible to a first-time reader; `WARN` = the action occurred but the consequence/route feedback is easy to miss; `FAIL` = prose obscures, contradicts, or omits the consequence (especially for `attempt` / `accommodate` / `world_block` / `promotion_hold` / `terminal` routes). The check verifies the page's prose realizes `SE.resolution.player_visible_feedback`.
- `story-fact-promotion-to-canon` — when a promotion candidate derives from an `SE` with `resolution.result: held_for_promotion`, include `resolution.player_visible_feedback` in the proposal package's evidence narrative.

### D4 — Causal-dependency threat scan

Detect when a turn's `state_delta` invalidates a record that an emitted `CHC`, an open `OBL` counterparty, a visible affordance, or an eligible `SLT` precondition depends on. **No contract, MCP, or validator change** — `CHC.grounded_in` (SPEC-25 D5), `STSTAT` (SPEC-25 D1), and `OBL`/`CNSQ` `urgency` (SPEC-25 D3) already supply the substrate; this is skill-prose, consistent with health-audit Phase 2's existing skill-prose replay architecture.

**Skills**:
- `branching-story-turn-cycle` — add a fifth turn-cycle-additional check `causal_dependency_threat_scan` (Phase 9), running after the `state_delta` is drafted and before snapshot hashes are computed. Four sub-checks:
  - `choice_dependency_clobbered` (**error**): a record in an emitted `CHC.grounded_in.records[]` is closed / superseded / moved / invalidated this turn, but the `CHC` remains emitted or player-visible.
  - `affordance_dependency_clobbered` (**error**): a `PG.state_snapshot.visible_affordances` entry remains after its grounding `STLOC` / `STOBJ` / `STENT` is no longer active, accessible, or located where the affordance asserts.
  - `obligation_counterparty_unavailable_without_transfer` (**error**): an entity owing or owed an open `OBL` becomes dead / captive / offstage / incapacitated / otherwise unavailable (per its active `STSTAT`), but the `OBL` is neither closed nor transferred.
  - `slt_precondition_clobbered` (**warning**): a high-salience open debt had an eligible author-pool `SLT` before this turn, but the new delta destroys that `SLT`'s preconditions without closing, transferring, or replacing the debt.
- `branching-story-health-audit` — add **Phase 2g: Causal dependency health**, applying the same four checks across the audit's branch replay. Phase 2 currently runs 2a–2f; 2g is the next sub-phase.

### D5 — Expected-witness discipline

Strengthen the mandatory belief-propagation phase from "were `BEL` records drafted?" to "is every expected witness accounted for?" **No contract, MCP, or validator change** — the computation runs over `STSTAT.location`, event targets, active `BEL`, and active `DA` / `STOBJ` evidence, all post-SPEC-25 existing state.

**Skills**:
- `branching-story-turn-cycle` Phase 4 — before drafting `BEL` records, compute `expected_witnesses`:
  - **direct**: active `STENT` records at the event location (per active `STSTAT`) with `agency` not unconscious / dead / incapacitated.
  - **indirect**: public or factional holders, when the event occurs through law, ritual, bureaucracy, artifact circulation, public violence, or visible environmental change.
  - **excluded**: `STENT` records concealed, offstage, unconscious, socially barred, or lacking access.
  Then require, for each relevant witness group, either a created/superseded `BEL` (`knows` / `suspects` / `misremembers` / `reports` / `deceives`) **or** an explicit non-propagation rationale (no witness / witness incapacitated / evidence concealed / institution suppresses report / event leaves no accessible trace).
- `branching-story-turn-cycle` Phase 9 additional check 3 — strengthen "belief/visibility coverage" to verify every expected witness group is accounted for by a `BEL` or an explicit non-propagation rationale, not merely that some `BEL` records exist.
- `branching-story-health-audit` Phase 2d — add an expected-witness-completeness check: events involving secrecy / betrayal / deception / violence / law / status / public ritual whose witness groups are not covered by `BEL` or a recorded non-propagation rationale.
