# Historical — superseded by the merged SPEC-58/59/60/63 STCHAR contracts; retained for audit trail

# **1. Executive verdict**

**Verdict: mostly complete architecturally, materially incomplete as a deterministic foundation.**

STCHAR is not a superficial addition. The merged implementation has a strong design center: `docs/FOUNDATIONS.md` defines STCHAR as story-local character authority; the shared story contract places STCHAR in active page state, page plans, prose receipts, and story-runtime authority rules; bootstrap, turn-cycle, prose-attach, health-audit, promotion, MCP retrieval, world-index parsing, and patch-engine op vocabulary all have real STCHAR integration. The direction is right.

The problem is that **several deterministic surfaces lag behind the contract**. The biggest risk is not “STCHAR doesn’t exist”; it is **split authority and class-set drift**: lawful STCHAR records can be generated by skills and schemas but missed or rejected by validators, schema unions, page-plan/prose validation, index edges, or stale docs.

Highest-priority fixes:

1. **Fix class-set mismatches immediately.**  
    `SE.state_delta.create/supersede/close` schemas allow `STCHAR`, but `state_delta_class_integrity` omits `STCHAR`, so lawful STCHAR lifecycle deltas can fail validation. `SE.record_introductions[]` allows STCHAR in the shared contract, but mid-story introduction validators/utilities omit STCHAR. `SREL.derived_from[]` is explicitly allowed to cite STCHAR in the shared contract but the JSON schema rejects it.  
2. **Make `PG.state_snapshot.active_records.STCHAR` non-optional for current bundles.**  
    There is no pre-STCHAR compatibility burden. Current validators/replay helpers still treat STCHAR as optional or warning-class compatibility. That undercuts the whole authority model.  
3. **Move page-plan §16a and prose receipt STCHAR checks from prose discipline into executable validation.**  
    The skill contracts are strong, but the implemented validator layer does not yet enforce packet presence, packet hash consistency, or required receipt fields robustly.  
4. **Expand the direct `CHAR-*` authority guard.**  
    The `no_char_authority_in_story_runtime` validator is conceptually correct, but its touched-path/op applicability is too narrow and can miss runtime surfaces such as relationships, storylets, facts, beliefs, secrets, questions, and audit artifacts.  
5. **Tighten over-broad record-id unions.**  
    Several schemas use generic record IDs where STCHAR should be forbidden: `STPLAN.blockers[]`, `STPLAN.current_step.target_records[]`, `STPLAN.fallback_steps[].target_records[]`, `STEMO.orientation.toward_records[]`, `STSEC.source_records[]`, `STQ.answer_records[]`, and most `SLT.effects`/`likely_effects` targets.  
6. **Fix world-index predicate argument extraction.**  
    `record_active(STCHAR-1)` is allowed by the predicate DSL, but the index parser extracts refs from predicate strings, not structured predicate argument fields such as `{ pred: "record_active", record: "STCHAR-1" }`. That means valid STCHAR predicate references can fail to appear as `storylet_predicate_ref` or plan predicate edges.  
7. **Update stale docs/reports that still describe `bound_char_id` or CHAR-seeded runtime.**  
    Active non-archive documentation still contains pre-STCHAR assumptions, especially the May 20 report and parts of the machine/context packet docs. These should be marked obsolete or rewritten so operators do not follow contradictory guidance.

# **3. Current merged STCHAR implementation summary**

## **What exists now**

`docs/FOUNDATIONS.md` is clear: STCHAR is the story-local character authority class; world `CHAR-*` remains story-agnostic; normal story runtime consumes STCHAR, not world character dossiers; `CHAR-*` in STCHAR frontmatter is provenance, not operational authority; STCHAR is not epistemic access and must not enter `BEL.basis.access_records[]`; no drama-manager, act-structure, or word-count ceilings should be introduced.

The shared contract defines STCHAR in the right places: `PG.state_snapshot.active_records.STCHAR`, non-background `STENT.bound_stchar_id`, `record_active(STCHAR-*)`, page-plan §16a STCHAR authority packets, prose-receipt STCHAR authority and profile-fidelity blocks, and no direct world `CHAR-*` page-plan authority.

The `story-character-profile` skill is strong. It supports `create_from_world_char`, `create_story_local`, and `regenerate`; it avoids mutating world `CHAR-*`; it requires a 13-section STCHAR body covering identity, source distillation, persona core, appraisal, pressure behavior, voice, page-plan voice block, perception/embodiment, agency/planning, relationship behavior, state derivation, prose rendering, and validation; and it computes profile, voice, and page-packet hashes.

Bootstrap uses STCHAR before meaningful story state: it creates STCHAR for selected non-background cast, binds STENT to STCHAR, includes STCHAR in page snapshots and page-plan §16a, aborts if STCHAR cannot be produced, and records operational cast bindings in `STORY_KERNEL.md.cast_bind_list`.

Turn-cycle is also strong at the skill level: it loads active STCHAR, cross-checks page active records, retrieves full or projected STCHAR sections before persona/voice/appraisal/pressure decisions, blocks complex new characters without STCHAR, avoids world `CHAR-*` runtime retrieval, and requires page-plan §16a.

Commitment-block authoring is appropriately conservative: exact `record_active(STCHAR-*)` can be used only where a branch-scoped/prefix block has explicit STCHAR authority, while generic persona/arc predicates are deliberately rejected.

Prose-attach has the right target design: it consumes page-plan §16a, checks active STCHAR, profile/voice/page-packet hashes, direct CHAR authority leaks, and performs judgment-assisted fidelity checks over voice, appraisal, pressure behavior, and relationship conduct.

Health-audit has an excellent STCHAR phase on paper: it checks missing bindings, unresolved STCHAR, inactive/superseded STCHAR in snapshots, missing page-plan packets, hash mismatches, underuse in CHC/STPLAN/STEMO/STINT/SREL, split authority, repeated profile-fidelity failure, and optional source drift without reading world CHAR by default.

Promotion flows are mostly correct: `story-fact-promotion-to-canon` treats STCHAR as evidence context only, not promotion authority; `story-promotion-closeout` can supersede STCHAR only if a story-character profile field actually changes, and never converts STCHAR into world `CHAR-*`.

World-index supports STCHAR node parsing, hybrid `story-characters/STCHAR-*.md`, STCHAR source/supersession/bound edges, STENT bound-STCHAR edges, page active-record edges, choice grounding, state deltas, alias bindings, and generic story references.

MCP retrieval has STCHAR support in `get_record`, `get_records`, `list_records`, `get_record_schema`, ID allocation vocabulary, and `story_bundle_context.active_story_characters`.

Patch-engine support is real: `expected_id_allocations.stchar_ids`, `append_story_character_authority_record`, `supersede_story_character_authority_record`, hybrid `body_markdown`, staging, schema introspection, and ID-allocation race checks exist.

## **What is incomplete**

The incomplete layer is not the high-level story architecture. It is the **mechanical closure**: schema unions, validator class sets, active-record shape enforcement, predicate edge extraction, prose receipt semantics, docs, and tests.

# **5. CHAR access / split-authority audit**

## **Allowed direct `CHAR-*` references found**

* `story-character-profile` reads world `CHAR-*` when creating or regenerating STCHAR from a world dossier. This is explicitly allowed and necessary.  
* `branching-story-bootstrap` uses selected cast `CHAR-*` as input to create initial STCHAR before meaningful story state exists. This is allowed.  
* STCHAR frontmatter uses `source_char_id` and `source_char_hash` as provenance. This is allowed by FOUNDATIONS and the STCHAR schema.  
* `branching-story-health-audit` has explicit `source_drift` mode that reads a source `CHAR-*` only when requested, only to compare hashes, and never to mutate/supersede automatically. This is allowed.  
* Promotion workflows may cite character provenance or STCHAR evidence context but do not promote STCHAR or silently create world `CHAR-*`. This is allowed.

## **Suspicious or stale direct `CHAR-*` references**

* `reports/story-character-dossier-retrieval-concerns.md` is still active and describes pre-STCHAR runtime concerns, including `STENT.bound_char_id` and turn-cycle re-seeding active bound `CHAR-*` dossiers. That report should now be marked obsolete or rewritten as “historical concern resolved by STCHAR, with remaining audit gaps.” Leaving it active creates contradictory operator guidance.  
* `docs/CONTEXT-PACKET-CONTRACT.md` and `docs/MACHINE-FACING-LAYER.md` still under-document STCHAR in context-packet/task/retrieval surfaces. `MACHINE-FACING-LAYER.md` says story-pipeline `seed_nodes` are world-scope seeds such as `CHAR` ids, which is safe for bootstrap but misleading for normal turn-cycle, where active STCHAR should be consumed through story context and targeted STCHAR retrieval.

## **Mechanical enforcement gap**

`no_char_authority_in_story_runtime` is the right validator, but `stchar-utils.ts` only applies STCHAR-relevant checking to a subset of ops and paths: entities, pages, choices, events, plans, emotions, story-characters, page plans, and prose receipts. It omits relationships, beliefs, facts, intentions, storylets, status, secrets, questions, clocks, artifacts, health-audit outputs, and promotion/closeout ledgers.

**Proposal:** keep the absolute runtime rule, but scope exceptions precisely:

* Allowed CHAR:  
  * STCHAR provenance fields: `source_char_id`, `source_char_hash`.  
  * Bootstrap selected cast input before STCHAR creation.  
  * `story-character-profile` source input.  
  * Health-audit `source_drift` advisory mode.  
  * Promotion/closeout provenance or adjudication context, never source authority.  
* Forbidden CHAR:  
  * page plans;  
  * CHC;  
  * STPLAN;  
  * STEMO;  
  * SREL;  
  * BEL;  
  * SF;  
  * SE state delta, `world_logic_rationale`, non-provenance fields;  
  * SLT;  
  * story context summaries;  
  * prose receipts;  
  * health-audit default structural/prose findings;  
  * story runtime skill outputs.

# **6. Skill-by-skill STCHAR exploitation audit**

## **`.claude/skills/story-character-profile`**

**Assessment: strong, with validation plumbing gaps.**

It supports all required modes: world-char source creation, story-local creation, and regeneration. It writes a full STCHAR authority profile rather than a thin STENT summary, avoids world mutation, records provenance/hashes, and includes sections that preserve voice, appraisal, pressure, relationship behavior, agency, perception, and prose/page-plan guidance.

Gaps:

* `tools/world-mcp/src/ranking/profiles/index.ts` lacks `story_character_profile` in `TASK_TYPES`, even though the skill uses that task type.  
* The STCHAR JSON schema checks frontmatter shape but does not validate the 13 required body sections or recompute/verify `profile_hash`, `voice_block_hash`, and `page_packet_hash`.  
* The schema requires source fields for `world_char`, but story-local/hybrid source-input completeness is less mechanically constrained.

Proposed changes:

* Add `story_character_profile` to context-packet task types/ranking profile.  
* Add `stchar_body_contract` validator:  
  * required headings;  
  * non-empty `Page-Plan Voice Block`;  
  * non-empty pressure/appraisal/relationship/prose sections;  
  * hash recomputation over canonical body slices.  
* Add tests for `source_kind: story_local`, `world_char`, and `hybrid`.

## **`.claude/skills/branching-story-bootstrap`**

**Assessment: strong.**

Bootstrap creates STCHAR before meaningful story state, binds STENT to STCHAR, includes STCHAR in initial active state, writes page-plan §16a, aborts when STCHAR cannot be generated, and uses selected `CHAR-*` only as input to STCHAR creation.

Gaps:

* No deterministic validator for `STORY_KERNEL.md.cast_bind_list`.  
* Active snapshot STCHAR key remains optional in machine validators.

Proposed changes:

* `story_kernel_cast_bind_list_integrity` validator:  
  * every non-background STENT in kernel cast list has `stchar_id`;  
  * every `stchar_id` resolves;  
  * `source_char_id`, if present, matches STCHAR provenance only;  
  * no `bound_char_id`.

## **`.claude/skills/branching-story-turn-cycle`**

**Assessment: strong at instruction level; weaker in midstory introduction plumbing.**

The skill loads relevant active STCHAR before resolution, choices, state deltas, plans, emotions, and page plans. It differentiates present/voice-bearing characters from offstage causal characters through page-plan §16a. It blocks meaningful complex new STENT creation without STCHAR and routes to `story-character-profile`.

Gaps:

* `phase-2-3-commitment-and-state-delta.md` and `mid-story-record-introduction.md` omit STCHAR in introduction guidance/utilities despite the shared contract allowing STCHAR introductions.  
* Midstory validators omit STCHAR introduction classes.

Proposed changes:

* Decide one policy and enforce it:  
  * **Preferred:** STCHAR introductions are allowed only when produced by `story-character-profile`/bootstrap, then referenced by turn-cycle. Turn-cycle may include them in `SE.record_introductions[]` only when the STCHAR was created as part of the same approved envelope.  
  * If skills cannot chain, turn-cycle must abort and instruct user to invoke `story-character-profile`.  
* Align midstory intro validators with whichever policy is selected.

## **`.claude/skills/commitment-block-authoring`**

**Assessment: aligned and restrained.**

It uses STCHAR where exact actor-specific behavior requires it, avoids plot rails and arc predicates, and forbids existential persona predicates.

Gaps:

* `SLT.effects` schema is too broad and could allow STCHAR lifecycle changes even though the skill’s intended policy is not to let storylets create/supersede STCHAR.

Proposed change:

* Add `storylet_effect_class_integrity` validator excluding `STCHAR` from `effects.*` and `exit_options[].likely_effects[]`.

## **`.claude/skills/branching-story-prose-attach`**

**Assessment: excellent contract, insufficient executable enforcement.**

It requires STCHAR packet presence, hash integrity, active snapshot checks, direct CHAR leak detection, and judgment-assisted profile fidelity.

Gaps:

* `prose-receipt.schema.json` defines `checks.char_authority_leak` but does not require it.  
* `prose_receipt_schema_compliance` only validates schema shape; it does not verify required STCHAR packet presence, hashes, active-in-snapshot, or page-plan/prose consistency.  
* The engine-jargon record-ID list shown in the skill omits newer IDs like `STCHAR`, `CLK`, `STSEC`, and `STQ`.

Proposed changes:

* Require `checks.char_authority_leak`.  
* Add `prose_receipt_stchar_integrity` validator.  
* Add `STCHAR-d+`, `CLK-d+`, `STSEC-d+`, `STQ-d+` to engine-jargon leak list.

## **`.claude/skills/branching-story-health-audit`**

**Assessment: strong design; needs test/validator backing.**

Phase 2m is exactly the right audit surface: missing STCHAR, unresolved STCHAR, inactive/superseded STCHAR, missing §16a packets, hash mismatch, STCHAR underuse, split authority, and repeated fidelity drift. Source drift is opt-in and advisory.

Gaps:

* Compatibility mode still names newer optional classes like CLK/STSEC/STQ/DA, but does not mention STCHAR active-record key hardening.  
* Phase 2m appears skill-level, not fully executable through existing validators/tests.

# **12. Research-informed improvement opportunities**

Three research findings sharpen the audit:

1. **Do not rely on long-context placement or generic summaries for character authority.**  
    Liu et al.’s “Lost in the Middle” shows that even long-context models can perform worse when relevant information is buried in the middle of long inputs; this supports the current page-plan §16a policy of placing page-relevant STCHAR packets directly in the page plan rather than forcing the prose writer to infer from record IDs or distant dossiers.  
2. **Persona/profile conditioning improves dialogue specificity and consistency, but only if the persona material is present and concrete.**  
    PersonaChat found that chit-chat models often lack specificity and consistent personality, and conditioning on profile information improves dialogue behavior; for Worldloom, that argues for stable voice blocks, line-shape examples, forbidden generic patterns, and relationship-specific conduct inside STCHAR and page-plan packets.  
3. **Agent behavior works best when memory, reflection, and planning are separated from momentary rendering.**  
    Park et al.’s generative-agent architecture combines memory, reflection, retrieval, and planning to produce believable behavior; this supports Worldloom’s split between STCHAR stable profile authority, STPLAN tactical state, STEMO affective state, and page-plan/prose rendering checks. It also supports the recommendation not to turn STCHAR into plot rails or global arc predicates.  
4. **Retrieval-grounding needs explicit, inspectable sources.**  
    Lewis et al.’s RAG paper frames retrieval as a way to use explicit non-parametric memory for more specific/factual generation; for Worldloom, the parallel is that STCHAR should be retrieved and packetized as explicit story-local authority, with hashes/provenance/section projections, rather than relying on the model’s memory of a previous dossier or a world `CHAR-*` pointer.

# **14. Rejected changes / anti-patterns**

Reject these:

* **World `CHAR-*` as normal runtime authority.** This reintroduces split authority and violates FOUNDATIONS.  
* **Making world `CHAR-*` story-aware.** STCHAR is the story-local projection; world dossiers remain world-level.  
* **Auto-promoting STCHAR or story-local character changes to world canon.** Promotion must stay explicit, opt-in, and adjudicated.  
* **Generic character-arc predicates.** No `any_story_character_with_wound`, no “arc stage,” no drama-manager predicates.  
* **Plot rails or act structure.** STCHAR should bias behavior, voice, perception, and pressure response; it should not mandate future beats.  
* **Word-count caps on STCHAR or page-plan packets.** The page plan is the prose writer’s sole authority; necessary character material should be included regardless of length.  
* **Treating profile-fidelity judgments as deterministic.** Hashes, required fields, active IDs, and packet presence are deterministic. Voice/profile quality is judgment-assisted.  
* **Adding fields just because they are aesthetically nice.** Every field must be consumed by validation, replay, retrieval, page-plan rendering, prose-attach, audit, or skill logic.
