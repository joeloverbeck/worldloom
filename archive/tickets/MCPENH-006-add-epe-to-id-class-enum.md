# MCPENH-006: Add EPE to id_class enum for allocate_next_id

**Status**: COMPLETED
**Priority**: MEDIUM
**Effort**: Small
**Engine Changes**: Yes — `tools/world-mcp/src/tools/allocate-next-id.ts` (`ID_CLASS_FORMATS` extension + EPE pressure-event filesystem scan); `tools/world-mcp/src/server.ts` (`ID_CLASSES` extension); `tools/world-mcp/tests/tools/allocate-next-id.test.ts` and `tools/world-mcp/tests/server/dispatch.test.ts` (package-local proof); `.claude/skills/emergent-pressure-events/SKILL.md` (Phase 3 + Process Flow diagram revert from manual-scan-primary to MCP-as-primary); `tools/world-mcp/README.md` (allocator scope note for EPE).
**Deps**: MCPENH-005 (registered the `emergent_pressure_events` task_type and the EPE skill convention); MCPENH-001 precedent for additive id_class enum extension.

## Problem

At intake (2026-04-30), `mcp__worldloom__allocate_next_id` did not accept `EPE` as an `id_class` value. The `ID_CLASS_FORMATS` map at `tools/world-mcp/src/tools/allocate-next-id.ts` and the `ID_CLASSES` tuple at `tools/world-mcp/src/server.ts` enumerated 28 values (CF, CH, PA, CHAR, DA, PR, BATCH, NWB, NWP, NCP, NCB, AU, RP, M, ONT, CAU, DIS, SOC, AES, OQ, ENT, plus the seven SEC-* prefixes) — `EPE` was absent.

At intake, the `emergent-pressure-events` skill (created 2026-04-30; auto-generated by `skill-creator` from `archive/brainstorming/emergent-pressure-events.md`) wrote EPE-NNNN-keyed pressure-event cards under `worlds/<slug>/pressure-events/`. Phase 3 of the skill needed to allocate the next EPE id per seed event. After the recent skill-audit on `emergent-pressure-events` (PA-prior-session friction), the skill's Phase 3 prose had been reverted to manual scan-and-increment of `pressure-events/EPE-*.md` because the MCP allocator would reject `id_class='EPE'` with `Unsupported id_class 'EPE'` per the validation guard at `tools/world-mcp/src/tools/allocate-next-id.ts`.

At intake, the skill carried a forward-note: "*when MCP `allocate_next_id` adds `'EPE'` as an `id_class` value, replace the manual scan with `mcp__worldloom__allocate_next_id(world_slug, 'EPE')` for consistency with sibling skills' allocation discipline.*" This ticket discharged that forward-note.

The gap is structurally identical to MCPENH-001 (NWB / NWP) and MCPENH-002 (NCP / NCB) — additive enum extension for IDs introduced after the original enum definition.

## Architecture Check

1. Adding `EPE` to the existing `ID_CLASS_FORMATS` and `ID_CLASSES` enums plus a narrowly scoped `pressure-events/` scan is the minimal change preserving the allocator's invariants (append-only IDs, scan for highest then increment, abort on collision at the skill write boundary). This parallels MCPENH-001's filesystem-backed scan for pipeline IDs while keeping ordinary world-scoped atomic/indexed classes on the existing index-backed path. The alternative — a separate "pressure-event-allocator" tool — duplicates code, fragments the contract, and pushes operators to learn two tools for the same operation.
2. No backwards-compatibility shims — the enum extension is additive. Existing consumers of `allocate_next_id` are unaffected; no aliasing, no deprecation period required. The skill's existing manual-scan code path becomes pure fallback (only fires if the MCP call errors).
