# Validator And Schema Migration Checks

Use this reference for tickets that change validators, JSON Schemas, hybrid frontmatter parsing, validator registries, grandfathering/waiver matchers, live-corpus validator baselines, or validator-package capstone / verification-matrix coverage. A broader capstone that only reads current validator registry/count/matrix state as one witness does not need this reference unless it changes validator/schema behavior or owns validator-matrix classification as an acceptance surface.

## Reassessment

- Identify every live entrypoint that materializes or exposes the validated record shape: direct file-input validation, DB-row reconstruction helpers, CLI helpers, pre-apply overlays, registry/list surfaces, package exports, schema-discovery tools such as `get_record_schema`, and envelope/schema-description surfaces such as `describe_envelope_schema`. Do not stop after the first parser call.
- Schema-discovery consumers include package tools that expose schema metadata, traverse JSON Schema `$ref`s, or project required fields and referenced schemas even when the ticket does not edit a JSON Schema file directly. A capstone that only reads current validator registry/count/matrix state as one witness does not need this reference unless it changes that validator/schema contract or uses validator-matrix classification as an acceptance owner.
- When a story record class is added to `PG.state_snapshot.active_records`, sweep the full active-record vocabulary before source edits: the shared story-state contract §4.2 / §5, `ACTIVE_RECORDS_CLASSES`, snapshot replay helpers, state-snapshot integrity ID/reference logic, predicate `record_active` parsing and reference sets, and focused parser/structural tests. Treat omissions in those consumers as same-seam validator fallout unless a live sibling ticket explicitly owns them.
- When retiring a schema field or enum that is backed by shared constants, distinguish record-schema consumers from independent public vocabulary or tool consumers before deleting exports. A constant may stop being part of `record_schema_compliance` while still lawfully backing a separate public surface such as `get_canonical_vocabulary`; retain or truth that public surface separately instead of assuming schema removal implies export removal.
- For validators over indexed story-bundle records, verify queried `record_type` / `node_type` strings against the live parser or persistence authority, patch-engine story-operation metadata, and any pre-apply overlay mapping before adding validator-local patch-plan merge logic. If a pre-apply overlay already materializes in-plan records, prefer correcting stale query keys or fixture vocabulary over duplicating the overlay inside one validator.
- When a validator needs to read an indexed table or column that older fixture databases may not contain, add a compatibility guard in the read surface before relying on broad package tests. The guard should fail closed to no findings or a clear skipped path for absent legacy tables, while current-schema fixtures prove the new table-backed behavior.
- When adding or registering a validator, classify its intended run-mode behavior before coding: `full-world`, `incremental`, and `pre-apply`. If the validator can run in pre-apply, read `docs/HARD-GATE-DISCIPLINE.md` and prove or record fail-closed behavior. If pre-apply is out of scope, make `applies_to` exclude that mode or record why the validator is harmless in that mode.
- When changing an existing validator's `applies_to` or run-mode selector, decide whether the edit can change a gating path before the pre-edit checkpoint. Read `docs/HARD-GATE-DISCIPLINE.md` if the edit can affect `pre-apply`, `validate_patch_plan`, `submit_patch_plan`, or another HARD-GATE-facing validation signal. If the edit is limited to incremental or full-world selection and the pre-apply branch is unchanged, record `HARD-GATE read: not required`, cite the unchanged pre-apply condition, and keep proof on the selector plus package build/test lane.
- When adding or registering a validator, pre-scan same-package inventory/capstone assertions before source edits: registry tests, CLI selector allowlists, package README inventory, integration/capstone tests that assert `ruleValidators.length` or expected validator-name lists, clean pre-apply execution-status tests that iterate every validator execution and classify `pass` vs `skipped`, and any portable CLI smoke that enumerates validator names. Treat stale counts, missing names, and stale skip/pass expectations as same-seam proof fallout, not as late broad-suite surprises.
  - Make the pre-scan concrete enough to catch list assertions before the first broad suite. Search the affected package tests and README for literals such as `validators_run`, `structuralValidators`, `ruleValidators`, `expectedValidators`, `validator_name`, the new validator name, and nearby existing validator names in the same registry family. Inspect any exact expected arrays, snapshot-like lists, CLI summary assertions, and inventory tables that the new registration should extend.
- When adding or changing a patch-engine operation that affects validated record shape, update the pre-apply overlay/materialized read surface in the same seam as the operation. Confirm the validator sees the post-operation shape during `validate_patch_plan`, not only after `submit_patch_plan` writes files.
- When a validator depends on a companion artifact outside the parsed/indexed record body, such as page prose, markdown body text, generated fixtures, or explicit file input, identify that source during reassessment. Record whether the validator reads it from indexed rows, `input.files`, temp fixtures, or the world-root filesystem, then prove every owned run mode that depends on it: focused unit tests, compiled CLI/full-world proof, and pre-apply materialization proof when the validator can run in `pre-apply`.
- For hybrid frontmatter records, explicitly decide the behavior for missing frontmatter. If the record class is in scope and required fields should be enforced, missing frontmatter should produce a structured schema failure, not a silent skip. If skipping is intentional, record why the file is outside the validator's authority.
- For JSON Schema tickets, inspect the package's existing schema compiler setup before accepting drafted compile probes. Match the live Ajv variant, draft version, strictness, formats, referenced-schema registration, and module-resolution root used by the package's validator/tests; for example, a schema declaring draft-2020-12 should be proved through the package's existing `Ajv2020` setup rather than a generic `new Ajv()` one-liner.
- For JSON Schema tickets that use conditional shape logic such as `if` / `then` / `else`, `allOf`, or conditional `required`, run a focused package schema-compilation path early after the edit, before combining it with unrelated focused tests. Prefer the existing compiled `record_schema_compliance` test or another live package schema-compile probe that exercises the edited schema under the package's real Ajv strict settings. If Ajv strict compilation fails, classify it as same-seam schema fallout to fix and record in closeout, not as an unrelated test failure.
- When adding `required` inside a conditional subschema, keep Ajv strict-required behavior in mind: declare the newly required property in the same subschema's `properties` block, even when the property already exists at the root schema level. Treat the local declaration as part of the same conditional contract, not as a duplicate schema authority.
- For JSON Schema tickets that add required fields, tighten enums, retire enum members, or otherwise make previously-valid records invalid, search same-package fixtures, fixture builders, helper records, integration plans, CLI tests, valid positive examples for that node type, and any repo-level fixture roots that same-package integration tests copy or index (for example `tests/fixtures/<world>/...`) before source edits. Partition hits into current-contract positive fixtures that must move with the schema, intentional rejection fixtures that should keep legacy values, and sibling/downstream legacy fixtures that must remain old-shaped. Record that partition in `Assumption Reassessment` so broad package failures do not turn into late, accidental fixture rewrites.
- For JSON Schema tickets that tighten string formats, regex `pattern`s, ID/reference shapes, or free-form string fields into structured tokens, treat the change like an enum/field tightening: search same-package fixtures, integration plans, CLI tests, shared templates, package README/examples, active authoring skill prose, and active follow-up tickets for old positive examples. Partition hits into current-contract examples that must move now, intentional rejection examples, historical/archive prose, and follow-up-owned operational prose; record any intentionally preserved active skill mismatch with the follow-up owner.
- For JSON Schema ID regex tickets, classify each ID-bearing field before editing instead of treating every pattern hit alike. Semantic references to other records are the usual cross-reference surface; allocator-authored record identity and lifecycle/lineage fields such as `id`, `supersedes`, `story_id`, `created_at_page`, parent page/branch ids, branch paths, selected-source ids, emitted-choice lists, and path-shaped identity fields stay on their existing strict allocator contract unless the ticket explicitly owns allocator or lineage behavior. Record the classification boundary in `Assumption Reassessment` when implementation-time grep widens or narrows the drafted file set.
- For JSON Schema required-field or property-set changes, pre-scan same-package schema inventory, roundtrip, and expected-field-set tests before source edits. Search for schema names, required-field arrays, representative valid records, and aggregate guards such as `contract-schema-roundtrip.test.ts` so field-list assertions move with the schema instead of surfacing only after the broad package suite.
- For JSON Schema required-field or property-set changes that can affect patch-plan validation, search downstream package tests and pre-apply fixtures that embed positive records for the changed schema, not only same-package validator fixtures. In Worldloom this commonly includes `tools/world-mcp/tests/**/validate-patch-plan*.test.*` and other `validate_patch_plan` / `create_*_record` fixtures that exercise the schema through `record_schema_compliance`. Treat stale downstream positive records as same-seam proof fallout: patch the active ticket's `Files to Touch`, `Verification Layers`, `Acceptance Criteria`, and `Test Plan` before editing those fixtures.
- When adding a load-bearing field under a permissive parent object such as `additionalProperties: true`, explicitly decide before coding whether the new field is machine-required, prose-required, transitional/optional, or enforced by a separate validator or skill gate. Record that decision in `Assumption Reassessment` / `## Deviations`; if it is machine-required, add missing-field rejection proof plus any required-field inventory updates. If it is not machine-required, add proof for the accepted typed value and record what surface enforces the practical obligation.
- When a ticket claims full-family coverage such as "all schemas", "all record classes", or an exact class/count, add or inspect an aggregate guard that enumerates every claimed member. Before closeout, compare that guard's table, fixture list, or generated member list against the claimed set so a broad package suite cannot pass while silently covering only a subset.
- When adding optional descriptive, precision, detail, rationale, or label fields alongside required routing fields, inspect every required-field list, `at least one of` gate, parse-time consumer prose, and producer template before coding. Optional precision fields must not become required, count as the only valid route target, or participate in deterministic joins unless the ticket explicitly owns that semantic promotion and updates the corresponding validators/tests.
- When renaming a schema, validator, code, message, enum value, registry name, or persisted verdict surface, search same-seam tests, fixtures, README/docs, specs, active sibling tickets, and grandfathering/waiver policy files for the old spelling before coding.
- When removing or retiring a schema field or enum value, broad stale-anchor greps may find live docs, specs, skills, sibling tickets, historical plans, archive records, and rejection tests. Classify every non-package hit that remains after implementation as `same-seam owned`, `sibling-owned`, `historical/archive`, or `intentionally excluded`, and record that classification in `Assumption Reassessment`, `## Deviations`, or `## Verification Result` before closeout. Do not leave current operational docs or skills with stale field guidance merely because the package tests pass.
- For staged schema families where a later ticket owns retiring legacy validators, parsers, or fixtures, partition test fixtures before editing: current-contract fixtures that prove the schema/pre-apply boundary must move to the new shape, while legacy fixtures used only by explicitly downstream retirement tickets may remain old-shaped. Record this partition in `Assumption Reassessment` so a broad suite failure does not cause accidental widening into the downstream ticket.
- If the ticket changes validator `code`, `message`, `validator`, file path, or node-id formatting, inspect exact-match grandfathering/waiver rows. Update same-seam rows to preserve the intended disposition or record that they are intentionally left unmatched because a follow-up owns the baseline change.
- Before deleting validator source or tests, check whether compiled outputs such as `dist/` may still be picked up by the package test command. Use the package clean script when available before the final proof, then classify the regenerated ignored output.
- For live-corpus baselines, record both pre-change and post-change counts when the ticket changes emitted verdict shape or matching behavior. A non-zero post-change corpus result can be the correct acceptance state when a later content or migration ticket owns cleanup.
- For validator, audit, or live-corpus baseline tickets, run the smallest truthful live-corpus probe before coding when acceptance claims zero findings or a clean baseline. Classify every finding as validator/tool bug, current-ticket cleanup, or pre-existing corpus baseline for a named bootstrap/audit owner; do not suppress real findings or force stale zero-fail acceptance when the live corpus truthfully exposes existing defects.
- When a drafted proof cites a `/tmp/...` envelope, gitignored local world/story path, archived live-corpus artifact, or other checkout-local proof input, verify that the exact path exists before source edits. If the path is absent or not portable, patch the active ticket's `Verification Layers`, `Acceptance Criteria`, and `Test Plan` to the strongest truthful substitute before implementation, such as present live corpus, synthetic records, temp-seeded fixtures, a direct handler probe, or a focused `record_schema_compliance`/package test. Record what the substitute proves and what it does not prove.
- When selecting validator CLI proof commands, distinguish rule selectors from structural validator selectors before preserving drafted command text. For `world-validate`, structural validators such as `record_schema_compliance` may need `--structural` or another structural path rather than `--rules <validator_name>`; verify the live help/source and patch stale command text before source edits.
- When a validator, audit, or live-corpus baseline ticket claims grandfathering, waiver rows, allowlists, or other disposition metadata can change the command's pass/fail result, verify the live validator/CLI actually consumes that mechanism before accepting it as an acceptance path. If the mechanism is only persisted audit data and emitted verdicts are recomputed independently, keep the findings visible, rewrite the active ticket to the truthful baseline/proof seam, and route real cleanup or policy implementation to a separate owner.
- If a validator grandfathering, waiver, baseline, or allowlist mechanism is implemented in a shared validator runner, also prove that pre-apply and other hard-gate paths remain fail-closed unless the ticket explicitly owns weakening that gate. A full-world bootstrap disposition must not accidentally downgrade engine pre-apply failures, Hook failures, or other canon-mutation gate verdicts.
- For explicit validator grandfathering policies, require an auditable minimum shape before treating the policy as real: stable disposition id, human rationale, exact validator name, exact code, exact file path, optional node id, and exact original message or another equivalently collision-resistant finding key. The implementation must downgrade only exact matched findings, preserve the finding as a queryable emitted verdict such as `info`, avoid DB-only insertion as the source of truth, and leave unmatched/new findings as failures.
- When a validator must temporarily read a prose/text surface because no structured schema field exists yet, define the accepted mini-format during reassessment, name the transitional source field explicitly, and record why a structured field is not currently available. Do not present the text convention as a stable schema contract or silently infer broad prose semantics.
- For validators over indexed scoped records, such as story-bundle records keyed by `story_slug`, keep reference validation scoped to each container even during an unscoped full-world run. Do not validate references against a combined cross-scope ID pool. Add or update tests with at least two scopes when overlapping authored IDs, missing IDs, or scope-filter behavior could otherwise pass accidentally.
- When structural validator tests build synthetic `IndexedRecord` fixtures directly, make each fixture's `file_path` match the live structural-authority path for that record class. Hybrid story records such as `story_character_authority_record` use paths like `stories/<story>/story-characters/STCHAR-<n>.md`, not `_source/` YAML paths; an authority-path mismatch can make `queryStructuralRecords` filter the fixture out and turn an acceptance test into an unresolved-record failure.
- For story-scope recursive/reference validators, resolve candidate IDs by both `node_type` and `story_slug` before classifying missing records or branch leaks. Some ID classes can overlap across layers, such as `DA-<integer>` for world-level diegetic artifacts and story-local artifact records. A world-level record can be a lawful non-branch-scoped reference even when the same ID shape would be branch-scoped inside a story bundle, so add focused tests for overlapping ID classes whenever the validator treats unresolved story-shaped IDs as failures.
- For recursive/reference-closure validators, build positive fixtures with every traversed record present, including IDs embedded in metadata-like fields such as visibility prefixes, provenance chains, or branch anchors, unless the implementation explicitly excludes that field through the validator's non-edge/skip-list contract. A "valid" fixture that omits a traversed ancestor can prove only missing-record behavior, not the intended acceptance branch.
- For validator capstone or spec-verification matrix tickets, classify every named scenario before coding as `mechanized`, `surrogate`, `manual/organic`, or `dropped from capstone`. Preserve that classification in the ticket/spec when the implemented test cannot or should not exercise skill-flow behavior directly.

## Verification

- Add a narrow unit test for the new valid shape and a rejection-path test for the retired or legacy shape. For hybrid frontmatter migrations, include an absent-frontmatter fixture if legacy files exist.
- When legacy fixtures are intentionally preserved for a downstream retirement ticket, add or update the owned schema/pre-apply proof with a separate current-contract fixture. Do not mutate the legacy fixture just to make a broad package suite green if that would erase the downstream validator's remaining witness.
- When a ticket only changes a structural validator's local acceptance/rejection logic, focused structural tests plus the validators package build/test lane can be the truthful acceptance surface. A direct `tools/world-mcp/dist/src/cli/validate-patch-plan.js <plan-path>` smoke is optional unless the ticket owns envelope construction, handler/CLI wiring, pre-apply overlay materialization, or a live-world reproduction as an acceptance target.
- When an optional direct `validate-patch-plan` smoke uses a historical envelope, preserve its value as a reproduction artifact rather than treating it like a fresh submit candidate. If the target validator emits the expected owned verdict while the same envelope also reports stale `id_allocation_race`, index freshness, missing local world, or other advanced-current-state failures, record the owned verdict and classify the rest as historical-envelope drift. Only fix or widen for those extra failures when the active ticket owns the envelope's current submitability or the failures are caused by the new validator/schema behavior.
- For transitional prose/text-backed validator contracts, test the accepted mini-format, rejection or shortfall behavior, and any grandfathering or not-applicable path. Prefer focused synthetic records unless a live-corpus fixture is the actual authority.
- Prove the old parser/helper/validator symbol is gone with a negative grep or equivalent symbol check when the ticket claims removal.
- Run the package's build/test lane from the package root after cleaning stale compiled output if files were renamed or deleted.
- If a live-corpus command is part of acceptance, capture the post-change summary and the key targeted counts, including retired-validator zero-count checks and renamed-code counts.
- When adding, removing, or renaming validators in the registry, run the downstream `tools/world-mcp` capability-parity proof after the validators package proof. At minimum, from `tools/world-mcp`, run `npm run build` followed by `node --test dist/tests/server/capability-parity.test.js`; run the full package suite when the ticket also changes handler, schema-discovery, `validate_patch_plan`, or capability metadata behavior. The validators package can be green while `world-mcp` still has a stale expected validator-name list.
- For shared producer vocabularies or schemas consumed through a local `file:` or symlinked package, rebuild the producer and verify the consumer-resolved artifact before trusting consumer proof.
- For patch-engine operation/schema migrations, prove validate/submit parity with at least one focused plan that exercises the new or changed operation through the pre-apply validator and the submit/apply path. Include a rejection or legacy-shape proof when the ticket retires a field or shape.
- For capstone surrogates, prove the production/default validator or pre-apply path stays fail-closed and name what the surrogate does not prove, especially when a skill-flow scenario is represented by a hand-authored envelope, fixture, or direct validator call.

## Closeout

- Update the active ticket's `Files to Touch`, `Acceptance Criteria`, `Test Plan`, `Outcome`, and `Verification Result` to match any changed baseline, registry count, validator count, or intentional non-zero command exit.
- Label old failure evidence as historical intake evidence when the validator no longer emits the old code or message.
- Truth the fixture plan against the landed proof surface. If the draft expected a new fixture directory but the implementation used inline fixtures, temp fixtures, or an existing fixture repurposed for the new schema, update `Files to Touch`, `New/Modified Tests`, `Test Plan`, and `Verification Result` to name the actual fixture surface rather than preserving the drafted directory.
- If a drafted live envelope, local world, or gitignored story artifact is absent or not portable, and a synthetic or temp-seeded pre-apply fixture proves the same validator invariant, record that substitution in closeout. Name what the synthetic proof covers, why the live artifact was not used, and any behavior it does not prove, such as CLI argv parsing, external MCP transport, or the full interactive skill flow.
- If current-contract and legacy fixture surfaces now coexist, name both in closeout: which fixtures prove the active ticket's schema, which old fixtures remain only for a named downstream retirement or migration owner, and which broad-suite failures were avoided by preserving that split.
- Record exact grandfathering/waiver matcher changes separately from content cleanup so the ticket does not imply canon/source normalization happened when only the matcher surface changed.
- Name any remaining visible live-corpus failures and the ticket or spec that owns them.
- For verification-matrix closeout, update same-seam spec/status docs when scenario ownership changes from full skill-flow proof to mechanized proof, surrogate proof, or manual/organic verification. Do not leave the spec implying an end-to-end skill run happened when only package-local validator coverage was executed.
