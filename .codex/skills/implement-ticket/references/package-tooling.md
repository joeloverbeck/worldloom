# Package And Tooling Checks

Use this reference for tickets whose owned seam includes `tools/`, package manifests, package-local commands, serializers, hashes/checksums, public exports, or package-local user-facing docs/examples. Also use the relevant verification-only parts when a docs/skill ticket keeps implementation out of `tools/` but proves its invariant through a read-only package handler, CLI, compiled artifact, or local package probe.

## Reassessment

### Compact Package Checkpoint

Before coding a package/tool ticket, inspect the package manifest and test/build scripts, dry-run or otherwise verify drafted proof command shapes and their `cwd`, check whether drafted direct `mcp__worldloom__...` invocations are exposed in the active Codex session, locate existing same-seam tests before creating new files, and confirm live fixture/count assumptions when tests copy or assert against current world state.

When a ticket adds, removes, renames, or registers validators, inspect same-package validator inventory surfaces such as the package README before source edits. Treat stale validator counts, missing validator names, or retired validator names in those inventories as same-seam package fallout, and patch the active ticket's file list/proof plan before coding when they must move with the registry change.

If reassessment changes the ticket's problem model, proof surface, public response shape, package command shape, or consumer contract, patch the active ticket before source edits. This is a hard pre-edit stop even when the implementation remains same-seam and obvious. Update `Problem`, `Assumption Reassessment`, `What to Change`, `Files to Touch`, `Verification Layers`, `Acceptance Criteria`, and `Test Plan` enough that the later code edit is implementing the live contract rather than the stale draft.

When a drafted proof names a machine-facing repo command such as `world-index validate`, `world-validate`, `validate_patch_plan`, `submit_patch_plan`, or an equivalent package CLI, verify the current command name, entrypoint, and working-directory contract against `docs/WORKFLOWS.md`, the package manifest, and the command's help or source before implementation. Patch stale command text in the active ticket before source edits.

For `tools/world-mcp` schema-discovery tickets, including `get_record_schema`, `describe_envelope_schema`, schema metadata projection, required-field projection, or JSON Schema reference traversal, also load `references/validator-schema-migrations.md` before coding. Treat `$ref` resolution, schema compiler setup, `source_path`, `required_fields`, `referenced_schemas`, and similar schema-derived response fields as part of the schema contract even when the active ticket only changes an MCP consumer and does not edit JSON Schema files directly.

For `tools/world-mcp` context-packet projection or payload-shape tickets, verify where the target node types actually appear across all packet layers before coding. Do not assume the named layer in the ticket is the only implementation seam: inspect `local_authority`, `exact_record_links`, `scoped_local_context`, `governing_world_context`, and `impact_surfaces` call sites. Make additive field shapes available consistently wherever the packet type can carry them, but populate expensive payloads such as parsed full records or raw full bodies only in the layers authorized by the live task, budget, and delivery contract. Record any broader-than-drafted but same-seam layer coverage, plus any intentionally preview-only layers, in `Assumption Reassessment` and closeout.

For `tools/world-mcp` context-packet overflow, recovery, budget, or payload-shape tickets, inspect the live assembly branch order before coding: full layer assembly, class filtering, optional full-body delivery, token-budget enforcement, serialized-response ceiling enforcement, persisted-output behavior, and error construction. Decide and record whether the active change must run before destructive layer drops, after layer drops, or only on the final error path. Do not assume the external MCP harness can persist an oversize response while `world-mcp` returns a sibling inline payload; first verify whether the live package already prevents oversize responses from reaching that harness boundary.

For any `tools/world-mcp` tool whose handler can return a large payload, verify whether the package bounds the response before it reaches the external MCP harness. If not, prefer a package-owned recovery shape: persist full JSON through the shared tool-results policy, return a bounded inline response with explicit recovery fields, and document the recovery path in package docs, repo-level machine-facing docs, and registered capability metadata. Do not rely on harness-authored persisted files under session-state directories as the tool's recovery contract unless the ticket explicitly owns that external harness behavior.

When a large-response ticket's owned invariant is server-side narrowing, projection, filtering, ranking, or budget reduction, do not widen it into package-owned persistence unless reassessment proves recovery behavior itself is the ticket owner. Record external MCP harness overflow as intake evidence or a deviation, then prove the narrowing with handler or dispatch tests plus response-size assertions against a truthful fixture.

For `tools/world-mcp` context-packet tickets that make a payload, node class, layer, or retry/error condition required rather than opportunistic, prove the required surface after the normal lower-priority drop path has had a chance to run. Do not emit `packet_incomplete_required_classes` merely because the fully assembled packet with the required payload is too large before droppable layers are removed. The truthful boundary is: keep the required surface, drop lower-priority optional layers, and only then fail if the required layer or payload still cannot fit under the token or effective harness ceiling.

For `tools/world-mcp` context-packet tickets that edit canonical docs examples such as `docs/CONTEXT-PACKET-CONTRACT.md`, inspect tests that parse those examples before source edits. In particular, check shape/contract fixtures like `tests/context-packet/shape-conformance.test.ts` so indentation, key order, and documented YAML shape stay test-truthful while the implementation changes.

For `tools/world-mcp` `get_context_packet` task-type or profile changes, treat `docs/CONTEXT-PACKET-CONTRACT.md` as a reassessment surface before source edits. Inspect and truth task-type enum prose, full-body candidate tables, reserve-policy tables, profile sections, and any parsed examples alongside package README, `docs/MACHINE-FACING-LAYER.md`, registered metadata, and tests.

For `tools/world-mcp` `get_context_packet` task-type or profile changes, pre-scan package tests for every affected `task_type` literal before source edits. Classify each hit as behavior-owned, a generic fixture that needs neutral request parameters, or intentionally unchanged. This catches tests that use a task type only to exercise generic budget, truncation, class-filter, delivery-mode, or layer-drop mechanics before the broad suite exposes stale request shapes.

For `tools/world-mcp` tickets whose draft says a tool is absent or new, first verify the live split between source registration and the running MCP connector with `src/tool-names.ts`, `src/server.ts`, tests/docs, and `mcp__worldloom__describe_capabilities()` when available. If the tool already exists and only its response shape, enum, docs, or coverage is incomplete, rewrite the ticket to an existing-tool completion before coding. Preserve the live tool names and enum values unless the ticket explicitly owns a rename; do not add backwards-compatibility aliases just because the draft used older or friendlier names.

- Inspect the package's `package.json`, `tsconfig.json`, and existing package-local docs/examples before trusting drafted command shapes, module formats, or emitted artifact paths.
- For `tools/world-mcp` tickets that change an existing tool's public response shape, hint/message wording, enum values, descriptions, or capability metadata, inspect `src/server.ts` during reassessment before source edits. Treat stale registration descriptions or capability metadata as same-seam package surface, alongside the handler, tests, package `README.md`, and repo-level `docs/MACHINE-FACING-LAYER.md`. When the changed tool belongs to targeted retrieval, context-packet follow-up retrieval, whole-class enumeration, or another FOUNDATIONS-named machine-facing read path, also inspect `docs/FOUNDATIONS.md` §Tooling Recommendation / §Read discipline and `docs/CONTEXT-PACKET-CONTRACT.md` for same-seam contract wording before coding or closeout.
- For `world-mcp` handlers or package probes that depend on indexed rows, `nodes`, `file_versions`, `world.db`, or another `world-index`-produced artifact, inspect the corresponding `world-index` parser, persistence, or schema producer before deciding whether the fix belongs in MCP handler logic, indexer coverage, or the active ticket's proof boundary.
- When a `tools/world-mcp` ticket adds or changes a tool input schema, grep `.claude/skills/`, package docs, and repo-level command docs such as `docs/MACHINE-FACING-LAYER.md` for stale call signatures, "schema accepts only" wording, old caller-side filtering instructions, and other old-schema claims. Truth same-seam hits before source edits when they define the implementation boundary, or during closeout when they are downstream prose consumers; record any intentionally excluded hits in `Assumption Reassessment` or `## Deviations`.
- When a ticket wraps, decorates, changes error handling for, or otherwise changes semantics of a shared package helper, enumerate direct helper consumers before coding. Use a focused search such as `rg -n 'helperName\\(' <package>/src <package>/tests`, classify each hit as owned, excluded, or already covered by a downstream wrapper, and patch `Assumption Reassessment` / `Files to Touch` before source edits if the live consumer set is broader than the ticket draft.
- When a shared helper starts returning richer error/details payloads, verify that every public wrapper, CLI, MCP handler, or status-response adapter preserves, intentionally projects, or explicitly drops those details. Do not stop at the helper-level test if a public wrapper converts the helper result into another response shape; prove the public response still carries the owned diagnostic fields or record the projection boundary in the active ticket.
- Before the first package-manager, build, test, formatter, generator, or codegen command likely to create ignored artifacts, run `git status --short --ignored <package-dir>` or an equivalent package-scoped ignored-aware check. Repeat it before final response, then classify ignored artifacts as pre-existing, expected generated artifacts, cleaned state, or unexpected fallout. Do not rely on `git status --short` alone for `node_modules/`, `dist/`, coverage output, caches, or compiled test output.
- If a verification command builds or tests multiple packages, snapshot ignored state for every package the command may touch before the sweep when feasible. If you skip non-owned package snapshots, record that limitation before closeout so later `dist/`, `node_modules/`, cache, or coverage dirt is not over-attributed to the active ticket.
- For consumer package ignored artifacts, take the ignored-aware snapshot only when the run actually builds, tests, installs, or executes that consumer, or when producer changes require consumer artifact freshness proof. If a drafted consumer CLI smoke is replaced by a producer/package-local proof and no consumer command runs, do not add consumer `dist/`, `node_modules/`, or secret files to the ticket ledger just because the original draft mentioned that consumer.
- Before adding or changing `.gitignore` for a generated package or world artifact, check whether an existing ignore rule already covers the exact path, for example with `git check-ignore -v <path>` when the path exists or by inspecting the nearby glob. Avoid redundant ignore rules unless the duplicate is an intentional clarifying rule; if so, record that reason in reassessment or closeout.
- If a drafted proof command uses a workspace filter or root package-manager command (`pnpm --filter ...`, `npm --workspace ...`, `turbo ...`, etc.), verify the root workspace manifests and lockfiles exist before trusting it. If the repo has only package-local manifests, rewrite the proof to package-local commands during reassessment.
- When a ticket mixes package-local build/test commands with a CLI that reads repo-root state via `process.cwd()` or a similar ambient root, split the proof surface truthfully: keep build/type/test commands at the package root, but run the CLI smoke check from the repo root that owns the world/artifact state. Do not force both onto one `cwd`.
- If verification uses an exported function, inline `node -e` probe, or other package-local runtime entrypoint, run it from the package root when module resolution depends on package-local dependencies.
- If verification uses compiled output such as `dist/src/...` or `dist/tests/...`, prove that the artifact is fresh for the exercised seam. Prefer running the package build before the probe; if rebuilding is outside the ticket boundary or would disturb unrelated dirty package work, compare the relevant source and compiled artifact or explicitly record why the existing compiled output is being treated as the proof surface.
- If a staged package ticket describes future adapter or integration behavior over an opaque placeholder type, verify whether the active ticket owns the adapter/parser or only the core callable surface. If a later ticket owns materializing the opaque input into the current package's runtime shape, record that boundary in `Assumption Reassessment` before coding and do not invent a speculative adapter.
- If a staged tool/schema ticket's public API omits a scope parameter but the current helper layer is scope-bound, verify whether the missing scope can be derived internally before broadening the public contract. If it can, keep the public API stable and record the helper-vs-tool mismatch in reassessment.
- If a staged tool/schema ticket adds an optional scope parameter to an existing API, classify every affected enum or class value by scope before coding: unchanged unscoped behavior, newly scoped-only behavior, or dual-scope behavior selected by argument presence. For dual-scope values, add tests for both the old unscoped path and the new scoped path so an existing public value is not accidentally moved wholesale into the new scope.
- For scoped allocation tickets, distinguish flows that create the scoped container from flows that append inside an existing scoped container before updating consumers. A first-run bootstrap may correctly use deterministic first IDs before the container exists, while runtime or continuation flows should use the scoped allocator once the container exists. Record that split in reassessment so bootstrap prose is not rewritten as if it can call an allocator that requires a not-yet-created scope.
- When changing `allocate_next_id`, ID class formats, ID regexes, allocation scope, or expected-allocation race contracts, sweep same-seam skill prose, templates, validation gates, package README/docs, registered metadata, and tests for old literal ID shapes or stale manual-allocation instructions before source edits. Truth same-seam hits in the active ticket's file list and proof plan, and classify preserved legacy-history mentions explicitly so they are not confused with current contract text.
- When a staged tool/schema ticket extends a tool or MCP response, inspect whether the live response is per-input, aggregate across batched inputs, or mixed. Additive fields must preserve query/item attribution when inputs are batched; do not accept a singular response field when it would be ambiguous for multi-item calls.
- For staged tool/schema tickets that validate YAML or frontmatter records, verify the exact parser package, parser options, and schema mode that the future validator or tool will use before freezing JSON Schema field types; record parser-driven shape facts such as timestamp coercion, unquoted-colon mapping items, or grandfathered legacy values in reassessment; when a hybrid record class is in scope, decide and record how missing frontmatter behaves instead of silently skipping the file.
- For index-backed filter or query tickets, verify whether unknown-field validation has a static schema for the requested record type or only observed parsed rows. If validation is derived from existing rows, qualify acceptance and tests for empty valid record sets; an empty set may be unable to distinguish an unknown filter path from a valid field with no matching rows.
- For staged tool/schema tickets that translate authored record fields into parser/index rows, graph edges, synthetic nodes, or other derived artifacts, verify the producer-emitted row/edge/type names directly from the parser or persistence code; do not assume the prose field name is the persisted contract.
- For staged tool/schema tickets that compare persisted hashes, checksums, canonical serialization, or drift markers across packages, inspect the producer of the stored value and reuse its canonicalization algorithm or record the intentional difference before coding.
- For staged tool/schema tickets that emit derived rows into an existing table, inspect the live schema for foreign keys and companion-artifact requirements before coding; if the row must also emit a backing `nodes` record, alias row, cleanup path, or other dependent artifact to satisfy the current contract, treat that as same-seam owned fallout and record it in reassessment.
- For staged tool/schema tickets that verify expected ID allocations, next-ID races, or other index-backed allocation contracts, prove both the current-index next value and any same-plan allocation overlay before coding. When multiple new IDs can share one prefix in a single submitted plan, the verifier must account for already-accepted IDs in that same plan so sequential allocations such as `ONT-2`, `ONT-3` do not falsely race against the unchanged index state.
- For staged tool/schema tickets that generate or auto-add follow-on operations, verify whether the generated operation can target the same physical file as an authored operation; if so, confirm the live staging layer merges same-file changes safely or rewrite the implementation/proof to a single staged write before claiming atomicity.
- For staged tool/schema tickets, verify every drafted structured error code, error taxonomy table, and error enum named by the ticket or spec against the live authority (`errors.ts`, shared error docs, or package-local contract surface) before assuming malformed-input or sentinel-error behavior is already representable.
- For error-family or ordered-validation tickets, construct proof fixtures that satisfy every earlier validation stage so the intended error branch is actually reached. For example, if the live flow checks envelope shape, HMAC, parser shape, then payload fields in that order, a payload-shape test must use an envelope and signature valid enough to reach payload validation; otherwise the test only proves an earlier guard. Record branch-order corrections in `Assumption Reassessment` or `## Deviations` when the drafted proof would stop at the wrong guard.
- When extending a TypeScript tuple, enum, or union such as `TASK_TYPES`, pre-scan same-package consumers for exhaustive maps and branches before coding: `Record<...TaskType`, `switch (taskType)`, keyed object registries, Zod/schema registrations, default tables, and tests that iterate the exported tuple. Treat required updates to those exhaustive consumers as same-seam fallout unless they cross a real ownership boundary. When consumers derive schema, validation, or handler behavior from the imported tuple, do not require literal grep hits in those consumers; prove the tuple source plus compile/runtime tests instead.
- For staged tool/schema or retrieval tickets that emit backing `nodes` rows as implementation detail, verify whether default user-facing tools should surface those backing nodes directly, suppress them, or surface only their source records; record the intended visibility contract in reassessment before coding so synthetic nodes do not leak into default result sets by accident.
- For scaffold, package, or build-surface tickets, verify every drafted built-artifact path, compiled entrypoint, registration target, or config target against the package's actual `tsconfig.json`, build script, and emitted output shape before implementation.
- For scaffold, package, or build-surface tickets that draft workspace-level package commands, verify the repo root actually has the claimed package-manager workspace (`package.json`, `pnpm-workspace.yaml`, lockfile, or equivalent). If it does not, correct the ticket to the live package-local command surface before coding.
- When a ticket proposes generating or rewriting a tracked source module during build, first verify whether the invariant can be satisfied by process-start metadata, checked-in static source, or ignored build output instead. Add tracked-source generation only when the generator itself is the owned package contract, then record why repeated builds will not create noisy source churn.
- For scaffold or package-consumer tickets that import an existing package export map, inspect at least one existing sibling consumer's `tsconfig.json` / resolver settings before choosing the new package's `module` and `moduleResolution`; do not assume default Node resolution can consume an existing export-map path.
- For package public-surface tickets that add or change `package.json` `exports` or exported symbols from an already-exported entrypoint, verify the full producer-consumer contract before trusting the drafted snippet: `require` / `import` / `default` / `types` conditions match the real emitted module format, the producer build emits the advertised runtime and `.d.ts` artifacts, and the intended consumer package's resolver settings can import that public entry without falling back to a private path.
- When adding symbols to an existing exported public module, treat the producer source, producer build output, and consumer-resolved artifact as one proof chain: update the active ticket's file list to include the producer module when needed, build the producer before consumer tests, and verify the consumer can see the emitted runtime or declaration symbol from its actual dependency path.
- For cross-package public export tickets where a consumer depends on the producer through a local workspace or `file:` dependency, inspect the consumer's installed dependency shape before coding. Record whether it is a symlink or copied install so the proof plan knows whether a producer build plus consumer-resolved artifact check is enough, or whether an install/update refresh is required before consumer proof.
- When a ticket or sibling spec says a downstream consumer can import an "exported" helper, constant, type, schema, or validator, distinguish TypeScript/source export from package-public export-map exposure before coding. Inspect the producer `package.json` `exports` map and record one truthful route: public package subpath, same-package source-module import, generated declaration import, or prose-only source-of-truth reference. If the claimed package subpath is absent, truth downstream tickets/spec references in the same family instead of leaving future consumers pointed at a non-existent import.
- For cross-package roundtrip proof, preserve the live dependency direction. If the drafted proof would make a producer import its consumer or otherwise introduce a package cycle, move the integration proof to the existing downstream consumer package and expose only the minimal producer public surface needed for that consumer-side test.
- For new consumer packages that depend on an existing exported public surface, apply producer-consumer checks even when the producer export map is not changing: match the consumer resolver settings to the live producer export contract, build the producer if declarations are generated, refresh the local dependency, and confirm the consumer is not compiling against stale installed artifacts.
- If a package tool reads sibling-package data files directly without modifying that sibling package's runtime or declaration surface, verify whether the dependency is a symlink or copied install and record the source-resolution strategy. Do not require producer artifact greps unless producer outputs changed; do ensure the tool is reading the intended live data path rather than a stale copied dependency.
- If a drafted shared-contract ticket names a downstream consumer file as a possible edit target, first verify whether the live consumer already has a generic pass-through or schema-tolerant path for the additive code, field, or error object. When the consumer is already correct, do not force a token source edit just to satisfy `Files to Touch`; prove the pass-through with the narrowest package test or grep and record `verified; no source edit required` in `Assumption Reassessment`, `Files to Touch`, or `## Deviations`.
- If the ticket already records runnable verification commands, dry-run the drafted command shape early enough to correct the ticket before implementation, not only during final proof.
- If a ticket names runnable package commands or CLIs, inspect adjacent same-package usage docs/examples early enough to confirm command shape and `cwd` expectations before treating the drafted proof lane as truthful.
- If a ticket adds or changes a user-facing CLI subcommand, flag, or option, treat parser/help wiring as part of the public surface. Update package README/help examples as needed and add a compiled CLI smoke test or equivalent command-level proof; handler or function tests alone are not enough unless the ticket explicitly excludes CLI invocation behavior.
- For new CLI flags/options, classify the proof boundary explicitly in the ticket before closeout: checked-in compiled entrypoint test, manual compiled CLI smoke, or a documented deviation explaining why parser-path proof is not portable. Tests that call command functions or wrappers directly can prove command behavior, but must not be described as CLI parser/entrypoint proof unless they exercise the compiled `cli` entrypoint or an equivalent parser path.
- If a CLI subprocess proof has brittle stdout/stderr capture or harness-specific transport behavior, do not change production output mechanics solely to satisfy that test. Prefer an existing stable CLI-smoke pattern, a side-effect assertion paired with manual compiled CLI smoke, or an explicit closeout deviation that keeps the owned proof truthful.
- If a package/tool ticket drafts an end-to-end HARD-GATE or canon-mutating skill dry-run as acceptance, verify whether that run is actually owned by the active ticket. When the ticket only changes a package/CLI handoff inside the workflow and does not own the canon-mutating skill execution, rewrite acceptance during reassessment to mechanized package proof plus skill-prose grep/manual review, then record why the full skill flow is out of scope.
- For verification-capstone tickets that span packages, docs, and skills, build the proof from portable mechanized witnesses first: temp-seeded repo/world roots instead of gitignored local worlds, direct package APIs or compiled package tests instead of unavailable MCP connector calls, generated fixtures instead of mutating `worlds/<slug>`, and static skill/template contract review when the real skill flow is interactive or canon-mutating. If the capstone must represent a hard-gate, Hook, approval, or skill-flow scenario with a surrogate, name the surrogate in `Assumption Reassessment` / `## Deviations`, preserve production/default fail-closed behavior, and avoid claiming that the full workflow executed.
- For validator-package tickets whose drafted `validate-patch-plan` CLI proof only needs validator-handler semantics, and whose live-world fixture state is stale, already committed, gitignored, or otherwise not portable, prefer a temp-seeded package test that calls the shared `validatePatchPlan` handler directly. Record that the CLI delegates to the same handler, why the direct CLI/live-world proof was not used, and what the package test does not prove (for example, CLI argv parsing or repo-root cwd behavior).
- When a capstone test inspects prose-only skills, templates, README inventories, or implementation-order/spec matrices, prefer stable live anchors, exported registries, or grouped semantic assertions over exact drafted prose. If live wording differs from the ticket/spec, truth the ticket/spec to the landed wording rather than adding marker text solely to satisfy a brittle static assertion.
- If a ticket adds or changes a user-facing CLI flag, command, tool inventory, machine-layer command surface, error code behavior, recovery behavior, audit field, or troubleshooting semantics, inspect repo-level quick-reference and troubleshooting docs during reassessment, especially `docs/WORKFLOWS.md` and `docs/MACHINE-FACING-LAYER.md` when they mention that surface or failure mode. Do this before coding so same-seam stale examples and recovery instructions are part of the owned boundary instead of late closeout surprises.
- For `tools/world-mcp` tickets whose drafted acceptance uses direct `mcp__worldloom__...` invocation, verify whether that external MCP tool is actually exposed in the active Codex session before code edits. If it is unavailable, rewrite `Acceptance Criteria` and `Test Plan` during reassessment to the strongest truthful package-local substitute: built-artifact in-memory MCP client/server smoke for registration, input-schema, or wrapped-tool behavior; direct handler/assembler proof for pure handler behavior. Record the substitution boundary in `Assumption Reassessment` instead of waiting until closeout.
- For `tools/world-mcp` tickets that change an already-exposed MCP tool's response shape, enum values, descriptions, or capability metadata, direct MCP calls made before the source change prove only the deployed-current baseline. After source edits, treat direct MCP acceptance as valid only if the package has been rebuilt and the MCP server/client session has been restarted or otherwise proven to load the new artifact. Without that restart proof, use package-local handler tests and in-memory MCP client/server dispatch tests as the truthful post-change proof, and record the direct MCP call as pre-edit smoke or post-restart operational smoke.
- For `tools/world-mcp` input-enum or capability metadata changes, use the narrowest proof that exercises both the handler and the MCP registration boundary: build the producer package first when the enum comes from a sibling `file:` dependency, build `tools/world-mcp`, run the focused handler/assembler test for the changed class or enum, then run an in-memory server/client dispatch or `describe_capabilities` assertion filtered to the changed tool. Treat a later full `dist/tests/**/*.test.js` sweep as broad verification; if it fails in unrelated tools, record the focused handler plus capability proof as the ticket's acceptance surface and classify the unrelated failures explicitly.
- For `validate_patch_plan` / `submit_patch_plan` response-shape or validation-signal changes, apply this same-seam propagation checklist before closeout: handler response type/projection, CLI output/help prose, package `README.md`, `docs/HARD-GATE-DISCIPLINE.md`, `docs/MACHINE-FACING-LAYER.md`, and any canon-mutating skills that consume the validation/submit response for HARD-GATE or checklist construction. If an item is intentionally outside the active ticket, record that boundary in `Assumption Reassessment` or `## Deviations`.
- For new or changed patch-engine operations, apply this parity checklist before closeout: operation schema/union, staging implementation, operation ordering tier, world-mcp validation/submit introspection, validator pre-apply overlay or materialized read surface, submit/apply behavior, and validate/submit parity tests. Do not accept submit-path success alone when pre-apply validation still reads the pre-change record shape.
- When a package build fails on an exhaustive registry, tuple, switch, or schema-discovery branch for a HARD-GATE-facing surface such as `describe_envelope_schema`, `validate_patch_plan`, `submit_patch_plan`, `OPERATION_KINDS`, approval-token helpers, or pre-apply validation metadata, classify the compile failure before editing. If the missing branch is same-package prerequisite fallout required for the ticket's build/proof lane, patch the active ticket before the source edit, read `docs/HARD-GATE-DISCIPLINE.md` when validation or submit signals are affected, and add focused introspection proof for the branch rather than hiding it inside a broad build.
- For `tools/world-mcp` tickets that add a new registered tool, use the full registration checklist before coding: handler under `src/tools/`, `src/tool-names.ts`, `src/server.ts` input schema and registration, `tests/server/list-tools.test.ts`, `tests/server/dispatch.test.ts`, package `README.md`, and `docs/MACHINE-FACING-LAYER.md` when the user-facing retrieval or mutation surface changes. If any item is intentionally outside the active ticket, record the boundary in reassessment or closeout.
- For `tools/world-mcp` retrieval-tool additions, also inspect `docs/FOUNDATIONS.md` §Tooling Recommendation when it enumerates the targeted-retrieval family. Truth the list when the new tool extends that family, or record why the new tool is intentionally outside that FOUNDATIONS-level contract.
- If a new or changed `tools/world-mcp` tool introduces a public structured error code, update the shared error taxonomy in `src/errors.ts` and the exact taxonomy witness in `tests/errors.test.ts`; document the error when it changes user-facing recovery behavior. Do this before treating focused handler, list-tools, or dispatch tests as complete proof.
- For newly added `tools/world-mcp` tools, a direct `mcp__worldloom__...` call may require rebuilding the package and restarting the MCP client session before the tool appears. Treat that direct call as post-restart operational smoke unless it is actually available in the active session; keep acceptance on the truthful package-local handler or in-memory MCP proof.
- When a package script wraps `node --test`, inspect `package.json` before trusting extra positional args; `pnpm test <path>`, `npm test -- <path>`, or similar passthrough can end up executing a source `.ts` path directly instead of the compiled `dist/...` test and produce misleading `ERR_UNKNOWN_FILE_EXTENSION` failures.
- When using package-script filters such as `--test-name-pattern`, grep, or positional test selectors, confirm the output actually narrowed to the intended subtests or files before recording it as a targeted proof. If the wrapper still reports the full package lane, record it as a broad package proof and use a more direct compiled test, handler probe, or in-memory dispatch command when a genuinely narrow proof is needed.
- If the ticket claims it will add or expand a script/test proof surface, verify whether the named file or package-script already exists and already runs before treating that proof work as live delta.
- If the ticket names a checked-in fixture path for proof, verify that the fixture actually exists. When the drafted fixture is missing but the package already has a live temp-seeded or generated-fixture harness, rewrite the ticket to that truthful proof surface before coding instead of treating proof as absent.
- When changing a shared test fixture builder, seed helper, or story-bundle/world fixture, pre-scan its consumers before editing with a focused search such as `rg -n 'fixtureBuilderName|fixturePath' <package>/tests`. Classify fixed-count, fixed-list, default-search-result, and broad-query assertions as same-seam expected fallout when the shared fixture gains or loses records; update those assertions with the fixture change before relying on a broad package suite to find them.
- If package tests copy a live world tree or assert fixed live-world fixture counts, verify those counts directly from the current fixture before treating failures as implementation defects. When recent canon additions make the expected counts stale, classify the update as proof-surface truthing rather than behavior change, and record the measured source paths/counts in reassessment or closeout.
- If a package test depends on a gitignored local world under `worlds/<slug>/`, prefer a temp-seeded fixture or checked-in minimal fixture when that can prove the same invariant. If the ticket specifically needs a local live-world artifact, make the test skip when the artifact is absent, assert the exact local path when present, and record in reassessment or closeout that the proof is checkout-local rather than portable CI evidence.
- Before running a broad package suite that depends on a gitignored live-world `_index/`, check whether the index schema version is fresh when practical. If the suite fails with `index_version_mismatch`, compare the live `worlds/<slug>/_index/index_version.txt` to the package's current schema version, rebuild the derived index through the real `world-index build <slug>` path when needed, and classify the refreshed `_index/` state as expected ignored derived dirt rather than ticket-owned source fallout.
- When a package change is task-type-specific, audit tests that use the affected task type only as a convenient generic fixture. If a test is proving generic budget, truncation, class-filter, or layer-drop mechanics rather than the task-specific behavior, switch it to a neutral task type or fixture instead of weakening the new task-specific contract. Keep separate focused tests for the changed task type's new behavior and record the split as proof-surface truthing when it affects closeout.
- For DB-backed or migration-sensitive package tickets, inspect same-package test helpers and fixture builders that create temp repos, temp DBs, or apply raw migrations before freezing `Files to Touch` or `Test Plan`; stale bootstrap schema, seed contracts, schema-version assertions, table-inventory assertions, and migration-upgrade tests count as same-seam proof fallout when the package's real verification depends on them.
- If a drafted inventory or count proof relies on grep over inline literals, verify whether the live implementation routes those names through exported constants, registries, or helper tables first. When registration is indirect, prefer a runtime probe or exported introspection helper over stale grep-count proof.
- If the ticket changes context-packet token accounting, required-class sizing, `minimum_required_budget`, `retry_with`, or another retry hint, prove the round trip: first assert the intended insufficiency/error payload, then rerun with the emitted retry value and assert that the same request succeeds or reaches the intended next diagnostic. Do not trust a computed retry budget without exercising it.
- For JS/TS package-local schema, type, or contract tickets, verify whether the drafted compile gate is package-wide (`src/**/*`, `tests/**/*`, or equivalent) before treating it as a narrow proof surface; if downstream consumers compile in the same lane, reassess the owned boundary before coding.
- For JS/TS package-local tickets, treat missing declaration-package compile failures caused by newly typed code as package-manifest fallout when the runtime dependency is already part of the package contract. Add the narrow `@types/*` dependency and lockfile change, then record any package-manager audit/funding warnings in closeout when dependency remediation is outside scope.
- If the ticket compares persisted hashes, checksums, canonical serialization, or drift markers, identify the producer of the stored value and reuse its canonicalization algorithm. If the implementation intentionally differs, record that difference in `Assumption Reassessment` before coding.
- If a new dependency is needed only to preserve an existing package contract, treat the manifest and lockfile update as same-seam fallout. Record package-manager audit, funding, or deprecation output in closeout when remediation is outside scope.

## Closeout Hard Stop

Before final response for a package/tool ticket, inspect adjacent same-package user-facing surfaces even if the ticket did not name them:

- `README.md`
- example config files, such as `.mcp.json.example`
- package-local usage snippets or command examples
- scripts that document or wrap the changed command/API

If the ticket adds or changes a user-facing CLI, workflow command, machine-layer command surface, error code behavior, recovery behavior, audit field, or troubleshooting semantics, also inspect repo-level quick-reference and troubleshooting docs that users rely on for invocation or diagnosis, especially `docs/WORKFLOWS.md` and `docs/MACHINE-FACING-LAYER.md` when they mention the command, tool, error, or recovery path. Treat stale same-seam command status, flags, examples, planned/present wording, or recovery instructions as closeout fallout unless a later ticket explicitly owns that docs update.

If same-seam docs, skill references, package READMEs, examples, or troubleshooting files were already dirty before the ticket and also need package-owned edits, classify the changed hunks before closeout. Keep pre-existing user work separate from ticket-owned public-surface updates in the final dirty-worktree ledger instead of attributing the whole file to the active ticket.

For each stale same-seam surface, either truth it in the active ticket or record why it belongs to a separate follow-up. When the stale package doc, entrypoint, script, or example is real but outside the active ticket, name the existing owner or create/recommend a bounded follow-up ticket unless the user requested implementation-only with no follow-up drafting; in that case, record the excluded drift in `Assumption Reassessment` or `## Deviations`. Do not leave known stale package docs/examples unmentioned after changing package-local behavior.

When a stale same-seam hit lives in a pre-existing dirty skill or doc file and the active ticket explicitly excludes that prose, classify it before editing: current operational guidance belongs in the active ticket or a named follow-up, while historical/audit-detection wording can be left untouched if the active ticket records the exclusion and likely owner. Do not mix ticket-owned package/API changes into an already-dirty skill file solely to clean up historical examples.

For MCP tool changes, also sweep the registered tool descriptions and capability metadata that are surfaced through `describe_capabilities`. Search for old scope, response-shape, input-schema, enum, or recovery wording in `src/server.ts` and adjacent capability/description helpers, then either update it or record why the old wording is intentionally still true. This sweep is required even when tests pass, because stale descriptions can survive a behavior change and mislead downstream skills.

For `tools/world-mcp` context-packet shape or layer-count changes, include layer-count and old-profile stale anchors in closeout sweeps. Useful literals include `five layers`, `five-layer`, `five content layers`, `local_authority through impact_surfaces`, `world-canon-only`, `returns only world-canon`, and old task-profile request fragments. Truth same-seam hits in docs, package README, registered metadata, test names, assertion messages, and ticket closeout before the final proof.

## Verification

- Run producer commands before consumer proofs.
- Before broad `tools/world-mcp` or other package suites that may read gitignored live worlds, check whether the suite depends on `worlds/<slug>/_index/` or copied live-world state. If focused package proofs already cover the owned invariant, keep acceptance on those focused proofs and record live-index failures such as `index_version_mismatch` as deviations unless the active ticket owns refreshing or repairing that live-world/index state.
- Run package-local builds/tests from the package root when module resolution depends on package-local dependencies.
- For retrying package APIs or CLIs that emit a machine-readable retry hint, include a focused proof that the emitted retry value is self-consistent. For example, a packet request that returns `packet_incomplete_required_classes` with `retry_with.token_budget` should be rerun with that value before closeout when the ticket changes token estimates or required payload size.
- Before an optional broad package sweep, snapshot ignored state for each package the sweep may touch when feasible. If you skip a pre-sweep ignored-state snapshot for non-owned packages, say so in closeout before classifying later `dist/`, `node_modules/`, cache, coverage, or secret-file dirt.
- When tests consume compiled output such as `dist/tests/**/*.js` and a source or test file was renamed or removed, prevent stale compiled files from remaining in the proof lane. Prefer the package clean script if present; otherwise explicitly check and remove the stale generated file before rerunning the accepted proof, then classify the ignored generated state in closeout.
- When a consumer package depends on a local sibling package via a workspace or `file:` dependency, refresh the consumer's installed dependency view after producer-side package/export changes and before consumer proof; do not assume the consumer is exercising the newly built public surface until that refresh has happened.
- If the consumer dependency is a symlink to the producer package, a producer build plus grepping the consumer-resolved runtime and declaration artifacts is the refresh check. If the dependency is a copied install, run the package install/update step before consumer proof.
- After refreshing a local workspace or `file:` dependency, verify the installed dependency artifact that the consumer will actually resolve contains the new runtime or declaration surface when that surface is the proof target. For TypeScript type/export tickets, this may mean grepping the consumer's installed `.d.ts` file before rerunning the consumer build.
- If the producer changes again after the first consumer proof, repeat the consumer-resolved artifact check before final closeout. Do not rely on an earlier install or build when later edits could have left a copied dependency stale.
- For public export changes, inspect existing public-surface tests for import-time IO or side-effect guards before choosing a re-export shape. Preserve or extend those guards so a new public constant does not accidentally make a narrow contract import perform filesystem work or other package initialization.
- When a permissive consumer boundary such as an MCP or CLI input schema delegates into a stricter producer API, keep the public consumer schema stable and bridge only after the consumer's local validation. In TypeScript, prefer deriving the producer argument type from the imported function (`Parameters<typeof producerFn>[0]`) unless the producer intentionally exports the named input type in its emitted declarations; do not import private source-only types just to satisfy the consumer build.
